Overview of queues in RouterOS: rate limiting principles, committed and maximum rates, interface queues, and links to the Simple queue, Queue tree, queue type, HTB, burst and queue size pages.

Queues

This section covers RouterOS queueing and bandwidth management. Use it to configure HTB, PCQ, burst behavior, queue sizes, and queue types for traffic shaping.

Overview

A queue is a collection of data packets that wait to be transmitted by a network device, in a pre-defined order. Queuing works almost like the queue at a bank or a supermarket, where customers are served in the order of their arrival.

Queues are used to:

  • Limit data rate for certain IP addresses, subnets, protocols, ports, etc.
  • Packet prioritization.
  • Configure traffic bursts for traffic acceleration.
  • Apply different time-based limits.
  • Share available traffic among users equally, or depending on the load of the channel.

The queue implementation in RouterOS is based on the Hierarchical Token Bucket (HTB). HTB allows the creation of a hierarchical queue structure and determines relations between queues. These hierarchical structures can be attached at two different places, in the input and in the postrouting stage of the packet flow.

There are two different ways to configure queues in RouterOS:

  • Simple queue (/queue/simple) - limits the upload and download of an address, a network or an interface with one entry.
  • Queue tree (/queue/tree) - limits traffic in one direction by packet mark, on an interface or globally. Packet marks come from /ip/firewall/mangle.

Queues can be configured in 8 levels. The first level is an interface queue from the /queue/interface menu, and the other 7 are lower-level queues that can be created in simple queues and queue trees.

Rate limitation principles

Rate limiting is used to control the rate of traffic flow sent or received on a network interface. Traffic with a rate that is less than or equal to the specified rate is sent, whereas traffic that exceeds the rate is dropped or delayed.

Rate limiting can be performed in two ways:

  1. Discard all packets that exceed the rate limit – rate-limiting (dropper or shaper).
  2. Delay packets that exceed the specific rate limit in the queue and transmit them when it is possible – rate equalizing (scheduler).

The next figure explains the difference between rate limiting and rate equalizing:

[gambar: Two pairs of traffic graphs. Rate limiting (shaper) cuts the traffic peaks at the rate limit. Rate equalizing (scheduler) also cuts the peaks at the rate limit and sends the delayed traffic afterwards.]

In the first case, all traffic that exceeds a specific rate is dropped. In the other case, traffic that exceeds a specific rate is delayed in the queue and transmitted later when it is possible. A packet can be delayed only while the queue is not full. If there is no more space in the queue buffer, packets are dropped. Queue size shows the effect of the buffer size.

For each queue we can define two rate limits:

  • CIR (Committed Information Rate) – (limit-at in RouterOS) In a worst-case scenario, the flow will get this amount of traffic rate regardless of other traffic flows. At any given time, the bandwidth should not fall below this committed rate.
  • MIR (Maximum Information Rate) – (max-limit in RouterOS) In a best-case scenario, the maximum available data rate for the flow, if there is any free part of the bandwidth.

A simple queue limits the upload and download rate of a target: an address, a network or an interface. It needs no packet marks.

See Simple queue for the examples: a limit for a device or a network, the order of queues, a guaranteed rate, limits by time and by destination.

Queue Tree

A queue tree limits traffic in one direction, selected by packet mark, on an interface or globally. A queue tree with an interface as the parent also limits FastTracked traffic.

See Queue tree for the examples: a limit for an Internet connection without mangle rules, priority for voice traffic and limits for marked traffic.

Queue Types

A queue type is a named set of settings for a queuing algorithm, such as FIFO, PCQ, FQ-CoDel or CAKE. Queue types are in /queue/type, and simple queues, queue trees and interface queues use them.

See Queue types for the kinds, the default queue types and examples for each kind.

Interface Queue

Before sending data over an interface, it is processed by the queue. An Interface Queue is a transmit (egress) queue; it does not process packets received by that interface.

For forwarded client traffic, the WAN-facing Interface Queue processes uploads, and the LAN-facing Interface Queue processes downloads. Each direction uses a separate queue instance. If traffic can leave through several LAN interfaces, configure every required transmit path or use a Simple Queue or Queue Tree that matches the traffic at a common point.

The /queue/interface menu lists the interfaces of the router and allows changing the queue type of an interface. The list is generated automatically:

[admin@MikroTik] > /queue/interface/print

3  eoip1      no-queue             no-queue           
4  lo         no-queue             no-queue

In this output, the Ethernet interfaces have the only-hardware-queue type and the virtual interfaces have no-queue. To change the queue type of an interface, set its queue property. See CAKE for an example that shapes upload with an interface queue.

Simple queue

A simple queue limits the traffic of a target in both directions with one entry. The target is an IP address, a network or an interface. Simple queues are in /queue/simple.

Upload and download are seen from the target: upload is the traffic that the target sends, and download is the traffic that it receives. Properties with two values, such as max-limit=5M/25M, take the upload value first and the download value second.

The router checks the simple queues in order, from the top of the list. A packet goes to the first queue whose target matches it and skips all following queues.

WARNING

A simple queue must match a packet either by its source or by its destination, not by both. If both the source and the destination of a connection are inside the target, the queue counts and limits all packets of the connection as download, and the upload limit has no effect. Do not put both ends of the traffic into the target of one queue.

Before you start: FastTrack

The default configuration has a FastTrack rule for established connections, and simple queues do not limit FastTracked connections. Without this step, the examples on this page do not limit established TCP and UDP connections.

Disable the FastTrack rule:

/ip/firewall/filter
disable [find action=fasttrack-connection]

Check that the rule is disabled. The command counts the disabled FastTrack rules:

/ip/firewall/filter/print count-only \
    where action=fasttrack-connection and disabled
1

FastTrack makes forwarding faster, so without it the router needs more processor time for the same traffic. There are two other ways:

  • Leave the rule enabled and keep only the connections that the queues limit out of FastTrack. See the example in FastTrack.
  • Use a queue tree with an interface as the parent. It limits FastTracked traffic too.

Limit one device

This example limits the device 192.168.88.10 to 5 Mbps upload and 25 Mbps download:

/queue/simple
add name=tv target=192.168.88.10/32 max-limit=5M/25M

Check that the queue counts the traffic of the device. The counters grow while the device sends and receives:

/queue/simple/print bytes where name=tv
Columns: NAME, TARGET, BYTES, TOTAL-BYTES
# NAME  TARGET            BYTES          TOTAL-BYTES
0 tv    192.168.88.10/32  185000/185000            0

Limit a network

With a network as the target, all devices of the network share one limit. This example limits the whole LAN to 20 Mbps upload and 100 Mbps download:

/queue/simple
add name=lan target=192.168.88.0/24 max-limit=20M/100M

Check that the queue counts the traffic of the LAN:

/queue/simple/print bytes where name=lan
Columns: NAME, TARGET, BYTES, TOTAL-BYTES
# NAME  TARGET           BYTES          TOTAL-BYTES
0 lan   192.168.88.0/24  189000/189000            0

The target can also be an interface, for example target=bridge. The queue then limits the traffic of all devices behind this interface.

To give each device of the network its own limit with one queue, or to share the rate equally between the devices, use a PCQ queue type.

Give one device a different limit

Because a packet goes to the first queue that matches, a queue for one device must be before the queue for its network. place-before adds a queue before another queue. This example limits the LAN and gives the server 192.168.88.10 its own, higher limit:

/queue/simple
add name=lan target=192.168.88.0/24 max-limit=20M/100M
add name=server target=192.168.88.10/32 max-limit=50M/50M \
    place-before=lan

Check the order and the counters. The server queue is first and counts the traffic of the server, and the lan queue counts the traffic of the other devices:

/queue/simple/print bytes
Columns: NAME, TARGET, BYTES, TOTAL-BYTES
# NAME    TARGET            BYTES          TOTAL-BYTES
0 server  192.168.88.10/32  210000/210000            0
1 lan     192.168.88.0/24   208000/208000            0

Guarantee a rate for one device

limit-at is the rate that a queue gets when the devices together ask for more than the limit of the parent queue. limit-at has an effect only between queues with the same parent.

In this example, the LAN has 20 Mbps upload and 100 Mbps download. The server always gets at least 5 Mbps upload and 20 Mbps download. Each child queue can use the whole rate when the other does not use it:

/queue/simple
add name=lan target=192.168.88.0/24 max-limit=20M/100M
add name=server parent=lan target=192.168.88.10/32 \
    limit-at=5M/20M max-limit=20M/100M
add name=others parent=lan target=192.168.88.0/24 \
    limit-at=15M/80M max-limit=20M/100M

The limit-at values of the child queues together must not be more than the max-limit of the parent queue.

Check that each queue counts its traffic. The parent queue counts the traffic of both child queues:

/queue/simple/print bytes
Columns: NAME, TARGET, BYTES, TOTAL-BYTES
# NAME    TARGET            BYTES          TOTAL-BYTES
0 lan     192.168.88.0/24   421000/421000            0
1 server  192.168.88.10/32  210000/210000            0
2 others  192.168.88.0/24   211000/211000            0

See HTB for how limit-at, max-limit and priority work between parent and child queues.

Limit at certain hours

time makes a queue active only in a time range and on the selected days. The router uses its own clock, so check that the time and the time zone in /system/clock are correct. This example limits the LAN on working days from 8:00 to 18:00:

/queue/simple
add name=work-hours target=192.168.88.0/24 max-limit=10M/50M \
    time=8h-18h,mon,tue,wed,thu,fri

Check the queue. This output is from inside the time range. Outside the time range, the flag I is in front of the name, and the queue limits no traffic:

/queue/simple/print where name=work-hours
0  name="work-hours" target=192.168.88.0/24 parent=none packet-marks=""
   priority=8/8 queue=default-small/default-small limit-at=0/0
   max-limit=10M/50M burst-limit=0/0 burst-threshold=0/0 burst-time=0s/0s
   bucket-size=0.1/0.1 time=8h-18h,mon,tue,wed,thu,fri

Limit the traffic to one destination

dst limits the queue to the traffic between the target and one destination address or network. Other traffic of the target does not go to this queue. This example limits the traffic between the device 192.168.88.10 and a backup server at 203.0.113.10 to 5 Mbps:

/queue/simple
add name=backup target=192.168.88.10/32 dst=203.0.113.10/32 \
    max-limit=5M/5M

Check that the queue counts the traffic to the backup server:

/queue/simple/print bytes where name=backup
Columns: NAME, TARGET, BYTES, TOTAL-BYTES
# NAME    TARGET            BYTES          TOTAL-BYTES
0 backup  192.168.88.10/32  215000/215000            0

Limit upload and download together

The total- properties set one limit for upload and download together. This example limits the LAN to 50 Mbps for the sum of both directions:

/queue/simple
add name=lan target=192.168.88.0/24 total-max-limit=50M

Check the queue. With a total limit, the total- counters count the traffic:

/queue/simple/print stats where name=lan
0  name="lan" target=192.168.88.0/24 rate=0bps/0bps total-rate=472.0kbps
   packet-rate=0/0 total-packet-rate=59 queued-bytes=0/0 total-queued-bytes=0
   queued-packets=0/0 total-queued-packets=0 bytes=0/0 total-bytes=390000
   packets=0/0 total-packets=390 dropped=0/0 total-dropped=0

More properties

  • queue selects the queue type for upload and for download. A new simple queue uses default-small.
  • burst-limit, burst-threshold and burst-time allow a higher rate for a short time. See Queue Burst.
  • packet-marks limits the queue to packets that have one of the listed packet marks. Mark the packets in the prerouting or forward chain of mangle.
  • priority and bucket-size control how child queues share the rate of their parent. See HTB.

NOTE

A CAKE queue type can buffer more traffic in a simple queue than in an equivalent queue tree. Set cake-memlimit on the CAKE queue type to bound its memory use.

Queue tree

A queue tree in RouterOS limits traffic in one direction, selected by packet mark, on an interface or globally. This page shows how to limit an Internet connection without mangle rules, give priority to voice traffic...

Queue tree

A queue tree entry limits traffic in one direction. It selects packets by their packet mark, not by address. Queue trees are in /queue/tree.

Two properties define what a queue limits:

  • parent is where the queue is attached. With an interface as the parent, the queue limits the traffic that leaves the router through this interface. With parent=global, the queue limits marked traffic in all directions. With another queue as the parent, the queue is a child of that queue.
  • packet-mark selects the packets. no-mark selects the packets that have no packet mark. A queue with children needs no packet mark: it gets the traffic of its children. A queue without children and without a packet mark gets no traffic.

Packet marks come from mangle rules. Queue trees have no order: each packet goes to the queue with its packet mark.

Limit an Internet connection

Upload leaves the router through the WAN interface, and download leaves through the LAN interface. One queue on each interface with packet-mark=no-mark limits all traffic, and no mangle rules are necessary. Queues with an interface as the parent also limit FastTracked traffic, so the FastTrack rule of the default configuration stays as it is. In the default configuration, the WAN interface is ether1 and the LAN interface is bridge:

/queue/tree
add name=upload parent=ether1 packet-mark=no-mark max-limit=20M
add name=download parent=bridge packet-mark=no-mark max-limit=100M

The download queue limits all packets that leave through bridge, also the packets that the router itself sends to the LAN. It does not limit traffic that the bridge forwards between its own ports.

Check that both queues count traffic:

/queue/tree/print stats
0  name="upload" parent=ether1 packet-mark=no-mark rate=244112 packet-rate=30
   queued-bytes=0 queued-packets=0 bytes=201486 packets=203 dropped=0
1  name="download" parent=bridge packet-mark=no-mark rate=241416 packet-rate=30
   queued-bytes=0 queued-packets=0 bytes=200814 packets=199 dropped=0

To keep the delay low while the connection is full, add a queue type such as FQ-CoDel or CAKE to both queues.

Packet marks and FastTrack

The default configuration has a FastTrack rule for established connections. FastTracked packets skip the mangle rules, so they get no packet mark, and they skip queues with parent=global. A queue tree that works with packet marks needs the connections of its traffic outside FastTrack.

The following examples do this with a connection mark. They change the FastTrack rule so that it takes only connections without a connection mark, and they mark the connections that the queues handle:

/ip/firewall/filter
set [find action=fasttrack-connection] connection-mark=no-mark

All other connections stay FastTracked.

Give priority to voice traffic

Child queues with different priorities share the rate of their parent. priority=1 is the highest and priority=8 is the lowest. When the connection is full, each child first gets its limit-at, and then the queue with the higher priority gets the rest first.

This example gives upload priority to calls. IP phones and voice applications send their voice packets with DSCP 46. The first mangle rule marks the connections that carry such packets, which also keeps them out of FastTrack. The second rule marks the packets of these connections that leave through the WAN interface. All other packets have no packet mark and go to the upload-other queue:

/ip/firewall/filter
set [find action=fasttrack-connection] connection-mark=no-mark
/ip/firewall/mangle
add chain=forward dscp=46 connection-mark=no-mark \
    action=mark-connection new-connection-mark=voice
add chain=postrouting out-interface-list=WAN connection-mark=voice \
    action=mark-packet new-packet-mark=voice passthrough=no
/queue/tree
add name=upload parent=ether1 max-limit=20M
add name=upload-voice parent=upload packet-mark=voice priority=1 \
    limit-at=2M max-limit=20M
add name=upload-other parent=upload packet-mark=no-mark priority=8 \
    limit-at=18M max-limit=20M

Check that the voice queue counts the marked packets and the parent queue counts all upload:

/queue/tree/print stats
0  name="upload" parent=ether1 packet-mark="" rate=464496 packet-rate=57
   queued-bytes=0 queued-packets=0 bytes=436062 packets=431 dropped=0
1  name="upload-voice" parent=upload packet-mark=voice rate=239304
   packet-rate=29 queued-bytes=0 queued-packets=0 bytes=218010 packets=215
   dropped=0
2  name="upload-other" parent=upload packet-mark=no-mark rate=239384
   packet-rate=29 queued-bytes=0 queued-packets=0 bytes=218052 packets=216
   dropped=0

See HTB for how limit-at, max-limit and priority work between parent and child queues.

Limit marked traffic in both directions

With parent=global, a queue limits its packet mark wherever the packets go. This example limits the devices of the address list limited to 2 Mbps upload and 10 Mbps download. The first two mangle rules mark the connections from and to these devices, which keeps them out of FastTrack. The other two rules mark the packets of these connections by direction:

/ip/firewall/address-list
add list=limited address=192.168.88.10
/ip/firewall/filter
set [find action=fasttrack-connection] connection-mark=no-mark
/ip/firewall/mangle
add chain=forward src-address-list=limited connection-mark=no-mark \
    action=mark-connection new-connection-mark=limited
add chain=forward dst-address-list=limited connection-mark=no-mark \
    action=mark-connection new-connection-mark=limited
add chain=forward connection-mark=limited src-address-list=limited \
    action=mark-packet new-packet-mark=limited-up passthrough=no
add chain=forward connection-mark=limited dst-address-list=limited \
    action=mark-packet new-packet-mark=limited-down passthrough=no
/queue/tree
add name=limited-up parent=global packet-mark=limited-up max-limit=2M
add name=limited-down parent=global packet-mark=limited-down \
    max-limit=10M

Check that both queues count traffic. The traffic of devices that are not in the address list does not go to these queues:

/queue/tree/print stats

   packet-rate=29 queued-bytes=0 queued-packets=0 bytes=222000 packets=222
   dropped=0

   packet-rate=29 queued-bytes=0 queued-packets=0 bytes=222000 packets=222

HTB (Hierarchical Token Bucket)

HTB (Hierarchical Token Bucket) is a queuing discipline in RouterOS for rate limiting and burst handling, using a token bucket algorithm to manage data rates with configurable capacity and limits.

HTB (Hierarchical Token Bucket)

HTB (Hierarchical Token Bucket) is a classful queuing discipline for rate limiting and burst handling. RouterOS uses a modified version of HTB in Simple queues and Queue trees. This page describes HTB as RouterOS implements it: the token bucket of a queue, the two rate limits, priority, and how a queue structure shares a rate.

How a queue passes packets

[gambar: HTB diagram with the token bucket, the packet queue and the token rate selection]

Token bucket (red part of the diagram)

The token bucket algorithm is based on an analogy to a bucket where tokens, represented in bytes, are added at a specific rate. The bucket itself has a specified capacity. If the bucket fills to capacity, newly arriving tokens are dropped.

Bucket capacity = bucket-size * max-limit

bucket-size is a number from 0 to 10. The default value is 0.1.

Before a packet passes through the queue, the queue bucket is inspected to see if it contains sufficient tokens at that moment.

If yes, the appropriate number of tokens is removed ("cashed in") and the packet passes through the queue.

If not, the packet stays at the start of the packet queue until the appropriate amount of tokens is available.

In a multi-level queue structure, tokens used in a child queue are also charged to its parent queues. In other words, child queues borrow tokens from their parent queues.

Packet queue (blue part of the diagram)

The size of the packet queue, the sequence in which packets are added to it, and when packets are discarded are determined by:

  • the queue type that the queue uses (queue) - see Queue types
  • the queue size of that queue type - see Queue size

Token rate selection (black part of the diagram)

The maximal token rate at any given time is equal to the highest active value of these:

  • limit-at: guaranteed data rate of the queue.
  • max-limit: maximal data rate of the queue.
  • burst-limit: maximal data rate of the queue while the burst is active.

burst-limit is active only when the burst is in the allowed state, see Queue Burst.

When limit-at is the highest value, extra tokens are issued to compensate for all the tokens that were not borrowed from the parent queue.

Bucket size in action

The examples in this section limit all traffic from and to one address, 192.168.88.101. The mangle rules mark its packets. bridge is the LAN interface and ether1 is the WAN interface, as in the default configuration:

/ip/firewall/mangle
add chain=forward action=mark-connection \
    new-connection-mark=pc1_conn connection-mark=no-mark \
    src-address=192.168.88.101
add chain=forward action=mark-connection \
    new-connection-mark=pc1_conn connection-mark=no-mark \
    dst-address=192.168.88.101
add chain=forward action=mark-packet new-packet-mark=pc1_traffic \
    connection-mark=pc1_conn

NOTE

Mangle rules do not process FastTracked packets, and the default configuration FastTracks established connections. Keep the connections that the queues have to limit out of FastTrack, see Packet marks and FastTrack. This applies to all examples on this page.

Default queue bucket

/queue/tree
add name=download parent=bridge packet-mark=pc1_traffic max-limit=10M
add name=upload parent=ether1 packet-mark=pc1_traffic max-limit=10M

In this case bucket-size=0.1, so the bucket capacity is 0.1 x 10M = 1M.

If the bucket is full (that is, the client was not using the full capacity of the queue for some time), the next 1 Mb of traffic passes through the queue at an unrestricted speed. After that, the queue passes 10 Mbit/s.

Large queue bucket

Set the bucket size of both queues to its maximal value:

/queue/tree
set download,upload bucket-size=10

In this case bucket-size=10, so the bucket capacity is 10 x 10M = 100M.

If the bucket is full, the next 100 Mb of traffic passes through the queue at an unrestricted speed, in addition to the 10 Mbit/s of new tokens. So you can have:

  • 20 Mbit/s transfer speed for 10 s.
  • 30 Mbit/s transfer speed for 5 s.
  • 60 Mbit/s transfer burst for 2 s.
  • 1 Gbit/s transfer burst for approximately 100 ms.

When the bucket is empty, the rate of the queue returns to 10 Mbit/s.

The bucket permits a type of burstiness of the traffic that passes through the queue. The behavior is similar to the burst feature, but it has no upper limit of the burst rate. A queue structure adds this limit.

Large child queue bucket, small parent queue bucket

/queue/tree
remove download,upload
add name=download_parent parent=bridge max-limit=20M
add name=download parent=download_parent packet-mark=pc1_traffic \
    max-limit=10M bucket-size=10
add name=upload_parent parent=ether1 max-limit=20M
add name=upload parent=upload_parent packet-mark=pc1_traffic \
    max-limit=10M bucket-size=10

In this case:

  • parent queue bucket-size=0.1, bucket capacity is 0.1 x 20M = 2M
  • child queue bucket-size=10, bucket capacity is 10 x 10M = 100M

The parent runs out of tokens much faster than the child queue. The child queue borrows tokens from the parent queue, so the whole system is restricted to the token rate of the parent queue, in this case to max-limit=20M. This rate is sustained until the child queue runs out of tokens. Then the child queue is restricted to its own token rate of 10 Mbit/s.

In this way, the queue allows a burst at 20 Mbit/s for up to 10 seconds.

Queue structure

There are three basic steps to create an HTB structure:

  • Match and mark traffic – classify traffic for further use. It consists of one or more matching parameters to select packets for the specific class.
  • Create rules (policy) to mark traffic – put specific traffic classes into specific queues and define the actions that are taken for each class.
  • Attach a policy for a specific interface(-s) – append the policy to all traffic (parent=global), to a specific interface, or to a specific parent queue.

HTB allows the creation of a hierarchical queue structure and determines relations between queues, like "parent-child" or "child-child".

As soon as a queue has at least one child, it becomes an inner queue. All queues without children are leaf queues. Leaf queues make actual traffic consumption, inner queues are responsible only for traffic distribution. All leaf queues are treated on an equal basis.

In RouterOS, the parent property assigns a queue as a child to another queue.

Dual limitation

Each queue in HTB has two rate limits:

  • CIR (Committed Information Rate) – limit-at in RouterOS. The worst case scenario: the flow gets this amount of traffic no matter what (assuming the interface can actually send so much data).
  • MIR (Maximal Information Rate) – max-limit in RouterOS. The best case scenario: a rate that the flow can get up to if the parent of its queue has spare bandwidth.

In other words, at first the limit-at (CIR) of all queues is satisfied. Only then child queues try to borrow the necessary data rate from their parents in order to reach their max-limit (MIR).

WARNING

CIR is assigned to the corresponding queue no matter what, even if the max-limit of the parent is exceeded. Example 4 on this page shows it.

That is why, to ensure the designed usage of the dual limitation feature, keep to these rules:

  • The sum of the committed rates of all children is less than or equal to the amount of traffic that is available to the parent.

CIR(parent) ≥ CIR(child1) + ... + CIR(childN)

If the parent is the main parent, CIR(parent) = MIR(parent).

  • The maximal rate of any child is less than or equal to the maximal rate of the parent.

MIR(parent) ≥ MIR(child1) & MIR(parent) ≥ MIR(child2) & ... & MIR(parent) ≥ MIR(childN)

Priority

The limit-at (CIR) of all queues is given out no matter what.

Priority is responsible for the distribution of the remaining traffic of the parent queue to child queues, so that they are able to reach max-limit.

The queue with higher priority reaches its max-limit before the queue with lower priority. 8 is the lowest priority, and 1 is the highest.

Priority only works:

  • For leaf queues. Priority in an inner queue has no meaning.
  • If max-limit is specified (not 0).

Examples

The examples in this section use one HTB structure and change the options of its queues. They show how HTB distributes the rate in each case.

Structure

The HTB structure consists of five queues:

  • Queue01 inner queue with two children - Queue02 and Queue03
  • Queue02 inner queue with two children - Queue04 and Queue05
  • Queue03 leaf queue
  • Queue04 leaf queue
  • Queue05 leaf queue

Queue03, Queue04 and Queue05 are clients that require 10 Mbit/s all the time. The link behind the outgoing interface is able to handle 10 Mbit/s of traffic.

Remove the mangle rules and the queues of the bucket size examples before you add this structure. The mangle rules mark the packets of the three clients, and the queues are attached to the outgoing interface ether1:

/ip/firewall/mangle
add chain=forward action=mark-packet new-packet-mark=client3 \
    src-address=192.168.88.101 passthrough=no
add chain=forward action=mark-packet new-packet-mark=client4 \
    src-address=192.168.88.102 passthrough=no
add chain=forward action=mark-packet new-packet-mark=client5 \
    src-address=192.168.88.103 passthrough=no
/queue/tree
add name=Queue01 parent=ether1 max-limit=10M
add name=Queue02 parent=Queue01 limit-at=4M max-limit=10M
add name=Queue03 parent=Queue01 packet-mark=client3 \
    limit-at=6M max-limit=10M priority=1
add name=Queue04 parent=Queue02 packet-mark=client4 \
    limit-at=2M max-limit=10M priority=3
add name=Queue05 parent=Queue02 packet-mark=client5 \
    limit-at=2M max-limit=10M priority=5

These commands create the queues of Example 1. Each next example changes the queues of the previous one.

PCQ example

Per Connection Queue (PCQ) is a RouterOS queuing method for equalizing bandwidth among users, with examples showing how to set download/upload limits using Queue Tree and Simple Queues.

PCQ example

Per Connection Queue (PCQ) gives every device on a network its own speed limit with one queue, instead of one queue for each device. PCQ sorts the traffic into sub-streams with its classifier, for example one sub-stream for each destination address, and limits each sub-stream to pcq-rate.

Limit every device on a LAN

This example limits every device on the LAN 192.168.88.0/24 to 10 Mbit/s download and 5 Mbit/s upload.

WARNING

The queues of this example do not apply to FastTracked traffic, and the default configuration FastTracks established connections. Disable the FastTrack rule first, see Before you start: FastTrack.

Step 1: add PCQ in Queue Types

Add one queue type for download and one for upload. pcq-classifier=dst-address gives every device its own sub-stream for download traffic, and src-address for upload traffic. pcq-rate is the limit for each sub-stream, so for each device, in bits per second; the k and M suffixes work:

/queue/type
add name=PCQ_download kind=pcq pcq-rate=10M \
    pcq-classifier=dst-address
add name=PCQ_upload kind=pcq pcq-rate=5M pcq-classifier=src-address

pcq-limit is not a speed: it is the queue size of each sub-stream, in KiB (50KiB by default).

Step 2: deploy the PCQ

Simple Queues option

One simple queue for the whole LAN applies both types. queue takes the upload type first, then the download type:

/queue/simple
add name=lan-pcq target=192.168.88.0/24 \
    queue=PCQ_upload/PCQ_download

/queue/simple/print stats shows in pcq-queues how many sub-streams, here devices, the queue has. In this output three devices upload at the same time. Each of them gets 5 Mbit/s, and the rate of the queue is the sum:

[admin@MikroTik] > /queue/simple/print stats

   packet-rate=1254/5 total-packet-rate=0 queued-bytes=150000/0
   total-queued-bytes=0 queued-packets=100/0 total-queued-packets=0
   bytes=38369640/26830 total-bytes=0 packets=25695/166 total-packets=0
   dropped=24029/0 total-dropped=0 pcq-queues=3/3

Queue Tree option

Use the queue tree instead of the simple queue, not together with it. If you added the simple queue, remove it first with /queue/simple/remove lan-pcq. Mark the packets by the interface list they arrive from. In the default configuration, the LAN list has the interfaces where the clients are connected, and the WAN list has the interface to the Internet:

/ip/firewall/mangle
add chain=prerouting action=mark-packet \
    new-packet-mark=client_upload in-interface-list=LAN
add chain=prerouting action=mark-packet \
    new-packet-mark=client_download in-interface-list=WAN

Then, add two queues, one for download and one for upload:

/queue/tree
add name=pcq-download parent=global queue=PCQ_download \
    packet-mark=client_download
add name=pcq-upload parent=global queue=PCQ_upload \
    packet-mark=client_upload

/queue/tree/print stats shows pcq-queues for each queue in the same way.

Queue Burst

Queue Burst feature allows temporary bandwidth bursts beyond configured limits when average traffic stays below a threshold, using burst-limit and burst-time parameters to control the burst duration and size.

Queue Burst

Burst is a feature that allows satisfying queue requirements for additional bandwidth even if the required rate is bigger than MIR (max-limit) for a limited period of time.

Burst can occur only if the average rate of the queue for the last burst-time seconds is smaller than burst-threshold. Burst will stop if the average rate of the queue for the last burst-time seconds is bigger than or equal to burst-threshold.

The burst mechanism is simple - if a burst is allowed, the max-limit value is replaced by the burst-limit value. When the burst is disallowed, the max-limit value remains unchanged.

  • burst-limit: maximal upload/download data rate which can be reached while the burst is allowed.
  • burst-time: period of time, in seconds, over which the average data rate is calculated. This is not the time of the actual burst.
  • burst-threshold: the value of the burst on/off switch.

Simple queues and queue trees have these properties. The bucket size of a queue also lets traffic pass above max-limit for a short time. The examples on this page also use two values that are not properties of a queue:

  • average rate - every 1/16 part of the burst-time, the router calculates the average data rate of each class over the last burst-time seconds. The queue statistics do not show this value.
  • actual rate - the actual traffic transfer rate of the queue. The queue statistics show it as rate.

Example

Values: limit-at=1M, max-limit=2M, burst-threshold=1500k, burst-limit=4M

A simple queue with these values and burst-time=16s for one client:

/queue/simple
add name=burst target=192.168.88.101/32 limit-at=1M/1M \
    max-limit=2M/2M burst-limit=4M/4M \
    burst-threshold=1500k/1500k burst-time=16s/16s

Simple queues do not limit FastTracked connections, and a queue matches only the traffic that no earlier queue has matched. See Simple queue for both.

The client will try to download two 4MB (32Mb) blocks of data, the first download will start at zero seconds, and the second download will start at the 17th second. There was no traffic during the last minute.

Burst-time=16s

[gambar: Actual rate and average rate of the first download, seconds 0 to 15, with burst-time=16s]**[gambar: Actual rate and average rate of the second download, seconds 16 to 31, with burst-time=16s]

As we can see as soon as the client requested bandwidth it was able to get 4Mbps burst for 6 seconds. This is the longest possible burst with given values (longest-burst-time = burst-threshold * burst-time / burst-limit). As soon as the burst runs out, the rest of the data will be downloaded with 2Mbps. This way, a block of data was downloaded in 10 seconds - without burst, it would take 16 seconds. Burst has 7 seconds to recharge before the next download will start.

Note that burst is still disallowed when the download started and it kicks in only afterward - in the middle of a download. So with this example, we proved that a burst may happen in the middle of a download. The burst was ~4 seconds long and the second block was downloaded 4 seconds faster than without burst.

Queue size

This page explains how to configure queue size limits in MikroTik RouterOS, detailing the impact of setting maximum packet counts on traffic shaping and scheduling. It includes examples comparing 100% shapers,...

Queue size

The maximum permissible queue size could be specified as a maximum memory limit, but a lot of algorithms simplify it to a maximum number of packets, so the actual memory used varies depending on the size of the packets.

The queue size is a property of the queue type. The pfifo, mq-pfifo and red kinds count packets (pfifo-limit, mq-pfifo-limit, red-limit). The bfifo and pcq kinds count bytes (bfifo-limit, pcq-limit). The smallest value is 1 for pfifo-limit and pcq-limit, and 1000 for bfifo-limit.

The rest of this page shows the effect of the queue size with a queue that counts packets.

CAKE is different: it controls its memory use with cake-memlimit on the CAKE queue type, not with the packet-count queue size settings described on this page.

Example

This example shows the impact of the queue size on the traffic that a queue processes.

For a simplified visualization, the data is processed in steps. The number of packets received in every step is known, and dropped packets are not retransmitted.

[gambar: Timeline of 25 steps with 1610 incoming packets]

There are 25 steps and there are a total of 1610 incoming packets over this time frame.

100% Shaper

A queue is a 100% shaper when every packet that is over the allowed limits will be dropped immediately. This way all packets that are not dropped will be sent out without any delay.

Apply a max-limit=100 packets per step limitation to the example:

[gambar: 100% shaper drops packets above 100 packets per step]

With this type of limitation, only 1250 out of 1610 packets were able to pass the queue (22,4% packet drop), but all packets arrived without delay.

100% Scheduler

A queue is 100% Scheduler when there are no packet drops at all, all packets are queued and will be sent out at the first possible moment.

In each step, the queue must send out queued packets from previous steps first and only then send out packets from this step; this way it is possible to keep the right sequence of packets.

The limit is the same (100 packets per step).

[gambar: 100% scheduler delays packets above 100 packets per step]

There was no packet loss, but 630 (39,1%) packets had 1-step delay, and the other 170 (10,6%) packets had 2-step delay. (delay = latency)

Default-small queue type

It is also possible to choose the middle way when the queue uses both of these queuing aspects (shaping and scheduling). The default-small queue type, which simple queues and queue trees use by default, is pfifo with a queue size of 10 packets.

[gambar: Default-small queue type drops some packets and delays others]

There were 320 (19,9%) packets dropped and 80 (5,0%) packets had 1 step delay.

Default queue type

The default queue type is pfifo with a queue size of 50 packets.

[gambar: Default queue type drops fewer packets and delays more of them]

There were 190 (11.8%) packets dropped and 400 (24.8%) packets had a 1 step delay.
