cmr

Package: cmr Type: Settings Directory

Settings of the CMR server, the router that controls a fleet of CMR clients. Enable the server with enabled=yes; it then distributes software packages, discovers and tracks the devices, and evaluates the alert rules that monitor them. See CMR for an overview of the package.

Argument / Type / Description

  • enabled enum (yes | no) — Whether CMR server is enabled or not. Default: no.
  • local-id string — Unique CMR specific device identifier.
  • pairing-requirement enum (none | password | confirm) — Defines what the remote device must do before this device accepts the pairing: - none - this device accepts pairing automatically, without additional checks - password - the remote device may approve pairing by giving the username and password of a RouterOS user on this device; CMR has no separate pairing password - confirm - pairing must be approved locally by running the pair command on this device; approval from the remote side is not possible
  • packages-directory file — Directory on the server's file system containing RouterOS packages that the server distributes to the managed devices and serves from when it matches the version an upgrade needs. The value is picked from the router's file list: directory entries are entered with a trailing slash (for example cmrpkgs/), plain files without one. Packages are resolved individually: a package already present here for the required version is sent directly without downloading it again, and only the missing packages are downloaded and cached. A value that does not point to an existing directory is kept but cannot be used; the /cmr menu then shows directory does not exist, using memory and packages are served from memory instead.
  • packages-cache-type enum (directory | memory) — Where the server stores the package files it downloads: directory keeps them on the server's storage, memory keeps them in RAM. With directory, the server stores them in a cmrcache subdirectory of packages-directory, which it creates in the router's file list; packages that are already present in packages-directory are served from there without being downloaded. When the directory is missing or unusable the server reports directory does not exist, using memory in the /cmr menu, stores the packages in RAM instead, and switches back to the directory when it becomes available again.
  • packages-cache-limit num — Maximum amount of package data held in the cache, in megabytes. A value larger than the available RAM or storage is accepted and the server shows an informational note; the cache then uses all the space that is available and evicts older entries when a file larger than the remaining space must be stored.
  • upgrade-check-interval time — How often the CMR server checks the MikroTik update servers for available versions. The minimum value is 1 minute. Default: 10h.
  • track-topology bool — Enables network topology discovery. Fetches the following information from CMR clients: routes, WiFi registration table, ARP table, neighbors, DHCP state, and interface states. This information is required for full CMR functionality, for example, automatic link discovery in the /cmr/layout menu. Default: yes.
  • fetch-comments bool — Enables fetching of comments for interfaces/ports and the WiFi registration table. Default: yes.
  • controller-addresses multi { array-id, address: address (flags=46D) } — CMR server IP addresses that are sent to the devices when the controller address cannot be discovered automatically (MNDP, or DNS: the client resolves _cmr._tcp.lan and _cmr._tcp. followed by the domain name from DHCP).
  • apptraffic-devices object — Select devices using labels for which to collect app traffic data. Supports + and - signs as AND and AND NOT operators, respectively; if no sign is provided, the OR operator is used. Default: gateway; all selects every device.
  • auto-labels alt { auto-labels: enum (none | all) { none:0, all:0xffff } , auto-labels: ubit (version, architecture, model, board-name, identity, address, ssid) } — Whether to fetch labels information from the connected cmr-client devices. Can be configured to fetch only specific labels. Default: all.

Read-only Argument / Type / Description

  • self-client-id string — ID that is used by CMR server to connect to itself, for it to be displayed in a device list.

cmr/alert

Package: cmr Type: Directory

An alert rule defines conditions and runs its actions on the CMR controller. Device rules select devices with labels. State alerts remain active while all configured state conditions match and run actions once when they become active. They fire again only after their conditions stop matching and then match again. Event alerts run actions for each matching occurrence and never remain active or contribute to active-alert counters. A rule can contain multiple state conditions but at most one event condition. Most alerts apply per device; upgrade-job-done is a system event for a whole upgrade job. See CMR - Alert rules for conditions, actions, and alert scope.

Flag / Name / Description

  • X disabled — Alert rule is disabled.

Argument / Type / Description

  • name string — Name of the alert rule.
  • labels object — Select the devices, by labels, that the alert rule applies to. Supports + and - signs as AND and AND NOT operators, respectively; if no sign is provided, the OR operator is used. When labels is not set, the rule applies to all connected devices (labels=all).
  • connected bool — State condition that matches whether the device is connected (yes) or disconnected (no). Default: no.
  • cpu-above num — Alert when CPU load is above the given percent value (0..100); a value equal to the threshold also fires the rule. Default: unset.
  • cpu-below num — Alert when CPU load is below the given percent value (0..100); it fires only for values strictly below the threshold. Default: unset.
  • hdd-above num — Alert when disk (HDD) load is above the given percent value (0..100); a value equal to the threshold also fires the rule. Default: unset.
  • hdd-below num — Alert when disk (HDD) load is below the given percent value (0..100); it fires only for values strictly below the threshold. Default: unset.
  • mem-above num — Alert when RAM load is above the given percent value (0..100); a value equal to the threshold also fires the rule. Default: unset.
  • mem-below num — Alert when RAM load is below the given percent value (0..100); it fires only for values strictly below the threshold. Default: unset.
  • health-above num — Alert when the health sensor named by health-value goes above the given value; a value equal to the threshold also fires the rule. Devices that do not report the sensor are ignored. Default: unset.
  • health-below num — Alert when the health sensor named by health-value goes below the given value; it fires only for values strictly below the threshold. Devices that do not report the sensor are ignored. Default: unset.
  • health-value string — Name of the health sensor to compare, matching a name from /system/health/print, for example cpu-temperature. Uses the [cpu-temperature] style placeholder in the action text.
  • interface-change alt { change: enum (any) , change: ubit (running, not-running, added, removed) } — Alert on an interface state change: - any (default) - Any state change. - running - An interface's link comes up. - not-running - An interface's link goes down. - added - An interface is first seen. - removed - An interface is no longer seen. running and not-running follow the link state of the interface, not its admin state: enabling or disabling an interface with no connection does not fire, while an actual link loss or recovery does.
  • interface-type alt { type: enum (any) , type: ubit (ethernet, wifi, bridge) } — Restrict interface-change alerts to one interface type: - any (default) - Interfaces of any type. - ethernet - Ethernet ports. - wifi - Wireless interfaces. - bridge - Bridge interfaces.
  • upgrade-available bool — Alert when a newer RouterOS version is available for the device. Default: no.
  • disconnected-more-than time — Alert when a device has been disconnected for longer than the given time. Default: unset.
  • upgrade-job-done alt { cond: enum (yes) , cond: ubit (success, fail) } — Alert when an upgrade job finishes; the rule fires once for the whole job, when the last device of the job is done: - yes (default) - Any outcome. - success - The job finished successfully. - fail - The job failed. A job that ends without installing an upgrade is treated as a failed job, so the yes and fail variants both fire.
  • upgrade-done alt { cond: enum (yes) , cond: ubit (success, fail) } — Alert when the upgrade of a device finishes; the rule fires once for every device that finished its upgrade: - yes (default) - Any outcome. - success - The upgrade finished successfully. - fail - The upgrade failed. When no newer version is available for a device, its upgrade still finishes as a failure (the [upgrade-error] is no upgrade available), so the yes and fail variants both fire.
  • unpaired-device-connected bool — Alert when a device that is not paired to the controller connects. Default: no.
  • rebooted bool — Event condition that fires when the device reboots, also when the reboot is part of an upgrade or comes from /cmr/device/reboot. Default: no.
  • log-topics multi { array-id, array-id, topic: super { ! , topic: enum } } — Log topics to follow; prefix a topic with ! to exclude it. Together with log-regex, defines a log-message event condition. CMR automatically instructs the device to forward matching log messages.
  • log-regex string — Match log messages against the given regular expression. Each message matching the configured topics and regular expression fires the actions without creating a persistent active alert.
  • action.log string — Write a message to the log when the alert fires. The message may contain placeholders such as [device] or [cpu-usage], replaced with the values of the device that fired; an inapplicable placeholder is rendered as unknown.
  • action.log-topics multi { array-id, topic: enum } — Log topics to write the message to. Default: cmr,info, and cmr,warning for a log-line condition.
  • action.log-prefix string — Prefix for the log message. When set, the prefix is prepended to the message without a separator; when unset the message is written as it is.
  • action.script enum — Run a named system script when the alert fires. The script must allow itself to run with reduced rights; otherwise the action fails with executing script ... from cmr failed ... (not enough permissions). Set the script's dont-require-permissions to yes.
  • action.script-vars multi { array-id, script-var: string } — List of variable names to make available to the action.script: each variable is filled with the value for the device that fired. For example device, identity, address, board, version become $device, $identity, and so on in the script. A name with a hyphen (for example cpu-usage) cannot be read as an ordinary script variable.
  • action.http-url string — HTTP webhook URL to call when the alert fires. On a failed call the alert writes alert "<name>" HTTP action failed: <reason> to the cmr topic with warning severity and counts the failure in action-failures; the other actions still run.
  • action.http-method enum (get | post | put | delete | head | patch) — HTTP method used for the webhook: - get - post - put - delete - head - patch
  • action.http-body string — HTTP request body sent to the webhook. Supports the same placeholders as the log message, substituted per device (for example [device] and [version]). No Content-Type header is added automatically; add one with action.http-headers when the receiver expects it, for example Content-Type: application/json for a JSON body.
  • action.http-headers multi { header: string } — Additional HTTP headers sent with the webhook, each as Header: value. The request also carries the controller's RouterOS <version> user-agent.
  • reset-on-disconnect enum (yes | no) { yes:0, no:-1 } — Clear (reset) a state alert when the device disconnects, so a reconnecting device fires the rule again if it still matches: yes or no. Default: no (the state is kept across a disconnect). Event alerts have no persistent state to reset.
  • severity enum (critical | high | medium | low) — Severity of the alert: - critical - high - medium (default) - low
  • category multi { array-id, category: enum } — Categories assigned to the alert. The category is a grouping label: the server assigns one according to the rule's conditions (for example performance, availability, version, network, or logging), and it can be changed to any value.

Read-only Argument / Type / Description

  • devices num — Number of devices the alert rule matches (the devices selected by labels). When the rule covers all devices, this count includes the controller itself.
  • devices-on num — Number of devices with an active state alert. Event occurrences do not add to this count.
  • fired num — Total number of times the alert has fired.
  • action-failures num — Number of times an alert action has failed, for example a webhook that could not be reached.

  • labels multi { array-id, label: enum } — User labels assigned to the device (grouping/filtering).

Read-only Argument / Type / Description

  • board string — Board name.
  • version string — RouterOS version of the device.
  • minimum-version string — Minimum supported version.
  • allowed-versions string — Safe (safepkg) upgrade indicator.
  • address address (flags=46) — Current connection address.
  • auto-labels multi { array-id, label: string } — Automatically assigned labels.
  • packages multi { array-id, label: string } — Installed packages.
  • state string — Device state.
  • upgrade-rule enum — Upgrade rule covering this device. The first rule in the /cmr/upgrade rule list that covers the device claims it, so a labels=all rule placed at the top covers every device.
  • channel alt — Current upgrade channel/version.
  • available-version string — Newest available upgrade.
  • connected-time time — Time the device has been connected.
  • uptime time — Device uptime.
  • disconnected-since date — Time since the device disconnected.
  • alerts super { on: num , [all] /num , [critical] num , [high] /num , [medium] /num , [low] /num } — Enabled/total alert counts by severity.
  • serial string — Factory serial number.

upgrade

Starts an upgrade (job) for the selected devices. The upgrade runs as a job in /cmr/upgrade/job, with the same job states and result counters. On the console, the command shows the job's devices and their states...

cmr/device/upgrade

Package: cmr Type: Command

Starts an upgrade (job) for the selected devices. The upgrade runs as a job in /cmr/upgrade/job, with the same job states and result counters. On the console, the command shows the job's devices and their states until you press Control+C or the time given in duration ends; the job continues on the server. With order, the label groups are upgraded one after another; list the devices that others connect through, such as switches and gateways, last.

Flag / Name / Description

  • L controller — Include the CMR server itself (self-client).

Argument / Type / Description

  • labels object — Select the devices to upgrade using labels. Supports + and - signs as AND and AND NOT operators, respectively; if no sign is provided, the OR operator is used.
  • order object — Execution order (by labels).
  • channel alt — Upgrade channel (long-term, stable, testing, or development) or a pinned version, for example channel=7.24.4. When not set, each device upgrades on its own upgrade channel, the channel value shown in /cmr/device.
  • schedule-time super { time: date , [day] [ @enum (sun | mon | tue | wed | thu | fri | sat) { sun:1, mon:2, tue:3, wed:4, thu:5, fri:6, sat:7 }] } — When the upgrade starts: a time with an optional weekday given after @, for example 14:00:00 or 00:00:00@sat. The job waits in the scheduled state until the next occurrence of that time.
  • strategy enum (parallel | sequential) — How devices are upgraded: parallel upgrades all covered devices at the same time; sequential upgrades them one after another and waits for each to finish. With continue-order the devices are processed per label group in the order given by order: in parallel the devices of each group are upgraded together, in sequential one at a time. Default: parallel.
  • fail-policy enum (continue | stop | continue-order) — Behaviour if a device fails: continue skips the failed device and continues with the rest; stop stops the whole upgrade on the first failure and does not continue with the remaining devices or with the next label group; continue-order skips the failed device and continues with the next label group, processing the labels one group after another in the order given by order. With sequential the rest of the failed device's group is skipped; with parallel only the failed device is abandoned and devices already in progress in the group finish. Default: stop.
  • packages multi { package: string } — Packages to upgrade.

One upgrade job is one upgrade run. Jobs are created from upgrade rules, and their parameters are copied from the rule at creation and are read-only. A scheduled job resolves its device list only when it starts, so show-devices for a scheduled job can be empty. Remove a queued or processing job to cancel it. The job state becomes cancelled.

cmr/upgrade/trigger

Package: cmr Type: Command

Starts the job of a chosen rule right away, without waiting for the schedule-time. Only one upgrade job runs at a time; triggering another rule while a job is in progress places the new job in a queued state until the current job finishes.

Triggering forces an early upgrade of the rule's covered devices: the job runs immediately and upgrades each covered device that has a newer version available, without waiting for the schedule-time. Covered devices that are already up to date are skipped, so the run's counter counts only the upgraded ones. To upgrade a single device regardless of its rule, see /cmr/device/upgrade.

cmr/vlan

Package: cmr Type: Directory

The /cmr/vlan menu creates bridge and VLAN configuration on the selected CMR clients. Each rule selects the devices with labels and the ports with port-labels (matched against the interface names of a device and against the port labels assigned in /cmr/device), lists the vlan-ids, and assigns each port a role. On a selected device the rule adds the selected ports and their VLAN entries to the enabled bridge of the device. If the device has no enabled bridge, the rule creates a bridge named cmr-bridge with VLAN filtering enabled. Removing a rule removes the ports and VLAN entries that it added. See the VLAN provisioning section of the CMR guide.

Flag / Name / Description

  • X disabled — VLAN provisioning rule is disabled.

Argument / Type / Description

  • labels object — Select the CMR clients this rule provisions. Supports + and - signs as AND and AND NOT operators, respectively; if no sign is provided, the OR operator is used. If omitted, the rule applies to all connected devices.
  • port-labels object — Select the ports to configure on the selected devices, by interface name (for example ether1) or by a port label assigned to the port in /cmr/device (for example uplink). The argument is required, so a rule always names the ports it configures.
  • vlan-ids multi { vlan-range: range [1 .. 4094] } — VLAN IDs assigned to the selected ports, as a comma-separated list or a range, for example 100,200 or 100-200. On a trunk port every VLAN ID is tagged; on an access port only the first VLAN ID is used, as the port's PVID.
  • role enum (access | trunk) — Port role assigned to the selected ports: - access (default) - the port belongs to a single VLAN, which is set as the port's PVID, and carries untagged frames - trunk - the port carries multiple VLANs; frames are tagged with 802.1Q headers so the far end can tell them apart
