Pair Claire with Home Assistant on hAP be³ Media

Install the Thread-enabled Home Assistant app on hAP be³ Media and pair a Claire air quality sensor with the Home Assistant Companion app.

Pair your Claire or Claire Lite air quality sensor with Home Assistant on hAP be³ Media to view sensor readings on your phone or in a web browser, and use them in automations and alerts.

Claire connects over Matter over Thread. The router's built-in Thread radio provides the wireless connection, and the homeassistant-thread app includes Home Assistant, the OpenThread Border Router, and the Matter server.

NOTE

In earlier RouterOS versions, this app is named ha-otbr-matter. Select the Thread-enabled app available in your router's catalog.

Before you begin

Out of the box, hAP be³ Media has Apps configured, the required packages installed, and container support enabled in device-mode. You can proceed directly to the Home Assistant app installation.

Prepare the following:

  • A hAP be³ Media with internet access.
  • A USB drive connected to the router for app storage. If the drive is not ready for use in RouterOS, follow the disk setup instructions.
  • A powered Claire or Claire Lite within range of the router.
  • A phone with the Home Assistant Companion app installed, Bluetooth enabled, and access to the router's Wi-Fi network.

Connect your computer and phone to the router's local network for setup and pairing.

If you have reinstalled RouterOS or reset the unit, check that the container package is installed and container support is enabled in device-mode. Restore these settings if necessary. Physical access to the router is required to confirm a device-mode change. Run the Apps setup wizard if the app configuration is missing.

Install the Home Assistant app

  1. Connect to hAP be³ Media with WinBox or WebFig and open the App menu.
  2. If you have not configured app storage and networking, select Setup. Choose the USB drive, your LAN bridge, and the router's LAN IP address. Follow the Apps setup wizard for details.

[gambar: WinBox App setup wizard with usb1 selected as the Apps Disk.]

  1. Select homeassistant-thread, or ha-otbr-matter in earlier RouterOS versions, and select Enable.

[gambar: WinBox app catalog showing homeassistant-thread with Home Assistant, OpenThread Border Router, and Matter server.]

  1. Wait for the app to download, extract, and start. The app contains several container images, so installation can take several minutes.
  2. Open the app's UI URL link to access Home Assistant.

The Apps system configures the containers and their networking automatically.

Set up Home Assistant on your phone

  1. On the Home Assistant welcome page, create your administrator account and complete the initial setup.
  2. Open the Home Assistant Companion app on your phone.
  3. Select your Home Assistant instance. If it is not discovered automatically, enter the same URL you opened from UI URL.
  4. Sign in with the username and password you created in Home Assistant.
  5. Allow the permissions requested for pairing, including Bluetooth and camera access.

Use the Companion app on your phone to pair Claire. After pairing, you can view its readings from either the Companion app or the Home Assistant web interface.

Pair Claire

  1. In the Home Assistant Companion app, open Settings → Devices & services and select Matter.
  2. Select Add device. If asked whether the device is already in use, select No, it's new for an unpaired Claire. Follow the prompts to open the QR code scanner.
  3. On Claire, hold the side button for 3 seconds to open the settings menu.
  4. Use short button presses to highlight Pairing code.
  5. Hold the button for 1 second to display the Matter pairing QR code.
  6. Scan the QR code on Claire's screen with the Companion app and wait for pairing to finish. Keep your phone near Claire during setup.
  7. Give the device a name and assign it to an area, such as Living room.

Claire returns to its main screen after 30 seconds without button input. If the QR code disappears before you scan it, open Pairing code again.

View sensor readings

In Home Assistant, open Settings → Devices & services → Matter and select Claire. Its device page shows the available sensor readings. The sensors shown depend on your Claire model.

You can add the readings to a dashboard or create automations, such as a notification when CO₂ rises above a threshold you choose. Keep Claire powered and within Thread coverage so Home Assistant can receive updates.

If pairing does not finish

Phone and QR code

  • Pair from the Home Assistant Companion app on your phone. Use the web interface to view readings after pairing.
  • Enable Bluetooth and allow the app's camera, Bluetooth or nearby-device, and local-network permissions when requested. Keep the phone near Claire during pairing.
  • If an iPhone repeatedly refuses to pair, restart the iPhone, reopen the Companion app, and try again.
  • If the QR code disappears, open Pairing code on Claire again. Its screen returns to the main view after 30 seconds without button input.

Home Assistant and Thread

  • Confirm the homeassistant-thread app, or ha-otbr-matter in earlier RouterOS versions, has finished starting and its UI URL opens.
  • Keep the phone on the router's local Wi-Fi network. A guest network with client isolation or a VPN on the phone can prevent local discovery and communication, even if the Home Assistant web page opens. Disconnect the phone's VPN and use the main LAN for pairing.
  • Matter uses local IPv6 and multicast discovery. If you have customized the router's network or firewall configuration, check that IPv6 and the required local communication between Home Assistant, the phone, and the Thread border router are allowed.
  • Check Settings → Devices & services in Home Assistant for the Matter, Thread, and OpenThread Border Router integrations. Resolve any reported setup errors before retrying.
  • If the phone reports that a Thread border router is required, check the Thread integration and confirm the hAP be³ Media Thread network is available. If you have several Thread networks, check which one is preferred. Complete any Thread credential transfer or synchronization prompts in Home Assistant and the Companion app before retrying.
  • Move Claire closer to hAP be³ Media during setup. Keep it within Thread coverage after pairing so readings remain available.

Existing pairing and sensor updates

  • If Claire is paired to another home and you want to replace that pairing, use Unpairing in Claire's settings menu before repeating these steps. This removes its existing pairing.
  • Allow up to 10 minutes for Claire's sensors to stabilize after power-on. Readings update at different intervals: CO₂ updates every 30 seconds, and particulate matter every 5 minutes. A reading remaining unchanged for a short time does not necessarily indicate a connection problem.

For button controls and unpairing instructions, see the Claire hardware manual.

Container - FreeRADIUS server

Run a FreeRADIUS server in a RouterOS container, add a RADIUS client and a user, and log in to the router with that user.

Container - FreeRADIUS server

Introduction

With containers, RouterOS can run servers that would otherwise need a separate device or machine on your network.

RADIUS (Remote Authentication Dial-In User Service) lets RouterOS check user names and passwords against a central server, for example for PPP, PPPoE, L2TP, HotSpot and router logins. This guide runs the FreeRADIUS server in a container on the router, adds one user, and logs in to the router with it.

The image is freeradius/freeradius-server on Docker Hub. Check its tags for the architectures it is available for; the alpine tags are smaller and use other configuration paths than this guide.

Summary

Read the container guide first, especially the disclaimer and the requirements: the container package must be installed and containers enabled in device-mode.

The image takes about 90 MB to download and more after extraction, so this example extracts it to an external disk, disk1.

WARNING

This guide shows a basic configuration for testing. See the FreeRADIUS documentation for other options. Before using the server in production, use strong secrets and passwords, and run the server without debug mode.

Container configuration

Networking

Add a veth interface for the container:

/interface/veth/add name=veth3 address=172.20.0.2/24 gateway=172.20.0.1

Create a bridge for the container, give it an address, and add the veth interface to it:

/interface/bridge/add name=freeradius
/ip/address/add address=172.20.0.1/24 interface=freeradius
/interface/bridge/port/add bridge=freeradius interface=veth3

The router sends its RADIUS requests to the server from the bridge address, 172.20.0.1.

If the container needs internet access, add NAT for its outgoing traffic:

/ip/firewall/nat/add chain=srcnat action=masquerade src-address=172.20.0.0/24

Image

This example downloads the image from Docker Hub (see Registry); you can also import it from a .tar file. Set the directory where the downloaded image is extracted:

/container/config/set tmpdir=disk1/pull

Add the container:

/container/add remote-image=freeradius/freeradius-server:latest \
    interface=veth3 root-dir=disk1/freeradius logging=yes cmd="-X" \
    name=freeradius

cmd="-X" starts FreeRADIUS in debug mode: it writes every request and its result to the log, which helps while you set up the server.

RouterOS downloads and extracts the image. Check the progress with /container/print; when the extraction is done, the container status is stopped.

Start the container

/container/start [find where name=freeradius]

With container logging enabled, the log shows the server start (/log/print where topics~"container", some lines left out):

 2026-11-24 07:11:44 container,info,debug freeradius: Listening on auth address * port 1812 bound to server default
 2026-11-24 07:11:44 container,info,debug freeradius: Listening on acct address * port 1813 bound to server default
 2026-11-24 07:11:44 container,info,debug freeradius: Ready to process requests

Server configuration

The server's configuration files are in the container's root directory, under disk1/freeradius/etc/freeradius. Download them with SFTP (the SSH service must be enabled), edit them, and upload them back. This guide changes two files:

  • clients.conf - the RADIUS clients (devices such as the router) that may send requests to the server;
  • mods-config/files/authorize - the users.

Download both files:

sftp admin@192.168.88.1
sftp> cd disk1/freeradius/etc/freeradius
sftp> ls
README.rst          certs               clients.conf        dictionary          
experimental.conf   hints               huntgroups          mods-available      
mods-config         mods-enabled        panic.gdb           policy.d            
proxy.conf          radiusd.conf        sites-available     sites-enabled       
templates.conf      trigger.conf        users               
sftp> get clients.conf
sftp> cd mods-config/files
sftp> get authorize
sftp> exit

Clients

clients.conf comes with many commented examples; see the FreeRADIUS documentation for all options. For this example, replace its content with:

client router {
    ipaddr = 172.20.0.1
    secret = Example-secret-1
}
  • ipaddr - the address that the router sends its requests from, the bridge address. The server ignores requests from addresses that are not listed.
  • secret - the shared secret, which must match the secret of the RADIUS entry on the router. Use a long random string.

Users

In authorize, find the commented line for the user bob:

#bob    Cleartext-Password := "hello"

Remove the # and set a password; leave the other lines as they are:

bob Cleartext-Password := "Example-pass-1"

This adds the user bob. To add more users, add more lines in the same format.

Upload the files

Upload both files to the folders that you downloaded them from:

sftp admin@192.168.88.1
sftp> cd disk1/freeradius/etc/freeradius
sftp> put clients.conf
sftp> cd mods-config/files
sftp> put authorize
sftp> exit

Restart the container to load the new configuration:

/container/restart [find where name=freeradius]

Log in with a RADIUS user

Add the server to the router's RADIUS client, for router logins, with the secret from clients.conf:

/radius/add service=login address=172.20.0.2 secret="Example-secret-1"

Let router logins use RADIUS:

/user/aaa/set use-radius=yes

Log in to the router as bob with SSH, WinBox or WebFig. To test from the router's own terminal, connect with SSH to one of the router's addresses; the first time, confirm the host key, then enter bob's password:

/system/ssh 172.20.0.1 user=bob

In bob's session, list the sessions that RADIUS authenticated:

/user/active/print proplist=name,via,group where radius

Flags: R - RADIUS
Columns: NAME, VIA, GROUP
#   NAME  VIA  GROUP
0 R bob   ssh  read

The R flag shows that RADIUS authenticated the session. bob has the group read, the default-group of /user/aaa, because the server does not send a group for this user. See Log in to the router with RADIUS accounts for how to set the group on the server, and what to keep in mind when RADIUS accounts can log in to the router.

The container log shows the request and the answer:

2026-11-24 07:12:37 container,info,debug freeradius: (0) Sent Access-Accept Id 0 from 172.20.0.2:1812 to 172.20.0.1:37287 length 197

Container - HAProxy

Run HAProxy in a RouterOS container as a reverse proxy for other containers, and serve HTTPS with Let's Encrypt certificates that Certbot renews and installs in HAProxy without a restart.

Container - HAProxy

HAProxy is a reverse proxy and load balancer. In a container, it sits between users and the services that other containers run, so that those services are not exposed to the network directly. HAProxy can also terminate HTTPS for them.

This guide first runs HAProxy with a minimal HTTP configuration, then adds HTTPS with Let's Encrypt certificates that Certbot obtains and renews in a second container.

Summary

Read the container guide first, especially the disclaimer and the requirements: the container package must be installed and containers enabled in device-mode.

The examples use the container network of the container guide: the veth interface veth1 with the address 172.17.0.2, and a disk named disk1. Containers that use the same veth interface share its address, so HAProxy reaches a backend on veth1 at 172.17.0.2 and the backend's port.

The examples upload files to the router with SFTP; the SSH service must be enabled.

Basic configuration

  1. Add the mount for the HAProxy configuration folder:

routeros /container/mounts/add list=haproxy_etc src=disk1/haproxy-etc \ dst=/usr/local/etc/haproxy

  1. Add the HAProxy container:

routeros /container/add remote-image=haproxy:latest interface=veth1 \ root-dir=disk1/haproxy mountlists=haproxy_etc user=0:0 \ name=haproxy logging=yes

  1. Create the configuration file haproxy.cfg on your computer. This example forwards HTTP requests on port 80 to a backend on port 8008 of the same veth interface, such as the Matrix Synapse server:

```text defaults mode http timeout client 10s timeout connect 10s timeout server 10s timeout http-request 10s

frontend http_synapse bind *:80 use_backend synapse

backend synapse server server1 172.17.0.2:8008 maxconn 32 ```

  1. Upload the file into the mounted folder. The folder does not exist until the container starts for the first time, so create it first:

shell sftp admin@192.168.88.1 sftp> mkdir disk1/haproxy-etc sftp> put haproxy.cfg disk1/haproxy-etc/haproxy.cfg sftp> exit

  1. Start the container:

routeros /container/start [find where name=haproxy]

To reach HAProxy from the LAN or the internet, forward ports 80 and 443 to 172.17.0.2, as the Bridge with NAT example does for another port.

HTTPS with Certbot

This example serves HTTPS with a certificate from Let's Encrypt, and renews it automatically:

  • a Certbot container obtains the certificate with the DNS-01 challenge: it creates a TXT record in your domain with an RFC 2136 dynamic DNS update, so ports 80 and 443 do not have to be open for the validation;
  • a deploy hook copies each new certificate into the HAProxy configuration folder, and updates the running HAProxy through its runtime API, without a restart;
  • the RouterOS scheduler starts the Certbot container once a day; Certbot renews the certificate when it is due.

Both containers use veth1, so the hook reaches the HAProxy runtime API at 127.0.0.1.

You need:

  • a domain name that points to your router, router.example.com in this example;
  • a DNS server for that domain that accepts RFC 2136 updates signed with a TSIG key, and the key's name, algorithm and secret.

Replace router.example.com, admin@example.com and the DNS details with your own in all files and commands below.

HAProxy

  1. Add the mount and the HAProxy container:

routeros /container/mounts/add list=MOUNT_HAPROXY \ src=disk1/volumes/haproxy/config dst=/usr/local/etc/haproxy /container/add remote-image=haproxy:latest interface=veth1 \ root-dir=disk1/images/haproxy mountlists=MOUNT_HAPROXY \ name=haproxy start-on-boot=yes user=0:0 logging=yes

  1. Create haproxy.cfg on your computer, and adjust it to your needs. This configuration redirects HTTP to HTTPS, loads every certificate in the certs folder, refuses requests from a client address that sends more than 10000 requests in 10 seconds, and forwards the requests to a backend on port 8080:

```text global log stdout format raw local0 info stats socket ipv4@127.0.0.1:9999 level admin ssl-default-bind-ciphers EECDH+AESGCM:EDH+AESGCM ssl-default-server-ciphers EECDH+AESGCM:EDH+AESGCM ssl-default-bind-options ssl-min-ver TLSv1.2 ssl-default-server-options ssl-min-ver TLSv1.2 tune.ssl.default-dh-param 2048

defaults log global timeout client 10s timeout connect 10s timeout server 10s timeout http-request 10s

frontend frontend_webapp mode http option httplog option http-server-close option forwardfor except 127.0.0.0/8 stick-table type ipv6 size 100k expire 30s store http_req_rate(10s) http-request track-sc0 src http-request deny deny_status 429 if { sc_http_req_rate(0) gt 10000 } bind *:80 bind *:443 ssl crt /usr/local/etc/haproxy/certs/ http-request redirect scheme https unless { ssl_fc } http-request set-header X-Forwarded-Host %[req.hdr(host)] use_backend backend_webapp

backend backend_webapp mode http balance roundrobin option http-server-close option forwardfor server server1 172.17.0.2:8080 ```

  • stats socket ipv4@127.0.0.1:9999 level admin - the runtime API that the deploy hook uses. It accepts commands without authentication, so it listens only on 127.0.0.1, which only the containers on veth1 can reach.
  • option forwardfor - HAProxy adds the X-Forwarded-For header with the client's address to each request it forwards to the backend.
  1. Upload the file. Do not start HAProxy yet: it does not start without a certificate in the certs folder.

shell sftp admin@192.168.88.1 sftp> mkdir disk1/volumes sftp> mkdir disk1/volumes/haproxy sftp> mkdir disk1/volumes/haproxy/config sftp> put haproxy.cfg disk1/volumes/haproxy/config/haproxy.cfg sftp> exit

Certbot

Certbot reads its options from /etc/letsencrypt/cli.ini. With the options in this file, the container's cmd only names the Certbot command and the domain.

  1. Create these three files on your computer.

rfc2136.ini, the DNS server and the TSIG key for the update:

text dns_rfc2136_server = 192.0.2.53 dns_rfc2136_port = 53 dns_rfc2136_name = certbot. dns_rfc2136_secret = <TSIG secret> dns_rfc2136_algorithm = HMAC-SHA512

cli.ini, the Certbot options:

text non-interactive = true agree-tos = true email = admin@example.com authenticator = dns-rfc2136 dns-rfc2136-credentials = /etc/letsencrypt/rfc2136.ini deploy-hook = sh /etc/letsencrypt/haproxy-deploy.sh

haproxy-deploy.sh, the deploy hook. Certbot runs it after it receives a new certificate, and sets RENEWED_LINEAGE to the certificate's folder, /etc/letsencrypt/live/router.example.com:

shell #!/bin/sh # Certbot deploy hook: install a new certificate in HAProxy. # Certbot sets RENEWED_LINEAGE to /etc/letsencrypt/live/<name>. name=$(basename "$RENEWED_LINEAGE") mkdir -p /etc/haproxy/certs cat "$RENEWED_LINEAGE/fullchain.pem" "$RENEWED_LINEAGE/privkey.pem" \ > "/etc/haproxy/certs/$name.pem" # Update a running HAProxy through its runtime API (path as HAProxy sees it). crt=/usr/local/etc/haproxy/certs/$name.pem { echo "set ssl cert $crt <<"; cat "/etc/haproxy/certs/$name.pem"; echo; } \ | nc 127.0.0.1 9999 echo "commit ssl cert $crt" | nc 127.0.0.1 9999

Files uploaded to the router are not executable in the container, so cli.ini runs the hook with sh.

  1. Upload the files into the Certbot configuration folder:

shell sftp admin@192.168.88.1 sftp> mkdir disk1/volumes/certbot sftp> mkdir disk1/volumes/certbot/config sftp> cd disk1/volumes/certbot/config sftp> put rfc2136.ini sftp> put cli.ini sftp> put haproxy-deploy.sh sftp> exit

  1. Add the mounts and the Certbot container. The fourth mount gives Certbot the HAProxy configuration folder, where the hook writes the certificate:

routeros /container/mounts add list=MOUNT_CERTBOT src=disk1/volumes/certbot/config \ dst=/etc/letsencrypt add list=MOUNT_CERTBOT src=disk1/volumes/certbot/data \ dst=/var/lib/letsencrypt add list=MOUNT_CERTBOT src=disk1/volumes/certbot/log \ dst=/var/log/letsencrypt add list=MOUNT_CERTBOT src=disk1/volumes/haproxy/config \ dst=/etc/haproxy /container/add remote-image=certbot/dns-rfc2136 \ cmd="certonly -d router.example.com" interface=veth1 \ root-dir=disk1/images/certbot mountlists=MOUNT_CERTBOT \ name=certbot start-on-boot=yes logging=yes

  1. When the image is extracted (the container status is stopped), start the Certbot container:

routeros /container/start [find where name=certbot]

  1. Check the log. Certbot waits 60 seconds for the DNS record to propagate, then receives the certificate and stops (some lines left out):

routeros /log/print where topics~"container" and message~"certbot"

text 2026-11-24 06:57:28 container,info,debug certbot: Account registered. 2026-11-24 06:57:28 container,info,debug certbot: Requesting a certificate for router.example.com 2026-11-24 06:57:28 container,info,debug certbot: Unsafe permissions on credentials configuration file: /etc/letsencrypt/rfc2136.ini 2026-11-24 06:57:28 container,info,debug certbot: Waiting 60 seconds for DNS changes to propagate 2026-11-24 06:58:31 container,info,debug certbot: Hook 'deploy-hook' reported error code 1 2026-11-24 06:58:31 container,info,debug certbot: Successfully received certificate. 2026-11-24 06:58:31 container,info,debug certbot: Certificate is saved at: /etc/letsencrypt/live/router.example.com/fullchain.pem 2026-11-24 06:58:31 container,info,debug certbot: Key is saved at: /etc/letsencrypt/live/router.example.com/privkey.pem

Certbot warns about Unsafe permissions because files uploaded to the router are readable by every user in the container; only Certbot runs in it.

On this first run, HAProxy is not running yet, so the hook cannot reach the runtime API, and Certbot logs Hook 'deploy-hook' reported error code 1. The certificate is already in the certs folder, and HAProxy loads it when it starts.

  1. Start HAProxy:

routeros /container/start [find where name=haproxy]

  1. Start the Certbot container every day, for example at 06:30. Certbot renews the certificate when it is due; otherwise, it stops with Certificate not yet due for renewal; no action taken.

routeros /system/scheduler/add name=certbot-renew interval=1d \ start-time=06:30:00 \ on-event="/container/start [find where name=certbot]"

When Certbot renews the certificate, the hook replaces it in the running HAProxy, and the log shows the runtime API's answers (some lines left out):

 2026-11-24 06:59:04 container,info,debug certbot: Renewing an existing certificate for router.example.com
 2026-11-24 06:59:04 container,info,debug certbot: Waiting 60 seconds for DNS changes to propagate
 2026-11-24 07:00:07 container,info,debug certbot: Hook 'deploy-hook' ran with output:
 2026-11-24 07:00:07 container,info,debug certbot:  Transaction created for certificate /usr/local/etc/haproxy/certs/router.example.com.pem!
 2026-11-24 07:00:07 container,info,debug certbot:  Committing /usr/local/etc/haproxy/certs/router.example.com.pem.
 2026-11-24 07:00:07 container,info,debug certbot:  Success!
 2026-11-24 07:00:07 container,info,debug certbot: Successfully received certificate.

Container - HomeAssistant

Run Home Assistant in a RouterOS container: network, configuration mount, time zone, image download, first start and resource use.

Container - HomeAssistant

Introduction

With containers, RouterOS can run servers that would otherwise need a separate device or machine on your network.

Home Assistant is a home automation platform: it collects data from sensors and controls devices through a large number of integrations. This guide runs Home Assistant in a container on the router and opens its web interface.

The image is homeassistant/home-assistant on Docker Hub. Check its tags for the architectures it is available for; at the time of writing, these are ARM64 and AMD64 (CHR and x86).

Summary

Read the container guide first, especially the disclaimer and the requirements: the container package must be installed and containers enabled in device-mode.

Home Assistant needs more resources than most containers. The image takes about 650 MiB to download and about 2.3 GiB after extraction; keep about 3 GB free on the disk for the installation. This example extracts it to an external disk, disk1. When it runs without integrations, it uses about 500 MB of RAM (see Resources).

Container configuration

Networking

Add a veth interface for the container:

/interface/veth/add name=veth4 address=172.21.0.2/24 gateway=172.21.0.1

Create a bridge for the container, give it an address, and add the veth interface to it:

/interface/bridge/add name=ha
/ip/address/add address=172.21.0.1/24 interface=ha
/interface/bridge/port/add bridge=ha interface=veth4

Home Assistant uses internet services, for example to check for alerts. Add NAT for its outgoing traffic:

/ip/firewall/nat/add chain=srcnat action=masquerade src-address=172.21.0.0/24

Without this rule, Home Assistant still starts and serves its web interface, but the log shows errors such as Cannot connect to host alerts.home-assistant.io:443.

Configuration mount and time zone

Home Assistant keeps its configuration in the /config folder. Mount a folder on the disk there, so that the configuration is kept when the container is removed or updated:

/container/mounts/add list=ha_config src=disk1/ha_config dst=/config

Set the time zone with the TZ environment variable; use your own time zone name:

/container/envs/add list=ha_env key=TZ value=America/Los_Angeles

Image

This example downloads the image from Docker Hub (see Registry); you can also import it from a .tar file. Set the directory where the downloaded image is extracted:

/container/config/set tmpdir=disk1/pull

Add the container:

/container/add remote-image=homeassistant/home-assistant:latest \
    interface=veth4 root-dir=disk1/ha mountlists=ha_config \
    envlists=ha_env logging=yes name=homeassistant

RouterOS downloads and extracts the image, which takes several minutes. Check the progress with /container/print; when the extraction is done, the container status is stopped.

Start the container

/container/start [find where name=homeassistant]

On the first start, Home Assistant creates its configuration files in disk1/ha_config. It takes a few minutes before the web interface answers.

Home Assistant setup

Open the web interface in a browser at http://172.21.0.2:8123. Devices in the router's LAN reach the container network through the router.

Container - Matrix (Synapse)

Introduction

Matrix is a decentralized communication protocol. Each Matrix server operates independently, with its own users, rules and policies. With containers, you can host your own Matrix server on a RouterOS device and keep full control over your communication.

  • Federation - Matrix servers connect to each other, so that users on different servers can communicate securely without a central authority.
  • Bridges - a bridge relays messages between Matrix and another chat platform, such as WhatsApp, Discord, Signal or Telegram. With bridges, you can use one Matrix client, such as Element, to talk to users on several platforms.

This guide sets up Synapse, one of several Matrix servers, with a PostgreSQL database, and then adds a Discord bridge. Each of them runs in its own container.

Summary

Read the container guide first, especially the disclaimer and the requirements: the container package must be installed and containers enabled in device-mode.

All containers in this guide use the veth interface veth1 (172.17.0.2/24) with NAT from the container guide's Bridge with NAT example; create it first. Containers on the same veth interface share its address, so each service listens on its own port:

Container Port

postgresql_discord 5434
synapse_discord 29334

The images are downloaded from their registries (see Registry) and extracted to an external disk, disk1; set the directory for the downloads:

/container/config/set tmpdir=disk1/pull

The passwords in this guide are examples; use your own long random passwords. Consult the Synapse documentation for the latest configuration options and best practices, as configuration procedures can change with newer versions.

Synapse server

PostgreSQL database

Create the environment variables for the PostgreSQL container:

/container/envs/add list=postgres_synapse_envs key=POSTGRES_DB value="synapse"
/container/envs/add list=postgres_synapse_envs key=POSTGRES_PASSWORD value="Example-db-pass-1"
/container/envs/add list=postgres_synapse_envs key=POSTGRES_USER value="synapse_user"
/container/envs/add list=postgres_synapse_envs key=PGDATA value="/var/lib/postgresql/data/pgdata"
/container/envs/add list=postgres_synapse_envs key=POSTGRES_INITDB_ARGS value="--encoding='UTF8' --lc-collate='C' --lc-ctype='C'"
/container/envs/add list=postgres_synapse_envs key=PGPORT value=5433

Synapse needs a database with UTF8 encoding and the C collation, which POSTGRES_INITDB_ARGS sets when the database is created. PGPORT moves PostgreSQL to port 5433, so that it does not clash with other containers on veth1, such as the PostgreSQL example in the container guide (port 5432).

/container/mounts/add list=synapse_postgres_data src=disk1/synapse-postgres-data dst=/var/lib/postgresql/data

/container/add remote-image=postgres:17.2-alpine interface=veth1 \

/container/envs/add list=synapse_envs key=SYNAPSE_CONFIG_DIR value="/data"

/container/mounts/add list=synapse_data src=disk1/synapse-data dst=/data

Container - mosquitto MQTT server

Introduction

With containers, RouterOS can run servers that would otherwise need a separate device or machine on your network.

This guide shows how to run the eclipse-mosquitto MQTT broker in a container. MQTT is a lightweight publish-subscribe protocol, an OASIS and ISO standard, widely used in IoT networks. A typical setup has publishers (devices that send messages), a broker (the server that receives the messages and passes them on), and subscribers (devices that receive the messages for the topics they subscribed to).

RouterOS can publish and subscribe over MQTT itself; with a container, the router can also run the broker. The guide uses this to test the broker from the router.

The image is eclipse-mosquitto on Docker Hub. Check its tags for the architectures it is available for.

Summary

Read the container guide first, especially the disclaimer and the requirements: the container package must be installed and containers enabled in device-mode.

The example uses the router's own storage. The mosquitto image is small, so a device with 128 MB of storage, such as the RB1100AHx4, has room for it.

WARNING

This guide shows a very basic configuration. See the mosquitto documentation for other options and settings. Before using the broker in production, harden its security:

  • Use the firewall to allow access to the container only from trusted addresses.
  • Configure the broker with strong passwords and without anonymous access.
  • Use MQTT over TLS, as shown in the SSL MQTT section.

Container configuration

Networking

Add a veth interface for the container:

/interface/veth/add name=veth2 address=172.19.0.2/24 gateway=172.19.0.1

Create a bridge for the container and add the veth interface to it:

/interface/bridge/add name=msqt
/ip/address/add address=172.19.0.1/24 interface=msqt
/interface/bridge/port/add bridge=msqt interface=veth2

Optionally, to reach the broker through the router's LAN address (192.168.88.1 in this example) on the non-TLS port 1883, forward that port to the container:

/ip/firewall/nat/add action=dst-nat chain=dstnat \
    dst-address=192.168.88.1 dst-port=1883 protocol=tcp \
    to-addresses=172.19.0.2 to-ports=1883

Mount

The broker reads its configuration from /mosquitto/config/mosquitto.conf. Mount the whole folder, not only the file, so that you can also put the TLS certificates there later:

/container/mounts/add list=msqt_config src=/mosquitto_mounted \
    dst=/mosquitto/config

Image

This example downloads the image from Docker Hub (see Registry); you can also import it from a .tar file. Set the directory where the downloaded image is extracted:

/container/config/set tmpdir=pull

Add the container:

/container/add remote-image=library/eclipse-mosquitto:latest \
    interface=veth2 root-dir=mosquitto mountlists=msqt_config \
    logging=yes name=mosquitto

RouterOS downloads and extracts the image. Check the progress with /container/print; when the extraction is done, the container status is stopped.

SSL MQTT

Using MQTT without TLS in production is not secure: anyone who can capture the traffic between the broker and its clients can read the credentials and the messages.

The first step is to create the certificates. This example uses a simple root CA setup, without client certificates. Follow the official mosquitto-tls guide to create:

  • ca.crt - the certificate of the certificate authority (CA);
  • server.crt - the broker's certificate, signed by the CA;
  • server.key - the broker's private key.

Server configuration

Replace the content of mosquitto.conf with these lines:

listener 8883
tls_version tlsv1.2
allow_anonymous true
cafile /mosquitto/config/ca.crt
keyfile /mosquitto/config/server.key
certfile /mosquitto/config/server.crt
  • listener 8883 - the broker listens for connections on port 8883. The listener line must come before the TLS options, which apply to it; otherwise, the broker does not start and logs Error: The 'tls_version' option requires a listener to be defined first.
  • tls_version tlsv1.2 - the minimum TLS version.
  • allow_anonymous true - clients that connect without a user name are allowed.
  • cafile, keyfile, certfile - the paths to the CA certificate, the server key and the server certificate, as the container sees the mounted folder.

WARNING

This is a basic TLS configuration for testing. allow_anonymous true is not a secure setting in production.

Container - Postgres

PostgreSQL is a powerful, widely-used SQL database engine that serves as the backbone for numerous applications, ranging from small web projects to enterprise-level systems. This guide will walk you through the essential steps required to get PostgreSQL up and running on RouterOS. Additionally, this guide will provide you with the necessary instructions to set up pgAdmin—a feature-rich, web-based interface that allows you to easily manage your PostgreSQL database.

Configuration

This section provides step-by-step instructions for setting up a PostgreSQL container on your MikroTik RouterOS device. PostgreSQL is a powerful, open-source relational database system that supports SQL standards and offers advanced features such as transactions, subqueries, and user-defined types. Before proceeding, ensure that you have already created a container network as described in the Container network documentation.

Step 1: Create Mount Point for PostgreSQL Container

Before creating the container, you need to create a persistent storage location where PostgreSQL will store its database files. This ensures that your data persists even if the container is recreated or removed, protecting your valuable database information.

/container/mounts/add list=MOUNT_POSTGRES src=disk1/volumes/postgres/data dst=/var/lib/postgresql/data

This mount point maps your local data directory to the container's /var/lib/postgresql/data path, which is where PostgreSQL will store all database files, transaction logs, and system catalogs.

Step 2: Configure Environment Variables for PostgreSQL Container

Environment variables provide configuration parameters that PostgreSQL requires at startup. These variables define the initial database name, user credentials, and data directory location.

/container/envs/add list=ENV_POSTGRES key=POSTGRES_DB value="myapp"
/container/envs/add list=ENV_POSTGRES key=POSTGRES_PASSWORD value="<changeme>"
/container/envs/add list=ENV_POSTGRES key=POSTGRES_USER value="myapp"
/container/envs/add list=ENV_POSTGRES key=PGDATA value="/var/lib/postgresql/data/pgdata"
/container/envs/add list=ENV_POSTGRES key=POSTGRES_INITDB_ARGS value="--encoding='UTF8' --lc-collate='C' --lc-ctype='C'"

The POSTGRES_DB variable specifies the name of the initial database that will be created when PostgreSQL starts for the first time. The POSTGRES_USER and POSTGRES_PASSWORD variables define the superuser account credentials that you'll use to connect to and manage your database. The PGDATA variable indicates the location within the container where PostgreSQL will store its data files. The POSTGRES_INITDB_ARGS variable provides additional initialization parameters that set the database encoding to UTF8 and the locale settings to C for consistent behavior.

Step 3: Create the PostgreSQL Container

Now you're ready to create and configure the PostgreSQL container instance. This command pulls the official PostgreSQL Docker image from the remote registry and configures it with the environment variables and mount point which were established in the previous steps.

/container/add remote-image=postgres:15 interface=veth1 root-dir=disk1/images/postgres mountlists=MOUNT_POSTGRES envlists=ENV_POSTGRES name=postgres start-on-boot=yes logging=yes

NOTE

To run a different PostgreSQL version, replace postgres:15 with another PostgreSQL image tag.

Step 4: Start the PostgreSQL Container

With all configuration complete, you're now ready to initiate the PostgreSQL container. Starting the container will launch the PostgreSQL database server, which will become ready to accept connections from your applications.

/container/start [find where name=postgres]

On the first start, PostgreSQL creates the initial database and user from the environment variables. When the log shows database system is ready to accept connections, PostgreSQL accepts connections on port 5432 of the container's address (172.17.0.2 in the Bridge with NAT example). Because of start-on-boot=yes, the container also starts when the router boots.

Advanced: PostgreSQL with pgAdmin

This guide demonstrates how to configure and deploy pgAdmin, the popular web-based administration tool for PostgreSQL databases, as a container on your MikroTik RouterOS device. pgAdmin provides an intuitive graphical interface for managing your PostgreSQL databases servers, allowing you to create databases, execute queries, manage users, and perform various administrative tasks through a web browser.

Step 1: Create Mount Points Directories for pgAdmin Container

Before creating the container, you need to create persistent storage locations where pgAdmin will store its configuration files, session data, and server connection settings. This ensures that your settings and connections remain intact even after container restarts or updates.

/container/mounts/add list=MOUNT_PGADMIN_CONFIG src=disk1/volumes/pgadmin/config dst=/config
/container/mounts/add list=MOUNT_PGADMIN_DATA src=disk1/volumes/pgadmin/data dst=/var/lib/pgadmin

The first mount point maps your local configuration directory to the container's /config path, where pgAdmin will store server definitions and user preferences. The second mount point maps your local data directory to the container's /var/lib/pgadmin path, which houses session information, logs, and runtime data.

Step 2: Configure Environment Variables for pgAdmin Container

Environment variables provide configuration parameters that pgAdmin requires at startup. These variables define the application behavior, default credentials, and network settings.

/container/envs/add list=ENV_PGADMIN key=PGADMIN_LISTEN_PORT value=80
/container/envs/add list=ENV_PGADMIN key=PGADMIN_DEFAULT_EMAIL value="sysadmin@domain.com"
/container/envs/add list=ENV_PGADMIN key=PGADMIN_DEFAULT_PASSWORD value="<changeme>"
/container/envs/add list=ENV_PGADMIN key=PGADMIN_SERVER_JSON_FILE value="/config/servers.json"
/container/envs/add list=ENV_PGADMIN key=PGADMIN_PREFERENCES_JSON_FILE value="/config/preferences.json"
/container/envs/add list=ENV_PGADMIN key=PGPASS_FILE value="/config/pgpass"
/container/envs/add list=ENV_PGADMIN key=PGADMIN_DISABLE_POSTFIX value="True"

The PGADMIN_LISTEN_PORT variable specifies which port pgAdmin will listen on for incoming web connections—port 80 is used by default for standard HTTP access. The PGADMIN_DEFAULT_EMAIL and PGADMIN_DEFAULT_PASSWORD variables define the initial administrator credentials that you'll use to log into the pgAdmin web interface for the first time. The remaining variables specify file paths within the container where pgAdmin will store and retrieve server connection configurations, user preferences, and password files data.

Step 3: Create the pgAdmin Container

Now you're ready to create and configure the pgAdmin container instance. This command pulls the official dpage/pgadmin4 Docker image from the remote registry and configures it with the environment variables and mount points which were established in the previous steps.

/container/add remote-image=dpage/pgadmin4 envlists=ENV_PGADMIN mountlists=MOUNT_PGADMIN_CONFIG,MOUNT_PGADMIN_DATA interface=veth1 logging=yes name=pgadmin root-dir=disk1/images/pgadmin start-on-boot=yes user=0:0

This command specifies the official pgAdmin4 Docker image from Docker Hub, applies your previously defined environment variable list and mount point list, assigns the container to the veth1 virtual ethernet interface (the same interface as the PostgreSQL container, so both containers share its address), enables logging for troubleshooting purposes, names the container "pgadmin" for easy identification, stores the container image files in the designated disk location, configures the container to start automatically whenever the router boots, and runs the container with root user privileges.

Step 4: Start the pgAdmin Container

With all configuration complete, you're now ready to initiate the pgAdmin container. Starting the container will launch the pgAdmin web application.

/container/start [find where name=pgadmin]

On the first start, pgAdmin sets up its own database before it opens the web interface, which can take a few minutes on a slow device. Until then, connections to the container's port 80 are refused.

Step 5: Open the pgAdmin Web Interface

pgAdmin listens on port 80 of the container's address, not of the router, so it does not conflict with WebFig, and the www service can stay enabled. From a host that has a route to the container network, open http://172.17.0.2/.

To reach pgAdmin through the router's address instead, forward a free router port to the container. This rule forwards port 8080 for connections that arrive on the LAN interface list, so pgAdmin is not exposed on the WAN side:

/ip/firewall/nat
add chain=dstnat action=dst-nat protocol=tcp dst-port=8080 \
    in-interface-list=LAN to-addresses=172.17.0.2 to-ports=80 \
    comment=pgadmin

Open http://192.168.88.1:8080/ and log in with the email address and password from Step 2. To manage the database, register a server with host 172.17.0.2, port 5432, and the POSTGRES_USER and POSTGRES_PASSWORD values of the PostgreSQL container.

For the container commands used in this guide, see /container, /container/envs and /container/mounts.

Container - Kubernetes (RKE2) single-node cluster

This guide shows how to install a single-node Kubernetes cluster on a ROSE Data Server (RDS) with the RKE2 container for RouterOS: storage, network, configuration files, the container itself, and access with kubectl...

Container - Kubernetes (RKE2) single-node cluster

RKE2 is a Kubernetes distribution from Rancher. MikroTik publishes an RKE2 container image for RouterOS, mikrotik/rke2. This guide runs it as a single-node Kubernetes cluster on a ROSE Data Server (RDS) with the Calico network plugin.

WARNING

The image is published for testing. The container runs with privileged=yes. Run it on a router that you can dedicate to this task.

Requirements

  • A ROSE Data Server. RKE2 has its own hardware requirements for processor and memory.
  • Two U.2 NVMe disks of at least 100 GB each, inserted in the first two slots. The guide deletes all data on them.
  • The container and rose-storage packages.
  • Container mode enabled in device-mode.
  • Access from the router to Docker Hub, or to a private container registry.

The examples use these values. Replace them with the values of your network:

Value Meaning
bridge Bridge of the network where the cluster is reachable. This is the bridge of the default configuration
192.168.1.1 Gateway of this network
192.168.1.2 Address of the router
192.168.1.3 Address of the RKE2 container, and of the Kubernetes API. Use an address that no other device has and that is outside the DHCP pool
rke2.k8s Host name of the node
192.168.192.0/19 Pod network inside the cluster
192.168.224.0/19 Service network inside the cluster

The pod and service networks exist only inside the cluster. Change them only when they overlap with networks that the cluster must reach.

Prepare the router

Packages and device-mode

Enable the two packages. The router reboots when the changes are applied. If both packages are already enabled, skip this step:

/system/package/enable container
/system/package/enable rose-storage
/system/package/apply-changes

Check that container mode is enabled:

/system/device-mode/print

If the output shows container: no, enable it and confirm with the reset button of the router when the command asks for it. The router reboots:

/system/device-mode/update container=yes

Time

Kubernetes components reject TLS certificates when the clock is wrong. The container uses the clock of the router. Enable the NTP client of the router and use the NTP server of your network:

/system/ntp/client/servers/add address=pool.ntp.org
/system/ntp/client/set enabled=yes

Storage

RouterOS adds only disks without a file system to an array. If the disks were in use before, wipe them first:

/disk/format nvme1 file-system=wipe-quick
/disk/format nvme2 file-system=wipe-quick

Create a RAID 1 array from the two disks and format it. All data of the container and of the cluster is stored on this array:

/disk/add type=raid slot=raid1 raid-type=1 raid-device-count=2
/disk/set nvme1 raid-master=raid1 raid-role=0
/disk/set nvme2 raid-master=raid1 raid-role=1
/disk/format raid1 file-system=ext4 label=containers

WARNING

Wiping and formatting delete all data on both disks.

See RAID for the RAID types and for other disk layouts.

Network

The container connects to the network through a virtual Ethernet (veth) interface that is a port of the bridge:

/interface/veth/add name=ens18 address=192.168.1.3/24 \
    gateway=192.168.1.1
/interface/bridge/port/add bridge=bridge interface=ens18
/interface/bridge/settings/set use-ip-firewall=yes

The cluster requires use-ip-firewall=yes. With this setting, the traffic that the bridge forwards passes the IP firewall of the router. The setting applies to all bridges of the router.

WARNING

The container is a port of the bridge, so every device in this network reaches it directly. This includes the Kubernetes API on port 6443. Use a network that you trust, or a separate bridge or VLAN for the cluster.

Create the configuration files

Directories

Create the directories for the container layers and for the RKE2 data and configuration:

/file/add type=directory name=raid1/rke2/ntp
/file/add type=directory name=raid1/rke2/etc

restrict ::1
"

This file configures the Calico network plugin: VXLAN between pods, the iptables data plane, and the pod network. cidr must be the same as --cluster-cidr of the RKE2 container, and blockSize the same as node-cidr-mask-size. interface is the name of the veth interface.

      enabled: true
    felixConfiguration:

Use the iptables data plane (linuxDataplane: Iptables) in RouterOS containers. See the rke2-calico chart for all values.

Create the container

Container settings and mounts

/container/config/set registry-url=https://registry-1.docker.io

/container/config/set registry-url=https://registry.example.com

RKE2 container

The command starts the NTP daemon, the device manager, and then the RKE2 server. cmd is a list with commas between its items: /bin/bash, -c and the script. bash gets the script as one argument, spaces included (see cmd in /container):

/container/add \

remote-image=mikrotik/rke2:v1.36.6-rke2r1-ubuntu2604-beta \
interface=ens18 \
privileged=yes \
root-dir=raid1/containers/rke2 \
stop-time="00:00:30" \
restart-interval="00:00:10" \
restart-max-count=100 \
restart-policy=on-failure \
start-on-boot=yes \
healthcheck-cmd="kubectl get node rke2.k8s | grep --color=none -i ' ready ' || exit 1" \
healthcheck-interval="00:01:00" \
healthcheck-retries=10 \
healthcheck-start-interval="00:00:20" \
healthcheck-start-period="00:03:00" \
entrypoint="" \
cmd="/bin/bash,-c,\
  /usr/sbin/ntpd -c /mnt/rke2-ntp.conf && \
  /usr/lib/systemd/systemd-udevd --daemon && udevadm trigger --wait-daemon=20 && \
  /bin/rke2 server \
  --snapshotter=fuse-overlayfs \
  --kubelet-arg=feature-gates=KubeletInUserNamespace=true \
  --cni=calico \
  --cluster-cidr=192.168.192.0/19 \
  --service-cidr=192.168.224.0/19 \
  --cluster-dns=192.168.224.10 \
  --kube-controller-manager-arg=node-cidr-mask-size=21 \
  --tls-san=192.168.1.3 \
  --tls-san=rke2.k8s \
  --node-name=rke2.k8s \
  --ingress-controller=none \
  --data-dir=/var/lib/rancher/rke2" \
mountlists=RKE2_DATA,RKE2_ETC,RKE2_NTP_CONFIG \
hostname=rke2.k8s

What to change:

  • remote-image - the tag selects the Kubernetes version. The tag in this command is the one that this guide was tested with. Newer tags are listed on mikrotik/rke2.
  • --tls-san, --node-name, hostname and the node name in healthcheck-cmd - the address and the name of your node.
  • --cluster-cidr, --service-cidr, --cluster-dns and node-cidr-mask-size - only together with the Calico file.
  • --snapshotter - use fuse-overlayfs or native. The default RKE2 snapshotter, overlayfs, does not work in a RouterOS container.

With a private registry, add --private-registry=/mnt/rke2-registries.yaml \ after the --ingress-controller line, and add RKE2_REGISTRIES to mountlists.

Container - ThingsBoard MQTT/HTTP server

Run the ThingsBoard IoT platform in a RouterOS container, send data to it from RouterOS with MQTT, and enable HTTPS and MQTT over TLS with a certificate made on the router.

Container - ThingsBoard MQTT/HTTP server

Introduction

With containers, RouterOS can run servers that would otherwise need a separate device or machine on your network.

Many users need a server that collects data, stores it and shows it in a way that is easy to understand. ThingsBoard is such a platform. It is positioned as an IoT platform; see its use cases.

For RouterOS, ThingsBoard works as an MQTT broker and as an HTTP server: RouterOS can send data to it with MQTT publish or with an HTTP POST. See the ThingsBoard MQTT API and HTTP API.

With scripting, you can collect RouterOS statistics (uptime, GPS coordinates, packet counters and almost anything that you can print in the terminal), build a JSON message from them, and send it to ThingsBoard from the scheduler. See MQTT and ThingsBoard configuration for an example script. ThingsBoard stores the data and shows it in dashboards with widgets: graphs, tables, maps and more.

ThingsBoard provides single-instance images with different databases, for example:

  • thingsboard/tb-postgres - With PostgreSQL.
  • thingsboard/tb-cassandra - With Cassandra.

This guide uses tb-postgres, a single instance of ThingsBoard with a PostgreSQL database, with the in-memory queue. This is a setup for testing; for production, see the queue options in the ThingsBoard Docker installation guide.

Summary

Read the container guide first, especially the disclaimer and the requirements: the container package must be installed and containers enabled in device-mode. The MQTT test needs the iot package.

The tb-postgres image is available for ARM64 and AMD64 (CHR and x86) only; check its tags for the current list.

ThingsBoard is a server that needs more resources than most containers:

  • Disk - the image takes about 1 GB to download and about 1.1 GB after extraction, and the database grows with the data that you store. This example uses an external disk, disk1; plan a reserve, especially if you run more containers.
  • RAM - the ThingsBoard documentation recommends at least 1 GB of RAM for a single instance with PostgreSQL and a light load (a few messages per second), and 2-4 GB for more. ThingsBoard alone, without load, uses about 750 MB; on a router with 1 GB of RAM, little memory is left for RouterOS and other services, so use a device with more RAM. See Memory for how to limit the memory that a container uses.

Configuration

Networking

Add a veth interface for the container:

/interface/veth/add name=veth5 address=172.22.0.2/24 gateway=172.22.0.1

Create a bridge for the container, give it an address, and add the veth interface to it:

/interface/bridge/add name=thingsboard
/ip/address/add address=172.22.0.1/24 interface=thingsboard
/interface/bridge/port/add bridge=thingsboard interface=veth5

Add NAT for the container's outgoing traffic:

/ip/firewall/nat/add chain=srcnat action=masquerade src-address=172.22.0.0/24

Devices in the router's LAN can reach the container at 172.22.0.2. To use the router's LAN address instead (192.168.88.1 in this example), forward the ThingsBoard ports to the container: TCP 9090 for the web interface and TCP 1883 for MQTT.

/ip/firewall/nat/add action=dst-nat chain=dstnat dst-address=192.168.88.1 dst-port=9090 \
    protocol=tcp to-addresses=172.22.0.2 to-ports=9090
/ip/firewall/nat/add action=dst-nat chain=dstnat dst-address=192.168.88.1 dst-port=1883 \
    protocol=tcp to-addresses=172.22.0.2 to-ports=1883

WARNING

Plain HTTP (port 9090) and MQTT without TLS (port 1883) send passwords, access tokens and data unencrypted: anyone who can capture the traffic can read them. Use them only for testing in a local network or through a VPN.

Set everything up with local addresses first and confirm that it works. Before you allow access from the internet:

  • Change the passwords of the default ThingsBoard users, or remove the users (see the ThingsBoard documentation), and remove the demo devices.
  • Enable HTTPS and MQTT over TLS (see HTTPS and MQTT over TLS).
  • In the dst-nat rules, use the public address in dst-address, the TLS ports, and src-address or src-address-list to allow only trusted addresses, for example your branch office.

You are responsible for the security of the server. Opening a port to the internet without these steps lets anyone try to use it.

Environment variables and mounts

Check the tb-postgres documentation for the mounts and variables that the image uses.

Set the queue type:

/container/envs/add list=tb_envs key=TB_QUEUE_TYPE value="in-memory"

Mount folders for the data (including the database) and for the logs:

/container/mounts/add list=mytb-data src=disk1/tb/mytb-data dst=/data
/container/mounts/add list=mytb-logs src=disk1/tb/mytb-logs dst=/var/log/thingsboard

/container/config/set tmpdir=disk1/pull

/container/add remote-image=thingsboard/tb-postgres:latest interface=veth5 \

HTTPS and MQTT over TLS

By default, ThingsBoard uses HTTP and MQTT without TLS. As explained in Networking, this is safe only in a protected network, so enable HTTPS and MQTT over TLS. See the ThingsBoard guides HTTP over SSL and MQTT over SSL for all options.

TLS needs a certificate. This example makes a self-signed certificate on the router; you can also use a certificate from a certificate authority, or one made with OpenSSL or other tools. ThingsBoard reads the certificate and its key from PEM files, which this example passes to the container through a mount and environment variables. The settings are kept in the container configuration, so they stay when you update the image.

Create the certificate

Create a certificate for the addresses that clients use to connect: the router's LAN address and the container address. One certificate serves both HTTPS and MQTT:

/certificate/add name=thingsboard common-name=thingsboard \
    subject-alt-name=IP:192.168.88.1,IP:172.22.0.2 days-valid=3650
/certificate/sign thingsboard

Create a folder for the files and export the certificate and its key there. RouterOS exports a private key only with a passphrase:

/file/add name=disk1/tb/ssl type=directory
/certificate/export-certificate thingsboard type=pem \
    export-passphrase="Example-key-pass-1" file-name=disk1/tb/ssl/thingsboard

This creates disk1/tb/ssl/thingsboard.crt and disk1/tb/ssl/thingsboard.key. Use your own passphrase.

ThingsBoard cannot read the encrypted key that RouterOS exports, also not with SSL_PEM_KEY_PASSWORD, and Java cannot read the RouterOS PKCS#12 export as a keystore. Remove the passphrase on a PC with OpenSSL instead. Download thingsboard.key with SFTP (the SSH service must be enabled), then run the following and enter the passphrase:

openssl pkey -in thingsboard.key -out thingsboard-key.pem

Upload thingsboard-key.pem to disk1/tb/ssl:

sftp admin@192.168.88.1
sftp> put thingsboard-key.pem disk1/tb/ssl/thingsboard-key.pem
sftp> exit

The key in thingsboard-key.pem is not encrypted: anyone who can read the router's files can copy it. Keep access to the router's files limited to administrators.

Configure ThingsBoard

Mount the folder in the container:

/container/mounts/add list=mytb-ssl src=disk1/tb/ssl dst=/ssl

Add the TLS settings to the container's environment variables:

/container/envs/add list=tb_envs key=SSL_ENABLED value="true"
/container/envs/add list=tb_envs key=SSL_PEM_CERT value="/ssl/thingsboard.crt"
/container/envs/add list=tb_envs key=SSL_PEM_KEY value="/ssl/thingsboard-key.pem"
/container/envs/add list=tb_envs key=MQTT_SSL_ENABLED value="true"
/container/envs/add list=tb_envs key=MQTT_SSL_PEM_CERT value="/ssl/thingsboard.crt"
/container/envs/add list=tb_envs key=MQTT_SSL_PEM_KEY value="/ssl/thingsboard-key.pem"
  • SSL_* - HTTPS for the web interface, on the same port, 9090.
  • MQTT_SSL_* - MQTT over TLS on port 8883. MQTT without TLS on port 1883 stays available; to turn it off, see MQTT_ENABLED in the ThingsBoard documentation.

Stop the container, add the mount, and start it again:

/container/stop [find where name=thingsboard]
/container/set [find where name=thingsboard] mountlists=mytb-data,mytb-logs,mytb-ssl
/container/start [find where name=thingsboard]

If ThingsBoard cannot load the certificate or the key, the container stops, and the log shows the reason, for example Unable to load private key.

Confirm MQTT over TLS

MQTT over TLS uses port 8883. To use it at the router's LAN address, change dst-port and to-ports of the MQTT forwarding rule from Networking from 1883 to 8883.

This example tests a one-way SSL communication with an access token.

From the router that runs the container

The router that made the certificate already trusts it. Add a broker with TLS:

/iot/mqtt/brokers/add name=tbssl address=172.22.0.2 port=8883 username=YOUR_TOKEN ssl=yes

Publish a test message:

/iot/mqtt/publish broker="tbssl" topic="v1/devices/me/telemetry" message="{\"test\":\"123\"}"

From another device

Another RouterOS device, for example an LtAP with the iot package, must trust the certificate before it connects. Without it, the connection fails, and the log on that device shows ssl failure [ssl: no trusted CA certificate found].

On the router that runs the container, export the certificate without its key (no passphrase):

/certificate/export-certificate thingsboard type=pem file-name=thingsboard-cert

Copy thingsboard-cert.crt to the other device (for example, drag and drop it in WinBox Files), and import it there:

/certificate/import file-name=thingsboard-cert.crt passphrase=""

Do not copy the key to other devices: clients need only the certificate.

Add the broker with the router's address from the 8883 forwarding rule, and publish a test message:

/iot/mqtt/brokers/add name=tbssl address=192.168.88.1 port=8883 username=YOUR_TOKEN ssl=yes
/iot/mqtt/publish broker="tbssl" topic="v1/devices/me/telemetry" message="{\"test\":\"123\"}"

The value appears in the device's Latest telemetry tab in ThingsBoard.
