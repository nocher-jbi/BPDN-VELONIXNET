Quality of Service

This document describes Quality of Service (QoS) implementation in RouterOS for devices equipped with Marvell Prestera switch chips.

QoS is a collection of features in network switches that allows network administrators to prioritize traffic and allocate network resources to ensure that critical data flows smoothly with low latency.

The primary function of QoS in a network switch is to manage traffic in a way that meets the specific requirements of different types of network applications. For example, voice and video data require low latency and minimal packet loss to ensure high-quality communication, while file transfers and other data applications can tolerate higher levels of latency and packet loss.

QoS works by identifying the type of traffic flowing through the switch and assigning it a priority level based on its requirements. The switch then uses this information to modify packet headers and prioritize traffic flow, ensuring that higher-priority traffic receives preferential treatment over lower-priority traffic.

RouterOS v7.15 or later is required to support all QoS features:

  1. QoS Marking. QoS profile matching by ingress packet header, then egress header modification according to the assigned QoS profile.
  2. QoS Enforcement. Avoid or resolve congestion based on the assigned QoS profile and traffic shaping.
  3. QoS Policy. Assign QoS profiles via ACL rules.
  4. Active Queue Management: WRED (Weighted Random Early Detection), ECN notification and processing, PFC (Priority-based Flow Control).
  5. Traffic shaping.

QoS Changes in RouterOS v7.23

RouterOS v7.23 introduces significant changes to Quality of Service (QoS) offloading. These changes simplify the configuration process and add support for "lossless" traffic classes. Although hardware resources are finite, active queue management using ECN and/or PFC can prevent packet loss when all connected devices support these features and are properly configured. Previous RouterOS versions already supported ECN and PFC, but v7.23 streamlines how you set them up.

INFO

Not all devices support lossless traffic. Check the QoS Device Support table.

Configuration Change Summary

  • QoS Settings: most changes were set to "auto" by default, allowing RouterOS to pick the best known settings for the setup.
  • QoS Settings: added lossless-traffic-class and lossless-buffers, allowing explicit specification of lossless traffic and the reservation of queue resources for it. The user can leave those fields as "auto" as well.
  • QoS Monitor: displays the shared pool usage for lossy and lossless separately.
  • Tx Queue: removed shared pool index. RouterOS automatically selects the shared pool based on the traffic type (lossy or lossless).
  • QoS Profile: added automapping to the specified PCP and DSCP values (enabled by default). For example, adding a QoS profile with DSCP=46 automatically applies the profile to traffic received from trusted ports.

QoS Terminology

This section defines the key terms and abbreviations used throughout this documentation:

  • QoS - Quality of Service, a collection of features that allows network administrators to prioritize traffic and allocate network resources.
  • ACL - Access Control List, a set of switch rules used to filter network traffic based on specified criteria.
  • AQM - Active Queue Management, a congestion control mechanism that manages traffic flow by dropping or marking packets before queue overflow occurs.
  • DSCP - Differentiated Services Code Point, a 6-bit field in the IP header used to prioritize network traffic.
  • ECN - Explicit Congestion Notification, a mechanism that allows routers to signal congestion to endpoints devices without dropping packets.
  • ETS - Enhanced Transmission Selection, a traffic scheduling method that uses weighted round-robin to allocate bandwidth among multiple queues groups.
  • PCP - Priority Code Point, a 3-bit field in the VLAN header used to prioritize traffic within a VLAN.
  • PFC - Priority-based Flow Control (IEEE 802.1Qbb), a flow control mechanism that pauses traffic on specific priority queues to prevent packet loss.
  • RoCE - RDMA over Converged Ethernet, a protocol that enables remote direct memory access over Ethernet networks.
  • WRED - Weighted Random Early Detection, a congestion avoidance mechanism that randomly drops packets as a queue approaches capacity.
  • /in/eth/sw/ - A CLI shortcut for /interface/ethernet/switch/.

QoS Enhancements in new generation Marvell Prestera Switch Chips

MikroTik devices with new generation Marvell Prestera switch chips (e.g. CRS8xx series running the switch-marvell package offer a new approach in QoS enforcement. Previous models required making a tradeoff between guaranteed and shared Tx queue buffers. By increasing the shared buffer percentage, the device can absorb larger traffic bursts, but at the same time, one congested port can occupy all shared buffers, limiting the QoS capabilities of other ports. Using the new generation switch chips enables the best of both worlds by introducing Dynamic Buffers. A switch chip dynamically adjusts port and queue buffer limits based on the current congestion level. If there is no congestion within the device, a single port can absorb a large burst of traffic, preventing packet loss. When the Tx queue size increases across multiple ports, the device reduces per-port and per-queue limits, enforcing fair use of shared resources while ensuring enough buffers for non-congested queues to continue forwarding traffic. The entire process is automated, requiring zero configuration from the user.

Another improvement in the new generation Marvell Prestera switch chips is eliminating the shortage of enqueued packet descriptors for storing control data. The previous generation devices had Packet Cap and Use stats. When a device received a burst of small packets, it could start tail-dropping packets due to hitting Packet Cap, even though it had enough queue buffers to store the payload. The new generation devices ensure there is always enough memory to store control data, leaving the Dynamic Buffer size as the only limiting factor. That's why there are no Packet Cap/Use stats in the new generation devices.

New generation devices require QoS HW Offloading to be enabled at all times (qos-hw-offloading=yes). RouterOS ignores user requests to disable it while keeping the field for backward compatibility.

Applications and Usage Examples

Basic Configuration Example

This example demonstrates how to configure a single QoS level for VoIP (IP Telephony) on top of the standard Best Effort class. The configuration uses a CRS326-24G-2S+ device with the following setup:

  • All ports are bridged and use vlan-filtering;
  • sfp-sfpplus1 serves as a VLAN trunk connected to another switch;
  • ether1 through ether9 are dedicated ports for IP phones;
  • ether10 through ether24 are standard ports for host connection.

First, define a QoS profile. This profile specifies the DSCP and PCP values that will be applied to forwarded packets on egress:

/interface/ethernet/switch/qos/profile
add dscp=46 name=voip pcp=5 traffic-class=5

Next, assign the VoIP QoS profile to the dedicated ports for IP phones. This applies the profile to ingress traffic on these ports. All other Ethernet ports will use the default profile (where dscp=0 and pcp=0):

/interface/ethernet/switch/qos/port
set ether1 profile=voip
set ether2 profile=voip
set ether3 profile=voip
set ether4 profile=voip
set ether5 profile=voip
set ether6 profile=voip
set ether7 profile=voip
set ether8 profile=voip
set ether9 profile=voip

The trunk port receives both types of QoS traffic. To differentiate between them, enable trust-l3 and trust-l2:

/interface/ethernet/switch/qos/port
set sfp-sfpplus1 trust-l3=trust trust-l2=trust

Note: If you are running RouterOS version 7.23 or later, the VLAN priority and IP DSCP mapping is created automatically, so this step is not required. If you are using an earlier RouterOS version, you must manually create the VLAN priority and IP DSCP mapping with the QoS profile:

/interface/ethernet/switch/qos/map/ip
add dscp=46 profile=voip

/interface/ethernet/switch/qos/map/vlan
add pcp=5 profile=voip

Finally, enable QoS hardware offloading for the above settings to take effect:

/interface/ethernet/switch
set switch1 qos-hw-offloading=yes

You can verify the port QoS settings using the print command:

Dante

Starting from RouterOS v7.15, all MikroTik QoS-capable devices are compatible with Dante audio networking.

Dante hardware uses the following DSCP/Diffserv priority values for traffic prioritization:

Dante Priority Usage DSCP Label DSCP Value
High Time-critical PTP events CS7 56
Medium Audio, PTP EF 46
None Other traffic BE 0

This example assumes the switch is using its default configuration, which includes a default bridge interface with all Ethernet interfaces added as bridge ports. Any of these interfaces can be used for Dante.

First, create QoS profiles to match Dante traffic classes. There is already a pre-existing "default" profile that corresponds to Dante's None priority.

/interface/ethernet/switch/qos/profile
add name=dante-ptp dscp=56 pcp=7 traffic-class=7
add name=dante-audio dscp=46 pcp=5 traffic-class=5

If you are running RouterOS version 7.23 or later, the IP DSCP mapping is created automatically, so this step is not required. If you are using an earlier RouterOS version, create a QoS mapping to match QoS profile based on DSCP values:

/interface/ethernet/switch/qos/map/ip
add dscp=56 profile=dante-ptp
add dscp=46 profile=dante-audio

Configure the hardware queue to enforce QoS on Dante traffic:

/interface/ethernet/switch/qos/tx-manager/queue
set [find where traffic-class=7] schedule=strict-priority
set [find where traffic-class=5] schedule=strict-priority

Dante's High and Medium priority traffic is scheduled in strict priority order. The device transmits time-critical PTP packets until queue7 is empty, then proceeds with audio (queue5). Other traffic is transmitted only when PTP and audio queues are empty.

The next step is to enable trust mode for incoming Layer 3 packets (IP DSCP field):

/interface/ethernet/switch/qos/port
set [find] trust-l3=keep

Finally, enable QoS hardware offloading for the above settings to take effect:

/interface/ethernet/switch
set switch1 qos-hw-offloading=yes

When using Dante in multicast mode, it is beneficial to enable IGMP snooping on the switch. This feature directs traffic only to ports with subscribed devices, preventing unnecessary flooding. Additionally, enabling an IGMP querier (if not already enabled on another device in the same LAN), adjusting query interval, and activating fast-leave can further optimize multicast performance.

/interface/bridge
set [find name=bridge] igmp-snooping=yes multicast-querier=yes query-interval=60s

/interface/bridge/port
set [find] fast-leave=yes

RDMA over Converged Ethernet (RoCE)

RoCE enables direct memory access to remote storage systems over Ethernet networks without involving the host CPU. This significantly reduces latency and CPU overhead, making RoCE ideal for high-performance computing and data center environments. RoCE also allows a converged network where various services (such as data storage, networking, and multimedia) run over a single Ethernet infrastructure, simplifying network management and reducing the cost and complexity of maintaining separate networks.

RoCE achieves this through the use of ECN and PFC mechanisms. These features help prevent network congestion and packet loss, ensuring reliable, lossless communication. See the device feature table for compatible switches. While the switch can support a RoCE environment, the end hosts must also be compatible with the RoCE protocol and equipped with RDMA-capable network interface cards (NICs).

There are two main versions of RoCE. RoCEv1 operates as an Ethernet link layer protocol and uses Ethertype 0x8915. RoCEv2 works over standard IP networks, using UDP destination port number 4791. ECN bits in the IP header are marked to signal network congestion, and a Congestion Notification Packet (CNP) is used to acknowledge congestion to the sender. For traffic prioritization, DSCP 26 is used for RoCEv2 traffic, while DSCP 48 is used for CNPs.

The following example configures lossless RoCEv2 with PFC on four 100 Gbit/s ports. It assumes that the switch has its default configuration, with a bridge that has all Ethernet interfaces as bridge ports.

The hosts take part in the configuration. Each host marks its RoCEv2 packets with DSCP 26, trusts the DSCP value of received packets, and runs PFC on priority 3. Without the marking, the packets stay in the default traffic class, and PFC does not protect them. For a host configuration with NVIDIA ConnectX adapters, see NVIDIA DGX Spark clusters.

First, create the profiles. Non-RoCE traffic stays in the existing default profile with traffic class 1, RoCEv2 goes to traffic class 3, and CNP to traffic class 6. The switch maps the DSCP values to these profiles by itself.

/interface/ethernet/switch/qos/profile
add dscp=26 name=roce traffic-class=3
add dscp=48 name=cnp traffic-class=6

Configure the hardware queues and the scheduler. Use ETS (schedule=high-priority-group) for traffic class 1 and traffic class 3 with 50% of the bandwidth each (weight=1), and strict priority scheduling for traffic class 6.

/interface/ethernet/switch/qos/tx-manager/queue
set [find traffic-class=1] schedule=high-priority-group weight=1
set [find traffic-class=3] schedule=high-priority-group weight=1
set [find traffic-class=6] schedule=strict-priority

TIP

Although using schedule=low-priority-group allows you to create separate ETS scheduling and bandwidth allocation for a different set of traffic-classes, it is not recommended to use this setting together with lldp-dcbx=yes. The reason is that the ETS Configuration/Recommendation TLVs are designed to handle a single bandwidth allocation across traffic classes, thus schedule=high-priority-group should be used instead.

Create a PFC profile for traffic class 3 with a pause threshold of 128 KiB and a resume threshold of 64 KiB.

/interface/ethernet/switch/qos/priority-flow-control
add name=pfc-tc3 rx=yes traffic-class=3 tx=yes \
    pause-threshold=128KiB resume-threshold=64KiB

With these thresholds, the switch pauses a port when the packets it received fill 128 KiB of the buffer, and lets the port send again when they drop 64 KiB below that. The switch pauses only the ports that send to a congested port.

Set Layer3 trust mode (trust-l3=keep) on the switch ports of the RoCEv2 hosts. Assign the PFC profile, and set the egress rate of queue 3 to the link speed (egress-rate-queue3=100.0Gbps), which PFC receive uses to calculate the pause time. The example uses 100 Gbit/s QSFP28 ports. Change the port names and the rate to match your interfaces.

/interface/ethernet/switch/qos/port
set qsfp28-1-1 egress-rate-queue3=100.0Gbps pfc=pfc-tc3 trust-l3=keep
set qsfp28-2-1 egress-rate-queue3=100.0Gbps pfc=pfc-tc3 trust-l3=keep
set qsfp28-3-1 egress-rate-queue3=100.0Gbps pfc=pfc-tc3 trust-l3=keep
set qsfp28-4-1 egress-rate-queue3=100.0Gbps pfc=pfc-tc3 trust-l3=keep

Enable QoS hardware offloading for the settings to start working.

/interface/ethernet/switch
set switch1 qos-hw-offloading=yes

Enable the LLDP Data Center Bridging Capability Exchange Protocol (DCBX) to share the QoS settings and capabilities with neighboring devices. Hosts without a DCBX agent ignore these announcements: configure their QoS by hand.

/ip/neighbor/discovery-settings
set lldp-dcbx=yes

Set the L2MTU for jumbo frames, and an MTU of 9000 on the hosts. RDMA then sends the same data in fewer, larger packets. A change of l2mtu restarts the link for a few seconds.

/interface/ethernet
set [find switch=switch1] l2mtu=9500

To check the configuration, print the QoS settings of the ports. A ;;; comment line under a port names a setting that the port is missing.

/interface/ethernet/switch/qos/port/print

PFC frames appear only under congestion, for example when two hosts send to a third host at the full link rate. Reset the counters, run such a transfer, and read the counters:

/interface/ethernet/reset-counters [find name~"qsfp28-.-1"]
/interface/ethernet/print stats where name~"qsfp28-.-1"

On a working configuration, tx-pause grows on the ports of the sending hosts, and tx-drop-queue3-packet and rx-fcs-error stay at 0 on all ports.

QoS Marking

Understanding Map Ranges

To avoid defining every possible PCP and DSCP mapping individually, RouterOS allows you to specify multiple values or ranges for PCP and DSCP when creating QoS profile mappings.

In this example, PCP values 0 and 2 use the default QoS profile, values 1 and 3-4 use the streaming profile, value 5 uses the voip profile, and values 6-7 use the control profile:

/interface/ethernet/switch/qos/map/vlan
add pcp=1,3-4 profile=streaming
add pcp=5 profile=voip
add pcp=6-7 profile=control

This approach simplifies configuration by grouping related priority values together rather than creating separate mappings rules for each individual value.

QoS Marking via Switch Rules (ACL)

Starting from RouterOS v7.15, you can assign QoS profiles to network traffic using Switch Rules (ACL). This method allows for flexible traffic classification based on various packet attributes.

The following example assigns a QoS profile based on the source MAC address:

/interface/ethernet/switch/rule
add new-qos-profile=stream port=ether1,ether2 src-mac-address=00:01:02:00:00:00/FF:FF:FF:00:00:00 switch=switch1
add new-qos-profile=voip port=ether1,ether2 src-mac-address=04:05:06:00:00:00/FF:FF:FF:00:00:00 switch=switch1

QoS Enforcement

Hardware Queues

Each switch port has eight hardware transmission (Tx) queues (queue0 through queue7). Each queue corresponds to a traffic class (tc0 through tc7) defined by a QoS profile. When a packet enters the switch, it receives a QoS profile assignment, which determines the traffic class and consequently selects the appropriate egress queue for transmission.

Hardware queues have variable sizes configured by the Transmission Manager. Additionally, multiple ports and queues can share resources with each other through a mechanism called Shared Buffers. For example, a device with 25 ports has buffer memory sufficient to queue 1200 packets total. If resources are split equally, each port receives 48 exclusive buffers with a maximum of 6 packets per queue (48 divided by 8), which is typically insufficient to absorb even a short traffic burst. However, allocating 50% of buffers for sharing leaves each port with 24 exclusive buffers (3 per queue), while simultaneously allowing a single queue to grow up to 603 buffers (3 exclusive plus 600 shared).

RouterOS enables enabling or disabling the shared pool for each queue individually. This capability helps prevent low-priority traffic from consuming all available hardware memory. Additionally, port buffer limits can restrict a single low-speed port from occupying the entire shared pool. For more details, see QoS Settings and Transmission Manager.

INFO

The default best-effort traffic class (PCP=0, DSCP=0) is traffic class 1, while the lowest priority traffic (PCP=1) uses traffic class 0.

To CPU QoS

Prestera switch chips use a separate set of transmit queues for frames destined to the CPU (the control plane). This is independent of the port QoS queues used for forwarded traffic. The switch assigns every trapped packet a CPU code and maps high-priority codes to queue1. Every CPU lane has one queue0 and one queue1, and each packet leaves through one of them:

  • queue0 carries regular data traffic sent to the CPU.
  • queue1 is the high-priority queue and is served first.

The separation keeps the control plane responsive when data traffic saturates the CPU. A data packet storm toward the CPU fills queue0 and can be dropped there, while control traffic in queue1 continues to be delivered. On boards with several CPU lanes, for example CCR2116 and CRS520, each lane has its own queue pair and RouterOS distributes traffic between the lanes. The TO_CPU counters on these boards report one value per lane.

NOTE

TO_CPU traffic uses only two priorities. queue1 is the highest, unlike the eight port queues where queue7 is the highest. The port QoS profile, DSCP, and PCP marking of an ingress packet do not affect which TO_CPU queue the packet uses.

Default High-Priority Traffic

The switch assigns the high-priority CPU queue to control traffic trapped by these traffic types:

  • Spanning tree BPDUs and other reserved multicast control frames in the 01:80:C2:00:00:0x range, including LACP, 802.1X, MVRP, LLDP, and MLAG.
  • IPv6 ICMP and neighbor discovery.
  • ARP broadcast and ARP replies addressed to the router.
  • Traffic matched by a switch rule with cpu-high-priority=yes.

NOTE

Reserved multicast frames are sent to the CPU and prioritized only when the bridge setting forward-reserved-addresses is no, which is the default. With forward-reserved-addresses=yes the bridge forwards these frames instead, so they do not use the high-priority CPU queue. For the full list of reserved addresses and the protocols that use them, see bridge settings.

RouterOS also creates dynamic ACL rules with cpu-high-priority=yes for features that inspect packets in the control plane:

  • IGMP and MLD snooping.
  • DHCP and DHCPv6 snooping.
  • ARP inspection.
  • RA guard.
  • Loop protect.
  • RoMON.
  • PTP.

All other packets sent to the CPU use queue0.

Viewing TO_CPU Counters

The switch-cpu port reports per-queue counters in the QoS port statistics:

/interface/ethernet/switch/qos/port/print stats where name=switch1-cpu

The fields to monitor are:

  • tx-queue0-packet and tx-queue0-byte - regular traffic delivered to the CPU.
  • tx-queue1-packet and tx-queue1-byte - high-priority traffic delivered to the CPU.
  • tx-drop-queue0-packet and tx-drop-queue1-packet - packets dropped in the corresponding queue.

Queue0 counters growing while queue1 counters stay flat mean that data traffic is reaching the CPU without high-priority traffic. Queue0 drops under load are expected because the CPU cannot process every packet. Queue1 should keep delivering control traffic.

On boards with several CPU lanes, the same field prints one value per lane. To monitor the changes live, use:

/interface/ethernet/switch/qos/port/print stats proplist=name,tx-queue0-packet,tx-queue1-packet interval=1s where name~"cpu"

Prioritizing Management Access with ACL Rules

A Layer 2 loop or a broadcast storm can saturate the CPU with data traffic and make the switch unreachable. Prioritize the management traffic so you can still log in, find the cause, and stop the loop. The following rules put SSH and WinBox traffic received on ether1 into the high-priority CPU queue:

/interface/ethernet/switch/rule/add switch=switch1 ports=ether1 protocol=tcp dst-port=22 redirect-to-cpu=yes cpu-high-priority=yes
/interface/ethernet/switch/rule/add switch=switch1 ports=ether1 protocol=tcp dst-port=8291 redirect-to-cpu=yes cpu-high-priority=yes

Replace ether1 with the port where management traffic enters the switch. Use copy-to-cpu=yes instead of redirect-to-cpu=yes when the packet must also be forwarded to its destination.

You can use the same rule structure to prioritize dynamic routing protocol traffic, such as OSPF or BGP. cpu-high-priority=yes requires redirect-to-cpu=yes or copy-to-cpu=yes in the same rule, otherwise RouterOS rejects the rule.

Hardware Resources

The switch chip has limited hardware resources (memory). Two main hardware resources are relevant to QoS operations:

  • Packet descriptor - Contains packet control information such as the target port, header modifications, and other metadata.
  • Data buffer - Memory chunk that stores the actual packet payload. Buffer size varies depending on the switch chip model; typically 256 bytes.

One packet descriptor may use multiple buffers (depending on the payload size), and buffers may be shared by multiple descriptors in cases of multicast or broadcast traffic. If the hardware does not have enough free descriptors or buffers, the packet gets dropped (tail-drop).

Hardware resources can be limited per destination type (multicast/unicast), per port, and per TX queue. When any of these limits are reached, no additional packets can be enqueued for transmission, and subsequent packets get dropped.

Packets dropped because the multicast limit is reached are counted by the multicast-packet-drop field in QoS Monitor.

RouterOS abstracts low-level hardware details, allowing resource limits to be configured either in terms of packets or as a percentage of the total amount. RouterOS automatically calculates the required hardware descriptor and buffer count based on the user-specified packet limit and port's MTU. Additionally, RouterOS includes preconfigured hardware resources, eliminating the need for manual configuration in common QoS scenarios.

DANGER

Modifying any hardware resource allocation parameter at runtime causes a temporary device halt during which no packets can be enqueued or transmitted. Temporary packet loss is expected while the device is forwarding traffic.

Resource Saving (Previous Generation Devices)

INFO

This section applies only to devices that do not support Dynamic Buffers.

Because hardware resources cannot be reallocated at runtime, RouterOS cannot automatically release queue buffers reserved for inactive ports. These buffers remain unused. However, if you know that a specific port will never be used (for example, it stays physically disconnected), you can manually free the corresponding queue resources by assigning the built-in "offline" tx-manager with minimum resources:

/interface/ethernet/switch/qos/port

set sfp-sfpplus2 tx-manager=offline

DANGER

Do not configure the "offline" tx-manager on the switch-cpu port.

WARNING

When configuring the tx-manager setting for a QSFP+ or QSFP28 interface, you must apply the same configuration to all four sub-interfaces of that port. For example, if interface qsfp28-1-1 is active and linked at 100Gbps, while sub-interfaces (qsfp28-1-2, qsfp28-1-3, qsfp28-1-4) show a non-running flag, do not assign the "offline" tx-manager to those non-running sub-interfaces. Doing so will affect the 100Gbps link as well. However, if none of the four sub-interfaces are running, it is safe to assign the "offline" tx-manager setting.

Traffic Prioritization

The hardware supports two types of traffic transmission prioritization:

  • Strict Priority - traffic from higher queues is always transmitted first.
  • Enhanced Transmission Selection (ETS) - multiple queues participate in packet transmission scheduling at the same time using weighted round-robin.

Strict Priority queuing is straightforward. If the highest priority queue (Q7) has packets, those are transmitted first. When Q7 is empty, packets from Q6 get transmitted, and so on. The packets from the lowest priority queue (Q0) are transmitted only if all other queues are empty.

The downside of strict prioritization is increased latency in lower queues while "overprioritizing" higher queues. Suppose the acceptable latency of TC5 is 20ms, TC3 - 50ms. Traffic appearing in Q5 gets immediately transmitted due to the strict priority of the queue, adding extra latency to every packet in the lower queues (Q4..Q0). A packet burst in Q5 (e.g., a start of a voice call) may temporarily "paralyze" Q3, increasing TC3 latencies over the acceptable 50ms (or even causing packet drops due to a full queue) while TC5 packets get transmitted at <1ms (way below the 20ms limit). Slightly sacrificing TC5 latency by transmitting TC3 packets in between would make everybody happy. That is what ETS is for.

Enhanced Transmission Selection (ETS) schedules traffic for transmission from multiple queues (group members) in a weighted round-robin manner. A queue's weight sets the number of packets transmitted from the queue in each round. For example, if Q2, Q1, and Q0 are the group members, and their weights are 3, 2, and 1, respectively, the scheduler transmits 3 packets from Q2, 2 from Q1, and 1 from Q0. The actual transmission order in each round of the above example is "Q2, Q1, Q0, Q2, Q1, Q2" - for even fairer scheduling.

There are two hardware groups: low-priority-group and high-priority-group. There is a strict priority ordering between the two groups: the low-priority-group transmits only when all queues in the high-priority-group are empty. However, it is possible to use only one group for all queues.

The default (built-in) RouterOS queue setup is listed below. Q3-Q5 share the bandwidth within the high-priority group, where packets are transmitted while Q6 and Q7 are empty. Q0-Q2 are the members of the low-priority-group, where packets are transmitted while Q3-Q7 are empty.

Active Queue Management (AQM)

Weighted Random Early Detection (WRED)

WRED is a congestion control mechanism that operates on a per-queue basis. It signals congestion events to end-point devices by dropping packets before queue overflow occurs. WRED relies on rate throttling mechanisms in end-points that respond to packet loss, such as TCP/IP.

WRED uses a randomized packet drop algorithm to anticipate congestion events and respond to them by throttling traffic rates before congestion actually happens. The randomness property of WRED prevents throughput collapse caused by global synchronization of TCP flows.

WRED can be enabled or disabled per queue in each Tx Manager. Disable WRED for lossless traffic classes. There is also no reason to enable WRED on high-speed ports where congestion should not occur in the first place.

The behavior is controlled via the WRED threshold. The WRED threshold defines the maximum number of packets or bytes that can exceed the queue's shared buffer limit (cap). Random packet drops begin when queue usage exceeds its respective capacity:

  • queueX-packet-use > queueX-shared-packet-cap, or
  • queueX-byte-use > queueX-shared-byte-cap.

The more the usage exceeds the capacity, the higher the packet drop chance becomes, reaching 100% at queueX-shared-packet-cap + wred-packet-threshold (or byte equivalent).

RouterOS automatically selects the actual WRED threshold values based on queue or shared pool capacities. The user can adjust the thresholds via the QoS Settings.

DANGER

WRED requires the respective Tx queue to use shared buffers (use-shared-buffers=yes).

Choosing a WRED threshold value involves a tradeoff between congestion anticipation and burst absorption. Setting a higher WRED threshold may lead to earlier traffic rate throttling and, therefore, resolve congestion. However, a high threshold causes packet drops in limited traffic bursts that could be absorbed by the queue buffers and transmitted losslessly if WRED didn't activate.

For example, initiating a remote database connection usually starts with heavier traffic (a "packet burst") during the initialization phase, then the traffic rate drops to a "reasonable" level. Any packet drop during the initialization phase results in a slower database connection due to the need for retransmission. Therefore, lowering the WRED threshold or entirely disabling WRED on such traffic is recommended. The opposite case is video streaming, where early congestion detection helps select a comfortable streaming rate without losing too much bandwidth on retransmission or sacrificing quality level.

INFO

Use Switch Rules (ACL) or other QoS Marking techniques to differentiate traffic and place packets into queues with the desired WRED settings.

The following script applies WRED only to TCP/IP traffic by redirecting it to queue2. UDP and other packets remain in queue1 since their end-points typically cannot respond to early drops. Queue1 and queue2 are scheduled equally without prioritizing one queue over another:

/interface/ethernet/switch/qos/profile
add name=tcp-wred traffic-class=2 pcp=0 dscp=0

# move TCP traffic to queue2
/interface/ethernet/switch/rule
add new-qos-profile=tcp-wred ports=ether1,ether2,ether3,ether4 protocol=tcp switch=switch1

# set the same scheduling priority (weight) between queue1 and queue2
# apply WRED only to queue2 - TCP traffic
/interface/ethernet/switch/qos/tx-manager/queue/
set [find where traffic-class=1] weight=2 schedule=low-priority-group use-shared-buffers=yes wred=no
set [find where traffic-class=2] weight=2 schedule=low-priority-group use-shared-buffers=yes wred=yes

Explicit Congestion Notification (ECN)

Certain switch chip models support hardware-level ECN marking for IP packets, compliant with RFC 3168. This mechanism operates similarly to WRED but, instead of dropping packets during congestion, it marks them with the CE (Congestion Experienced, binary 11) flag in the ECN field. Only ECN-capable IP packets can receive this mark—those with the ECN field value set to ECT(1) or ECT(0) (binary 01 or 10). Non-ECN-capable transport packets (ECN=00) are never marked. If a packet already carries the CE mark (ECN=11), it retains this designation regardless of whether the device experiences congestion.

Enable ECN marking by setting ecn=yes on the desired Tx Manager Queue.

DANGER

The ECN marking mechanism requires the respective Tx queue to use shared buffers (use-shared-buffers=yes).

A packet receives the CE mark when all of the following conditions are met:

  1. The packet is IPv4 or IPv6.
  2. The ECN field value in the IP header is either ECT(1) or ECT(0).
  3. The egress port's Tx Queue has ecn=yes enabled and uses shared buffers (use-shared-buffers=yes).
  4. Queue usage exceeds the shared buffer capacity: queueX-packet-use > queueX-shared-packet-cap or queueX-byte-use > queueX-shared-byte-cap.

DANGER

Since enabling ECN (ecn=yes) prevents ECN-capable packet drops, queue usage may exceed WRED thresholds if the traffic sender does not respond to congestion notification in time.

Priority-based Flow Control (PFC)

Priority-based Flow Control (PFC) enables lossless operation for up to eight traffic classes, ensuring that congestion in one traffic class does not pause traffic in other classes. This allows loss-sensitive traffic types to coexist with loss-tolerant traffic types on the same network.

PFC-capable switch chips comply with IEEE 802.1Qbb PFC standard, meaning they can generate and respond to PFC frames. When congestion occurs on an egress port, the source port transmits a PFC frame for the affected traffic class. The generated PFC frames use timer value 0xFFFF for pause (XOFF) and 0x0 for resume (XON), with the appropriate bit set in the priority enable vector. On the receiving end, the PFC frame pauses the specific priority queues on the destination port for the duration specified in the PFC frame.

In RouterOS, PFC configuration is organized into profiles. Each port can be assigned to a specific PFC profile, which defines the traffic classes to enable PFC on, the pause and resume thresholds for sending XOFF and XON frames respectively, and whether the assigned ports should transmit and/or receive PFC frames.

When congestion occurs on an egress port, PFC is triggered on the ingress port. Shared buffers must be used to associate the amount of ingress traffic with the packets waiting in Tx queues. For each PFC-enabled traffic class, set use-shared-buffers=yes on the corresponding Tx queue.

INFO

RouterOS implements a 1:1 mapping between traffic classes and Tx queues. Packets with traffic class 0 are enqueued in queue0, TC1 in queue1, and so on up to TC7 in queue7. Therefore, the terms "traffic class" and "Tx queue" are used interchangeably throughout this documentation.

When selecting pause and resume thresholds, account for the delay in transmitting and processing PFC frames. For example, device A experiences congestion at time T, sends a PFC pause frame to device B, and B processes the frame and stops transmitting at time T+D. During the delta time D, device B continues sending traffic. If device A has configured the pause threshold to 100%, it has no free buffers available, and packets may drop, which is unacceptable for lossless traffic classes. Setting a lower pause threshold, such as 80%, sends a PFC pause frame while still retaining free memory to absorb traffic during the delta time D. The same principle applies to the resume threshold. Setting it to 0% keeps the device idle during the delta time, reducing overall throughput.

PFC receive requires setting the egress rate for all associated queues to calculate pause time, even if it matches the wire speed. For example, if PFC runs on traffic class 3, the assigned ports require the egress-rate-queue3 setting.

/interface/ethernet/switch/qos/priority-flow-control/add name=pfctc3 traffic-class=3 rx=yes
/interface/ethernet/switch/qos/port/set sfp-sfpplus1,sfp-sfpplus2 pfc=pfctc3 egress-rate-queue3=10G

MACsec

Media Access Control Security (MACsec), defined by IEEE 802.1AE, protects Ethernet traffic with confidentiality, integrity and authenticity. After negotiation, MACsec protects Layer 2 payloads, including ARP, DHCP, LLDP and higher-layer protocols.

RouterOS can run MACsec in software without special hardware. Hardware offload is available only on selected ports and modules; the H flag indicates that offload is active.

WARNING

RouterOS requires manually configured Connectivity Association Keys (CAKs) and Connectivity Association Names (CKNs). It does not provision or rotate these values automatically through dot1x. The software, CPSS and Alaska MACsec paths do not provide replay protection.

Secure a direct link

This example creates a routed MACsec link between two routers. Each router uses ether5 as the physical parent and a MACsec interface for IP traffic. Use a different parent if it is already your management interface, and remove that parent from any bridge first. Only one MACsec interface can exist on a parent.

On Router1, create the MACsec interface without CAK or CKN to generate random values:

/interface/macsec/add name=macsec1 interface=ether5
/ip/address/add address=192.0.2.1/24 interface=macsec1
/interface/macsec/print show-sensitive

On Router2, create an interface with the same CAK and CKN. The following values belong to this example only; use the values generated on your own router:

/interface/macsec/add name=macsec1 interface=ether5 \
    cak=30E8EE41D1127D738016A22475AC6459 \
    ckn=F5032E94636D5B68F3D31A9BB17A1F689B9EC4AD0EC6EC2C6E4BEC652112FD59
/ip/address/add address=192.0.2.2/24 interface=macsec1

Manage keys and ciphers

The CAK is 16 bytes (32 hexadecimal characters), and the CKN is 32 bytes (64 hexadecimal characters). If you omit either value, RouterOS generates it. Both ends need the same CAK and CKN; a mismatch leaves the link negotiating and prevents forwarding.

The MACsec Key Agreement (MKA) protocol elects a key server for each point-to-point connection and maintains peer liveness. The key server generates and distributes the Secure Association Key (SAK). Packet-number exhaustion triggers SA replacement. aes-gcm-xpn-128 extends the packet-number space and reduces exhaustion-driven replacements; it does not eliminate them.

Profiles control the election and cipher suites:

  • server-priority defaults to 10. A lower numeric value wins. Equal priorities use the lowest MAC address as the key server.
  • ciphers must be specified for custom profiles. The built-in default profile uses aes-gcm-128. The other supported suite is aes-gcm-xpn-128; AES-GCM-256 is not supported.
  • The key server selects the first common suite in its own profile order. Peers with no common suite cannot forward traffic. Check both ends: one side can report open-encrypted while the other remains negotiating.

Create an XPN profile on both routers and assign it to the MACsec interface:

/interface/macsec/profile/add name=site-xpn \
    ciphers=aes-gcm-xpn-128 server-priority=20
/interface/macsec/set [find name=macsec1] profile=site-xpn

Use a single matching suite for a deterministic configuration. When you list multiple suites, check the selected value with /interface/macsec/monitor.

Plan MTU

MACsec adds 32 bytes. The read-only L2MTU is the parent interface's L2MTU minus those 32 bytes, and it cannot be changed directly. The default MACsec MTU is 1468, which fits a 1500-byte parent MTU.

To carry a 1500-byte inner IP packet, increase the physical MTU to 1532 and set the MACsec MTU to 1500 on both routers. Ensure that the physical L2MTU also has enough headroom:

/interface/ethernet/set [find default-name=ether5] mtu=1532
/interface/macsec/set [find name=macsec1] mtu=1500

Wait for open-encrypted after changing MTU, then test the required packet size:

/ping 192.0.2.2 size=1500 do-not-fragment

Insufficient L2MTU can silently drop traffic even when ping or MACsec negotiation succeeds. Test application-sized packets and every bridge in the path rather than relying on negotiation status alone.

Monitor and troubleshoot

Use these commands to inspect negotiation, roles and detailed counters:

/interface/macsec/print detail
/interface/macsec/monitor [find name=macsec1] once
/interface/macsec/print stats

open-encrypted indicates local encrypted state, not successful peer negotiation or end-to-end forwarding. Check both peers and then work through the path:

  1. Compare CAK and CKN. Different values prevent negotiation. Use print show-sensitive when reading them.
  2. Compare profiles. Both peers need a common cipher suite. Check cipher-suite and key-server on both monitors.
  3. Check the parent. A parent already in a bridge produces an invalid interface with Interface is already a slave. A second MACsec on the same parent is rejected with interface already used.
  4. Check MTU and L2MTU. Small packets can pass while larger application traffic is dropped. Increase physical headroom or reduce the MACsec MTU.
  5. Check forwarding. Test routed traffic, bridge traffic and non-IP discovery protocols separately. /ip/neighbor/print can help verify CDP, LLDP and MNDP through a MACsec bridge.

The detailed statistics include aggregate Secure Channel (SC) counters and per-Secure Association (SA) values. They cover encrypted/decrypted traffic, validation failures and other error conditions defined by IEEE 802.1AE. Reset all detailed counters when starting a new measurement:

/interface/macsec/reset-counters [find name=macsec1]

Hardware offload

Software MACsec consumes CPU but requires no special MACsec hardware. Offload is optional and depends on the Ethernet port, pluggable module, board revision and cipher suite. XPN support is not available on every MACsec-capable port or module.

The H flag indicates active hardware offload; its absence does not prevent software forwarding. Do not infer offload support from the device family alone or assume that offloaded forwarding is always faster.

For all interface, profile, monitor and counter-reset details, see the MACsec CLI reference.

MACVLAN

A MACVLAN interface adds a virtual interface with its own MAC address on top of an existing interface. It shares the parent's Layer 2 segment, and its frames are not tagged. Use it to make one port appear as more than one host: an ISP that assigns an address per MAC, two DHCP client sessions on one link, or several PPPoE client sessions, each with its own MAC. For several VLANs over one port, use VLAN; to join segments at Layer 2, use bridging.

A MACVLAN is configured like a physical interface: assign addresses and routes, or run a DHCP client or a PPPoE client on it. RouterOS generates the MAC address automatically when mac-address is not set.

How MACVLAN works

The MACVLAN sends and receives through its parent interface, so the remote end sees the MACVLAN's own MAC address. Several MACVLAN interfaces can use the same parent, each with a separate MAC address.

A MACVLAN receives broadcast traffic, traffic addressed to its own MAC address, and a limited number of multicast addresses. It does not receive unicast traffic addressed to another MAC address on the segment. If a VLAN interface is configured on the parent, that VLAN interface receives the VLAN's tagged traffic first, so the MACVLAN does not receive it.

The parent can be any interface with a MAC address, such as an Ethernet, VLAN or bond interface. It cannot be in use as an active bridge port: creating the MACVLAN then fails with failed to create device, and the system log names the busy parent:

macvlan1 parent device is busy (code -16), please make sure other devices are not using the
same parent (ether5)

The nesting order is VLAN first, then MACVLAN: create the VLAN interface on the physical parent, then create the MACVLAN on the VLAN interface when that segment needs another MAC address. A VLAN interface cannot be created on a MACVLAN; RouterOS does not offer MACVLAN interfaces as VLAN parents. A MACVLAN can be added to a bridge as a port, but it then works as a bridge port, and a DHCP client cannot run on it. For bridging and complex Layer 2 setups with VLANs, use a dedicated switch.

MACVLAN does not support FastPath, so its traffic is processed by the CPU.

Private and bridge mode

The mode property controls communication between MACVLAN interfaces on the same parent:

  • bridge - the default. MACVLAN interfaces on the same parent can communicate with each other.
  • private - they cannot. With either interface set to private, communication between them stops.

Communication between two MACVLAN interfaces requires bridge mode on both. With either interface set to private, communication stops. To isolate two MACVLAN interfaces that share a parent, set both to private (one is enough):

/interface/macvlan/set macvlan1 mode=private
/interface/macvlan/set macvlan2 mode=private

The commands assume two interfaces named macvlan1 and macvlan2 on the same parent.

The MTU defaults to 1500 and cannot be higher than the parent's MTU. To use a lower value, set mtu; if the parent's MTU is lower than 1500, set mtu when creating the interface, otherwise creation fails with could not set mtu.

Two DHCP clients on one port

This example uses ether5, which connects to an uplink that assigns one address per MAC address. ether5 is not part of a bridge; if it is a bridge port, remove it from the bridge first. The router needs two addresses, one for each MAC. Create a MACVLAN on the port and run a DHCP client on both interfaces:

/interface/macvlan/add interface=ether5 name=macvlan1
/ip/dhcp-client/add interface=ether5 name=dhcp-ether5 \
    add-default-route=no
/ip/dhcp-client/add interface=macvlan1 name=dhcp-macvlan1 \
    add-default-route=no

Both clients in the example ignore the default route. Remove add-default-route=no from the client that should provide the default route.

Troubleshooting

The MACVLAN cannot be created

  • The parent is a bridge port. A MACVLAN cannot use a bridge port that is forwarding traffic. The command fails with failed to create device, and the log says parent device is busy (code -16), please make sure other devices are not using the same parent (<interface>). Remove the port from the bridge, or use another interface as the parent.
  • The parent's MTU is lower than 1500. Creation fails with could not set mtu. Create the interface with a matching mtu, for example /interface/macvlan/add interface=ether5 name=macvlan1 mtu=1400.

The MACVLAN runs but receives no traffic

  • VLAN on the parent. A VLAN interface on the same parent handles that VLAN's tagged traffic; the MACVLAN does not receive it. If the MACVLAN must work inside that VLAN, create it on the VLAN interface instead.
  • Traffic for another MAC address. The MACVLAN receives broadcast, traffic to its own MAC address and limited multicast. Unicast traffic addressed to another MAC on the segment does not reach it.
  • The uplink allows one MAC address. Some ISPs accept only one MAC address per port and drop traffic from a second one. Check the provider's policy before adding a MACVLAN.

A DHCP client does not obtain a lease

A client that stays in searching receives no DHCP reply. Check that the client runs on the MACVLAN interface and that the provider accepts a second MAC address on the port. /interface/macvlan/print shows the MAC address of each MACVLAN.

A DHCP client or VLAN interface does not work

  • DHCP client on a bridge port. If the MACVLAN was added to a bridge, the client is invalid with the comment DHCP client can not run on slave or passthrough interface!. Remove the MACVLAN from the bridge, or run the client on the parent interface instead.
  • VLAN on a MACVLAN. Not supported. Create the VLAN interface on the parent instead.

Technical details

MACVLAN is implemented by the Linux MACVLAN driver. A parent interface can carry several MACVLAN interfaces; each has its own MAC address and receives only the traffic the driver passes to it. RouterOS exposes the private and bridge modes. In bridge mode the driver delivers frames between the MACVLAN interfaces on the same parent locally; in private mode it drops them.

Because the interfaces share the parent's broadcast domain, a MACVLAN is not a substitute for a VLAN: a VLAN interface adds an 802.1Q tag and separates broadcast domains, whereas a MACVLAN adds a MAC address to the same segment.

The menu and its arguments are described in the /interface/macvlan CLI reference.

VXLAN

Configure VXLAN interfaces and static VTEPs, bridge Layer 2 networks and VLANs over IPv4 or IPv6, check the forwarding database, plan MTU, and understand hardware-offload restrictions.

VXLAN

Virtual eXtensible Local Area Network (VXLAN) carries Layer 2 frames over a routed IP network. It uses UDP and a 24-bit VXLAN Network Identifier (VNI) to distinguish overlay networks. The larger identifier space addresses the 4096-VLAN limit of IEEE 802.1Q. RFC 7348 defines the protocol.

A VXLAN Tunnel Endpoint (VTEP) encapsulates and decapsulates frames. A VXLAN interface can have multiple remote VTEPs, so it forms a one-to-many overlay rather than a point-to-point link. Configure static remote VTEPs in /interface/vxlan/vteps, or use EVPN to discover VTEPs and distribute MAC reachability through BGP.

RouterOS supports IPv4 and IPv6 underlays. One VXLAN interface uses one underlay address family, not a dual-stack VTEP list. The underlay routing table selects the egress interface and, when local-address is unset, its source address. Set vtep-vrf to use an underlay in another VRF; the overlay bridge can remain in main.

Connect two Layer 2 networks with static VTEPs

This example extends an Ethernet segment between two routers. Each router has a routed underlay on ether2 and a separate bridge1 for the overlay. The configuration preserves the underlay's Layer 3 boundary while allowing hosts connected to the overlay bridges to communicate at Layer 2. VXLAN adds encapsulation overhead and does not provide encryption.

Router1 uses 192.0.2.2 and 10.255.110.2; Router2 uses 192.0.2.3 and 10.255.110.3. The underlay addresses are on a connected subnet, so no additional static route is required. In a routed underlay, add routes to the remote VTEP addresses before configuring the tunnel.

Router1:

/interface/bridge/add name=bridge1 protocol-mode=none
/ip/address/add address=192.0.2.2/24 interface=ether2
/ip/address/add address=10.255.110.2/24 interface=bridge1
/interface/vxlan/add name=vxlan110 vni=110 \
    local-address=192.0.2.2 bridge=bridge1
/interface/vxlan/vteps/add interface=vxlan110 \
    remote-ip=192.0.2.3

Router2:

/interface/bridge/add name=bridge1 protocol-mode=none
/ip/address/add address=192.0.2.3/24 interface=ether2
/ip/address/add address=10.255.110.3/24 interface=bridge1
/interface/vxlan/add name=vxlan110 vni=110 \
    local-address=192.0.2.3 bridge=bridge1
/interface/vxlan/vteps/add interface=vxlan110 \
    remote-ip=192.0.2.2

The bridge property adds the VXLAN interface to the bridge as a dynamic port. Add the Ethernet ports that face your Layer 2 hosts to the same bridge. Do not bridge those hosts only to the underlay Ethernet port: traffic between two physical underlay ports does not enter VXLAN.

Both endpoints must use the same VNI and UDP port. The default destination and listening port is 4789. Permit UDP traffic between the VTEP addresses in the underlay firewall.

Carry VLANs over VXLAN

A VLAN ID and a VNI are independent identifiers. Bridge VLAN filtering determines which VLANs enter the VXLAN interface. An untagged service commonly uses a one-to-one VLAN-to-VNI mapping. A tagged VXLAN bridge port can carry multiple VLANs over one VNI.

This example continues the preceding topology with untagged VLAN 10 and tagged VLAN 20 in one VNI. Router1 keeps underlay address 192.0.2.2/24 and Router2 keeps 192.0.2.3/24 on ether2. Add the following objects without reassigning the underlay addresses.

Router1:

/interface/bridge/add name=bridge-vlan protocol-mode=none \
    pvid=10 vlan-filtering=yes
/ip/address/add address=10.255.70.1/24 interface=bridge-vlan
/interface/vxlan/add name=vxlan10070 vni=10070 \
    local-address=192.0.2.2 bridge=bridge-vlan bridge-pvid=10
/interface/vxlan/vteps/add interface=vxlan10070 \
    remote-ip=192.0.2.3
/interface/vlan/add name=vlan20 interface=bridge-vlan vlan-id=20
/ip/address/add address=10.255.72.1/24 interface=vlan20
/interface/bridge/vlan/add bridge=bridge-vlan vlan-ids=20 \
    tagged=bridge-vlan,vxlan10070

Router2:

/interface/bridge/add name=bridge-vlan protocol-mode=none \
    pvid=10 vlan-filtering=yes
/ip/address/add address=10.255.70.3/24 interface=bridge-vlan
/interface/vxlan/add name=vxlan10070 vni=10070 \
    local-address=192.0.2.3 bridge=bridge-vlan bridge-pvid=10
/interface/vxlan/vteps/add interface=vxlan10070 \
    remote-ip=192.0.2.2
/interface/vlan/add name=vlan20 interface=bridge-vlan vlan-id=20
/ip/address/add address=10.255.72.3/24 interface=vlan20
/interface/bridge/vlan/add bridge=bridge-vlan vlan-ids=20 \
    tagged=bridge-vlan,vxlan10070

The PVID creates the untagged VLAN 10 membership for the bridge and VXLAN port. The explicit VLAN 20 entry makes the bridge interface and VXLAN port tagged members, allowing the router's local vlan20 interface and the remote VTEP to exchange tagged frames. See bridge VLAN configuration for physical access and trunk port configuration.

Check both overlay subnets:

/ping 10.255.70.3
/ping 10.255.72.3

Forward unicast and BUM traffic

The VXLAN forwarding database (FDB) associates inner source MAC addresses with remote VTEP addresses. With learning=yes, received packets create these mappings dynamically. Later unicast frames can be sent only to the VTEP that owns the destination MAC. Set learning=no to suppress this learning. Static VTEP entries remain available for flooding and are not inbound access-control rules.

Broadcast, unknown-unicast and multicast (BUM) traffic needs replication:

  • Unicast head-end replication sends one copy to every static remote VTEP. This is the default when no multicast group is configured.
  • Multicast underlay sends BUM traffic to the configured multicast group. Set both group and interface; either property without the other is rejected.

For example, this interface uses multicast group 239.255.10.30 on the underlay interface:

/interface/vxlan/add name=vxlan10030 vni=10030 \
    local-address=192.0.2.2 group=239.255.10.30 \
    interface=ether2 bridge=bridge1

Configure the same VNI, group and UDP port on the other VTEPs, with their own local addresses. Static VTEP entries are not required for multicast flooding. The router joins the group with IGMP or MLD. A routed multicast underlay also requires multicast routing, such as PIM, and sufficient ttl. The automatic TTL is 1 for multicast and 64 for unicast underlay packets.

A VXLAN interface does not maintain a separate multicast database for each remote VTEP. When an IGMP-snooping bridge forwards a group to a VXLAN port with multiple static VTEPs, VXLAN can replicate it to all of them. Use separate VXLAN interfaces when you need independent flooding domains.

The configured UDP port is the listening and destination port. RouterOS varies the outer source port from inner-packet fields to provide entropy for load balancing. Each VTEP must be able to reach the remote listening port. A NAT between VTEPs must maintain return mappings for the entropy-derived source ports and forward incoming traffic to the VTEP behind NAT; do not assume that the source port is also 4789.

Check the overlay and troubleshoot failures

Inspect the interface, static VTEPs and learned mappings after sending traffic:

/interface/vxlan/print detail
/interface/vxlan/vteps/print
/interface/vxlan/fdb/print
/interface/bridge/host/print

Work through the path in order:

  1. Check the underlay route. Ping the remote VTEP address and confirm that the route uses the intended interface and routing table. Permit the configured UDP port and its return traffic through the underlay firewall.
  2. Compare the VNI, UDP port and address family. Both endpoints need the same VNI and port. Remote VTEPs opposite to the interface's vteps-ip-version are ignored. A VNI can be assigned to only one VXLAN interface on a router.
  3. Check the overlay bridge. The VXLAN interface, not the routed underlay port, belongs in the overlay bridge. For VLAN-filtering bridges, also check PVID and tagged or untagged membership.
  4. Check learning. An empty FDB is expected with learning=no or before traffic arrives. Static VTEP entries can still flood traffic when no FDB mapping exists.
  5. Check packet sizes. Test progressively smaller inner packets with DF set. Reduce the VXLAN MTU or increase the underlay MTU if large frames disappear.
  6. Capture the underlay. Compare VNI, UDP ports and inner Ethernet frames at both endpoints. A running interface and configured VTEP do not prove that packets arrive.

Start a UDP port 4789 capture on the underlay interface:

/tool/sniffer/set filter-interface=ether2 filter-port=4789 \
    file-name=vxlan.pcap
/tool/sniffer/start

Generate overlay traffic, then stop the capture with /tool/sniffer/stop.

Plan MTU and fragmentation

The outer IP packet is larger than the inner IP packet:

Underlay and inner tagging Added bytes Largest inner packet on a 1500-byte underlay
IPv4, untagged 50 bytes 1450 bytes
IPv4, one 802.1Q tag 54 bytes 1446 bytes
IPv6, untagged 70 bytes 1430 bytes
IPv6, one 802.1Q tag 74 bytes 1426 bytes

Carrying a 1500-byte untagged inner IP packet without fragmentation therefore requires an underlay IP MTU of at least 1550 bytes for IPv4 or 1570 bytes for IPv6. Add another 4 bytes for each 802.1Q tag. Increase the MTU along the entire underlay path, or reduce the VXLAN interface mtu to fit the existing path.

Without an associated multicast interface, the read-only l2mtu is 65535. When the associated interface exposes its own L2MTU, VXLAN subtracts 50 bytes for an IPv4 underlay or 70 bytes for IPv6. Reduce the VXLAN mtu if the default 1500 bytes does not fit the associated interface. The L2MTU does not prove that every hop in the underlay supports the required MTU.

The dont-fragment property controls outer-packet fragmentation:

  • disabled clears DF on an IPv4 outer packet and permits fragmentation. It also permits IPv6 outer fragmentation.
  • enabled sets DF on an IPv4 outer packet and prevents fragmentation. Oversized payloads are dropped instead of being fragmented. IPv6 outer packets are not fragmented either.
  • inherit copies the inner IPv4 DF decision to the IPv4 outer packet. Non-IP inner traffic has no outer DF flag. Inner IPv6 traffic sets outer IPv4 DF. On an IPv6 underlay, inherit permits fragmentation like disabled.
  • auto uses enabled on devices with VXLAN hardware offload and inherit otherwise.

Prefer an MTU that avoids outer fragmentation. Besides adding processing overhead, fragmentation requires every fragment to reach the remote VTEP before it can decapsulate the inner frame.

Hardware offloading

Supported switch chips can offload VXLAN encapsulation and decapsulation when hw=yes. The H flag on VXLAN interfaces and VTEPs indicates hardware-offloaded entries. Consult the L3HW device support matrix before designing for offload; a hardware-offloaded bridge port alone does not prove that the complete VXLAN path is offloaded.

The supported underlay is more restricted than software VXLAN:

  • Use a standalone routed Ethernet underlay. ECMP and bond, bridge or VLAN underlay interfaces are not supported.
  • Multicast underlay and IPv6 VTEP offload are not supported.
  • VXLAN-VRF offload is supported on CPSS switch chips. On other switch chips, keep the underlay in main unless the device support matrix explicitly lists VXLAN-VRF support. The software vtep-vrf property does not imply hardware support.

For the overlay, hardware supports static one-to-one untagged VLAN-to-VNI mappings and tagged VLAN-aware mappings within a VLAN-filtering bridge. The following restrictions apply:

  • Routing between different VNIs is not supported.
  • VTEPs are isolated, with no configurable horizon between them.
  • MDB entries on VXLAN ports are not offloaded for IGMP snooping. Enabling snooping can restrict multicast forwarding between Ethernet and VXLAN.
  • Bridged VXLAN interfaces are not supported by MLAG.

Configure static VLAN-to-VNI mappings

This example uses a loopback VTEP address and a routed underlay. Router1 has loopback 192.0.2.1/32, underlay 198.51.100.1/30, and access ports in VLANs 10 and 20. Router2 uses 192.0.2.2/32 and 198.51.100.2/30. Both endpoints have matching VNIs and access-port VLANs. The underlay MTU accommodates large encapsulated frames and must be supported along the whole path.

/interface/bridge/add name=bridge1 vlan-filtering=yes
/interface/ethernet/set [find default-name=sfp-sfpplus1] \
    l2mtu=9500 mtu=9500
/interface/vxlan/add name=vxlan-10010 vni=10010 \
    local-address=192.0.2.1 bridge=bridge1 bridge-pvid=10
/interface/vxlan/add name=vxlan-10020 vni=10020 \
    local-address=192.0.2.1 bridge=bridge1 bridge-pvid=20
/interface/bridge/port/add bridge=bridge1 \
    interface=sfp-sfpplus3 pvid=10
/interface/bridge/port/add bridge=bridge1 \
    interface=sfp-sfpplus4 pvid=20
/interface/vxlan/vteps/add interface=vxlan-10010 \
    remote-ip=192.0.2.2
/interface/vxlan/vteps/add interface=vxlan-10020 \
    remote-ip=192.0.2.2
/ip/address/add address=192.0.2.1/32 interface=lo
/ip/address/add address=198.51.100.1/30 \
    interface=sfp-sfpplus1
/ip/route/add dst-address=192.0.2.2/32 gateway=198.51.100.2
/interface/ethernet/switch/set 0 l3-hw-offloading=yes

On Router2, mirror the configuration with local addresses 192.0.2.2 and 198.51.100.2/30, remote VTEP 192.0.2.2 replaced by 192.0.2.1, and the route to 192.0.2.1/32 through 198.51.100.1.

Static routes are shown for brevity. OSPF or BGP can distribute the loopback VTEP addresses when the underlay meets the hardware restrictions.
