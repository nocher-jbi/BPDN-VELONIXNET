HotSpot - Captive portal

A HotSpot asks the users of a network to log in before they get network access. A device that connects to the HotSpot network gets an IP address and can resolve DNS names, but every web page that it opens over HTTP is replaced by the login page of the router, and all other traffic is rejected. After the user logs in, the device has network access until the user logs out or a limit is reached.

The HotSpot can:

  • authenticate users from a list on the router or on a RADIUS server;
  • limit each user by time, by traffic amount, and by data rate;
  • log in known devices without a login page, by their MAC address;
  • give time-limited trial access without an account;
  • let selected sites, services, and devices through without login (walled garden and IP bindings);
  • show your own login page, see HotSpot customisation.

Before you start

  • HotSpot works with IPv4 only.
  • Device-mode can block HotSpot. Check that hotspot is yes in /system/device-mode/print.
  • One HotSpot server runs on one interface. To serve several ports, put them in a bridge and run the HotSpot on the bridge interface, not on a bridge port. Do not put the interface that leads to the Internet into this bridge.
  • A user rate limit creates a simple queue. Simple queues do not limit FastTracked connections, see Simple queue.
  • If you set up the HotSpot on the interface through which you manage the router, you lose access until you log in on the login page. Manage the router through another interface, or add an IP binding for your computer first, as described in the IP bindings section of this page.

Set up a HotSpot

The /ip/hotspot/setup command asks a few questions and creates the HotSpot server together with everything that it needs.

Question What to answer
hotspot interface The interface with the clients. On a router with the default configuration this is bridge.
local address of network The address of the router on this interface. The address that the interface already has is offered.
masquerade network yes adds a source NAT rule for the HotSpot network.
address pool of network The addresses for the clients. If the interface has a DHCP server, its pool is offered.
select certificate Answer none, unless you use the https login method.
ip address of smtp server Keep 0.0.0.0.
dns servers The DNS servers that the router itself uses. The answer is written to /ip/dns, so do not enter the address of the router here.
dns name A name for the login page, for example hotspot.lan. The router resolves this name to its own address for the clients. Leave it empty to use the IP address.
name of local hotspot user, password for the user The first user account. These two questions are asked only when the router has no HotSpot user yet.

On a router with the default configuration, with bridge as the HotSpot interface and hotspot.lan as the DNS name, the setup creates this configuration:

/ip/hotspot/profile
add dns-name=hotspot.lan hotspot-address=192.168.88.1 name=hsprof1
/ip/hotspot
add address-pool=default-dhcp disabled=no interface=bridge \
    name=hotspot1 profile=hsprof1
/ip/hotspot/user
add name=user1
/ip/firewall/nat
add action=masquerade chain=srcnat \
    comment="masquerade hotspot network" src-address=192.168.88.0/24

The address-pool of the server does more than name the client addresses. With a pool, the HotSpot also serves a device whose own IP settings do not fit the network, for example a laptop with a static address from another network. The router answers for the gateway that the device expects and translates the address of the device to a free address of the pool; /ip/hotspot/host/print shows that address as to-address. With address-pool=none, the addresses are not translated and such a device gets no answer.

If the interface has no DHCP server, the setup also creates an IP pool and a DHCP server for it. The existing firewall rules of the router are not changed; the HotSpot adds its own dynamic rules, which are listed at the end of this page.

Check that the server runs:

/ip/hotspot/print

Columns: NAME, INTERFACE, ADDRESS-POOL, PROFILE, IDLE-TIMEOUT
# NAME      INTERFACE  ADDRESS-POOL  PROFILE  IDLE-TIMEOUT
0 hotspot1  bridge     default-dhcp  hsprof1  5m

Connect a device to the HotSpot network and open an HTTP page, for example http://example.com. The login page of the router opens instead. The device is now in the host list:

1 H 52:54:09:81:02:01  192.168.88.253  192.168.88.253  hotspot1  5m

Log in with the user that you created. The host gets the A (authorized) flag, and the session is in the active list:

To log a user out, remove the session from /ip/hotspot/active. The user can also open the status page, http://hotspot.lan/status, and log out there.

Add users and limits

Users are in /ip/hotspot/user. A user profile in /ip/hotspot/user/profile holds the settings that several users share.

Add a user:

/ip/hotspot/user/add name=anna password=ChangeMe-1

Limit the data rate and the session time

Create a profile for guests and a user with this profile:

/ip/hotspot/user/profile/add name=guest rate-limit=512k/2M \
    session-timeout=1h shared-users=1 address-list=hotspot-guests
/ip/hotspot/user/add name=guest1 password=ChangeMe-2 profile=guest
  • rate-limit is the upload/download limit of each user of the profile. The first value limits what the user sends, the second what the user receives.
  • session-timeout logs the user out after this time.
  • shared-users is the number of devices that can be logged in with the same user name at the same time. A login from one more device fails with the message "no more sessions are allowed for user".
  • address-list adds the address of each logged-in user to a firewall address list. Use the list in your own firewall, mangle, or queue rules.

While guest1 is logged in, the router has a dynamic simple queue and an address list entry for the user. Both are removed when the user logs out:

/queue/simple/print where dynamic
/ip/firewall/address-list/print where list=hotspot-guests

Flags: D - DYNAMIC

    packet-marks="" priority=8/8 queue=default-small/default-small
    limit-at=512k/2M max-limit=512k/2M burst-limit=0/0 burst-threshold=0/0

Limit the total time and traffic of a user

session-timeout in the profile limits one session, and the user can log in again. The limits of the user itself count over all sessions:

/ip/hotspot/user/add name=daypass password=ChangeMe-3 limit-uptime=1d \
    limit-bytes-total=2G

When a limit is reached, the user is logged out. A new login fails with the message "user daypass has reached uptime limit" or "user daypass has reached traffic limit". The counters of the user are in /ip/hotspot/user/print detail. To let the user in again, reset them:

/ip/hotspot/user/reset-counters daypass

Run a script at login and logout

The on-login and on-logout scripts of a user profile run for every user of the profile. This example writes a line to the log:

/ip/hotspot/user/profile/set guest \
    on-login=":log info \"HotSpot login: \$user \$address\"" \
    on-logout=":log info \"HotSpot logout: \$user \$cause\""

/log/print where message~"^HotSpot log"

 2026-11-13 20:45:47 script,info HotSpot login: guest1 192.168.88.253
 2026-11-13 20:45:49 script,info HotSpot logout: guest1 admin reset
 2026-11-13 20:51:40 script,info HotSpot login: guest1 192.168.88.254
 2026-11-13 20:51:45 script,info HotSpot logout: guest1 user request
 2026-11-13 20:51:50 script,info HotSpot login: guest1 192.168.88.254
 2026-11-13 20:51:54 script,info HotSpot logout: guest1 admin reset

The scripts can use these variables:

Variable Value
$user, $username The user name.
$address The IP address of the device.
$"mac-address" The MAC address of the device.
$interface The HotSpot interface. When the HotSpot runs on a bridge, this is the bridge, unless use-ip-firewall is enabled in the bridge settings; then it is the bridge port of the device.
$cause Only in on-logout: why the session ended, for example user request, session timeout, or traffic limit reached.
$"uptime-secs" Only in on-logout: the session time in seconds.
$"bytes-in", $"bytes-out", $"bytes-total" Only in on-logout: the bytes that the user sent and received.
$"packets-in", $"packets-out", $"packets-total" Only in on-logout: the packets that the user sent and received.

Select the login methods

The login-by setting of the server profile in /ip/hotspot/profile selects how users can log in. Several methods can be enabled at the same time. The default is cookie,http-chap.

Method How the user logs in
http-chap With a user name and password on the login page. The page does not send the password itself: JavaScript on the page hashes it together with a challenge from the router.
http-pap With a user name and password on the login page. The password is sent as plain text. A login link or an external page that sends the password directly needs this method.
https As http-pap, but the login page is opened over HTTPS. Set ssl-certificate in the server profile; the certificate has to be valid for the dns-name of the profile. The server then has the S flag in /ip/hotspot/print.
cookie Automatically, with a browser cookie from an earlier login with a user name and password. The cookie is valid for http-cookie-lifetime.
mac-cookie Automatically, by the MAC address of a device that has logged in before, for example a phone. It is a separate method from cookie and does not use the browser.
mac Automatically, when a user with the MAC address of the device as its name exists.
trial With a link on the login page, without an account, for a limited time.

Without http-pap, a login that sends the plain password fails with the message "web browser did not send challenge response (try again, enable JavaScript)".

Log in over HTTPS

With the https method, the login page opens over HTTPS, so the user name and the password are encrypted between the device and the router. The certificate of the login page has to meet two conditions:

  • It is valid for the DNS name of the login page, which is the dns-name of the server profile.
  • The devices of the users trust the authority that issued it. A certificate from a public certificate authority meets this condition without any setup on the devices.

This example uses the IP Cloud name of the router as the name of the login page, and a Let's Encrypt certificate for that name. The IP Cloud DDNS service has to be enabled; see Let's Encrypt certificate. To use a name of your own domain instead, see Certificate for your own domain name.

Request the certificate:

/certificate
add-acme name=hotspot-cert domain-names=[/ip/cloud/get dns-name]

When the certificate is issued, it has the flags K and a in /certificate/print. Then set the name, the certificate and the login method in the server profile:

/ip/hotspot/profile
set hsprof1 dns-name=[/ip/cloud/get dns-name] \
    ssl-certificate=hotspot-cert login-by=cookie,http-chap,https

The server now has the S flag:

[admin@MikroTik] > /ip/hotspot/print
Flags: S - HTTPS
Columns: NAME, INTERFACE, ADDRESS-POOL, PROFILE, IDLE-TIMEOUT
#   NAME      INTERFACE  ADDRESS-POOL  PROFILE  IDLE-TIMEOUT
0 S hotspot1  bridge     default-dhcp  hsprof1  5m

To check the result, connect a device to the HotSpot network and open an HTTP site. The device is redirected to https://<name>/login, where <name> is the IP Cloud name, and the login page opens without a certificate warning. Users do not type the name: they get to the login page through the redirect.

Remember devices with a MAC cookie

With mac-cookie, the user logs in once. After that, the router logs the device in by itself each time it comes back, until the cookie expires. This suits phones, which leave and join the network often.

/ip/hotspot/profile/set hsprof1 login-by=cookie,http-chap,mac-cookie

The user profile must have add-mac-cookie=yes, which is the default, and mac-cookie-timeout sets how long the cookie is valid. The cookies are in /ip/hotspot/cookie; a MAC cookie has the M flag:

/ip/hotspot/cookie/print

Flags: M - MAC-COOKIE
Columns: USER, MAC-ADDRESS, EXPIRES-IN
#   USER  MAC-ADDRESS        EXPIRES-IN
0 M anna  52:54:09:80:02:01  2d23h59m58s
1   anna  52:54:09:80:02:01  2d23h59m58s

The cookie is removed when the user logs out on the status page. To make a device log in again, remove its cookie from this list.

Log in devices by MAC address

With mac, a device needs no login page at all. Add a user whose name is the MAC address of the device:

/ip/hotspot/profile/set hsprof1 login-by=cookie,http-chap,mac
/ip/hotspot/user/add name=00:00:5E:00:53:10 comment="reception TV"

A MAC address is easy to copy, so use this method only for devices that cannot show a login page.

Give trial access

With trial, the login page shows a "Free trial available" link. A user who follows it gets access for trial-uptime-limit and can use the trial again after trial-uptime-reset:

/ip/hotspot/profile/set hsprof1 login-by=cookie,http-chap,trial \
    trial-uptime-limit=30m trial-uptime-reset=1d

The router creates a dynamic user named T- and the MAC address of the device for each trial, with the profile set in trial-user-profile. When the time is used up, a new trial login fails with the message "has reached uptime limit" until the reset time passes.

Let traffic through without login

Sites: walled garden

The walled garden lists the web sites that a device can open before login, for example your own site or a payment page. Rules in /ip/hotspot/walled-garden match HTTP and HTTPS requests by the host name of the site:

/ip/hotspot/walled-garden/add dst-host=example.com
/ip/hotspot/walled-garden/add dst-host=*.example.com

dst-host and path must match the whole value. Use * for any number of characters and ? for one character. A value that starts with : is a regular expression. It matches any part of the value, unless you anchor it with ^ at the start and $ at the end:

/ip/hotspot/walled-garden
add dst-host=":^example\\.com\$" action=allow

An HTTPS request is matched by its host name only. A rule that has path or method matches HTTP requests and no HTTPS requests.

Rules in /ip/hotspot/walled-garden/ip match packets by address, protocol, and port, so they also work for services other than the web:

/ip/hotspot/walled-garden/ip/add action=accept \
    dst-host=pay.example.com
/ip/hotspot/walled-garden/ip/add action=accept protocol=tcp \
    dst-port=443 dst-address=192.0.2.10

With dst-host, the router adds a dynamic rule with the address that the name resolves to.

The hits counter of a walled garden rule shows that it is used:

/ip/hotspot/walled-garden/print

Flags: X - DISABLED, D - DYNAMIC
Columns: DST-HOST, DST-PORT, ACTION, HITS
#    DST-HOST       DST-PORT  ACTION  HITS
0 D                      443  allow      0
;;; place hotspot rules here
1 X                           allow      0
2    example.com              allow      2
3    *.example.com            allow      1

Devices: IP bindings

An IP binding in /ip/hotspot/ip-binding sets how the HotSpot treats one device, selected by its MAC address or IP address:

/ip/hotspot/ip-binding/add mac-address=00:00:5E:00:53:20 type=bypassed \
    comment="office printer"
/ip/hotspot/ip-binding/add mac-address=00:00:5E:00:53:21 type=blocked
  • bypassed - the device has network access without login. It is in the host list with the P flag and is not in the active list.
  • blocked - the device has no access at all, also not to the login page.
  • regular - the device logs in as usual; with to-address, the HotSpot translates its address to this address.

To create a binding for a device that is already connected, use /ip/hotspot/host/make-binding on its entry in the host list.

Authenticate users with RADIUS

To keep the users on a RADIUS server, add the server for the hotspot service and enable RADIUS in the server profile:

/radius/add service=hotspot address=192.0.2.5 secret=ChangeMe-4
/ip/hotspot/profile/set hsprof1 use-radius=yes

Users that exist in /ip/hotspot/user still log in from the local list. A session that RADIUS authenticated has the R flag in /ip/hotspot/active. The reply of the server can set the limits of the session, for example Session-Timeout for the session time and Mikrotik-Rate-Limit for the rate limit. With radius-accounting=yes, which is the default, the router also sends accounting records for each session.

The attributes are listed on the RADIUS page. User Manager is a RADIUS server that runs on RouterOS.

How HotSpot behaves

Hosts and sessions

  • Every device that sends traffic to the HotSpot interface gets an entry in /ip/hotspot/host. found-by shows the packet that created the entry.
  • A logged-in user has an entry in /ip/hotspot/active. The session ends when the user logs out, when a limit or session-timeout is reached, when the device does not answer for the keepalive-timeout of the user profile, or when you remove the entry.
  • /ip/hotspot/active/login logs a connected device in from the console, without the login page.

What a device can do before login

  • Its DNS requests are answered by the router.
  • HTTP requests to a site in the walled garden pass. All other HTTP requests show the login page.
  • Everything else is rejected, including ping to the router: TCP with a reset, other protocols with an ICMP "prohibited" message.

Routing marks

The login page is served by the router itself. A mangle rule that puts a routing mark on all traffic from the HotSpot network, for example for load balancing between two uplinks, also marks the requests to the login page, and the page no longer opens. Exclude the traffic to the router from such a rule with dst-address-type=!local.

Firewall rules that HotSpot adds

A running HotSpot server adds dynamic rules to the NAT and filter tables. They are placed before your own rules.

In /ip/firewall/nat, the dstnat chain sends the packets of HotSpot clients to the hotspot chain:

     hotspot=local-dst dst-port=443

The rules redirect to four ports of the router, which /ip/service/print where dynamic lists:

Port Service What it does
64872 resolver Answers the DNS requests of the HotSpot clients, also those that a client sends to another DNS server.
64873 hotspot Serves the login page and the other HotSpot pages over HTTP.
64874 wproxy Receives the HTTP requests of clients that are not logged in. It lets the requests to walled garden sites through and answers the others with a redirect to the login page.
64875 wproxy Receives the HTTPS requests of clients that are not logged in and lets the requests to walled garden sites through.
  • hotspot redirects DNS requests and the requests to the login page to the HotSpot service, and sends the other TCP packets to hs-unauth (not logged in) or hs-auth (logged in).
  • hs-unauth redirects HTTP, the proxy ports 3128 and 8080, and HTTPS to the HotSpot service, which checks the walled garden and shows the login page. The rules for ports 3128 and 8080 catch the requests of a browser that is set to use a proxy server.
  • hs-auth redirects the packets of logged-in users that have the http HotSpot mark to the proxy on port 64874.
  • hs-smtp is empty until smtp-server is set in the server profile. Then it has a rule that sends the SMTP connections (TCP port 25) of the clients to that server.
  • A walled garden IP rule for TCP appears in hs-unauth as a return rule, so the matching packets are not redirected.
  • pre-hotspot is for your own rules: add rules to this chain to handle packets of HotSpot clients before the HotSpot rules.

In /ip/firewall/filter, the packets of clients that are not logged in go to their own chains:

/ip/firewall/filter/print dynamic where chain~"hs-" or hotspot

Flags: D - DYNAMIC
 0 D chain=forward action=jump jump-target=hs-unauth hotspot=from-client,!auth

 1 D chain=forward action=jump jump-target=hs-unauth-to hotspot=to-client,!auth

 2 D chain=input action=jump jump-target=hs-input hotspot=from-client

 3 D chain=input action=drop protocol=tcp hotspot=!from-client
     dst-port=64872-64875

 4 D chain=hs-input action=jump jump-target=pre-hs-input

 5 D chain=hs-input action=accept protocol=udp dst-port=64872

 6 D chain=hs-input action=accept protocol=tcp dst-port=64872-64875

 7 D chain=hs-input action=jump jump-target=hs-unauth hotspot=!auth

 8 D chain=hs-unauth action=reject reject-with=tcp-reset protocol=tcp

 9 D chain=hs-unauth action=reject reject-with=icmp-net-prohibited

10 D chain=hs-unauth-to action=reject reject-with=icmp-host-prohibited
  • hs-unauth handles the packets from clients that are not logged in, and hs-unauth-to the packets to them. Both reject everything that a walled garden IP rule does not allow.
  • hs-input accepts the connections of clients to the HotSpot service on the router.

  • pre-hs-input is for your own rules for packets from HotSpot clients to the router.

  • Rule 3 drops connections to the HotSpot service ports that do not come from a HotSpot client.

Each rule in /ip/hotspot/walled-garden/ip appears in the filter as two dynamic return rules, one in hs-unauth for the packets to the destination and one in hs-unauth-to for the replies. In the NAT table only the rules for TCP appear.

Hotspot customisation

The pages that the HotSpot shows to its users are HTML files on the router. You can edit them, or give each HotSpot server profile its own set of pages. The pages contain variables, for example $(username), which the router replaces with their values when it serves a page.

Where the pages are

A router with a HotSpot server has the hotspot directory in its files, with the default pages. On a router that has a flash folder in its file list, the directory is flash/hotspot. The html-directory setting of the server profile in /ip/hotspot/profile points to this directory.

To make your own pages:

  1. Download the hotspot directory from the files of the router to your computer, for example with WinBox, SFTP or FTP.
  2. Edit the pages. Use a text editor: an HTML editor can remove the variables and the other parts that the HotSpot needs.
  3. Upload the directory to the router under another name, for example hs-custom. If the file list of the router has a flash folder, upload the directory into flash: files outside it are lost on reboot. See Files.
  4. Set the directory in the server profile:

ros /ip/hotspot/profile/set hsprof1 html-directory-override=hs-custom

For a directory in the flash folder, set the path with the folder, html-directory-override=flash/hs-custom.

Open the login page, http://hotspot.lan/login, to check the result. If the directory in html-directory-override does not exist, the HotSpot uses the pages from html-directory.

To get the default pages back in the html-directory of a server, for example after an edit that broke the login page, run:

/ip/hotspot/reset-html hotspot1

Pages

The pages that the user sees:

  • redirect.html - redirects the user to another URL, for example to the login page.
  • login.html - the login page, which asks for a user name and password. The page accepts these parameters:
  • username - the user name.
  • password - the plain-text password (http-pap and https login), or the MD5 hash of the chap-id variable, the password, and the CHAP challenge (http-chap login). For trial users this value is used as an e-mail address.
  • dst - the URL that the user requested before the redirect. It is opened after a successful login.
  • popup - whether to open the status page in a pop-up window after a successful login.
  • radius\ - send the attribute with this ID to the RADIUS server as a text string. Only with RADIUS authentication.
  • radius\u - the same, as an unsigned integer.
  • radius\-\ - send the attribute with this ID and vendor ID to the RADIUS server as a text string.
  • radius\-\u - the same, as an unsigned integer.
  • md5.js - JavaScript for the MD5 hash of the password, used by the http-chap login method.
  • alogin.html - shown after a successful login. It opens the status page in a pop-up window and redirects the browser to the page that the user requested.
  • status.html - the status page with the statistics of the session and the logout button. It also opens advertisements.
  • logout.html - shown after logout, with the statistics of the finished session. The page accepts this parameter:
  • erase-cookie - on or true removes the cookie of the user on logout, so the browser is not logged in automatically the next time.
  • error.html - shown on fatal errors.
  • errors.txt - the texts of the error messages.

Pages for more control. If such a page does not exist, the HotSpot uses the page named in its description:

  • rlogin.html - redirects a user who is not logged in from the requested URL to the login page. The default page answers with the HTTP status 302.
  • rstatus.html - redirects a logged-in user who requests the HotSpot address to the status page. Not in the default set; redirect.html is used.
  • radvert.html - redirects the user to the advertisement that is due.
  • flogin.html - shown instead of login.html after a failed login. Not in the default set; login.html is used.
  • fstatus.html - shown when the status page is requested by a user who is not logged in. Not in the default set; redirect.html is used.
  • flogout.html - shown when the logout page is requested by a user who is not logged in. Not in the default set; redirect.html is used.

The xml sub-directory holds the pages for WISPr clients, which log in without a browser.

Which page is shown

The HotSpot handles five kinds of requests:

  1. A request for a remote host - The user is logged in and an advertisement is due: radvert.html, which redirects to the advertisement. - The user is logged in and no advertisement is due: the requested page. - The user is not logged in and the host is allowed by the walled garden: the requested page. - The user is not logged in and the host is not allowed: rlogin.html, or redirect.html to the login page.
  2. A request for / on the HotSpot address - The user is logged in: rstatus.html, or redirect.html to the status page. - The user is not logged in: rlogin.html, or redirect.html to the login page.
  3. A request for /login - The login succeeded, or the user is already logged in: alogin.html, or redirect.html to the requested page or the status page. - No user name was sent: login.html. - The login failed: flogin.html, or login.html, with the error message. - Fatal error: error.html.
  4. A request for /status - The user is logged in: status.html. - The user is not logged in: fstatus.html, or redirect.html to the login page.
  5. A request for /logout - The user is logged in: logout.html. - The user is not logged in: flogout.html, or redirect.html to the login page.

Variables

To insert a value into a page, write $(name), where name is the name of a variable. The router replaces the variables in the pages requested as /, /login, /status, and /logout, and in the other text and HTML files (.txt, .htm, .html) of the directory. For example, a link to the login page:

login

For a client with the address 192.168.88.254 that requested http://example.com/, on a HotSpot with the DNS name hotspot.lan, this line of a page:

ip=$(ip) mac=$(mac) link-login=$(link-login)

is served as:

ip=192.168.88.254 mac=52:54:09:80:02:01 link-login=http://hotspot.lan/login?dst=http%3A%2F%2Fexample.com%2F

Every variable also exists with the -esc suffix, for example $(mac-esc). This form is escaped for use inside a URL: 52:54:09:80:02:01 becomes 52%3A54%3A09%3A80%3A02%3A01. Use it when you put a variable into a link. For example, ` breaks when the user name is123&456=1 2; with$(mac-esc)and$(username-esc)the user name is sent as123%26456%3D1+2`.

Some links use http:// URLs. If you use HTTPS, build the link yourself, for example https://$(hostname)/$(target-dir)status instead of $(link-status).

Server

  • hostname - the DNS name of the HotSpot, or its IP address if no DNS name is set (hotspot.lan).
  • identity - the identity of the router (MikroTik).
  • login-by - the login method that the user used.
  • plain-passwd - yes if the http-pap login method is enabled, otherwise no.
  • server-address - the address and port of the HotSpot server (192.168.88.1:80).
  • ssl-login - yes if the page was requested over HTTPS, otherwise no.
  • server-name - the name of the HotSpot server in /ip/hotspot (hotspot1).

Links

  • link-login - the login page, with the requested URL (http://hotspot.lan/login?dst=http%3A%2F%2Fexample.com%2F).
  • link-login-only - the login page, without the requested URL (http://hotspot.lan/login).
  • link-logout - the logout page (http://hotspot.lan/logout).
  • link-status - the status page (http://hotspot.lan/status).
  • link-orig - the URL that the user requested (http://example.com/).
  • link-redirect - the URL to which the page redirects the user.
  • link-advert - the advertisement that is due.

Client

  • domain - the domain name of the user (example.com).
  • interface-name - the name of the HotSpot interface (bridge).
  • ip - the IP address of the client (192.168.88.254).
  • logged-in - yes if the user is logged in, otherwise no.
  • mac - the MAC address of the client (52:54:09:80:02:01).
  • trial - yes if the user can use trial access, otherwise no.
  • username - the name of the user (anna).
  • host-ip - the IP address of the client in /ip/hotspot/host.
  • vlan-id - the ID of the VLAN interface through which the client is connected.

Session

  • idle-timeout - the idle timeout (20m, or empty if none).
  • idle-timeout-secs - the idle timeout in seconds (88, or 0 if none).
  • limit-bytes-in - the limit of bytes that the user can send (1000000, or --- if none).
  • limit-bytes-out - the limit of bytes that the user can receive (1000000, or --- if none).
  • refresh-timeout - the refresh interval of the status page (1m30s, or empty if none).
  • refresh-timeout-secs - the refresh interval of the status page in seconds (90, or 0 if none).
  • session-timeout, session-time-left - the session time that is left (5h, or empty if none).
  • session-timeout-secs, session-time-left-secs - the session time that is left, in seconds (3475, or 0 if none).
  • uptime - the time since login (10h2m33s).
  • uptime-secs - the time since login in seconds (125).

Traffic counters

These variables have values only on the status and logout pages:

  • bytes-in - the number of bytes received from the user (15423).
  • bytes-in-nice - the same in a readable form.
  • bytes-out - the number of bytes sent to the user (11352).
  • bytes-out-nice - the same in a readable form.
  • packets-in - the number of packets received from the user (251).
  • packets-out - the number of packets sent to the user (211).
  • remain-bytes-in - the bytes left until limit-bytes-in is reached (337465, or --- if no limit).
  • remain-bytes-out - the bytes left until limit-bytes-out is reached (124455, or --- if no limit).
  • remain-bytes-total - the bytes left until limit-bytes-total is reached.

Other

  • session-id - the value of the session-id parameter of the last request.
  • var - the value of the var parameter of the last request.
  • error - the error message, if something failed (invalid username or password). Only on the login page.
  • error-orig - the original error message, before it is replaced by the text from errors.txt. Only on the login page.
  • chap-id - the CHAP ID (\371). Only on the login page.
  • chap-challenge - the CHAP challenge (\357\015\330\013\021\234\145\245\303\253\142\246\133\175\375\316). Only on the login page.
  • popup - true or false: whether to open the status pop-up window. Only on the login page.
  • advert-pending - yes if an advertisement is due, otherwise no.
  • http-status - sets the HTTP status code and message, as described in the HTTP status and headers section.
  • http-header - sets an HTTP header.

RADIUS

  • radius\ - the attribute with this ID as a text string. Empty if RADIUS authentication was not used.
  • radius\u - the attribute with this ID as an unsigned integer. 0 if RADIUS authentication was not used.
  • radius\-\ - the attribute with this ID and vendor ID as a text string.
  • radius\-\u - the attribute with this ID and vendor ID as an unsigned integer.

Request headers

The pages can read the HTTP headers of the request with $(header-name). For example, $(user-agent) is the browser of the user. The last example on this page uses it.

Conditions

A page can show a part of its content only when a condition is true:

  • $(if name) - true if the variable is not empty.
  • $(if name == value) and $(if name != value) - compare the variable with a value.
  • $(elif name == value), $(else), and $(endif) continue and end the condition.
some content, which is always displayed
$(if username == john)
Hey, your username is john
$(elif username == dizzy)
Hello, Dizzy! How are you? Your administrator.
$(elif ip == 10.1.2.3)
You are sitting at that old computer, which is so slow...
$(elif mac == 00:01:02:03:04:05)
This is an ethernet card, which was stolen few months ago...
$(else)
I don't know who you are, so let's live in peace.
$(endif)
other content, which is always displayed

Only one of the parts is shown: the first one whose condition is true.

HTTP status and headers

Two variables are set, not tested, although they are written as conditions. http-status sets the status line of the HTTP response, and http-header adds a header. The default rlogin.html starts with these lines:

$(if http-status == 302)Hotspot login required$(endif)
$(if http-header == "Location")$(link-redirect)$(endif)

If $(link-redirect) is http://192.168.88.1/login, the response to the client starts with:

HTTP/1.0 302 Hotspot login required
<regular HTTP headers>
Location: http://192.168.88.1/login

The syntax:

$(if http-status == XYZ)HTTP_STATUS_MESSAGE$(endif)
$(if http-header == HTTP_HEADER_NAME)HTTP_HEADER_VALUE$(endif)
  • XYZ - the status code: three digits, the first one not 0.
  • HTTP_STATUS_MESSAGE - the text after the status code.
  • HTTP_HEADER_NAME and HTTP_HEADER_VALUE - the name and the value of the header.

Variables and conditions inside the message and the header value are processed as usual. If the same header is added several times, the last one is used. This way a page can replace a regular header, for example Content-Type or Cache-Control.

Error messages

The texts of the error messages are in the errors.txt file of the directory. Edit the file to change or translate them. The file explains each message, and the messages can use variables. For example, this line:

invalid-username = wrong name or password for $(username) from $(ip)

shows "wrong name or password for anna from 192.168.88.253" on the login page after a failed login.

Several versions of the pages

One HotSpot server can have several sets of pages, for example one for each language. Create a sub-directory in the HTML directory and put the pages that differ into it. For a Latvian version, create the lv sub-directory with the translated login.html, logout.html, status.html, alogin.html, radvert.html, and errors.txt. A page that is not in the sub-directory is taken from the main directory.

The user selects the version with a link. In the main login.html:

and in the Latvian login.html:

English

The target parameter selects the sub-directory as well:

Latviski

After the user selects a version, the link variables contain its path, for example $(link-status) is http://hotspot.lan/lv/status. If the pages use the $(link-...) variables for all links, the user stays in the selected version.

The examples change the default pages. The lines that they refer to are from the default login.html:

<form name="login" action="$(link-login-only)" method="post" $(if chap-id) onSubmit="return doLogin()" $(endif)>

    <input type="hidden" name="popup" value="true" />

External authentication

The login page can be on another server, for example on a server that takes a payment before it gives access:

  1. Allow access to the external server in the walled garden.
  2. Change the login page of the HotSpot so that it redirects to the external server. The external server changes the RADIUS database as needed.
  3. The external server logs the user in by sending the browser back to the login page of the HotSpot with the user name and password.

This login page on the HotSpot router redirects to https://auth.example.com/login.php. Replace it with the address of your server:

<!--
   document.redirect.submit();
//-->
</script>
</body>
</html>

This page on the external server sends the user back to the HotSpot. Replace https://hotspot.example.com/login with the address of your HotSpot router, and http://www.mikrotik.com/ with the page to open after login:

<html>

The HotSpot asks the RADIUS server whether to allow the login. If the login is allowed, alogin.html is shown. If not, flogin.html or login.html is shown, which sends the user back to the external server.

PPP AAA

PPP users and profiles in RouterOS: create profiles and secrets for PPPoE, L2TP, SSTP and other PPP servers, assign addresses, routes and IPv6 prefixes, limit speed and traffic, filter user traffic, run scripts on...

PPP AAA

All PPP servers of RouterOS (PPPoE, L2TP, SSTP, OpenVPN, PPTP) share one user database:

  • /ppp/secret has the users: a name, a password and the settings of one user.
  • /ppp/profile has the profiles: settings that many users share, such as the addresses, the DNS server, a rate limit and firewall chains.
  • /ppp/active lists the users that are connected.
  • /ppp/aaa hands the authentication over to a RADIUS server for users that have no secret on the router.

The examples use an L2TP server. Profiles and secrets are used in the same way with the other PPP servers; the CLI reference names the few settings that do not apply to every server.

Create a profile and a user

This example gives the router the address 10.0.0.1 inside the tunnels and the users addresses from a pool:

/ip/pool/add name=vpn-pool ranges=10.0.0.10-10.0.0.100
/ppp/profile/add name=vpn local-address=10.0.0.1 \
    remote-address=vpn-pool
/ppp/secret/add name=alice password=Example-pass-1 profile=vpn \
    service=l2tp

service limits the user to one kind of PPP server. Without it, the user can log in to any of them.

The users connect to a PPP server, which must be enabled. For L2TP:

/interface/l2tp-server/server/set enabled=yes default-profile=vpn

The default firewall drops connections that come from the internet, so the users cannot connect until the firewall accepts the port of the server. For L2TP without IPsec this is UDP port 1701:

/ip/firewall/filter/add chain=input action=accept protocol=udp \
    dst-port=1701 in-interface-list=WAN comment="accept L2TP" \
    place-before=[find comment="defconf: drop all not coming from LAN"]

L2TP describes the server and IPsec for it.

dns-server in the profile gives the clients one or two DNS servers when the link comes up (the IPCP DNS options of RFC 1877). A client uses them only if it asks for them: a RouterOS PPP client does with use-peer-dns=yes. When the address is the router itself, the router must answer DNS requests (allow-remote-requests=yes in /ip/dns) and its firewall must accept them from the PPP users.

When the user connects, /ppp/active shows the session, the address the user connected from and the address from the pool:

[admin@MikroTik] > /ppp/active/print
Columns: NAME, SERVICE, CALLER-ID, ADDRESS, UPTIME, ENCODING
# NAME   SERVICE  CALLER-ID      ADDRESS    UPTIME  ENCODING
0 alice  l2tp     172.31.30.195  10.0.0.99  8s      MPPE128 stateless

Give a user a fixed address and a route

A remote office needs the same address every time, and the router needs a route to the network behind it. Set both in the secret:

/ppp/secret/set alice remote-address=10.0.0.5 \
    routes="192.168.50.0/24 10.0.0.5 1"

The format of a route is dst-address gateway metric. Several routes are separated with commas. The route exists while the user is connected:

[admin@MikroTik] > /ip/route/print where dst-address=192.168.50.0/24
Flags: D - DYNAMIC; A - ACTIVE; v - VPN
Columns: DST-ADDRESS, GATEWAY, ROUTING-TABLE, DISTANCE
    DST-ADDRESS      GATEWAY   ROUTING-TABLE  DISTANCE
DAv 192.168.50.0/24  10.0.0.5  main                  1

An address in the secret takes precedence over the address or the pool of the profile. ipv6-routes does the same for IPv6 networks.

Limit the speed

rate-limit in a profile limits each user of the profile. The first value is the upload of the user and the second the download:

/ppp/profile/set vpn rate-limit=5M/10M

The limit applies when the user connects again. The router then adds a dynamic simple queue for the interface of the user:

[admin@MikroTik] > /queue/simple/print where dynamic
Flags: D - DYNAMIC
0 D name="<l2tp-alice>" target=<l2tp-alice> parent=none packet-marks=""
    priority=8/8 queue=default-small/default-small limit-at=5M/10M
    max-limit=5M/10M burst-limit=0/0 burst-threshold=0/0 burst-time=0s/0s
    bucket-size=0.1/0.1

While the user sends and receives as much as the link allows, rate of the queue stays at the limits, and dropped counts the packets over the limit:

[admin@MikroTik] > /queue/simple/print stats where dynamic
Flags: D - DYNAMIC
0 D name="<l2tp-alice>" target=<l2tp-alice> rate=5.0Mbps/9.9Mbps
    total-rate=0bps packet-rate=791/1063 total-packet-rate=0 queued-bytes=0/0
    total-queued-bytes=0 queued-packets=0/0 total-queued-packets=0
    bytes=8368364/56349507 total-bytes=0 packets=17379/42613 total-packets=0
    dropped=3219/2273 total-dropped=0

The default configuration has a FastTrack rule, and simple queues do not limit FastTracked connections. See Simple queue for how to make the queues work with it.

The value can also set bursts, a priority and a guaranteed rate; the RADIUS page describes the format. parent-queue makes the queues of the users children of an existing simple queue, queue-type sets the queue types for upload and download, and insert-queue-before sets the place of the queue in the list.

Allow one session for each user

By default, a user can connect several times with the same name. To refuse a second connection while the first one is active:

/ppp/profile/set vpn only-one=yes

The second connection fails, and the log of the router has the message user alice is already active.

The setting counts all PPP servers together: a user who is connected to the L2TP server cannot log in to the SSTP server at the same time. It also applies to users that a RADIUS server authenticates.

Limit the traffic of a session

limit-bytes-in is the number of bytes the user can upload in one session, and limit-bytes-out the number the user can download:

/ppp/secret/set alice limit-bytes-in=1000000000 \
    limit-bytes-out=10000000000

[admin@MikroTik] > /ppp/active/print detail
0  name="alice" service=l2tp caller-id="172.31.30.195" address=10.0.0.5
   uptime=9s encoding="MPPE128 stateless" session-id=0x81100056
   limit-bytes-in=1000000000 limit-bytes-out=10000000000

When a limit is reached, the router disconnects the user. The limits count each session separately: a user who connects again gets the full amount again.

Put the addresses of users in an address list

/ppp/profile/set vpn address-list=vpn-users

[admin@MikroTik] > /ip/firewall/address-list/print where list=vpn-users
Flags: D - DYNAMIC
Columns: LIST, ADDRESS, CREATION-TIME

Filter the traffic of users

incoming-filter and outgoing-filter name firewall filter chains for the packets from and to the users of a profile. The router adds a dynamic jump rule to the chain ppp for each connected user. The firewall reaches the chain ppp only when a rule jumps to it: add a jump rule to each chain that applies the user rules, forward for the traffic through the router and input for the traffic to the router itself. This example stops the users from sending mail directly:

/ip/firewall/filter/add chain=forward action=jump jump-target=ppp \
    comment="PPP user rules"
/ip/firewall/filter/add chain=vpn-in action=drop protocol=tcp \
    dst-port=25 comment="VPN users: no direct SMTP"
/ppp/profile/set vpn incoming-filter=vpn-in

The example adds the jump rule at the end of the forward chain. With the default firewall this place works: the rules before it accept the packets of established connections, and the chain ppp gets the first packet of each new connection of a user. In a firewall with more rules, put the jump rule before any rule that accepts or drops the new connections of the users.

With the default firewall, a connected user can reach all devices of the LAN. Of the router itself, the user can only ping the address. To let the users reach one device only, here the file server 192.168.88.10, accept this address and drop the rest:

/ip/firewall/filter/add chain=vpn-in action=accept \
    dst-address=192.168.88.10
/ip/firewall/filter/add chain=vpn-in action=drop

A change of incoming-filter in the profile applies when the user connects again.

After the user connects again, the chain ppp has the rule for the interface of the user:

[admin@MikroTik] > /ip/firewall/filter/print where chain=ppp
Flags: D - DYNAMIC
0 D chain=ppp action=jump jump-target=vpn-in in-interface=<l2tp-alice>

The counters of the drop rule show the blocked packets:

[admin@MikroTik] > /ip/firewall/filter/print stats where chain=vpn-in
Columns: CHAIN, ACTION, BYTES, PACKETS
# CHAIN   ACTION  BYTES  PACKETS
;;; VPN users: no direct SMTP
1 vpn-in  drop      240        4

Run a script when a user connects

on-up and on-down run a script when a user of the profile connects and disconnects. The script can read the variables user, local-address, remote-address, caller-id, called-id and interface:

/ppp/profile/set vpn \
    on-up=":log info \"PPP user \$user is up\"" \
    on-down=":log info \"PPP user \$user is down\""

The log then has the lines PPP user alice is up and PPP user alice is down under the topic script.

remote-ipv6-prefix in a secret gives one user a fixed prefix. IPv6 PD over PPP has a complete example.

Restrict where a user connects from

caller-id in a secret accepts the user only from one address: an IP address for L2TP and PPTP, a MAC address in capital letters for PPPoE. A login from another address is refused, and the log has user alice called from ..., but was expected from ....

See and disconnect users

/ppp/active/print lists the connected users. The R flag marks a user that RADIUS authenticated. To disconnect a user:

/ppp/active/remove [find name=alice]

The client can connect again immediately. The secret keeps the time, the address and the reason of the last disconnect:

[admin@MikroTik] > /ppp/secret/print detail
0  name="alice" service=l2tp caller-id="" profile=vpn remote-address=10.0.0.5
   routes="192.168.50.0/24 10.0.0.5 1" ipv6-routes="" limit-bytes-in=1000000000
   limit-bytes-out=10000000000 last-logged-out=2026-11-19 10:15:03
   last-caller-id="172.31.30.195" last-disconnect-reason=nas-request

Authenticate users with RADIUS

With use-radius=yes in /ppp/aaa, the router asks a RADIUS server about each user that has no secret on the router. The server can send the address, the rate limit and most other settings of the profile for each user, and the router reports the sessions to it (accounting and interim-update in /ppp/aaa). A RADIUS user gets the settings that the server does not send from the default profile of the PPP server (default-profile in the settings of the server), or from the profile that the server names in the Mikrotik-Group attribute. See RADIUS for the setup and the attributes.

The Framed-MTU attribute of a RADIUS server is not applied: PPP negotiates the MTU with LCP before the authentication.

How the settings are combined

  • The settings of a user come from three places. The secret has the highest priority, then the profile of the secret, then the default profile of the PPP server that the user connects to.
  • A profile setting with the value default takes the value from the default profile of the PPP server.
  • A user without profile uses the profile default.
  • In a profile, local-address and remote-address accept an address or the name of an IP pool. A secret takes an address only, and that address takes precedence over a pool.
  • The two built-in profiles, default and default-encryption, cannot be removed. Both have change-tcp-mss=yes, and default-encryption has use-encryption=yes.

L2TP tunnel secrets

/ppp/l2tp-secret sets a secret for the L2TP tunnel itself, for clients that connect from the given address or network. A client that does not use this secret cannot connect.

RADIUS

RADIUS (Remote Authentication Dial-In User Service) keeps user accounts on a central server. The RouterOS RADIUS client asks the server whether a user is allowed to connect, applies the settings that the server returns for the user (an address, a rate limit, a session time), and reports the session to the server for accounting. One server can manage the users of many routers.

The /radius menu holds the list of servers. Each entry names the router services that use it: ppp, login (router users), hotspot (HotSpot), dhcp (DHCP server), dot1x (Dot1X), ipsec (IPsec) and wireless. The ppp service covers all PPP servers: PPPoE, L2TP, SSTP and the others. Each service also has its own setting that turns RADIUS on.

A PPP secret or a router user that exists on the router is checked on the router. The router does not ask the server about that name.

On the server, add the router as a client with the same shared secret, and load the MikroTik attribute dictionary (see RADIUS attributes at the end of this page). User Manager is a RADIUS server that runs on RouterOS. The server examples on this page use the users file format of FreeRADIUS.

Authenticate PPP users

This example sends the logins of a PPP server, for example a PPPoE server, to the RADIUS server at 192.0.2.10. Add the server and turn RADIUS on for PPP:

/radius/add service=ppp address=192.0.2.10 secret=Example-secret-1
/ppp/aaa/set use-radius=yes

On the server, the user gets a fixed address and a rate limit:

alice Cleartext-Password := "Example-pass-1"
    Framed-IP-Address = 10.0.0.10,
    Mikrotik-Rate-Limit = "10M/50M"

When the user connects, the session has the R flag and the address from the server:

[admin@MikroTik] > /ppp/active/print
Flags: R - RADIUS
Columns: NAME, SERVICE, CALLER-ID, ADDRESS, UPTIME
#   NAME   SERVICE  CALLER-ID          ADDRESS    UPTIME
0 R alice  pppoe    00:00:5E:00:53:0B  10.0.0.10  9s

The rate limit is a dynamic simple queue on the interface of the user. The first value limits the upload of the user and the second the download:

[admin@MikroTik] > /queue/simple/print where dynamic
Flags: D - DYNAMIC
0 D name="<pppoe-alice>" target=<pppoe-alice> parent=none packet-marks=""
    priority=8/8 queue=default-small/default-small limit-at=10M/50M
    max-limit=10M/50M burst-limit=0/0 burst-threshold=0/0 burst-time=0s/0s
    bucket-size=0.1/0.1

The default configuration has a FastTrack rule, and simple queues do not limit FastTracked connections. See Simple queue before you rely on these queues.

Framed-IP-Address or Framed-Pool from the server replaces remote-address of the PPP profile. Settings that the server does not send come from the default profile of the PPP server (default-profile in the settings of the server). Mikrotik-Group in the reply selects another PPP profile for the user.

Log in to the router with RADIUS accounts

This example lets administrators log in to the router with accounts from the same server. Add login to the services of the entry and turn RADIUS on for router users:

/radius/set [find address=192.0.2.10] service=ppp,login
/user/aaa/set use-radius=yes

On the server, Mikrotik-Group names the user group of the account:

netadmin Cleartext-Password := "Example-pass-2"
    Mikrotik-Group = "full"

Log in with the account and list the sessions that RADIUS authenticated:

[netadmin@MikroTik] > /user/active/print where radius
Flags: R - RADIUS
Columns: WHEN, NAME, ADDRESS, VIA
#   WHEN                 NAME      ADDRESS     VIA
0 R 2026-11-20 08:57:50  netadmin  192.0.2.20  ssh

ADDRESS is the address that the administrator logged in from.

WARNING

Every account that the server accepts for a login request can log in to the router. An account without Mikrotik-Group, or with a group that does not exist on the router, gets the group set in default-group of /user/aaa, which is read by default. The read group can do more than look: see User for its policies. When the same server also holds PPP or HotSpot users, configure it to accept requests with Service-Type Login only for administrator accounts.

The router does not ask the server about names that exist in /user, so keep a local administrator account for the time when the server cannot be reached.

Authorize DHCP clients

With RADIUS, the DHCP server asks the RADIUS server before it gives a lease. The server can set the address, the lease time and a rate limit for each device. The example uses the DHCP server of the default configuration, defconf:

/radius/set [find address=192.0.2.10] service=ppp,login,dhcp
/ip/dhcp-server/set defconf use-radius=yes

With the default settings, the router sends the MAC address of the device as the user name, with an empty password. On the server, accept the device by its MAC address:

00:00:5E:00:53:0A Auth-Type := Accept
    Framed-IP-Address = 192.168.88.50,
    Session-Timeout = 3600,
    Mikrotik-Rate-Limit = "5M/20M"

Session-Timeout is the lease time in seconds. The lease has the R flag:

[admin@MikroTik] > /ip/dhcp-server/lease/print
Flags: R - RADIUS, D - DYNAMIC
Columns: ADDRESS, MAC-ADDRESS, HOST-NAME, SERVER, RATE-LIMIT, STATUS,
         LAST-SEEN
#   ADDRESS        MAC-ADDRESS        HOST-NAME  SERVER   RATE-L  STATUS  LAS
0 R 192.168.88.50  00:00:5E:00:53:0A  laptop     defconf  5M/20M  bound   12s

A device that the server rejects gets no address. Add all devices of the network to the server before you turn RADIUS on for a DHCP server that is in use.

Authenticate HotSpot users

Add hotspot to the services of the entry and set use-radius=yes in the HotSpot server profile. The HotSpot page describes the HotSpot server and its profiles.

Authenticate IPsec users

An IKEv2 server can pass the EAP authentication of its clients to RADIUS. IPsec has the complete server setup; this example shows the RADIUS part. The server certificate is ike-server. Add ipsec to the services of the entry and set auth-method=eap-radius in the identity:

/radius/set [find address=192.0.2.10] \
    service=ppp,login,dhcp,ipsec
/ip/pool/add name=ike-pool ranges=10.10.10.10-10.10.10.100
/ip/ipsec/mode-config/add name=ike-conf address-pool=ike-pool
/ip/ipsec/peer/add name=ike-clients passive=yes exchange-mode=ike2
/ip/ipsec/identity/add peer=ike-clients auth-method=eap-radius \
    certificate=ike-server generate-policy=port-strict \
    mode-config=ike-conf

On the server, Framed-IP-Address gives the client a fixed address in place of one from the pool:

bob Cleartext-Password := "Example-pass-3"
    Framed-IP-Address = 10.10.10.50

A client that logs in with EAP-MSCHAPv2 is listed with its user name and the address from the server:

[admin@MikroTik] > /ip/ipsec/active-peers/print
Flags: R - RESPONDER
Columns: ID, STATE, UPTIME, PH2-TOTAL, REMOTE-ADDRESS, DYNAMIC-ADDRESS
#   ID   STATE        UPTIME  PH2-TOTAL  REMOTE-ADDRESS  DYNAMIC-ADDRESS
0 R bob  established  9s              1  192.0.2.50      10.10.10.50

Authenticate Dot1X clients

The Dot1X server passes the EAP authentication of the devices on an Ethernet port to RADIUS. Add dot1x to the services of the entry and add the port to the Dot1X server:

/radius/set [find address=192.0.2.10] \
    service=ppp,login,dhcp,ipsec,dot1x
/interface/dot1x/server/add interface=ether2 auth-types=dot1x

carol Cleartext-Password := "Example-pass-4"

When the device has logged in, the port is authorized:

[admin@MikroTik] > /interface/dot1x/server/state/print
Columns: INTERFACE, STATUS
#  INTERFACE  STATUS
0  ether2     authorized

With auth-types=mac-auth, the router sends the MAC address of the device as the user name, by default with an empty password, as the DHCP server does. mac-auth-mode and radius-mac-format of the Dot1X server change the password and the format of the address.

Send accounting

The router reports the start and the end of each session to the server, and the traffic counters in between when an interim interval is set. Accounting is on by default in /ppp/aaa, /user/aaa and the Dot1X server (accounting=yes); interim-update in the same menus sets the interval. For DHCP, both settings are in /ip/dhcp-server/config. In a HotSpot server profile the settings are radius-accounting and radius-interim-update. The server can set the interval for one session with Acct-Interim-Interval.

Add a second server

The router uses the entries in the order of the list. This example adds a second server for the time when the first one does not answer, and a third one that keeps a copy of the accounting records:

/radius/add service=ppp,login,dhcp address=192.0.2.11 \
    secret=Example-secret-2
/radius/add service=ppp,dhcp address=192.0.2.12 \
    secret=Example-secret-3 accounting-backup=yes

[admin@MikroTik] > /radius/print detail
0  service=ppp,login,dhcp,ipsec,dot1x called-id="" domain="" address=192.0.2.10
   authentication-port=1812 accounting-port=1813 timeout=1s100ms
   radsec-timeout=3s300ms accounting-backup=no realm="" protocol=udp
   certificate=none require-message-auth=yes-for-request-resp status=""

1  service=ppp,login,dhcp called-id="" domain="" address=192.0.2.11
   authentication-port=1812 accounting-port=1813 timeout=1s100ms
   radsec-timeout=3s300ms accounting-backup=no realm="" protocol=udp
   certificate=none require-message-auth=yes-for-request-resp status=""

2  service=ppp,dhcp called-id="" domain="" address=192.0.2.12
   authentication-port=1812 accounting-port=1813 timeout=1s100ms
   radsec-timeout=3s300ms accounting-backup=yes realm="" protocol=udp
   certificate=none require-message-auth=yes-for-request-resp status=""
  • The router sends a request to the first enabled entry that matches the service. It sends the request three times. When no answer arrives, it sends the request to the next matching entry.
  • Each new request starts at the first entry again.
  • An entry with accounting-backup=yes gets a copy of every accounting request, in addition to the entry that answers. The router does not send authentication requests to it.
  • place-before in /radius/add puts a new entry before an existing one.

Change or disconnect a session from the server

The server can end a session with a Disconnect-Request and change a running session with a Change of Authorization (CoA) request (RFC 5176, earlier RFC 3576). The router ignores these requests until you allow them:

/radius/incoming/set accept=yes

The router listens on UDP port 3799; port changes it, and vrf selects the VRF in which the router listens. The server signs the request with the shared secret of its /radius entry.

The default firewall drops these requests when the server is on the WAN side. Accept the port from the address of the server, before the default drop rule:

/ip/firewall/filter/add chain=input action=accept protocol=udp \
    dst-port=3799 src-address=192.0.2.10 comment="RADIUS CoA" \
    place-before=[find comment="defconf: drop all not coming from LAN"]

This command, run on the server, changes the rate limit of a connected PPP user. radclient is part of FreeRADIUS:

echo 'User-Name=alice,Mikrotik-Rate-Limit="20M/100M"' | \
    radclient -x 192.0.2.1:3799 coa Example-secret-1

Sent CoA-Request Id 179 from 0.0.0.0:52783 to 192.0.2.1:3799 length 43
    User-Name = "alice"
    Mikrotik-Rate-Limit = "20M/100M"
Received CoA-ACK Id 179 from 192.0.2.1:3799 to 192.0.2.10:52783 length 38
    Message-Authenticator = 0x3e08daec066d6cdd8aab7b9d6f3b98c7

The queue of the user has the new limit, and the session stays connected:

[admin@MikroTik] > /queue/simple/print where name~"alice"
Flags: D - DYNAMIC
1 D name="<pppoe-alice>" target=<pppoe-alice> parent=none packet-marks=""
    priority=8/8 queue=default-small/default-small limit-at=20M/100M
    max-limit=20M/100M burst-limit=0/0 burst-threshold=0/0 burst-time=0s/0s
    bucket-size=0.1/0.1

This command disconnects the user:

echo 'User-Name=alice' | \
    radclient -x 192.0.2.1:3799 disconnect Example-secret-1

Sent Disconnect-Request Id 18 from 0.0.0.0:34758 to 192.0.2.1:3799 length 27
    User-Name = "alice"
Received Disconnect-ACK Id 18 from 192.0.2.1:3799 to 192.0.2.10:34758 length 38
    Message-Authenticator = 0x15c3ee3b3b79a6f8b4fd44b83b46bb1a
  • A PPP session is found by User-Name or by Acct-Session-Id.
  • A HotSpot session is found by Framed-IP-Address, the address of the device.
  • When no session matches, the router answers with CoA-NAK or Disconnect-NAK.
  • The router does not answer a request with a wrong secret. /radius/incoming/monitor counts it in bad-requests.

RouterOS doesn't support POD (Packet of Disconnect), an older way to end a session.

Encrypt the connection with RadSec

RadSec carries RADIUS over TLS on TCP port 2083. Use it when the path between the router and the server is not trusted. The router needs:

  • A client certificate with its private key.
  • The certificate authority that signed the certificate of the server, as a trusted certificate.
  • A server certificate that contains the address set in address of the entry.

Certificates explains how to create, sign, export and import certificates. In this example the client certificate is imported with the name radius-client. Change the entry to RadSec:

/radius/set [find address=192.0.2.10] protocol=radsec \
    certificate=radius-client

After the first request, status shows the state of the TLS connection:

[admin@MikroTik] > /radius/print detail where address=192.0.2.10
0  service=ppp,login,dhcp,ipsec,dot1x called-id="" domain="" address=192.0.2.10
   authentication-port=1812 accounting-port=1813 timeout=1s100ms
   radsec-timeout=3s300ms accounting-backup=no realm="" protocol=radsec
   certificate=radius-client require-message-auth=yes-for-request-resp
   status="TLS connected"
  • With RadSec, the router connects to TCP port 2083. authentication-port and accounting-port are not used.
  • secret is not used. RFC 6614 sets the shared secret of RadSec to radsec: configure this secret on a server that asks for one.

When the server is User Manager on another router, set the server certificate and mark the router entry as a RadSec client:

/user-manager/set enabled=yes radsec-certificate=radius-server
/user-manager/router/add name=router1 address=192.0.2.1 \
    protocol=radsec

Check and troubleshoot

/radius/monitor counts the requests and answers of one entry:

[admin@MikroTik] > /radius/monitor [find address=192.0.2.10] once

          requests: 3
           accepts: 3
           rejects: 0
           resends: 0
          timeouts: 0
       bad-replies: 0
  last-request-rtt: 10ms
  • accepts counts the accepted logins and the accounting answers.
  • rejects counts the logins that the server refused.
  • resends and timeouts count requests without an answer.
  • bad-replies counts answers that failed the check of the shared secret or of the Message-Authenticator.

/radius/reset-counters sets the counters of all entries to zero. The read-only status of an entry shows the last connection error, or the state of the RadSec connection.

To see each request and answer in the log, add the radius topic:

/system/logging/add topics=radius,debug,!packet

How the router selects an entry

An entry is used for a request when all of these match:

  • service contains the service that makes the request.
  • called-id is empty or equals the Called-Station-Id of the request. For PPPoE, this is the service name of the PPPoE server.
  • domain is empty or equals the domain of the user name. The domain is the part before \ or after @.

A user who logs in as EXAMPLE\alice is sent to the server as alice, with EXAMPLE in the MS-CHAP-Domain attribute. A user who logs in as alice@example.org is sent with the complete name, and example.org in MS-CHAP-Domain.

realm sets the Mikrotik-Realm attribute in the Access-Requests of the entry. Without realm, the attribute has the domain of the user name, and it is not sent when the name has no domain.

src-address sets the source address of the packets. The same address is sent as NAS-IP-Address.

address can be an IPv6 address; the router then sends NAS-IPv6-Address in place of NAS-IP-Address. To reach a server in a VRF, add the VRF name to the address: address=192.0.2.10@vrf1.

Message-Authenticator

The router adds the Message-Authenticator attribute to every Access-Request. With require-message-auth=yes-for-request-resp, the default, the router also drops an answer to an Access-Request that has no Message-Authenticator and counts it in bad-replies. Accounting requests and their answers do not have the attribute. Set require-message-auth=no only for a server that cannot send the attribute. The router drops an answer with a wrong Message-Authenticator with either value.

RADIUS attributes

Two dictionary files list the attributes that RouterOS supports:

  • RADIUS reference dictionary is a complete dictionary in the FreeRADIUS format. It can conflict with the default dictionary of your RADIUS server. Correct the configuration of the server, not the dictionary: RouterOS supports no other attributes.
  • MikroTik vendor attributes has only the MikroTik vendor-specific attributes, to include in an existing dictionary.

On a router with User Manager, /user-manager/attribute/print lists the attributes that User Manager can send.

The attributes that the server sends override the settings of the service: the PPP profile, the HotSpot user profile or the DHCP server. A setting that the server does not send comes from the service.

Access-Request

  • Service-Type - Framed for PPP, DHCP, Dot1X and IPsec; Login for router login and HotSpot.
  • Framed-Protocol - PPP (PPP only).
  • NAS-Identifier - Identity of the router.
  • NAS-IP-Address - Address of the router: the source address of the request. With an IPv6 server, NAS-IPv6-Address is sent.
  • NAS-Port - Port number of the session on the router.
  • Acct-Session-Id - Session ID, eight hexadecimal digits. The first two digits depend on the service. The next digit is incremented on each reboot, and the last digits on each new session, so an ID is not repeated for 1 million connections of one service after a boot. If the server gets a Start message for a new session while it still keeps an older session open, the Stop message of the older session was lost: the server must close the old session and start the new one.
  • NAS-Port-Type - Async PPP and SSTP - Async; PPTP, L2TP and IPsec - Virtual; PPPoE, DHCP and Dot1X - Ethernet; ISDN - ISDN Sync; HotSpot - Ethernet, Cable or Wireless-802.11, as set in nas-port-type of the HotSpot server profile.
  • Calling-Station-Id - PPPoE and HotSpot - MAC address of the client in capital letters; PPTP, L2TP, SSTP and IPsec - public IP address of the client; router login - IP address of the client; DHCP - client ID of the device; Dot1X - MAC address of the device, written with dashes.
  • Called-Station-Id - PPPoE - service name; PPTP, L2TP, SSTP and IPsec - IP address of the server; HotSpot - name of the HotSpot server; DHCP - name of the DHCP server; Dot1X - MAC address of the port of the router, written with dashes.
  • NAS-Port-Id - Async PPP - serial port name; PPPoE, DHCP and Dot1X - name of the interface on which the server runs; HotSpot - name of the physical HotSpot interface (if bridged, the bridge port name); not present for ISDN, PPTP, L2TP and SSTP.
  • Framed-IP-Address - IP address of the HotSpot client after Universal Client translation.
  • Mikrotik-Host-IP - IP address of the HotSpot client before Universal Client translation (the original IP address of the client).
  • User-Name - Login name of the client. For DHCP and Dot1X MAC authentication, the MAC address of the device, by default in capital letters.
  • Framed-MTU - 1400 (Dot1X and IPsec).
  • EAP-Message - EAP packet of the client (Dot1X and IPsec).
  • MS-CHAP-Domain - Domain of the user name, if present.
  • Mikrotik-Realm - Value of realm of the entry. Without realm, the same value as MS-CHAP-Domain.
  • WISPr-Location-ID - Value of radius-location-id of the HotSpot server profile.
  • WISPr-Location-Name - Value of radius-location-name of the HotSpot server profile.
  • WISPr-Logoff-URL - Full link to the HotSpot logout page.
  • Message-Authenticator - Signature of the request.

The password attributes depend on the authentication method. Router login uses MS-CHAPv2. HotSpot uses CHAP by default, PAP if unencrypted passwords are enabled, and cannot use MS-CHAP. DHCP and Dot1X MAC authentication send an empty User-Password by default. Dot1X and IPsec carry the EAP method of the client in EAP-Message.

  • User-Password - Encrypted password (PAP).
  • CHAP-Password, CHAP-Challenge - Encrypted password and challenge (CHAP).
  • MS-CHAP-Response, MS-CHAP-Challenge - Encrypted password and challenge (MS-CHAPv1).
  • MS-CHAP2-Response, MS-CHAP-Challenge - Encrypted password and challenge (MS-CHAPv2).

Access-Accept

  • Framed-IP-Address - IP address of the client. For PPP, if the address belongs to the 127.0.0.0/8 or 224.0.0.0/3 networks, the address comes from the pool of the profile. If Framed-IP-Address is sent, Framed-Pool is ignored. For IPsec, the address given to the client by mode config.
  • Framed-IP-Netmask - Netmask of the client. PPP - together with Framed-IP-Address, adds a route to the network of the address through the client; HotSpot - ignored.
  • Framed-Pool - Name of the IP pool on the router that gives the address of the client.
  • Framed-IPv6-Prefix - IPv6 prefix that the router advertises to the PPP client.
  • Framed-IPv6-Pool - Name of the IPv6 pool on the router that gives the prefix advertised to the PPP client.
  • Delegated-IPv6-Prefix - IPv6 prefix that the router delegates to the PPP client with DHCPv6.
  • Mikrotik-Delegated-IPv6-Pool - Name of the IPv6 pool on the router that gives the delegated prefix.
  • Idle-Timeout - Overrides idle-timeout of the service.
  • Session-Timeout - Overrides session-timeout of the service. For DHCP, the lease time.
  • Port-Limit - Maximal number of simultaneous connections with the same user name (overrides shared-users of the HotSpot user profile).
  • Class - Cookie. The router includes it unchanged in the accounting requests of the session.
  • Framed-Route - Route to add on the router. The format is specified in RFC 2865 (chapter 5.22). Can be sent several times.
  • Filter-Id - Name of a firewall filter chain. For PPP, the router adds dynamic rules to the ppp chain that jump to this chain for the packets from and to the client. For HotSpot, the rules are added to the hotspot chain. Jump rules from the forward chain to the ppp or hotspot chain must exist. The suffix .in or .out after the name adds the rule only for incoming or only for outgoing traffic. If Filter-Id is sent several times, only the last ones for incoming and outgoing are used.
  • Mikrotik-Mark-Id - Packet mark (HotSpot only). The router adds dynamic rules to the hotspot chain of the firewall mangle that mark the packets from and to the client. The suffix .in or .out adds the rule only for incoming or only for outgoing traffic. If the attribute is sent several times, only the last ones for incoming and outgoing are used.
  • Mikrotik-Address-List - Name of a firewall address list. The router adds the address of the client to the list while the session or the lease is active.
  • Mikrotik-DHCP-Option-Set - Name of a DHCP option set on the router that is sent to the device (DHCP only).
  • Acct-Interim-Interval - Interval of the Interim-Update accounting requests in seconds. PPP - if 0, the interval of /ppp/aaa is used. HotSpot - only respected if radius-interim-update=received in the HotSpot server profile.
  • MS-MPPE-Encryption-Policy - require-encryption property (PPP only).
  • MS-MPPE-Encryption-Types - use-encryption property. A non-zero value means to use encryption (PPP only).
  • Ascend-Data-Rate - Data rate limit. If the attribute is sent two times, the first limits the transmit rate and the second the receive rate. If it is sent together with Ascend-Xmit-Rate, it sets the receive rate. 0 means unlimited. Ignored if Mikrotik-Rate-Limit is present.
  • Ascend-Xmit-Rate - Transmit rate limit. 0 means unlimited. Ignored if Mikrotik-Rate-Limit is present.
  • MS-CHAP2-Success - Authentication response if MS-CHAPv2 was used.
  • MS-MPPE-Send-Key, MS-MPPE-Recv-Key - Encryption keys for encrypted PPP, sent by the server only if MS-CHAPv2 was used (PPP only).
  • Ascend-Client-Gateway - Client gateway for the DHCP-pool HotSpot login method (HotSpot only).
  • Mikrotik-Recv-Limit - Total receive limit in bytes for the client.
  • Mikrotik-Recv-Limit-Gigawords - Upper 32 bits of the receive limit (bits 32..63, when bits 0..31 are sent in Mikrotik-Recv-Limit).
  • Mikrotik-Xmit-Limit - Total transmit limit in bytes for the client.
  • Mikrotik-Xmit-Limit-Gigawords - Upper 32 bits of the transmit limit (bits 32..63, when bits 0..31 are sent in Mikrotik-Xmit-Limit).
  • Mikrotik-Total-Limit - Limit in bytes for the received and transmitted traffic together (HotSpot).
  • Mikrotik-Wireless-Forward - Does not forward the frames of the client back to the wireless infrastructure if this attribute is set to "0" (wireless only).
  • Mikrotik-Wireless-Skip-Dot1x - Disables 802.1x authentication for the wireless client if set to a non-zero value (wireless only).
  • Mikrotik-Wireless-Enc-Algo - WEP encryption algorithm: 0 - no encryption, 1 - 40-bit WEP, 2 - 104-bit WEP (wireless only).
  • Mikrotik-Wireless-Enc-Key - WEP encryption key for the client (wireless only).
  • Mikrotik-Wireless-VLANID - VLAN ID for the client (wireless only).
  • Mikrotik-Wireless-VLANIDtype - VLAN ID type for the client: 0 - 802.1q tag, 1 - 802.1ad tag (wireless only).
  • Mikrotik-Switching-Filter - Dynamic switch rules for a client that the Dot1X server authenticates.
  • Tunnel-Type, Tunnel-Medium-Type, Tunnel-Private-Group-ID - VLAN of a client that the Dot1X server authenticates.
  • Mikrotik-Rate-Limit - Data rate limit for the client. See Rate limit format.
  • Mikrotik-Group - Router login - name of the user group; HotSpot - name of the HotSpot user profile; PPP - name of the PPP profile.
  • Mikrotik-Advertise-URL - URL of the page with advertisements that is displayed to HotSpot clients. If this attribute is sent, advertisements are enabled, including the transparent proxy, even if they are disabled in the user profile. The server can send the attribute several times; the URLs are used in turn.
  • Mikrotik-Advertise-Interval - Time between two advertisements. The server can send the attribute several times. The values are used one by one for each successful advertisement, and the last value is used when the end of the list is reached.
  • WISPr-Redirection-URL - URL to which HotSpot clients are redirected after a successful login.
  • WISPr-Bandwidth-Min-Up - Minimal data rate (CIR) for the upload of the HotSpot client.
  • WISPr-Bandwidth-Min-Down - Minimal data rate (CIR) for the download of the HotSpot client.
  • WISPr-Bandwidth-Max-Up - Maximal data rate (MIR) for the upload of the HotSpot client.
  • WISPr-Bandwidth-Max-Down - Maximal data rate (MIR) for the download of the HotSpot client.
  • WISPr-Session-Terminate-Time - Time when the user is disconnected, in the form "YYYY-MM-DDThh:mm:ssTZD": Y - year; M - month; D - day; T - separator between date and time; h - hour (24-hour format); m - minute; s - second; TZD - time zone as "+hh:mm", "+hhmm", "-hh:mm" or "-hhmm".

Mikrotik-Rate-Limit takes precedence over the other ways to set the data rate. The Ascend attributes come second and the WISPr attributes last.

Rate limit format

The format of Mikrotik-Rate-Limit is:

rx-rate[/tx-rate] [rx-burst-rate[/tx-burst-rate]
[rx-burst-threshold[/tx-burst-threshold]
[rx-burst-time[/tx-burst-time] [priority [rx-rate-min[/tx-rate-min]]]]]]

The value is one line with spaces between the fields. The rates are from the point of view of the router: rx is the upload of the client and tx the download. All rates are numbers with an optional k (1 000) or M (1 000 000).

  • If tx-rate is not set, it is the same as rx-rate. The same applies to the burst rate, the burst threshold and the burst time.
  • If the burst thresholds are not set but a burst rate is, rx-rate and tx-rate are the burst thresholds.
  • If the burst times are not set, they are 1 second.
  • priority is 1 to 8, where 1 is the highest priority.
  • If rx-rate-min and tx-rate-min are not set, they are the same as rx-rate and tx-rate. They cannot be higher than rx-rate and tx-rate.

Examples:

  • 128k - rx-rate=128000, tx-rate=128000 (no bursts).
  • 64k/128M - rx-rate=64000, tx-rate=128000000.
  • 64k 256k - rx/tx-rate=64000, rx/tx-burst-rate=256000, rx/tx-burst-threshold=64000, rx/tx-burst-time=1s.
  • 64k/64k 256k/256k 128k/128k 10/10 - rx/tx-rate=64000, rx/tx-burst-rate=256000, rx/tx-burst-threshold=128000, rx/tx-burst-time=10s.

Accounting-Request

An accounting request has the attributes of the Access-Request, without the password attributes and the Message-Authenticator, and these:

  • Acct-Status-Type - Start, Stop, or Interim-Update.
  • Acct-Authentic - Whether RADIUS or the router authenticated the session.
  • Class - Cookie of the server, as received in the Access-Accept.
  • Acct-Delay-Time - How long the router has tried to send this request.
  • Event-Timestamp - Time of the event.
  • Framed-IP-Address - Address of the client.

Stop and Interim-Update requests also have:

  • Acct-Session-Time - Connection uptime in seconds.
  • Acct-Input-Octets - Bytes received from the client: the upload of the client.
  • Acct-Input-Gigawords - Upper 32 bits of the bytes received from the client (bits 32..63, when bits 0..31 are sent in Acct-Input-Octets).
  • Acct-Input-Packets - Number of packets received from the client.
  • Acct-Output-Octets - Bytes sent to the client: the download of the client.
  • Acct-Output-Gigawords - Upper 32 bits of the bytes sent to the client (bits 32..63, when bits 0..31 are sent in Acct-Output-Octets).
  • Acct-Output-Packets - Number of packets sent to the client.

Stop requests also have:

  • Acct-Terminate-Cause - Cause of the session end (see RFC 2866, chapter 5.10).

Change of Authorization

A CoA request can change these attributes of a running session:

  • Mikrotik-Group
  • Mikrotik-Recv-Limit
  • Mikrotik-Xmit-Limit
  • Mikrotik-Rate-Limit
  • Ascend-Data-Rate (only if Mikrotik-Rate-Limit is not present)
  • Ascend-Xmit-Rate (only if Mikrotik-Rate-Limit is not present)
  • Mikrotik-Mark-Id
  • Filter-Id
  • Mikrotik-Address-List
  • Mikrotik-Advertise-URL
  • Mikrotik-Advertise-Interval
  • Session-Timeout
  • Idle-Timeout
  • Port-Limit

A CoA request cannot change the IP address, the pool or the routes of a session. Disconnect the user to change them.
