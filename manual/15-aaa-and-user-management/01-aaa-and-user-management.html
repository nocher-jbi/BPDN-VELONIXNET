AAA and User Management

Authentication, authorization and accounting in RouterOS: router users, certificates, RADIUS, User Manager, PPP users and profiles, Dot1X and the HotSpot captive portal.

AAA and User Management

This section is about who can use the router and the network behind it, what each user can do, and how the use is counted.

  • User has the accounts that manage the router itself.
  • Certificates has the certificates and keys that the secure services of the router use.
  • RADIUS lets a central server authenticate the users of PPP, DHCP, HotSpot, Dot1X, IPsec, wireless and the router login.
  • User Manager is a RADIUS server that runs on RouterOS.
  • PPP AAA has the users and profiles of the PPP servers: PPPoE, L2TP, SSTP and others.
  • Dot1X authenticates the devices on Ethernet ports with IEEE 802.1X.
  • HotSpot shows a login page to the users of a network before they get access.

Certificates

Certificates in MikroTik RouterOS: create a certificate authority and sign certificates on the router, use them for services, export and import them, trust other authorities, request certificates, check revocation...

Certificates

RouterOS keeps certificates and their private keys in the /certificate menu. Services such as WebFig over HTTPS, the API, VPN servers and clients, CAPsMAN, RADIUS and Fetch refer to a certificate by its name, and verify the certificates of other devices against the authorities this menu trusts.

The page covers these tasks:

  • Create a certificate authority (CA) on the router and sign server and client certificates.
  • Assign a certificate to a service.
  • Export certificates for other devices, and import certificates and keys.
  • Trust the certificate authority of another device.
  • Request a certificate from an authority outside the router.
  • Revoke certificates and check certificate revocation lists (CRL).
  • Enrol certificates automatically with the Simple Certificate Enrollment Protocol (SCEP).
  • Get a public certificate with the Automatic Certificate Management Environment (ACME) client.

The examples use two devices. The router 192.168.88.1 is the certificate authority and the HTTPS server with the name router.example.com. A second RouterOS device in the same network is the client.

Create a certificate authority and sign certificates

A certificate starts as a template. The add command creates the template with the subject and the key settings, and the sign command generates the key and turns the template into a certificate with the same name. A template signed without the ca parameter becomes a self-signed certificate. With ca, the named authority signs it.

Set key-usage in every template. A template without it gets all the default usages, which include the right to sign other certificates. An authority has key-cert-sign and crl-sign, a server certificate has tls-server, and a client certificate has tls-client.

Clients compare the name or address they connect to with the subject-alt-name of the server certificate. List every DNS name and IP address the server is reached by.

Create the authority, a certificate for the HTTPS server of the router, and a certificate for one client:

/certificate
add name=ca common-name="Example Root CA" days-valid=3650 \
    key-usage=key-cert-sign,crl-sign
sign ca ca-crl-host=192.168.88.1
add name=router common-name=router.example.com \
    subject-alt-name=DNS:router.example.com,IP:192.168.88.1 \
    key-usage=digital-signature,key-encipherment,tls-server
sign router ca=ca
add name=client1 common-name=client1 key-usage=tls-client
sign client1 ca=ca

The ca-crl-host parameter makes the authority publish a certificate revocation list. The router serves the list over HTTP at this address, and every certificate the authority signs carries the link to it. The www service of the router serves the list on TCP port 80: keep the service enabled and reachable for the devices that check the list.

Check the result:

[admin@MikroTik] > /certificate/print where name~"ca|router|client1"
Flags: K - PRIVATE-KEY; L - CRL; A - AUTHORITY; I - ISSUED; T - TRUSTED
Columns: NAME, TRUST-STORE, COMMON-NAME, SUBJECT-ALT-NAME
#       NAME     TRUST-STORE  COMMON-NAME         SUBJECT-ALT-NAME
1 KLA T ca       all          Example Root CA
2 K  I  router   all          router.example.com  DNS:router.example.com
                                                  IP:192.168.88.1
3 K  I  client1  all          client1

The authority has the flags K (the private key is on the router), L (it publishes a revocation list), A (authority) and T (trusted). RouterOS trusts a self-signed authority it created. The signed certificates have the flag I (issued) and are not trusted as authorities.

A template without key-size and days-valid gets a 2048-bit RSA key and is valid for 365 days. For an elliptic curve key, set key-size to a curve name, for example key-size=prime256v1.

WARNING

When you remove the authority certificate, RouterOS also removes all certificates it issued.

Assign a certificate to a service

Services take the certificate by name. Enable the HTTPS service of the router with the server certificate:

/ip/service
set www-ssl certificate=router disabled=no

Check that the service has the certificate:

[admin@MikroTik] > /ip/service/print where name=www-ssl
Columns: NAME, PORT, PROTO, CERTIFICATE, VRF, MAX-SESSIONS
# NAME     PORT  PROTO  CERTIFICATE  VRF   MAX-SESSIONS
0 www-ssl   443  tcp    router       main            20

Other services refer to certificates in the same way. For browser access to the router, see WebFig.

Export certificates

Other devices need the certificate of the authority to verify the router, and a client needs its own certificate with the private key. Export the authority certificate without its key, and the client certificate with its key in a PKCS12 file:

/certificate
export-certificate ca file-name=example-ca
export-certificate client1 type=pkcs12 file-name=client1 \
    export-passphrase=Use-a-long-passphrase

The files appear in the file list:

[admin@MikroTik] > /file/print where name~"example-ca|client1"
Columns: NAME, TYPE, SIZE, LAST-MODIFIED
# NAME            TYPE       SIZE  LAST-MODIFIED
1 client1.p12     .p12 file  3316  2026-11-16 09:09:18
2 example-ca.crt  .crt file  1155  2026-11-16 09:09:18
  • Without export-passphrase, the command exports only the certificate, as a PEM file with the .crt extension. The private key stays on the router.
  • With export-passphrase and the default type=pem, the command also writes the private key to a .key file, encrypted with the passphrase.
  • With type=pkcs12, the command writes one .p12 file with the certificate, its private key and the certificate of the authority, encrypted with the passphrase (AES-256).
  • Without file-name, the files are named cert_export_<certificate name>.

The export-certificate command requires the sensitive user policy. Download the files with one of the methods in Files, and delete them from the router afterwards.

Trust a certificate authority

A device verifies a certificate only when it trusts the authority that signed it. On the second device, a download from the router with certificate checking fails with no trusted CA certificate found until the authority is imported.

Upload example-ca.crt to the second device and import it:

/certificate

     certificates-imported: 1
     private-keys-imported: 0
            files-imported: 0
       decryption-failures: 0
  keys-with-no-certificate: 0

The import deletes the file. The certificate is in the store with the T (trusted) flag:

[admin@MikroTik] > /certificate/print where name=example-ca
Flags: L - CRL; T - TRUSTED
Columns: NAME, TRUST-STORE, COMMON-NAME
#    NAME        TRUST-STORE  COMMON-NAME
0 LT example-ca  all          Example Root CA

The device has to resolve the name of the router. When no DNS server knows the name, add a static entry:

/ip/dns/static
add name=router.example.com address=192.168.88.1

Check that the device now verifies the router. The download succeeds only when the authority is trusted and the name in the URL is in the certificate:

/tool/fetch url=https://router.example.com/ output=none \
    check-certificate=yes

  status: connecting

      status: finished
        code: 200
  downloaded: 1KiB
       total: 1KiB
    duration: 1s

A URL with a name that is not in the certificate fails with name verification failed.

Limit the trust to some services

An imported certificate is trusted by all services. The trust-store property limits it to the listed services, and trusted=no removes the trust. Let only the fetch and www services use the authority:

/certificate
set example-ca trust-store=fetch,www

[admin@MikroTik] > /certificate/print where name=example-ca
Flags: L - CRL; T - TRUSTED
Columns: NAME, TRUST-STORE, COMMON-NAME
#    NAME        TRUST-STORE  COMMON-NAME
0 LT example-ca  fetch        Example Root CA
                 www

A service that is not in the list rejects certificates signed by this authority.

When you import a certificate that is not an authority, add trusted=no to the import command.

Paste a certificate

A certificate in PEM format can be pasted into the command line instead of uploaded as a file. Put the whole text, with its line breaks, in quotes after pem=:

/certificate
add name=example-ca pem="-----BEGIN CERTIFICATE-----
MIIDKTCCAhGgAwIBAgIIYSWvMzKnLtQwDQYJKoZIhvcNAQELBQAwGjEYMBYGA1UE
...
+Aw0thQcxQIt2pwFk4LLhEQODijRmWjMPrjujInd9bMmzVJoBDeTZtCV39zv
-----END CERTIFICATE-----"

The example shows only the first and the last line of the certificate, with ... for the lines between them. Paste your own certificate with all its lines. Without the line breaks the command fails with bad PEM data.

Import a certificate with its private key

A PKCS12 file holds a certificate, its key and the authority. Upload client1.p12 to the device and import it with the passphrase it was exported with:

/certificate

    passphrase=Use-a-long-passphrase trusted=no
     certificates-imported: 1
     private-keys-imported: 1
            files-imported: 1
       decryption-failures: 0
  keys-with-no-certificate: 0

The certificate has the K flag, so the device can use it to identify itself:

[admin@MikroTik] > /certificate/print where name~"client1|example"
Flags: K - PRIVATE-KEY; L - CRL; T - TRUSTED
Columns: NAME, TRUST-STORE, COMMON-NAME
#     NAME        TRUST-STORE  COMMON-NAME
1  LT example-ca  all          Example Root CA
2 K   client1     all          client1

For a certificate and a key in separate PEM files, import the certificate first and the key file second. The key is added to the certificate it belongs to. An encrypted key needs the passphrase parameter.

The pem= parameter accepts keys too, and one string can hold a certificate followed by its key. The /certificate/import command accepts an encrypted key together with passphrase. The /certificate/add command accepts only an unencrypted key.

To keep an imported private key on the device, add no-key-export=yes to the import command. An export of this certificate with a passphrase then fails with Private key export is disallowed for this entry!.

Request a certificate from another authority

When the authority is outside the device, the device creates the key and a certificate request, and the authority signs the request. The private key stays with the device.

Create a template and the request on the device that needs the certificate:

/certificate
add name=office common-name=office.example.com \
    subject-alt-name=DNS:office.example.com \
    key-usage=digital-signature,key-encipherment,tls-server
create-certificate-request template=office \
    key-passphrase=Use-a-long-passphrase

The command writes two files: the request and the private key, encrypted with key-passphrase:

[admin@MikroTik] > /file/print where name~"certificate-request"
Columns: NAME, TYPE, SIZE, LAST-MODIFIED
# NAME                         TYPE       SIZE  LAST-MODIFIED
0 certificate-request_key.pem  .pem file  1834  2026-11-16 09:11:20
1 certificate-request.pem      .pem file  1017  2026-11-16 09:11:20

Send certificate-request.pem to the authority. Keep the key file on the device.

When the authority is a RouterOS router, upload the request to it, here as office.csr, and sign it:

/certificate
sign-certificate-request file-name=office.csr ca=ca

The new certificate gets the common name of the request as its name:

[admin@MikroTik] > /certificate/print where name~"office"
Flags: I - ISSUED
Columns: NAME, TRUST-STORE, COMMON-NAME, SUBJECT-ALT-NAME
#   NAME                TRUST-STORE  COMMON-NAME         SUBJECT-ALT-NAME
1 I office.example.com  all          office.example.com  DNS:office.example.com

Export it:

/certificate
export-certificate office.example.com file-name=office

Back on the requesting device, upload the signed certificate, here office.crt. Import the certificate, then the key file, and remove the template:

/certificate

    passphrase=Use-a-long-passphrase
remove office

The certificate has its private key:

[admin@MikroTik] > /certificate/print where name~"office"
Flags: K - PRIVATE-KEY
Columns: NAME, TRUST-STORE, COMMON-NAME, SUBJECT-ALT-NAME
#   NAME         TRUST-STORE  COMMON-NAME         SUBJECT-ALT-NAME
0 K office-cert  all          office.example.com  DNS:office.example.com

Revoke a certificate and check revocation

An authority with ca-crl-host lists the certificates it has revoked. Other devices use the list only when revocation checking is on.

On the client, turn the checking on and download the lists:

/certificate/settings
set crl-use=yes crl-download=yes
/certificate/crl
download

RouterOS adds the list of an authority dynamically when the imported authority certificate contains a link to it. With crl-use=yes, a connection fails with crl not found as long as the list of the authority is not downloaded. The crl-download setting lets the device download and update the lists by itself, and the download command fetches them immediately.

On the authority, revoke the certificate:

/certificate
issued-revoke router

The certificate now has the R (revoked) flag:

[admin@MikroTik] > /certificate/print where name=router
Flags: K - PRIVATE-KEY; R - REVOKED
Columns: NAME, TRUST-STORE, COMMON-NAME, SUBJECT-ALT-NAME
#    NAME    TRUST-STORE  COMMON-NAME         SUBJECT-ALT-NAME
0 KR router  all          router.example.com  DNS:router.example.com
                                              IP:192.168.88.1

On the client, download the updated list. The REVOKED column shows how many certificates the list contains:

/certificate/crl
download

[admin@MikroTik] > /certificate/crl/print
Flags: D - DYNAMIC
Columns: CERT, TRUST-STORE, LAST-UPDATE, NUM, REVOKED
#   CERT        TRUST-STORE  LAST-UPDATE          NUM  REVOKED
0 D example-ca  all          2026-11-16 14:07:24    1        1

Check that the client now refuses the revoked certificate:

/tool/fetch url=https://router.example.com/ output=none \
    check-certificate=yes

  status: connecting

      status: failed
  downloaded: 0KiB

failure: SSL: ssl: cert is revoked by crl - "CN=router.example.com" (6) (/tool/fetch; line 1)

The HTTPS service of the authority still uses the revoked certificate. Sign a new certificate and give it to the service:

/certificate
add name=router2 common-name=router.example.com \
    subject-alt-name=DNS:router.example.com,IP:192.168.88.1 \
    key-usage=digital-signature,key-encipherment,tls-server
sign router2 ca=ca
/ip/service
set www-ssl certificate=router2

The client accepts the new certificate:

[admin@MikroTik] > /tool/fetch url=https://router.example.com/ output=none \
    check-certificate=yes
  status: connecting

      status: finished
        code: 200
  downloaded: 1KiB
       total: 1KiB
    duration: 1s

A certificate issued by an authority that publishes a revocation list cannot be removed from the authority, only revoked.

Enrol certificates with SCEP

With the Simple Certificate Enrollment Protocol (SCEP), a device creates its key, sends the request to the authority over HTTP and receives the signed certificate without file transfers. A RouterOS router can be the SCEP server and the SCEP client.

On the authority, add a SCEP server for the authority certificate:

/certificate/scep-server
add ca-cert=ca path=/scep/example days-valid=365

Clients reach the server at http://192.168.88.1/scep/example. The SCEP server also uses the www service on TCP port 80. If the service is disabled, the certificate on the client shows the requesting-ca-capabilities-failed status.

Generate a one-time password for the device you enrol. A request with a valid password is signed without confirmation:

[admin@MikroTik] > /certificate/scep-server/otp/generate minutes-valid=30
  password: a0209edb24f942297d5e

On the client, create a template and enrol it with the password:

/certificate
add name=branch common-name=branch.example.com \
    key-usage=digital-signature,key-encipherment,tls-client
add-scep template=branch challenge-password=a0209edb24f942297d5e \
    scep-url=http://192.168.88.1/scep/example

Check that the client has the certificate with its key:

[admin@MikroTik] > /certificate/print where name=branch
Flags: K - PRIVATE-KEY; T - TRUSTED
Columns: NAME, TRUST-STORE, COMMON-NAME
#    NAME    TRUST-STORE  COMMON-NAME
0 KT branch  all          branch.example.com

On the authority, the request is listed as authorized:

[admin@MikroTik] > /certificate/scep-server/requests/print
Columns: AUTHORITY, STATUS, COMMON-NAME, CREATED
#  AUTHORITY  STATUS      COMMON-NAME         CREATED
0  ca         authorized  branch.example.com  2026-11-16 09:12:37

A request without a password stays in the pending status. Approve it on the authority with /certificate/scep-server/requests/grant. The client collects the certificate the next time it asks the server.

ACME client

The ACME client gets a certificate from a public certificate authority and renews it automatically. Browsers and other devices trust such a certificate without importing anything.

Let's Encrypt certificate

The add-acme command requests the certificate. Without directory-url, the client uses Let's Encrypt.

For the IP Cloud name of the router, the client proves the ownership of the name through DNS, so no port has to be open from the internet. Enable the IP Cloud DDNS service first, then request the certificate:

/certificate
add-acme name=cloud-name domain-names=[/ip/cloud/get dns-name]

The certificate appears in /certificate with the flags K and a (ACME managed). Check its status. When the certificate is issued, the status shows the time of the next renewal:

[admin@MikroTik] > :put [/certificate/get cloud-name acme-status]
next update at 2027.01.27-07:09:16

The command also accepts the wildcard of the IP Cloud name, *.<name>.sn.mynetname.net. The certificate is then valid for every name under the IP Cloud name.

The client renews the certificate when 80 % of its validity time has passed. To renew it immediately, use /certificate/acme-renew cloud-name.

Certificate for your own domain name

For a name that is not an IP Cloud name, the authority validates the name over HTTP. Three conditions have to be met:

  • The name resolves to the public address of the router.
  • The www service is enabled on TCP port 80.
  • TCP port 80 of the router is reachable from the internet.

Request the certificate:

/certificate
add-acme name=public-name domain-names=router.example.com

Check the status in the same way as for the IP Cloud name. When the validation fails, the entry stays in /certificate with the error as its comment, for example http-01 challenge validation failed. Remove the entry, correct the cause and run add-acme again.

WARNING

An open TCP port 80 also makes the WebFig login page of the router reachable from the internet. When the IP Cloud name is enough, use it: it needs no open port.

Built-in trust store authorities

RouterOS contains a list of public root certificate authorities. Services use the list to verify public servers without importing a certificate, for example Fetch with check-certificate=yes or DNS over HTTPS.

The authorities are listed in /certificate/builtin.

Settings

The builtin-trust-store setting in /certificate/settings selects the services that use the list:

  • default - the services in the read-only current-defaults setting: fetch, mqtt, email, netwatch, container, lora, wiliot, dns, www and reverse-proxy.
  • A list of services, for example fetch,dns - only these services.
  • untrusted - no service. Every authority then has to be imported.

Technical details

  • The sign command keeps the name of the template.
  • An imported certificate is trusted unless the import command has trusted=no.
  • The import command reports how many certificates and private keys it imported.
  • A certificate with a weak RSA public exponent (7 or lower) continues to work. It is marked with the comment key uses insecure RSA public exponent! in /certificate/print. Replace such a certificate with one that has a stronger key.
  • Certificate checks compare the validity dates with the clock of the device. Set the clock, for example with the NTP client, before you rely on them.

For all properties and commands, see /certificate, /certificate/settings, /certificate/crl, /certificate/builtin and /certificate/scep-server in the CLI reference.

Dot1X

Dot1X is the IEEE 802.1X implementation of RouterOS: authenticate the devices on Ethernet ports with RADIUS, assign VLANs, use guest, reject and server-fail VLANs, authenticate by MAC address, add dynamic switch...

Dot1X

Dot1X is the RouterOS implementation of IEEE 802.1X, port-based network access control. A device must authenticate before the Ethernet port that it is connected to passes its traffic. The authentication uses EAP over LAN (EAPOL). 802.1X has three roles:

  • The supplicant is the device that connects, the client. RouterOS can be a supplicant: /interface/dot1x/client.
  • The authenticator is the switch or router with the port. RouterOS can be an authenticator: /interface/dot1x/server.
  • The authentication server is a RADIUS server that checks the credentials. RouterOS can be one with the User Manager package.

[gambar: A supplicant connects to a port of the authenticator, and the authenticator asks the RADIUS server]

NOTE

Dot1X is not available on SMIPS devices (hAP lite, hAP lite TC and hAP mini).

Authenticate the devices on a port

Add the RADIUS server for the dot1x service, and add the port to the Dot1X server:

/radius/add address=10.1.2.3 secret=Radius-Secret-1 service=dot1x
/interface/dot1x/server/add interface=ether2
  • The RADIUS server does not have to be in the same network as the authenticator, but the authenticator must reach it. When the path to the server is not trusted, use RadSec: see RADIUS.
  • interface is an Ethernet interface or an interface list. For many ports, use a list (the example follows).
  • From now on the port passes only EAPOL frames until a device authenticates. Do not add the port that you manage the router through.

One server entry with an interface list covers several ports:

/interface/list/add name=dot1x-ports
/interface/list/member/add list=dot1x-ports interface=ether3
/interface/list/member/add list=dot1x-ports interface=ether4
/interface/dot1x/server/add interface=dot1x-ports

/interface/dot1x/server/state shows the state of each port:

[admin@MikroTik] > /interface/dot1x/server/state/print
Columns: INTERFACE, STATUS
#  INTERFACE  STATUS       
0  ether2     un-authorized

When a device authenticates, the state changes to authorized and the device is listed in /interface/dot1x/server/active:

[admin@MikroTik] > /interface/dot1x/server/active/print detail
0  interface=ether2 username="tst" client-mac=52:54:0B:7D:02:01
   session-id="00002086" auth-info="dot1x"
State Meaning
authorized The port passes traffic.
un-authorized No device is authenticated. The port passes only EAPOL frames.
rejected-holding The RADIUS server rejected the device.
iface-down The interface is not running.

An authorized port accepts all traffic that it receives. If the port is connected to a shared medium with several devices, all of them have access after one of them authenticates. Dynamic switch rules can limit the port to the MAC address of the authenticated device.

While the port waits for authentication, its bridge port is inactive and both /interface and /interface/bridge/port show the comment blocked by dot1x. The comment is not shown while the link is down, the same as for a port that spanning tree blocks.

Assign a VLAN from RADIUS

The RADIUS server can put the port of a device into a VLAN. The port must be in a bridge with VLAN filtering. On a router that already has a bridge, read Bridge VLAN table before you turn VLAN filtering on: a wrong order of the steps can cut your access to the router.

/interface/bridge/add name=bridge1 vlan-filtering=yes
/interface/bridge/port/add bridge=bridge1 interface=ether1
/interface/bridge/port/add bridge=bridge1 interface=ether2
/interface/bridge/vlan/add bridge=bridge1 tagged=ether1 vlan-ids=12

ether1 is the uplink and carries VLAN 12 tagged.

The server sends the VLAN in three attributes of the Access-Accept. In the users file of FreeRADIUS:

vlanuser  Cleartext-Password := "Example-pass-1"
          Tunnel-Type = VLAN,
          Tunnel-Medium-Type = IEEE-802,
          Tunnel-Private-Group-Id = "12"

With the radius,debug log topics, the attributes are in the log of the authenticator:

/system/logging/add topics=radius,debug action=memory

09:51:45 radius,debug,packet received Access-Accept with id 64 from 10.1.2.3:1812
09:51:45 radius,debug,packet     Tunnel-Type = 13 
09:51:45 radius,debug,packet     Tunnel-Medium-Type = 6 
09:51:45 radius,debug,packet     Tunnel-Private-Group-ID = "12" 
(..)
09:51:45 radius,debug,packet     User-Name = "dot1x-user"

After the authentication the session has the VLAN ID:

[admin@MikroTik] > /interface/dot1x/server/active/print detail
0  interface=ether2 username="vlanuser" client-mac=52:54:0B:7D:02:01
   session-id="0f002086" vlan-id=12 auth-info="dot1x"

The bridge adds the port to VLAN 12 as an untagged port. /interface/bridge/vlan/print shows this in a dynamic entry with the comment added by pvid.

  • Only devices with hardware offloaded VLAN filtering do this in the switch chip.
  • A server that authenticates with EAP-PEAP or EAP-TTLS must send the attributes in the outer reply. In FreeRADIUS this is use_tunneled_reply = yes.

Put devices that fail into a VLAN

A port can get a VLAN when the authentication does not succeed. A typical use is a guest network. All three settings need a bridge with VLAN filtering, and all are off by default.

/interface/dot1x/server/set [find interface=ether2] \
    guest-vlan-id=50 reject-vlan-id=30 server-fail-vlan-id=40
Setting The port gets the VLAN when auth-info of the session
guest-vlan-id The device does not answer EAP requests, because it has no supplicant. The VLAN is set after three retrans-timeout periods. dot1x (guest vlan)
reject-vlan-id The RADIUS server answers with Access-Reject. dot1x (reject vlan)
server-fail-vlan-id The RADIUS server does not answer. dot1x (server fail vlan)

In each case the state of the port is authorized and the session shows the VLAN:

[admin@MikroTik] > /interface/dot1x/server/active/print detail
0  interface=ether2 username="vlanuser" client-mac=52:54:0B:7D:02:01
   session-id="11002086" vlan-id=30 auth-info="dot1x (reject vlan)"
  • With the default retrans-timeout of 30 seconds, a device without a supplicant gets the guest VLAN after 90 seconds.
  • A device of a visitor that has a supplicant gets an Access-Reject and not the guest VLAN. To give all visitors the same network, set reject-vlan-id to the same VLAN as guest-vlan-id.
  • Add the VLANs to the uplink port as tagged in the VLAN table of the bridge.
  • When a supplicant starts on a port in the guest VLAN and authenticates, the port leaves the guest VLAN.
  • reject-vlan-id is not used when the RADIUS server does not answer. Without server-fail-vlan-id, the authentication then times out and the port stays closed.

Authenticate devices by MAC address

Printers, cameras and other devices without a supplicant can be authenticated by their MAC address. The authenticator asks the RADIUS server with the MAC address of the device as the user name:

/interface/dot1x/server/set [find interface=ether2] \
    auth-types=mac-auth

In the users file of FreeRADIUS, an entry for a device with the default settings accepts the MAC address without a password:

52:54:0B:7D:02:01  Auth-Type := Accept
  • The authenticator learns the MAC address from a frame that the device sends. A device that sends nothing is not authenticated.
  • With mac-auth-mode=mac-as-username (the default) the password of the request is empty. With mac-as-username-and-password the MAC address is also the password.
  • radius-mac-format sets how the MAC address is written. The default is XX:XX:XX:XX:XX:XX.
  • The RADIUS server can send a VLAN in the same way as for a Dot1X device.

The session has auth-info="mac-auth":

[admin@MikroTik] > /interface/dot1x/server/active/print detail
0  interface=ether2 username="52:54:0B:7D:02:01" client-mac=52:54:0B:7D:02:01
   session-id="17002086" vlan-id=12 auth-info="mac-auth"

With both types, the authenticator tries Dot1X first. If the device does not answer in three retrans-timeout periods, it tries the MAC address:

/interface/dot1x/server/set [find interface=ether2] \
    auth-types=dot1x,mac-auth

A MAC address is easy to copy from another device. Give MAC-authenticated devices only the access that they need, for example their own VLAN.

Re-authenticate and send accounting

  • reauth-period makes the authenticator authenticate each device again after this time. A Dot1X device gets a new EAP request, and a MAC-authenticated device is checked with the RADIUS server again. By default devices are not authenticated again.
  • accounting=yes (the default) sends the start and the end of each session to the RADIUS server. interim-update also sends an update at this interval.
/interface/dot1x/server/set [find interface=ether2] \
    reauth-period=1h interim-update=5m

Add switch rules for a device

The RADIUS server can limit what an authenticated device can reach. It sends rules in the Mikrotik-Switching-Filter attribute, and the authenticator adds them as dynamic switch rules on the port of the device. The rules exist while the session is active and the interface is running.

WARNING

Dynamic switch rules need a switch chip with rule support: MikroTik devices with a Marvell Prestera switch chip, and the QCA8337, Atheros8327 and Atheros8316 switch chips. CRS1xx and CRS2xx series switches do not support them. Each device has a maximum number of rules: see MikroTik devices with Marvell Prestera switch and the switch chip table.

The format of the attribute:

  • The conditions are mac-protocol, src-mac-address, src-address (IPv4 address and mask), dst-address (IPv4 address and mask), protocol (IPv4), src-port and dst-port.
  • mac-protocol and protocol take a decimal or a hexadecimal number, for example protocol 17 or protocol 0x11.
  • src-port and dst-port take one port or a range, for example src-port 10 or src-port 10-20.
  • src-mac-address takes the format xx:xx:xx:xx:xx:xx or xxxxxxxxxxxx. The word none makes a rule without a source MAC address: src-mac-address none.
  • The authenticator sets switch and ports of each rule. It also sets src-mac-address to the address of the device, unless the attribute sets it.
  • A rule ends with action drop or action allow. Without an action, the rule allows.
  • Several rules are separated with commas.

Drop ARP frames (EtherType 0x0806, decimal 2054):

Mikrotik-Switching-Filter = "mac-protocol 2054 action drop"

/interface/ethernet/switch/rule/print
Flags: X - disabled, I - invalid, D - dynamic 
 0  D ;;; dot1x dynamic
      switch=switch1 ports=ether1 src-mac-address=CC:2D:E0:11:22:33/FF:FF:FF:FF:FF:FF mac-protocol=arp copy-to-cpu=no redirect-to-cpu=no mirror=no new-dst-ports=""

Allow UDP (IP protocol 17) to the destination port 100 and drop everything else:

Mikrotik-Switching-Filter = "protocol 17 dst-port 100 action allow, action drop"

/interface/ethernet/switch/rule/print
Flags: X - disabled, I - invalid, D - dynamic 
 0  D ;;; dot1x dynamic
      switch=switch1 ports=ether1 src-mac-address=CC:2D:E0:11:22:33/FF:FF:FF:FF:FF:FF protocol=udp dst-port=100 copy-to-cpu=no redirect-to-cpu=no mirror=no 

 1  D ;;; dot1x dynamic
      switch=switch1 ports=ether1 src-mac-address=CC:2D:E0:11:22:33/FF:FF:FF:FF:FF:FF copy-to-cpu=no redirect-to-cpu=no mirror=no new-dst-ports=""

Allow only the MAC address of the authenticated device and drop all other source addresses:

Mikrotik-Switching-Filter = "action allow, src-mac-address none action drop"

/interface/ethernet/switch/rule/print 
Flags: X - disabled, I - invalid; D - dynamic 
 0  D ;;; dot1x dynamic
      switch=switch1 ports=ether1 src-mac-address=CC:2D:E0:01:6D:EB/FF:FF:FF:FF:FF:FF copy-to-cpu=no redirect-to-cpu=no mirror=no 

 1  D ;;; dot1x dynamic
      switch=switch1 ports=ether1 copy-to-cpu=no redirect-to-cpu=no mirror=no new-dst-ports=""

Example

The device on ether2 can reach only the network 192.168.50.0/24 on the UDP port 50. The switch rules work on hardware offloaded bridge ports, so check the H flag first:

/interface/bridge/port/print
Flags: X - disabled, I - inactive, D - dynamic, H - hw-offload 
 #     INTERFACE                   BRIDGE                   HW  PVID PRIORITY  PATH-COST INTERNAL-PATH-COST    HORIZON
 0   H ether1                      bridge1                  yes    1     0x80         10                 10       none
 1   H ether2                      bridge1                  yes    1     0x80         10                 10       none
 2   H ether12                     bridge1                  yes    1     0x80         10                 10       none

The RADIUS server sends the attribute in the Access-Accept:

02:35:38 radius,debug,packet received Access-Accept with id 121 from 10.1.2.3:1812 
(..)
02:35:38 radius,debug,packet     MT-Switching-Filter = "mac-protocol 2048 dst-address 192.168.50.0/24 dst-port 50 protocol 17 action allow,action drop"

The authenticator adds two rules:

/interface/ethernet/switch/rule/print 
Flags: X - disabled, I - invalid; D - dynamic 
 0  D ;;; dot1x dynamic
      switch=switch1 ports=ether2 src-mac-address=CC:2D:E0:11:22:33/FF:FF:FF:FF:FF:FF mac-protocol=ip dst-address=192.168.50.0/24 protocol=udp dst-port=50 copy-to-cpu=no redirect-to-cpu=no mirror=no 

 1  D ;;; dot1x dynamic
      switch=switch1 ports=ether2 src-mac-address=CC:2D:E0:11:22:33/FF:FF:FF:FF:FF:FF copy-to-cpu=no redirect-to-cpu=no mirror=no new-dst-ports=""

Connect a RouterOS port as a supplicant

A router or switch can authenticate its own port to an 802.1X network. The methods are EAP-MSCHAPv2, EAP-PEAP (PEAPv0 with EAP-MSCHAPv2), EAP-TTLS and EAP-TLS.

With a name and a password:

/interface/dot1x/client/add interface=ether2 \
    eap-methods=eap-peap identity=tst password=Example-pass-1
  • EAP-PEAP, EAP-TTLS and EAP-TLS check the certificate of the RADIUS server. Import the certificate authority that signed it as a trusted certificate first. Without it the client stays in authenticating, and the log has no trusted CA certificate found.
  • EAP-MSCHAPv2 needs no certificate, but it does not check the server.
  • anon-identity is the name that EAP-PEAP and EAP-TTLS show outside the encrypted tunnel. Without it, identity is used. With it, the authenticator lists the session with the outer name.
  • eap-methods can list several methods.

EAP-TLS uses a client certificate in place of the password. Import the certificate with its private key, and name it in certificate:

/interface/dot1x/client/add interface=ether2 eap-methods=eap-tls \
    identity=tst certificate=dot1x-client

[admin@MikroTik] > /interface/dot1x/client/print detail
0  ;;; d1x
   interface=ether2 eap-methods=eap-tls identity="tst" anon-identity=""
   certificate=dot1x-client status="authenticated"
Status Meaning
authenticated The authentication succeeded.
authenticating The client reached the authenticator and the authentication is in progress.
rejected The server refused the client.
disabled The client is disabled.
interface is down The interface is not running.
error An internal error.

Check and troubleshoot

What you see What to check
The port stays un-authorized. The device has no supplicant. For such devices, use guest-vlan-id or auth-types=dot1x,mac-auth.
The port is rejected-holding, the client is rejected. The RADIUS server refused the name, the password or the certificate. Check the log of the server.
The client stays authenticating, and its log has no trusted CA certificate found. Import the certificate authority of the RADIUS server on the client as a trusted certificate.
The client stays authenticating and the RADIUS server gets no request. The authenticator cannot reach the server. Check the /radius entry: it needs service=dot1x, the address and the secret. See RADIUS.
The device is authenticated but not in the VLAN. The bridge needs vlan-filtering=yes, and the Access-Accept must have the three tunnel attributes. Check them with the radius,debug log topics.

Keep RSTP or MSTP enabled on a bridge that has Dot1X ports: without a spanning tree protocol, EAP packets from the device may not be accepted. A bridge has protocol-mode=rstp by default. For a port that must not send BPDUs or must ignore received BPDUs, set edge=yes on the bridge port.
