Overview

TG-BT5-OUT is a new addition to our MikroTik equipment. It is a Bluetooth tag (a very small gadget) that can be attached to other equipment or other belonging. Bluetooth tags play a big role in IoT topologies, where Bluetooth is used to broadcast the data over short distances. Once installed and configured, the tag will broadcast advertising packets in iBeacon, Eddystone, or MikroTik telemetry (default packet format) to the gateway (for example, KNOT). Gateway, on the other hand, pushes the advertising packet payload to the remote server utilizing MQTT or HTTP protocols.

Tag modes

When the product arrives from manufacturing it is set into factory sleep mode. In this mode, all components are shut-down as much as possible and MCU is put into the deepest sleep state. The current draw is reduced to a minimum, so this is the preferred mode to use when the tag is stored and/or not in use. To exit this mode put a magnet to the tag's edge (where the switch icon is) and hold it for 3-10 seconds until LED turns off. After that, the tags exits sleep mode and enters advertising mode.

In the Advertising mode, the tag will broadcast Bluetooth advertising packets. By default, MikroTik's advertisement packets are sent once every 5 seconds. This can be changed in the Configuration mode.

Configuration mode can be entered only from advertising mode by applying a magnet to the same switch icon as in the exiting factory sleep procedure. After applying a magnet for 5-10 seconds LED will turn off and the tag enters configuration mode. If you apply a magnet for longer than 15 seconds or won't connect to the tag with the configuration app, it will go back into advertising mode.

TG-LR82 / TG-LR92 User Manual

Quickstart Guide

  • Register device on LoRaWAN network server. Use tg-lrx2-2.0-ul-dec.js payload decoder script if device model not supported.

  • Activate the device: new devices start in SHUTDOWN. Hold the magnet near the switch for about 1.5 s to enter digit 2, then remove it. The device confirms the command with short LED blinks and restarts in RUN mode.

  • Wait for network join. Default profile 0 sends current-state and device-orientation every 5 minutes. The first uplink after join can also contain version, serial-number, cfg-state, and dev-health frames.

  • Decode the first uplink to verify temperature, humidity, orientation, battery, and device identity data. Use downlink commands as the primary method for configuration and management; see Device Commands and Command Encoding. Magnet switch commands remain available for activation and local operations such as profile or region selection; see Magnet Switch.

LoRaWAN

Device supports Class A and B, and can operate in two frequency bands: BAND_1GHz and BAND_2GHz. User can configure periodic link check, MAC time synchronization (DeviceTimeReq) and network ADR.

Join Procedure

Once activated (RUN) device will attempt to join network. Device sends Join-Request on primary band and if Join-Accept is not received it will wait back-off interval and send next Join-Request on secondary band if enabled, otherwise primary-band again.

NOTE

Join attempt interval depends on time on air for last Join-Request and total join time. See 1 section 7. If last join request used slower data rate - expect longer interval.

Join configuration commands: lora primary-band, lora second-band, lora join-cfg. See Command Encoding on how to convert text commands to binary encoding for downlink.

Link Check

Link check lets the end device verify that the network is still reachable. Most uplinks can be non-confirmed, so they do not prove that the network received them. Use periodic link check or confirmed uplinks when the device must detect a lost network.

Link check can be configured specifically for each band using lora link-chk. If link check fails, the device leaves the network and restarts the join procedure. A failed confirmed uplink has the same effect.

NOTE

Any network downlink will restart link check timer to prevent unnecessary LinkCheckReq.

Time Synchronization

Time synchronization gives stored events absolute timestamps instead of device uptime. Events and telemetry can be stored locally and sent later, so absolute time lets the application know when an event actually occurred. This is useful when the device is outside network coverage and reports the collected data after it returns to coverage.

Device supports optional time synchronization using DeviceTimeReq MAC command. See command lora clk-sync for configuration parameters or to request immediate synchronization.

Class B

Device supports Class B operation. Class B operation can be either manually requested using lora class or device can be configured to automatically switch to class B on network join using lora cfg-class-b.

ADR Configuration

It is possible to disable network ADR and set fixed data rate using lora adr-cfg.

WARNING

In FW 2.0.1, ADR changes made while the device is joined may not take effect until the device rejoins or restarts (LORA-281). With network ADR disabled, only DR0 works as a fixed data rate (LORA-282). Reset the device after changing ADR; when network ADR is disabled, use DR0.

Leaving Network

In case of Link Check or confirmed uplink failure device leaves network and restarts join procedure.

Credentials

Device has factory configured default credentials that come with each device: DevEUI, JoinEUI, AppKey.

DevEUI and JoinEUI are IEEE 64-bit EUI (2) written MSB first. On air byte order is LSB first. See 1 section 6.2.5.

AppKey is 16 byte AES128 encryption key and is written as stored in device memory. AppKey must be kept secret!

To change JoinEUI and AppKey use commands: lora join-eui, lora net-key and lora cred. Commands lora join-eui and lora net-key can be issued in any order and multiple times to write new pending join credentials.

Once new pending credentials are written “lora cred 600,1” or “app reset 0” can be executed to attempt join with new credentials. If new credentials are not confirmed by join accept device will revert to previous. See LORA-275, LORA-276 for known issues!

Example sequence where JoinEUI and AppKey are written and join is attempted:

lora join-eui 87904163,0x00,0x16,0xC0,0x01,0xFF,0xFE,0x00,0x00
lora net-key 87904163,0x00,0x01,0x02,0x03,0x04,0x05,0x06,0x07,0x08,0x09,0x0A,0x0B,0x0C,0x0D,0x0E,0x0F
lora cred 600
app reset 0
// device reboots and attempts join using new credentials with 600s timeout

JoinEUI from previous example can be copy/pasted as is 00 16 C0 01 FF FE 00 00 to register new device. lora join-eui parameters are MSB first.

WARNING

Executing lora cred <confirm-timeout-s>,87904163 will force confirm credentials without verification join attempt! You may lose access to device!

Uplink Messages

Each LoRaWAN uplink can carry one or more pending Data Frames. Frames are added in ascending frame-ID order. The first frame-type delta is encoded in the FPort field; additional type deltas are encoded at the start of FRMPayload, followed by the frame contents. The FPort value therefore depends on the first frame type and is not a fixed application port.

The device packs only frames that fit in the current payload. Frames that do not fit remain pending for the next uplink. If any packed frame is configured as confirmed, the whole uplink is sent as confirmed. A failed confirmed uplink causes the device to leave the network and restart the join procedure.

NOTE

See tg-lrx2-2.0-ul-dec.js script for frame encoding details. This script can be used as is in application server payload decoders.

Factory Defaults and Custom Configuration

The device ships with a complete factory configuration. When creating a custom configuration, send only the commands needed to change the factory values. Settings that are not changed keep their factory values. Reusing factory settings reduces both the number and size of downlink messages.

Factory profiles 1-4 also contain example rules. If a custom use case does not need those rules, remove all rules at once before adding the new ones:

data del-rule

data del-rule without a rule number removes every rule, including the factory rules. Rule numbers can then be used for the new configuration without mixing it with the factory examples.

To return to a known test state, restore the factory configuration:

app factory-reset 984651411,,2500

This returns the device to the exact factory state, including the factory rules, and resets the join nonces. The device must join the network again, and custom credentials or settings that were written after production are lost. Use this command when you need a repeatable baseline before experimenting with new configurations.

Configuring Sensors

Sampling Intervals

Periodic temperature, humidity and battery voltage sampling can be configured for specific use cases using data poll-cfg command. Device can sample data at a higher rate than uplink frames are sent. This gives opportunity to send average values or to perform rule based decisions. Since sampling interval influences device power consumption this can be leveraged to improve lifetime.

Frame-Triggered Sensor Refresh

data poll-cfg includes the on-ul-stale option. It is enabled by default in the factory configuration. Its intended use is to keep sensor data reasonably fresh and aligned with uplink timing when the normal polling interval is longer than the frame interval. In that configuration, frame scheduling acts as an additional sensor-polling trigger.

When on-ul-stale is enabled, scheduling current-state, device-orientation, last-temp, ema-temp, last-humid, ema-humid, or dev-health causes the device to check the age of the temperature/humidity, battery, and orientation samples. Any sensor group older than the stale timeout is flagged for a forced sample. The request is handled asynchronously by the data service and does not block frame scheduling. The check covers all three groups regardless of which fields the scheduled frame contains. For example, scheduling current-state can also refresh battery and orientation data, and scheduling dev-health can refresh temperature, humidity, and orientation.

The current stale timeout is 15 seconds. It is a fixed firmware value and is not configurable through data poll-cfg. The device uses a strict “older than” comparison, so a sample that is exactly 15 seconds old is not refreshed. A forced sample does not shift the normal periodic sampling schedule. If frames are scheduled less than 15 seconds apart, not every frame triggers a new sample.

Frame scheduling as a polling trigger can be configured without changing the normal periodic intervals:

data poll-cfg 32,3600,0,0,0,0,0,1,21600
frame set-cfg 32,300,0,0,current-state

In this example temperature/humidity have a one-hour periodic interval and battery has a six-hour interval, while current-state is scheduled every five minutes. Each scheduled frame refreshes any of the three sensor groups that is older than 15 seconds. Because all groups are checked, a frequent current-state frame can also keep battery and orientation sampling active; include this in the power budget.

Set on-ul-stale to 0 to disable frame-triggered refresh. Frames then use the most recent samples even when they are old.

WARNING

on-ul-stale is checked when the frame is scheduled, not when it is transmitted. If the uplink is delayed by the duty-cycle limit, the frame can be transmitted with sensor data older than the stale timeout. The check is not repeated while the frame is pending.

Averaging

Device also tracks average of sampled values in: temperature_ema, humidity_ema, battery_mv_ema, angle_ema. Command data ema-cfg configures exponential moving average (EMA) period and optionally can send EMA values in current-state, dev-health, device-orientation if send-ema-* is enabled.

Count parameters temp-cnt, humid-cnt, bat-cnt, orient-cnt in data ema-cfg determine coefficient a used for moving average calculation. Moving EMA is calculated based on previous value ema and new value sample as:

ema(t) = sample(t) * a + ema(t-1) * (1 - a)

To get approximate time constant t of EMA you need to use sampling intervals configured by data poll-cfg and data orient-cfg (interval) and respective count parameter (N):

t ~ (N + 1) * interval / 2

To get required count parameter value for data ema-cfg:

N ~ 2 * t / interval - 1

Example:

Temperature sampling interval th-poll-int is configured to 30s using data poll-cfg. To configure EMA with time constant t ~ 60 minutes:

temp-cnt = 2 * 3600 / 30 - 1 = 239

Assuming profile #0 is used and we don’t want to change other parameters we need to send command:

data ema-cfg 1,239
Histogram

All periodic samples are added to temperature and humidity histograms. Histograms can be used in addition to regular telemetry or simply stand alone to monitor temperature and humidity distribution. Configure bins and epoch intervals using data temp-histo-cfg, data humid-histo-cfg commands and/or enable temp-histogram, humid-histogram frames. All histogram frames contain epoch number to detect histogram counter reset. Since frame size is limited to 1B per bin, if internal bin counter value is above 255 histogram will be normalized (probability type) for uplink.

Example configuration:

data temp-histo-cfg 1,86400,0,0,1,1,-10,0,10,15,17.5,20,22.5,25.0,30
data humid-histo-cfg 1,86400,0,0,1,1,10,20,30,40,50,60,70,80,90

Activity Monitor

Device has activity monitoring service based on accelerometer. This service will automatically manage simple state machine that determines movement/activity. activity_s, high_activity_s, total_activity_s count accumulated time in each state activity_state, activity_state_etm hold state information.

Command data activity-cfg can be used to configure mode and thresholds for activity monitoring. data activity-cal can be used to automatically perform calibration for specific mode.

level1-th and level2-th units are 1/64 * 2G irrespective of other accelerometer settings (like in data acc-cfg). level2-cnt is internally computed and not user configurable. level2-cnt is always in range 7..15 and calculated as:

level2-cnt = 7 + round((1 - ((level2-th - level1-th - 1) / 61)) * 8)

Single Mode

Mode in data activity-cfg is set to single.

  • If accelerometer sample value in any axis is above level1-th device transitions from IDLE to LOW state.

  • If all samples for at least 1.3s are below level1-th device transitions from LOW to IDLE state.

NOTE

The 1.3 s LOW-to-IDLE timing applies to single-level mode. In dual mode the accelerometer and state machine use different timing; use the 5 s transitions in the Dual Mode table only for dual mode.

Example to set profile #0 single mode with threshold 0.25G:

data activity-cfg 1,1,8,63
Dual Mode

Mode in data activity-cfg is set to dual.

In dual mode LOW state has two sub states: LOW1 and LOW2 that both represent LOW. Device will report LOW state during both of these and actvity counter values are incremented as if in LOW state. Only difference is transition logic between these states.

activity_state dual mode state transitions

Current Next Condition
IDLE LOW2 sample > level1-th
LOW2 LOW1 sample < level2-th at least 5s
LOW1 LOW2 sample > level1-th
LOW2 HIGH sample > level2-th at least level2-cnt times
LOW1 IDLE sample < level1-th at least 5s
HIGH LOW1 sample < level2-th at least 5s

Example to set profile #0 dual mode with thresholds 0.25G and 0.5G:

data activity-cfg 1,2,8,16
Calibration

In addition to manually configuring level1-th and level2-th there is activity calibration functionality. Executing command data activity-cal will perform auto calibration of cal-level. level-one will calibrate level1-th and level-two will calibrate level2-th for all profiles selected in profile-mask. For dual mode you can run level-one and level-two in sequence. Calibration time is 15s. This functionality is mostly suited for periodic motion/vibration.

NOTE

It may be useful to enable LED during calibration procedure or activity monitor testing to ensure correct operation.

Example to calibrate profile #0 with single level activity monitor:

  2. Send commands:

  2. Test motion detection. During LOW activity device will blink LED 3x/1s.

  3. If calibration results are acceptable send command to disable LED:

  1. Place device in environment with periodic motion/activity for level 1 calibration.

Impact and Free fall

Command data acc-cfg can be used to configure device accelerometer for basic impact and free-fall detection. Frames: motion-events, impact-count contain relevant data fields. current-state contains impact_evnt, free_fall_evnt flags that indicate new event. These can be used if explicit read is preferred.

Variables impact_cnt, impact_cnt_x, impact_cnt_y, impact_cnt_z, impact_etm, free_fall_cnt, free_fall_etm allow rule based logic.

If Activity Monitor is enabled impact and free fall detection can’t be used and will be ignored.

Data Rules

Up to 32 user rules can be stored using data set-rule and data del-rule. A rule contains a test expression, optional input expressions, and optional actions. If <rule-num> is omitted, the first free rule slot is used. data del-rule without a rule number deletes all rules; with a rule number it deletes one rule. Rule configuration persists across reboots; rule evaluation state is reset on reboot.

NOTE

When building a different use case, data del-rule without a rule number removes all factory example rules at once. See Factory Defaults and Custom Configuration.

Command syntax to add or override rules:

data set-rule [<rule-num>],<test-expr>,[<input-expr>],[<switch-profile>],[<make-event-0>],[<make-event-1>], [<make-event-2>],[<make-event-3>],[<send-frame-0>],[<send-frame-1>],[<send-frame-2>],[<send-frame-3>],[<clr-timer-mask>]
Rule Model

The test expression is evaluated against one value from User Variables and produces the rule local state. The local state combined with optional input rules produces the rule combined state.

An action is executed only when combined state changes from false to true. While it remains true, actions are not repeated. When it changes back to false, no action is executed.

Rules are evaluated in dependency order. Rules without inputs are evaluated first, then rules whose input rules have already been evaluated. Rule numbers identify rules and input references; they do not define evaluation order. A rule that depends on itself directly or through other rules is not evaluated.

Test Expression

<test-expr>: [^] <variable-type> <operator> <argument>

Element Description
[^] use the absolute value of the variable in the expression
variable-type variable name or numeric ID from User Variables
<operator> >, >=, <, <=, ==, !=, %
<argument> numeric value

The % operator is true when the integer part of abs(variable) % abs(argument) is zero. <argument> must not be zero.

Fractional arguments are supported and use fixed-point encoding. Prefer integer arguments where possible because fractional values increase rule encoding size. Use == and != only for exact-value variables; for measured analog values, prefer threshold comparisons.

Time values such as mag_sw_etm, impact_etm, timer_1, profile_etm, and activity_state_etm are in seconds. daytime_tm and unix_time are only useful after Time Synchronization.

Example:

data set-rule 0,profile == 0
data set-rule 1,^temperature > 30.55
data set-rule 2,impact_etm < 60

Use variable names in rule commands. The tg-lrx2-encode utility converts variable and frame names to numeric IDs and encodes the commands into the compact binary downlink format.

Input Expression

Input expression is used if a rule needs to depend on the result of other rules. This allows constructing logic based on multiple test expressions.

<input-expr>: [&][|][!]<input-rule>[<]...

Term Description
[&] AND input with the current combined value
[|] OR input with the current combined value
[!] invert the input value
<input-rule> rule number whose state is used
[<] use the input rule combined state, otherwise its local state.

The first input term is combined with the rule local state. Each additional term is applied to the result. There are no parentheses and no operator precedence.

WARNING

Terms are applied in ascending input-rule number order, regardless of the order written in the command. This is easy to miss when composing expressions.

Following configuration will send current-state data frame if magnet switch changed state less than 15s ago and temperature or humidity are out of range (-5..55 and 10..90%):

data del-rule
data set-rule 0,temperature < -5
data set-rule 1,temperature > 55
data set-rule 2,humidity < 10
data set-rule 3,humidity > 90,|0|1|2
data set-rule 4,mag_sw_etm < 15,&3<,,,,,,current-state

Rule 3 combines its own result with rules 0, 1, and 2 using OR. Rule 4 combines its own result with the combined state of rule 3 using AND. The action of rule 4 therefore runs when the magnet switch changed recently and any temperature or humidity threshold is true.

WARNING

Rule numbers are not evaluation order. Rules are evaluated in dependency order. Avoid circular dependencies: rules in a cycle are not evaluated. Input rules must be enabled; disabled input rules are not part of the evaluation order.

Actions

If combined state changes to true, actions are executed once for that transition. Actions execute in this order: generate events, schedule frames, reset user timers. The optional profile switch is applied after all rules in the current evaluation pass. Rules in the same pass therefore still see the previous profile; the new profile is used from the next evaluation pass.

If <switch-profile> parameter is given, the active profile is changed. The value range is 0..5. This does not make the profile the default; use app profile with make-default or a magnet profile command to persist it. For example if temperature drops below 15 C device will switch to profile 5 (Device Profiles):

data set-rule 1,temperature < 15,,5

Up to 4 different Data Frames can be scheduled per rule. Scheduled frames are sent as soon as the network stack has air time; they do not wait for the configured periodic uplink interval:

data set-rule 0,impact_cnt % 10,,,,,,,current-state,device-orientation,dev-health,ema-temp

NOTE

Rule chaining can be used if more than 4 frames should be sent.

Up to 4 different events can be generated per rule. Events are captured when the action executes and are described in Events:

data set-rule 0,impact_cnt % 10,,,temperature_ema,humidity_ema,activity_state,timer_1

The optional <clr-timer-mask> resets user timers when the action executes. See Timers and Rule ID Events.

Events

Actions can optionally generate events. Events are stored in device memory and sent in the device-events frame. Event storage is configured per profile using data event-cfg:

Option Description
max-count Maximum stored events (0 disables event storage, range 1..100).
send-th Schedule device-events when the pending count is at least this value. 0 schedules a frame after every new event.
discard Select oldest or newest event when storage is full.
send-all After a device-events frame is sent, schedule another frame while events remain.

Events are sent when the device-events frame is scheduled periodically using frame set-cfg, immediately using frame send, by a rule send-frame action, or automatically by the send-th threshold. Use data erase-events to erase all events or a selected number of oldest events.

Each event record in the device-events frame contains:

  • a length byte; bit 7 set means more records follow;

  • a 4-byte timestamp;

  • a 1-byte event code;

  • an optional value.

The timestamp is UNIX time after Time Synchronization, otherwise device uptime. Event codes 0..99 are user-variable events and carry the variable value. Event codes 100..229 are reserved for rule events; meta_rule_id uses code 100 + rule-number and carries no value. The supplied payload decoder interprets these records.

Example commands:

data event-cfg 1,50,10,0,1
data erase-events
data erase-events 10

The first command configures profile 0 to store at most 50 events, schedule device-events when at least 10 events are pending, discard the oldest event when full, and keep sending while events remain. The second command erases all events; the third erases the 10 oldest events.

Timers and Rule ID Events

timer_1, timer_2, timer_3, and timer_4 are free-running user timers. They count seconds from the last reset and are reset on device reboot.

data timer sets the elapsed value of selected timers. Omitted parameters are left unchanged:

data timer 0
data timer ,0
data timer ,,,0

The first command resets timer_1, the second resets timer_2, and the third resets timer_4.

The <clr-timer-mask> action parameter is a 4-bit mask: bit 0 resets timer_1, bit 1 resets timer_2, bit 2 resets timer_3, and bit 3 resets timer_4.

meta_rule_id is a special event-action value. It cannot be used as a normal test variable. When an action generates an event for meta_rule_id, the event code is 100 + rule-number and the event has no value. The decoder reports this event as data_rule. This identifies which rule fired when several rules send the same frame. For example:

data set-rule 0,temperature > 30,,,temperature,meta_rule_id,,,current-state
data set-rule 1,humidity > 90,,,humidity,meta_rule_id,,,current-state

When either rule fires, current-state is scheduled and the event identifies the rule that triggered it.

Magnet Switch

Device has magnet switch that can be used for command input or as magnetic field sensor. If unused, command input can be completely disabled or PIN protected using mag svc command.

NOTE

Unique PIN code comes with each device.

Command Input

User must apply command sequence of 1 to 4 digits. Each digit is entered consecutively. After 2.5s idle, valid input command is executed and device indicates result using LED. Successfully executed command is indicated with 3x 0.2s LED blinks and failure is 1s long LED pulse. Invalid commands are ignored.

When magnetic field is applied to device, LED starts blinking with interval 500ms ON, 500ms OFF (or according to mag cfg configured blink-mode). When LED is switched on, internal counter is incremented starting from 0. When magnetic field is removed counter value is latched as user input digit. If magnetic field is applied again, next digit in input sequence is started. If interval after applying digit is larger than 2.5s, sequence is evaluated.

NOTE

When applying input code based on time, ensure to follow this equation: T = N - 0.5, where N is input digit from 1 to 9 and T is time in seconds to apply magnetic field. The interval between digits must be less than 2.5s, but more than 200ms.

Some commands require PIN mode to be entered and some can be optionally protected by PIN mode. See table Magnet switch commands. To enter PIN mode, user must apply sequence of PIN digits provided with the device. Once PIN mode is entered it will expire after configurable time and device will return back to normal mode.

WARNING

It is also possible to completely disable magnet commands. Only way to re-enable is using LoRaWAN downlink command. This can be useful if magnet sensor is used only for detecting external signals and no user commands are expected or allowed.

Command Encoding

Device commands are binary encoded to reduce downlink message size. We provide Python utilities to verify, encode and publish commands as LoRaWAN binary downlink messages.

Install from PyPI with pip install tg-lrx2-utils.

Downlink Ports

Port Purpose
2 Binary command message. After the commands are processed, the device schedules a cfg-state uplink with the current configuration checksums.

tg-lrx2-encode places all encoded messages on the command port except the last message, which is placed on the configuration port to trigger the cfg-state response. Send all generated messages in file order. If –max-len splits a script into several messages, the order is required.

Example configuration to set current-state and activity frame uplink every 600 seconds and mag-switch every 43200 seconds as confirmed message:

# lora-script.txt

tg-lrx2-encode --script ./lora-script.txt --max-len=50 --out ./lora-pub.yml

Device Commands

All device commands consist of group-name and cmd-name. Optional parameters are given in square brackets. Parameters must be comma separated for tg-lrx2-encode script. group-name and cmd-name can also be comma separated but spaces are also accepted.

Example:

app factory-reset <key>,[<fw-def>],<delay-ms>

Parameters <key> and <delay-ms> are mandatory, but <fw-def> is optional and can be omitted:

app factory-reset 984651411,,2500

Each parameter has a valid input range and format. Some parameters allow only a specific choice between values or a choice between ranges.

Most parameters accept integer values. %f indicates that parameter accepts fractional value. Use of these values results in larger downlink payload so if possible integer values should be preferred. variable-type indicates that parameter accepts either user variable name or respective integer ID. frame-type indicates that parameter accepts either data frame name or integer ID. tg-lrx2-encode automatically converts these names to numeric ID.

The reference includes advanced manual commands such as data sample and data next-epoch. See Advanced Operations.

frame set-cfg accepts multiple frame IDs after the shared period, confirmed, and on-join settings. If several frames use the same settings, list them in one command instead of repeating the command:

frame set-cfg 32,900,0,0,current-state,dev-health

The profile mask in the first parameter can also select multiple profiles. Only the listed frames and profiles are changed; other configuration remains as it was.

Example Configurations

The examples below are downlink configuration scripts and assume the device is joined. Most examples use profile 5, which is empty by default, so existing profile settings remain unchanged. The day/night example also uses the factory default profile 0 and leaves profile 0 unchanged.

Temperature and Humidity Reporting

Configure profile 5 to report temperature and humidity every 15 minutes and battery voltage every 6 hours:

data poll-cfg 32,900,0,0,0,0,0,0,21600
frame set-cfg 32,900,0,0,current-state
frame set-cfg 32,21600,0,0,dev-health
app profile 5,1

The current-state frame carries temperature, humidity, and the remaining device state fields. Battery voltage is sent in the dev-health frame. Profile 5 is empty by default, so orientation and activity monitoring are not needed.

Door/Window Switch

Use profile 5. The device sends current-state every 6 hours and reports immediately when the magnet switch changes state:

mag cfg 600,1,1
frame set-cfg 32,21600,0,0,current-state
data del-rule
data set-rule 0,mag_sw_etm < 2,,,,,,,current-state,mag-switch
app profile 5,1

mag cfg 600,1,1 enables PIN protection for normal magnet commands with a 600-second PIN-mode timeout and selects pulse LED blink mode. Magnet switch events continue to work normally; the PIN is supplied with the device.

The rule uses the elapsed time since the last magnet switch change, so either opening or closing triggers current-state and mag-switch. The latter contains the full counter and last-change timestamp. Bit 0 of mag_sw_cnt_u8 is the current switch state.

Threshold Alarm With Cooldown

Use profile 5. Rule 0 is a five-minute cooldown gate. Rule 1 sends an alarm and resets the gate when temperature exceeds 30 C. The event contains both the temperature value and the rule ID:

data poll-cfg 32,30
data event-cfg 32,20,0,0,1
data timer 300
data del-rule
data set-rule 0,timer_1 >= 300
data set-rule 1,temperature > 30,&0,,temperature,meta_rule_id,,,current-state,,,,1
app profile 5,1

The timer is preset so the first alarm can trigger immediately. After each alarm, timer_1 is reset and the gate closes for five minutes. The expected uplink is current-state plus a device-events frame containing the temperature and data_rule 1.

Impact and Free Fall Profile Switch

Use profile 5 and configure impact and free-fall detection for it. The app profile 5,1 command at the end activates profile 5 and makes it the default:

data acc-cfg 32,0,1,1,1,8,0,1,7,0,13,2,0,1
data del-rule
data set-rule 0,impact_etm < 20,,,meta_rule_id,,,,impact-count
data set-rule 1,free_fall_etm < 15,,,meta_rule_id,,,,motion-events
app profile 5,1

The expected uplink is impact-count or motion-events plus a device-events frame that identifies rule 0 or 1.

WARNING

Impact and free-fall detection cannot be used while Activity Monitor is enabled.

Orientation Change Event

Use the last profile, profile 5, and orientation EMA; no reference vectors are needed. A change of at least 20 degrees relative to the orientation EMA generates an event:

data orient-cfg 32,1,2,3
data ema-cfg 32,6,6,6,20
data del-rule
data set-rule 0,angle_ema >= 20,,,angle_ema,meta_rule_id,,,device-orientation
app profile 5,1

The expected uplink is device-orientation plus a device-events frame with the measured angle_ema and data_rule 1. orient-cnt 20 sets the EMA time constant to approximately 30 seconds at the 3-second orientation polling interval. The example makes profile 5 the default.

Magnet-Only Setup

Use case: prepare a TG-LR device for a door/window installation without any downlinks. The device starts in SHUTDOWN, so the settings are applied first and the device is activated last.

Magnet-only setup for profile 2

Step Sequence Action
1 4-3-9 Disable the secondary band (2.4 GHz). The device will use the 1 GHz band only.
2 4-1-3 Switch to profile 2 (Magnet Switch) and make it the default.
3 2 Activate the device and start it in RUN mode. The device restarts and joins the network.

After the device joins, it uses profile 2 by default and sends current-state, mag-switch, and device-events every 60 minutes. A mag_sw_cnt event is generated when the magnet has been removed for at least 20 seconds. The secondary band remains disabled and profile 2 remains the default after reboot.

Confirmed Event Journal

Use profile 5 to store temperature, humidity, and battery voltage as events. The event frame is sent as a confirmed message in batches:

data poll-cfg 32,60,0,0,0,0,0,1,120
data event-cfg 32,100,101,0,1
data del-rule
data set-rule 0,timer_1 >= 60,,,temperature,humidity,,,,,,,1
data set-rule 1,timer_2 >= 120,,,battery_mv,,,,,,,,2
data timer 0,0
frame set-cfg 32,360,1,1,device-events
app profile 5,1

Temperature and humidity are sampled and stored every 60 seconds. Battery voltage is sampled and stored every 120 seconds. The first rule uses timer_1 and resets it; the second rule uses timer_2 and resets it. data timer 0,0 clears both timers, so the first temperature/humidity event is generated after 60 seconds and the first battery event after 120 seconds.

data event-cfg stores up to 100 events. The send threshold is set to 101, which is above the maximum stored event count, so automatic event flushing is effectively disabled. Events are sent when the device-events frame is scheduled by frame set-cfg every six minutes or on network join. send-all drains the remaining events after a frame. The device-events frame is confirmed, so pending events are sent after a normal leave/rejoin recovery. Event timestamps become absolute after the default time synchronization completes.

NOTE

Event storage is a finite buffer, not a permanent archive. A long outage can fill the 100-record buffer and discard the oldest events.

Day/Night Profiles

Use the factory default profile 0 for daytime telemetry and profile 5 for sparse nighttime telemetry:

frame set-cfg 32,3600,0,0,current-state,dev-health
data del-rule
data set-rule 0,daytime_tm >= 28800,,0
data set-rule 1,daytime_tm >= 64800,,5
data set-rule 2,daytime_tm < 28800,,5

Profile 0 is not reconfigured and keeps its factory polling and frame settings. Profile 5 sends current-state and dev-health every hour. Profile selection is what changes the daytime and nighttime uplink rate.

The third rule handles the midnight boundary. At 00:00, rules 0 and 1 become false and rule 2 becomes true, so profile 5 is selected even when this configuration is applied at midnight. At 08:00, rule 0 switches back to profile 0; at 18:00, rule 1 selects profile 5 again.

data del-rule removes all user and factory rules, which is required so the existing profile rules do not override this schedule. Profile 0 frame configuration remains at its factory defaults. Profile 5 is not made the default; profile switching is performed only by these rules. daytime_tm is seconds since midnight GMT, and this example does not distinguish weekdays. Time synchronization is already enabled in the default configuration.

Vehicle Activity Tracking

Use profile 5 to report movement start and stop events for a car or other vehicle, together with the accumulated activity time. The activity and device-events frames are confirmed; dev-health is a periodic unconfirmed uplink.

data del-rule
data activity-cfg 32,1,4,63,1
frame set-cfg 32,0,1,0,activity,device-events
frame set-cfg 32,3600,0,0,dev-health
data set-rule 0,timer_1 >= 60
data set-rule 1,activity_state_etm >= 60
data set-rule 2,activity_state == 0,,,,,,,,,,,1
data set-rule 3,activity_state == 0, &1,,activity_state,,,,activity
data set-rule 4,activity_state != 0, &0,,activity_state,,,,activity
data timer 500
app profile 5,1

The final 1 in data activity-cfg enables the activity indication LED. After testing is complete, disable the LED with:

data activity-cfg 32,,,,0

Rule 2 resets timer_1 when the activity state becomes idle. Rule 0 then requires timer_1 to be at least 60 seconds, so rule 4 generates a start event only when movement resumes after at least 60 seconds of idle. Rule 1 requires the idle state to have lasted 60 seconds, after which rule 3 generates the stop event. This suppresses start/stop flapping for short state changes.

data timer 500 presets timer_1 so a tag that starts in motion can generate an initial start event immediately. If it starts idle, rule 2 clears the timer and the first stop event is generated after 60 seconds of idle.

Both transitions schedule the activity frame, which contains the accumulated total_activity_s. The event carries activity_state, which identifies whether the transition is a start or a stop. dev-health reports battery voltage every hour.

Description: If credential changes are initiated with secondary band disabled - device will not timeout join. Device will be stuck attempting join until either it succeeds or is restarted.

Description: When lora cred is executed device will timeout join procedure on next join attempt based on total uptime instead of command execution time. If uptime is longer than confirm-timeout-s parameter device will timeout exactly after single failed join attempt.

Description: If activity calibration is performed while orientation detection is enabled device may fault and restart.

Description: Changing the ADR setting with lora adr-cfg while the device is joined may not take effect until the device rejoins or restarts. Uplinks may continue using the previous ADR mode and data rate.

Workaround: Reset the device with app reset after changing the ADR setting.

LORA-282

Description: When network ADR is disabled, only DR0 works as a configured fixed data rate. Configuring any other fixed data rate may not take effect.

Workaround: Enable network ADR with lora adr-cfg.

Advanced Operations

The operations below are public but not required for normal end-device operation.

Manual Sampling

data sample forces one temperature, humidity, battery, and orientation sampling cycle. Forced samples update the last measured values and event flags, but do not update EMA or histogram counters except for the first sample. Use it for diagnostics or to refresh data before a manual read.

Manual Histogram Epoch

data next-epoch immediately starts a new temperature and humidity histogram epoch. Use data next-epoch temp or data next-epoch humid to reset only one histogram. The next histogram frame reports the new epoch number.

Configuration Export Frames

Frames full-cfg, app-cfg, net-cfg, frame-cfg, data-cfg, and rules-cfg carry fragmented configuration data. They are intended for configuration backup and verification tooling, not for normal telemetry. The cfg-state frame is the normal automatic checksum response after a configuration downlink.
