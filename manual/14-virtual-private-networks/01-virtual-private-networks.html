Virtual Private Networks

The VPN and tunnel types of RouterOS and when to use each: WireGuard, IPsec, L2TP, SSTP, OpenVPN, PPPoE, GRE, IPIP, EoIP, 6to4, ZeroTier and PPTP.

Virtual Private Networks

RouterOS has several ways to connect networks and remote users over another network. Some encrypt the traffic and some only carry it, so choose by what you need:

You want to Use
Connect two sites or remote users with strong encryption and little configuration WireGuard
Connect to devices and services of other vendors with a standard, encrypted VPN IPsec
Give remote users access with a user name and a password, with clients that are built into Windows and other systems L2TP with IPsec, or SSTP
Give remote users access where only web traffic passes the firewalls SSTP, or OpenVPN over TCP
Serve or connect OpenVPN clients OpenVPN
Connect subscribers on an Ethernet network, or connect to an internet provider PPPoE
Carry IP packets between two routers without encryption, or with IPsec added GRE, IPIP
Carry Ethernet frames between two sites EoIP, or L2TP Ether on the L2TP page
Carry IPv6 over an IPv4 network 6to4
Join a ZeroTier network ZeroTier

PPTP is an old protocol with weak encryption. Use it only for devices that have nothing else.

The users of the L2TP, SSTP, OpenVPN, PPPoE and PPTP servers are in one database: see PPP AAA.

6to4

6to4 in RouterOS: carry IPv6 over an IPv4 network, connect two IPv6 networks with a tunnel, allow IP protocol 41 in the firewall, and get IPv6 from a tunnel broker.

6to4

A 6to4 interface carries IPv6 packets inside IPv4 packets (IP protocol 41). Use it to connect IPv6 networks over a network that has only IPv4, for example to get IPv6 from a tunnel broker when your internet provider has none. The interface works in two modes:

  • With remote-address, it is a tunnel to one IPv4 address. All IPv6 packets that are routed to the interface go to that address.
  • Without remote-address, the router takes the IPv4 destination from the IPv6 destination address. This works for addresses in 2002::/16, where the 32 bits after 2002 are an IPv4 address.

The tunnel does not encrypt the traffic. Both routers need IPv4 addresses that the other one can reach: over the internet, these must be public addresses.

Connect two IPv6 networks

In this example the office router has the IPv4 address 203.0.113.1 and the branch router 203.0.113.2. The tunnel itself uses the IPv6 network 2001:db8:ffff::/64.

On the office router:

/interface/6to4/add name=6to4-branch local-address=203.0.113.1 \
    remote-address=203.0.113.2
/ipv6/address/add address=2001:db8:ffff::1/64 advertise=no \
    interface=6to4-branch

On the branch router:

/interface/6to4/add name=6to4-office local-address=203.0.113.2 \
    remote-address=203.0.113.1
/ipv6/address/add address=2001:db8:ffff::2/64 advertise=no \
    interface=6to4-office

Each router can now ping the other one, for example /ping 2001:db8:ffff::2 on the office router.

[admin@Server] > /interface/6to4/print detail
Flags: R - RUNNING
0 R name="6to4-branch" mtu=auto actual-mtu=1480 local-address=203.0.113.1
    remote-address=203.0.113.2 dscp=inherit clamp-tcp-mss=yes dont-fragment=no

To reach the IPv6 network behind the other router, add a route. The branch LAN in this example is 2001:db8:b::/64:

/ipv6/route/add dst-address=2001:db8:b::/64 gateway=2001:db8:ffff::2
  • The MTU of the interface is 1480 bytes: the IPv4 header takes 20 bytes.
  • keepalive=10s,3 sends a keepalive packet every 10 seconds and removes the running flag of the interface after 3 packets without an answer. Routes through the interface then become inactive.

Allow the tunnel in the firewall

The default firewall drops the packets of the tunnel that come from the internet. Accept IP protocol 41 from the address of the other router, before the default drop rule:

/ip/firewall/filter/add chain=input action=accept \
    protocol=ipv6-encap src-address=203.0.113.2 \
    comment="accept 6to4" \
    place-before=[find comment="defconf: drop all not coming from LAN"]

The IPv6 packets from the tunnel then pass the IPv6 firewall of the router as packets from the 6to4 interface. Check that the IPv6 firewall rules treat this interface as you intend.

Get IPv6 from a tunnel broker

A tunnel broker gives you an IPv6 connection through a 6to4 tunnel. This example uses the Hurricane Electric Tunnel Broker. You need a public IPv4 address, and the broker must be able to ping it.

When you create a tunnel, the broker shows the addresses of the tunnel and a routed /64 prefix for your network:

[gambar: The tunnel details page of the tunnel broker with the IPv4 and IPv6 addresses of both ends and the routed prefix]

The broker also shows ready commands for RouterOS in its "Example Configurations". In this example your public IPv4 address is 194.105.56.170:

/interface/6to4/add name=sit1 mtu=1280 \
    local-address=194.105.56.170 remote-address=216.66.80.90 \
    comment="Hurricane Electric IPv6 Tunnel Broker"
/ipv6/route/add dst-address=2000::/3 gateway=2001:470:27:37e::1
/ipv6/address/add address=2001:470:27:37e::2/64 advertise=no \
    interface=sit1

The router now reaches IPv6 hosts, but the devices of the LAN do not. Give the LAN bridge an address from the routed prefix, and announce it to the devices:

/ipv6/address/add address=2001:470:28:37e::/64 interface=bridge \
    advertise=yes

Announce a DNS server to the devices, and give the router IPv6 DNS servers. These are the public DNS servers of Google; the broker has its own at 2001:470:20::2:

/ipv6/nd/set [find default=yes] advertise-dns=yes
/ip/dns/set allow-remote-requests=yes \
    servers=2001:4860:4860::8888,2001:4860:4860::8844

WARNING

With a public IPv6 prefix, every device of the LAN has an address that the internet can reach. Check that the IPv6 firewall of the router protects the LAN before you announce the prefix: see IPv6 firewall.

Open https://test-ipv6.com on a device of the LAN to test the connection.

Automatic 6to4 addresses

Without remote-address, an interface needs no tunnel for each destination. Each router makes its IPv6 address from its IPv4 address: 2002, then the IPv4 address in hexadecimal. For 10.0.1.1 this is 2002:a00:101::, and for 10.0.2.1 it is 2002:a00:201::.

WARNING

This mode does not pass traffic at present: the routers send the packets, but do not accept the packets that they receive. Use remote-address.

[gambar: Two routers with 6to4 addresses made from their IPv4 addresses]

On the first router:

/interface/6to4/add name=6to4-tunnel1
/ipv6/address/add address=2002:a00:101::/128 advertise=no \
    interface=6to4-tunnel1
/ipv6/route/add dst-address=2002::/16 gateway=6to4-tunnel1

On the second router:

/interface/6to4/add name=6to4-tunnel1
/ipv6/address/add address=2002:a00:201::/128 advertise=no \
    interface=6to4-tunnel1
/ipv6/route/add dst-address=2002::/16 gateway=6to4-tunnel1

EoIP

Ethernet over IP (EoIP) is a MikroTik RouterOS protocol that creates an Ethernet tunnel between two routers over an IP network. It is based on GRE encapsulation (RFC 1701 and RFC 1702) and transports full Ethernet frames across routed IP infrastructure, effectively extending one Layer 2 network between remote sites. EoIP uses its own GRE protocol type, so an EoIP tunnel does not interconnect with generic GRE or Ethernet-over-GRE tunnels. EoIP is a MikroTik protocol without a published specification. Some other systems include their own, unofficial implementation of it, for example the eoip interface in OpenBSD; MikroTik does not maintain these implementations and does not guarantee compatibility with them.

The EoIP tunnel interface appears as a virtual Ethernet interface in RouterOS. Added to a bridge, it forwards all Ethernet traffic — broadcasts, multicast and non-IP protocols — as if the endpoints were connected by a physical Ethernet link. RouterOS connects the two endpoints over any IP transport (a direct link or the internet), so EoIP is typically used to bridge LAN segments across a routed network or a wireless link, and to extend a LAN across an encrypted tunnel when combined with IPsec.

EoIP is configured in the /interface/eoip (over IPv4) and /interface/eoipv6 (over IPv6) menus.

How the tunnel works

Over IPv4, the router puts the whole Ethernet frame — destination and source MAC addresses, EtherType and payload — inside a GRE packet (outer IP protocol 47) and sends it to the remote tunnel endpoint. The receiving router decapsulates it and injects the original frame into its local bridge. The tunnel carries whatever the bridge on the other end sends: broadcasts, ARP, RSTP and other protocol frames travel through the tunnel, so the bridged networks behave like one Ethernet segment.

EoIP over IPv6 (/interface/eoipv6) uses a different encapsulation, not GRE: the Ethernet frame follows a 2-byte header that carries the tunnel ID, in an IPv6 packet with next header 97 (EtherIP). The header layout differs from standard EtherIP (RFC 3378), so an EoIPv6 tunnel does not interconnect with standard EtherIP tunnels or with EoIP over GRE carried in IPv6.

The router considers the tunnel running (the R flag) after the remote end has answered. Keepalive keeps it that way: the router probes the remote end every keepalive interval, and when the peer does not answer for interval × retries, the running flag is removed. Keepalive is enabled by default (10s,10); the minimum interval is 1 second, and setting it to a disabled value (0,0, off, none) is rejected. It can be turned off by unsetting the keepalive property (/interface/eoip/unset <name> keepalive for IPv4 tunnels or the same on /interface/eoipv6) — with keepalive off, the running flag is not removed when the peer stops answering. For faster failover, shorten the interval: with keepalive=1s,2 a dead peer is detected within about two seconds.

Each tunnel is identified by tunnel-id (any value from 0 to 65535). Both ends must use the same tunnel-id for traffic to pass — the router drops tunneled frames and keepalives that carry a different id. With mismatched ids the running flag does not appear, and when the id changes on one end of a running tunnel, the flag is removed after interval × retries. With keepalive turned off, the running flag stays up regardless of the ids.

TIP

EoIP adds 42 bytes to every tunneled frame it sends (8-byte GRE header with key, 14-byte inner Ethernet header, 20-byte outer IP header). With the default mtu=auto the router sizes the tunnel accordingly: actual-mtu is 1458 on a 1500-byte path for EoIP over IPv4. EoIP over IPv6 adds 56 bytes (2-byte EoIPv6 header, 14-byte inner Ethernet header, 40-byte IPv6 header), so its actual-mtu is 1444. In both cases l2mtu stays at 65535. With the default dont-fragment=no, a frame larger than the path can carry unfragmented is split into IP fragments on the outer packet (with dont-fragment=inherit and the DF bit set, the frame is dropped instead). The bridge forwards frames up to l2mtu (65535), so oversized frames reach the tunnel and are fragmented on the outer packet — keep the underlying path MTU large enough for the frames you bridge, and avoid relying on fragmentation where jumbo or full-size frames must cross the tunnel.

All EoIP properties are described in the /interface/eoip and /interface/eoipv6 CLI references.

MAC addresses

Give every tunnel on a bridge its own MAC address — spanning tree and MAC learning assume each bridge port has a distinct one. The tunnel's MAC address is auto-generated as a locally administered address (such as FE:...), and RouterOS accepts any value you set instead. Auto-generated addresses are not guaranteed unique across routers, so with several tunnels on a bridged setup, assign each a distinct address of your own:

/interface/eoip/set eoip-main mac-address=02:00:5E:80:00:01

Set the locally administered bit (second bit of the first octet, as in 02:...) on addresses you assign yourself; the IANA-reserved range 00:00:5E:80:00:00 - 00:00:5E:FF:FF:FF is set aside for such private unicast addresses. Changing the MAC of a running tunnel briefly drops the running flag until the remote end answers again.

Encrypting the tunnel

Set ipsec-secret on both ends to encrypt the tunnel with a pre-shared key — RouterOS then creates a dynamic IPsec peer and policy for the tunnel automatically.

On /interface/eoip (IPv4), IPsec and fast path are mutually exclusive: set allow-fast-path=no on the tunnel first, otherwise the router rejects the ipsec-secret value. Removing the secret alone does not re-enable fast path — the block lingers until the tunnel is removed (which also removes the dynamic IPsec objects). /interface/eoipv6 has no allow-fast-path property, so IPsec works without that step.

Example: bridge two sites over a wireless link

This example bridges the LANs of two sites over a wireless point-to-point link, so both sites share one Layer 2 broadcast domain. Wireless stations cannot be bridged directly; without WDS, an EoIP tunnel over the wireless link achieves the same result.

[gambar: EoIP tunnel between two routers]

The wireless link between the routers is assumed to be established — only the EoIP and bridging configuration is shown here. The same commands work over any IP link between the routers, wired or over the internet.

Create the EoIP tunnel on the AP router:

/interface/eoip/add name=eoip-remote remote-address=10.0.0.2 tunnel-id=1

The names are arbitrary (eoip-remote on the AP, eoip-main on the station) — what matters is that both tunnel-ids match and each remote-address points at the other router.

Verify the tunnel is created — the R flag appears once the remote end answers:

/interface/eoip/print

The output on a running tunnel looks like this (match the R flag, mtu=auto with actual-mtu=1458 on a 1500-byte path, and the locally administered FE:... MAC):

Flags: R - RUNNING
0 R name="eoip-remote" mtu=auto actual-mtu=1458 l2mtu=65535
    mac-address=FE:7D:4A:93:14:56 arp=enabled arp-timeout=auto arp-accept=no
    loop-protect=default loop-protect-status=off loop-protect-send-interval=5s
    loop-protect-disable-time=5m local-address=0.0.0.0 remote-address=10.0.0.2
    tunnel-id=1 keepalive=10s,10 dscp=inherit clamp-tcp-mss=yes
    dont-fragment=no allow-fast-path=yes

Create the matching tunnel on the station router — the tunnel-id and the remote-address must point at the other end:

/interface/eoip/add name=eoip-main remote-address=10.0.0.1 tunnel-id=1

Bridge the local interfaces with the EoIP tunnel. Check which bridge already carries the LAN ports on each router:

/interface/bridge/port/print

On the AP router, add the EoIP interface to the bridge that carries the local LAN — the default RouterOS configuration already has one:

/interface/bridge/port/add bridge=bridge1 interface=eoip-remote

On the station router, add the EoIP tunnel to the same LAN bridge:

/interface/bridge/port/add bridge=bridge1 interface=eoip-main

NOTE

On the default RouterOS configuration all LAN ports are already in the default bridge, so the EoIP tunnel only joins that bridge — an interface can belong to only one bridge, so do not create a second bridge for it. If a router instead starts from an empty configuration, create the bridge and add both the LAN port and the EoIP tunnel to it:

/interface/bridge/add name=bridge1
/interface/bridge/port/add bridge=bridge1 interface=ether2
/interface/bridge/port/add bridge=bridge1 interface=eoip-main

Once both sites share one broadcast domain, only one router may act as DHCP server and gateway — the default RouterOS configuration runs a DHCP server on its LAN bridge, so disable it on the second router.

Both sites are now in the same Layer 2 broadcast domain. Verify it by assigning addresses from one subnet to the bridge at each end and pinging across the tunnel — on the AP router:

/ip/address/add address=10.1.1.10/24 interface=bridge1

and on the station router:

/ip/address/add address=10.1.1.11/24 interface=bridge1

From the station router, a ping to the AP router's bridge address crosses the tunnel:

/ping 10.1.1.10

Troubleshooting

  • The tunnel has no running flag. The remote end has not answered: check with /ping <remote-address> that the tunnel endpoint is reachable, that the tunnel exists on both routers, and that local-address is set correctly. The running flag appears only after the remote end responds. A common cause is mismatched tunnel-id values on the two ends, because keepalives with a different id are dropped: check the tunnel-id on both routers (/interface/eoip/print, valid values 0 to 65535) and make them match. Also check that nothing filters IP protocol 47 (GRE), or IP protocol 97 for EoIPv6, between the endpoints and that the tunnel traffic is not NAT-ed.
  • The running flag is up but nothing passes through. With keepalive turned off, the running flag stays up even when the tunnel-id values do not match, so compare them on both routers.
  • Large traffic stalls or disappears. If the path between the endpoints cannot carry a full-size frame unfragmented, the tunnel fragments the outer packet, and some paths drop fragments or reorder them. Raise the path MTU where possible (for example jumbo frames on the connecting links) and avoid sizing the tunnel above the path.
  • VLAN tags do not behave on large tagged traffic. On top of paths with a tight MTU, tagged VLAN frames add another 4 bytes on top of the EoIP overhead, and in some cases the MSS clamp does not apply to tagged traffic, so large TCP connections over the tunnel can stall. Carry tagged traffic only where the path MTU leaves room for the extra bytes, or lower the MSS at the endpoints.
  • Duplicates, flapping or loops on the bridge. Bridged tunnels share the L2 domain, so every tunnel needs its own MAC address, and when several tunnels are bridged together spanning tree (RSTP) must be able to break the loop — it runs over the tunnel by default, so do not disable it.

GRE

Generic Routing Encapsulation (GRE) is a tunneling protocol originally developed by Cisco to encapsulate a wide variety of network layer protocols over an IP network. It creates a virtual point-to-point link between tunnel endpoints, allowing different protocol traffic to be carried across routed infrastructure.

In RouterOS, GRE is implemented as virtual interfaces in the /interface/gre (over IPv4) and /interface/gre6 (over IPv6) menus. The interfaces are routed (Layer 3) tunnels: a GRE tunnel carries only IP and IPv6 packets between the two endpoints. For Layer 2 connectivity over an IP network (bridging Ethernet frames), use EoIP instead.

How the tunnel works

GRE is a stateless tunnel, similar in behavior to IPIP and EoIP. No session state is maintained between the endpoints: the router keeps forwarding packets toward the remote endpoint even if it becomes unreachable, and the tunneled traffic is dropped until connectivity is restored or the tunnel is reconfigured.

The router considers the tunnel running (the R flag) after the remote end has responded at least once. Keepalive monitors the remote end from then on: the router sends GRE echo probes to the remote-address every keepalive interval and answers the remote end's probes while the tunnel is up. Keepalive is enabled by default (10s,10 — interval 10 seconds, 10 retries) and the interval can be as short as 1 second for faster detection (a 0-second setting is rejected). If the remote end stops answering the probes, the router removes the running flag after the configured time and retries — about 100 s with the default, faster with a shorter interval — and the tunneled traffic is dropped until the remote end answers again. Without keepalive (unset) nothing removes the running flag, so a tunnel to an unreachable remote end stays running. If an automated failover must react to a dead tunnel, watch the running flag (its removal follows the keepalive timeouts) or probe the remote end directly.

TIP

A GRE tunnel adds per-packet overhead: over IPv4 24 bytes (4-byte GRE header + 20-byte IP header), over IPv6 44 bytes (4-byte GRE header + 40-byte IPv6 header). With the default mtu=auto the router sets the tunnel MTU accordingly — actual-mtu is 1476 on a 1500-byte interface for GRE over IPv4 and 1456 for GRE over IPv6. The tunnel carries only IP and IPv6 packets (EtherType 0x0800 and 0x86DD). Do not use the "Check gateway" option arp when a GRE tunnel is used as a route gateway.

All GRE properties are described in the /interface/gre and /interface/gre6 CLI references.

Example: connect two sites

The example connects two sites over the internet with a GRE tunnel and gives each site Layer 3 access to the other site's local network.

[gambar: GRE tunnel between two sites]

Site1 has the local network 10.1.101.0/24, Site2 the local network 10.1.202.0/24. The tunnel endpoints are the routers' public addresses, here 192.168.80.1 (Site1) and 192.168.90.1 (Site2) — substitute your routers' own internet addresses.

Create the tunnel on the Site1 router:

/interface/gre/add name=myGre \
    remote-address=192.168.90.1 local-address=192.168.80.1

And on the Site2 router:

/interface/gre/add name=myGre \
    remote-address=192.168.80.1 local-address=192.168.90.1

NOTE

The example leaves keepalive at its default (10s,10). The tunnel shows the running flag after the remote end has answered, and keeps it while the remote end answers the probes. GRE is stateless: if one end becomes unreachable, the running flag is removed after the keepalive timeouts (about 100 s with the default), and traffic into the tunnel is dropped until the remote end is reachable again.

Both ends now have a tunnel, but need addresses to route over it. Give the tunnel ends addresses from a private range, and add routes to the remote site's local network. On the Site1 router:

/ip/address/add address=172.16.1.1/30 interface=myGre
/ip/route/add dst-address=10.1.202.0/24 gateway=172.16.1.2

On the Site2 router:

/ip/address/add address=172.16.1.2/30 interface=myGre
/ip/route/add dst-address=10.1.101.0/24 gateway=172.16.1.1

At this point both sites have Layer 3 connectivity over the GRE tunnel. Verify it end to end — the ping to the far tunnel address must be answered and the tunnel must show the R flag on both sites:

/ping 172.16.1.2
/interface/gre/print where name=myGre

Troubleshooting

  • The tunnel has no running flag. The remote end has not answered yet. Check with /ping <remote-address> that the tunnel endpoint is reachable, that the remote router has a matching tunnel with remote-address pointing back, and that the tunnel has local-address set correctly. The running flag appears only after the remote end responds.
  • Traffic through the tunnel is lost. GRE is stateless: when the remote end is unreachable, the router keeps sending tunneled traffic into the tunnel and it is dropped. Check the reachability of remote-address, and compare the tunnel's actual-mtu against the path MTU between the sites (an MTU mismatch drops oversized packets).
  • The tunnel is up but no traffic passes between the sites. The WAN firewalls between the sites must allow GRE (IP protocol 47) between the two tunnel endpoints — and the IPsec ports if the tunnel has an ipsec-secret — and the tunneled traffic must not be NATed.
  • The remote end's address changed. remote-address takes an IP address, not a hostname; if a site's public address changes, update the tunnel on the other end or use an endpoint with a stable address.
  • Non-IP traffic does not go through. GRE is a routed tunnel and carries only IP and IPv6 packets. To bridge Ethernet frames over an IP network, use EoIP.

IPIP

IPIP (IP-in-IP) places an IPv4 packet inside another IP header and sends it between two tunnel endpoints. Use it for a routed link between two networks over a plain IP path, for example a site-to-site connection that does not need Layer 2 or encryption. The tunnel carries IPv4 only and adds 20 bytes of overhead over an IPv4 path, or 40 bytes over an IPv6 path.

An IPIP interface is a virtual interface: assign it an address and create routes through it, as with a physical link. IPIP has no encryption, authentication or integrity protection. Protect the tunnel with IPsec, or use it only on a trusted path. For a tunnel that also carries IPv6, use GRE; to extend a Layer 2 segment, use EoIP; for an encrypted tunnel without IPsec, use WireGuard.

RouterOS has two IPIP menus:

  • /interface/ipip carries IPv4 inside IPv4.
  • /interface/ipipv6 carries IPv4 inside IPv6.

Both menus share most properties; /interface/ipip has allow-fast-path and /interface/ipipv6 does not. Before you begin, make sure local-address is an address already assigned to the router, each router has a route to the other router's endpoint address that does not use the tunnel, and the path passes the tunnel packets. The interface name is local and does not have to match on the other router.

How the tunnel works

The sending router takes an IPv4 packet from the tunnel interface, puts it after a new outer IPv4 header and sends the result to the remote endpoint. The outer header uses IP protocol 4. The receiving router removes the outer header and delivers the original packet, so the tunneled packet keeps its addresses and DSCP value.

For /interface/ipipv6, the outer header is IPv6 and its next header is 4 (IPIP). The inner packet is still IPv4.

RouterOS does not negotiate the tunnel: both endpoints must be configured, with each router's local-address set to the address that the other router reaches as remote-address. The tunnel then carries packets in both directions; the routes for the LANs are configured separately.

The interface shows the R (running) flag when the tunnel is up. Keepalive decides when the flag is removed: with keepalive enabled, the router sends a probe to the remote endpoint and keeps the flag only while the peer answers. Without keepalive, the router does not remove the flag when the peer stops answering.

The outer header takes space from the path MTU. With the default mtu=auto, the router sets actual-mtu to the MTU of the underlying interface minus 20 bytes (IPv4) or 40 bytes (IPv6): 1480 and 1460 on a 1500-byte path. A fixed mtu overrides this value.

By default dscp=inherit copies the DSCP value of the tunneled packet to the outer header. Set dscp to a number to mark the outer packets with that value instead, for example dscp=46 for traffic that the network should prioritize.

Connect two sites with an IPIP tunnel

The example connects R1 (LAN 192.168.10.0/24) and R2 (LAN 192.168.20.0/24) over an IPv4 path. The routers reach each other at 192.0.2.1 and 192.0.2.2 on a direct link, and their LAN addresses are 192.168.10.1 and 192.168.20.1. The example assumes those addresses are already configured; replace them with your own, and make sure the two LAN subnets differ. The tunnel uses the subnet 10.10.10.0/30, which gives one address to each end.

On routers with the default firewall, accept protocol 4 from the peer before the tunnel can come up (see the firewall section below).

On R1:

/interface/ipip/add name=ipip1 local-address=192.0.2.1 \
    remote-address=192.0.2.2
/ip/address/add address=10.10.10.1/30 interface=ipip1
/ip/route/add dst-address=192.168.20.0/24 gateway=10.10.10.2

On R2:

/interface/ipip/add name=ipip1 local-address=192.0.2.2 \
    remote-address=192.0.2.1
/ip/address/add address=10.10.10.2/30 interface=ipip1
/ip/route/add dst-address=192.168.10.0/24 gateway=10.10.10.1

The static route sends the other site's LAN through the tunnel. Each router needs its own route; configuring one router does not make the return path work.

Check the interface and the tunnel address:

/interface/ipip/print
Flags: R - RUNNING
Columns: NAME, MTU, ACTUAL-MTU, LOCAL-ADDRESS, REMOTE-ADDRESS, KEEPALIVE, 
         DSCP
#   NAME   MTU   ACTUAL-MTU  LOCAL-ADDRESS  REMOTE-ADDRESS  KEEPALIVE  DSCP   
0 R ipip1  auto        1480  192.0.2.1      192.0.2.2       10s,10     inherit

The R flag appears after the remote endpoint answers a keepalive probe; with the default 10s,10, allow up to 10 seconds. Test the tunnel and the route:

/ping 10.10.10.2 count=3

    1 10.10.10.2                                 56  64 257us     
    2 10.10.10.2                                 56  64 299us     
    sent=3 received=3 packet-loss=0% min-rtt=257us avg-rtt=302us 
   max-rtt=351us

/ping 192.168.20.1 count=3
  SEQ HOST                                     SIZE TTL TIME       STATUS      
    0 192.168.20.1                               56  64 198us     
    1 192.168.20.1                               56  64 304us     
    2 192.168.20.1                               56  64 311us     
    sent=3 received=3 packet-loss=0% min-rtt=198us avg-rtt=271us

The first ping reaches R2's tunnel address, the second one reaches R2's LAN address through the tunnel. Test from a host on each LAN too, because a ping from the router does not exercise forwarding.

Keepalive

Keepalive is on by default (10s,10): the router probes the remote endpoint every 10 seconds and removes the R flag after 10 unanswered probes, so about 100 seconds after the peer stops answering. Shorten it for faster failover, for example keepalive=1s,2 detects a dead peer in about two seconds. The interval must be at least 1 second and the retry count at least 1.

With keepalive enabled, the remote end must answer RouterOS keepalive probes. A Linux ipip tunnel does not answer them. The tunnel then never reaches the R flag, even though the peer is reachable, and no traffic passes. Disable keepalive on the RouterOS side in that case:

/interface/ipip/unset ipip1 keepalive

For /interface/ipipv6, use the same command on that menu. Without keepalive, the R flag stays set when the peer stops answering, so the tunnel cannot detect a dead peer on its own. Use it when the peer does not support RouterOS keepalive.

MTU and fragmentation

actual-mtu is the largest inner packet that the tunnel accepts. With mtu=auto, it follows the MTU of the underlying interface: when that interface's MTU is smaller, actual-mtu drops by the same amount. Auto does not track a smaller MTU on the path beyond the router. If the path MTU is lower, or you want a fixed value, set mtu explicitly:

/interface/ipip/set ipip1 mtu=1400

Packets larger than the tunnel MTU are fragmented on the outer packet when the outer header allows fragmentation. To keep TCP connections working across the tunnel, clamp-tcp-mss (enabled by default) lowers the MSS in received TCP SYN packets to fit the tunnel; UDP and ICMP traffic needs a smaller mtu instead.

The dont-fragment property controls the DF bit in the outer header: no (the default) clears it, so the outer packet can be fragmented; inherit copies the DF flag from the tunneled packet and drops an inner packet whose DF bit is set when it exceeds the tunnel MTU.

Filter tunnel traffic

The firewall protocol name ipip in RouterOS means IP protocol 94. An IPIP tunnel itself uses IP protocol 4, which the firewall names ipencap. Use protocol=ipencap in firewall rules; a rule with protocol=ipip never matches an IPIP tunnel.

On a router with the default firewall, the input chain drops packets that do not come from the LAN, including tunnel packets addressed to the router. Accept them from the remote endpoint before that rule:

/ip/firewall/filter/add chain=input action=accept protocol=ipencap \
    src-address=192.0.2.2 \
    place-before=[find comment="defconf: drop all not coming from LAN"]

Use the remote endpoint address in src-address and create a rule for each peer. If the router does not have that default rule, add the accept rule at the top of the input chain instead.

With allow-fast-path=yes (the default), packets of an established flow can bypass the firewall, so the rule counters do not show every packet. Set allow-fast-path=no on the tunnel if every packet must pass the firewall; see Packet flow in RouterOS.

Protect the tunnel with IPsec

Set the same ipsec-secret on both ends to encrypt the tunnel. RouterOS adds a dynamic IPsec peer and a transport-mode policy for the tunnel packets; keepalive packets are protected too.

On /interface/ipip, set allow-fast-path=no first. RouterOS does not support FastPath together with IPsec, and setting the secret while FastPath is enabled fails with cannot enable fastpath together with ipsec yet:

/interface/ipip/set ipip1 allow-fast-path=no
/interface/ipip/set ipip1 ipsec-secret=change-this-secret

/interface/ipipv6 has no allow-fast-path property, so set ipsec-secret directly there. Run the commands on R1 and R2, with the same secret. Check that the peer is established:

/ip/ipsec/active-peers/print
Flags: R - RESPONDER
Columns: STATE, UPTIME, PH2-TOTAL, REMOTE-ADDRESS
#    STATE        UPTIME  PH2-TOTAL  REMOTE-ADDRESS
;;; ipip1
0    established  14s             2  192.0.2.2     
;;; ipip1
1 R  established  8s                 192.0.2.2

Both ends have the secret, so each router lists two sessions: the one it started and the one it answered, marked R - RESPONDER. An established state with a non-zero PH2-TOTAL shows that the tunnel is encrypted.

IPsec adds its own overhead to the outer packet, so actual-mtu becomes smaller: 1438 bytes on a 1500-byte path with the default proposal in this example. Adjust mtu or the MSS if connections through the tunnel stall on large packets.

To remove the encryption and the dynamic IPsec entries, unset the secret on both ends:

/interface/ipip/unset ipip1 ipsec-secret

For /interface/ipipv6, unset the secret on that menu instead.

IPv4 over IPv6

/interface/ipipv6 carries IPv4 over an IPv6 path, for example an IPv4 site-to-site link across an IPv6-only provider. Use the IPv6 addresses of the two endpoints; the inner configuration is IPv4. The example puts the endpoints on a direct link with global addresses; in practice use the addresses your provider assigns.

On R1:

/interface/ipipv6/add name=ipipv6-1 local-address=2001:db8:0:5::1 \
    remote-address=2001:db8:0:5::2
/ip/address/add address=10.20.20.1/30 interface=ipipv6-1

On R2, swap the endpoint addresses and the tunnel address:

/interface/ipipv6/add name=ipipv6-1 local-address=2001:db8:0:5::2 \
    remote-address=2001:db8:0:5::1
/ip/address/add address=10.20.20.2/30 interface=ipipv6-1

/interface/ipipv6/print

    0 10.20.20.2                                 56  64 380us

actual-mtu is 1460 on a 1500-byte IPv6 path: the 40-byte IPv6 header is larger than the 20-byte IPv4 header. Keepalive, DSCP and MTU work as for /interface/ipip; IPsec works without the allow-fast-path step. Create routes for the LANs as in the IPv4 example.

Troubleshooting

The tunnel has no R flag

  • Disabled interface. A disabled interface shows the X flag in /interface/ipip/print. Enable it and allow up to one keepalive interval (10 seconds with the default) for the flag to appear.
  • Keepalive and the peer. The endpoint can be reachable but not answer RouterOS keepalive probes, as a Linux ipip tunnel does. Disable keepalive with /interface/ipip/unset <name> keepalive and ping the remote tunnel address: the flag no longer proves the path, so the ping does.
  • Endpoint addresses. Each router must reach the other's remote-address through a route that does not use the tunnel itself, and local-address must be an address assigned to the router. Test the path with /ping <remote-address> src-address=<local-address>.
  • Firewall. The input chain must accept protocol=ipencap from the remote endpoint. A rule written as protocol=ipip matches protocol 94 and does not help.
  • Both ends. The remote router must have a tunnel with the local and remote addresses reversed. With keepalive enabled, a tunnel with only one end configured never gets the flag.

The tunnel is running but traffic does not pass

  • Return route. Create a route on the remote router for the local LAN. A ping that works in one direction and fails in the other usually misses this route.
  • Tunnel addresses. The addresses at the two ends of the tunnel must be in the same subnet and must not overlap with a LAN.
  • NAT or firewall on the path. The outer packets are ordinary IP packets from the endpoint addresses; a NAT rule or firewall on the path that blocks protocol 4 stops the tunnel.
  • IPsec mismatch. Both ends need the same ipsec-secret; with a secret on one end only, ping over the tunnel fails in both directions.

Large packets fail

Reduce mtu on both ends to the largest inner packet that passes. For TCP, clamp-tcp-mss=yes negotiates a smaller MSS; UDP and ICMP traffic needs the smaller mtu. A ping with size=1492 do-not-fragment fails on a 1500-byte path because the packet exceeds the 1480-byte tunnel MTU. With IPsec, use a smaller value still, because the IPsec header and trailer add to the outer packet.

Setting the IPsec secret fails

On /interface/ipip, setting the secret fails while FastPath is enabled. Set allow-fast-path=no first; the error message is cannot enable fastpath together with ipsec yet.

Technical details

An IPIP packet is an outer IPv4 header with protocol 4 followed by the unchanged inner IPv4 packet. The header adds 20 bytes, so the tunnel MTU is 20 bytes below the path MTU: a packet at the tunnel MTU (1480 bytes on a 1500-byte path) fills the path exactly. /interface/ipipv6 uses an outer IPv6 header with next header 4 and adds 40 bytes.

A keepalive probe is an outer packet with an empty payload: for /interface/ipip, an IPv4 packet with protocol 4 and an inner IPv4 header without data (40-byte outer packet); for /interface/ipipv6, an IPv6 packet with next header 41 instead of the next header 4 used for data. The probe travels from the local endpoint to the remote endpoint, and the running flag remains while replies arrive.

IPIP is stateless: there is no session establishment, and the running flag is the only state. The tunnel does not fragment the inner packet: packets above the tunnel MTU rely on outer fragmentation or on the sender reducing its packet size.

The IPv4 encapsulation is defined in RFC 2003. The menus and every property are described in the /interface/ipip and /interface/ipipv6 CLI references.
