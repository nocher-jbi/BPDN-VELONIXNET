PPPoE

Point-to-Point Protocol over Ethernet (PPPoE, RFC 2516) carries PPP links over an Ethernet network. Internet providers use it to give each subscriber a connection with a user name and a password, in place of a static address or DHCP. RouterOS has both sides:

  • The PPPoE client connects a router to any PPPoE server, for example to an internet provider.
  • The PPPoE server, also called the access concentrator, serves many PPPoE clients. Clients exist for almost all operating systems and routers.

Both work on any layer 2 interface: Ethernet, wireless, VLAN, EoIP and others. The users of a PPPoE server and their settings are in the PPP user database or on a RADIUS server: see PPP AAA.

[gambar: A PPPoE client connects to a PPPoE server over an Ethernet network]

Connect to an internet provider

Add a PPPoE client on the interface that is connected to the provider, with the user name and the password that the provider gave you:

/interface/pppoe-client/add name=pppoe-out1 interface=ether1 \
    user=alice password=Example-pass-1 add-default-route=yes \
    use-peer-dns=yes disabled=no
  • add-default-route=yes adds a default route through the connection.
  • use-peer-dns=yes uses the DNS servers that the provider sends.
  • With the default configuration, the firewall and NAT use the interface list WAN. Add the PPPoE client interface to this list: /interface/list/member/add list=WAN interface=pppoe-out1.

monitor shows the state of the connection, the server and the addresses:

[admin@Client] > /interface/pppoe-client/monitor pppoe-out1 once

               uptime: 12s                  
         active-links: 1                    
             encoding:                      
         service-name: internet             
              ac-name: Server               
               ac-mac: 52:54:0B:80:03:01

   local-ipv6-address: fe80::7fe3:8e52:0:b

scan lists the PPPoE servers that answer on an interface, with their service names:

[admin@Client] > /interface/pppoe-client/scan ether1 duration=5
Columns: SERVICE, MAC-ADDRESS, AC-NAME
SERVICE   MAC-ADDRESS        AC-NAME
          52:54:0B:80:03:01  Server 
internet  52:54:0B:80:03:01  Server
  • With an empty service-name, the client connects to any service. With a name, it connects only to a server that has this service.
  • ac-name limits the client to the access concentrator with this name.
  • Do not use a large number of PPPoE clients on one device.

Run a PPPoE server

Add a pool, a profile and a user, and then a server on the interface where the clients are:

/ip/pool/add name=pppoe-pool ranges=10.0.0.10-10.0.0.100
/ppp/profile/add name=subscribers local-address=10.0.0.1 \
    remote-address=pppoe-pool
/ppp/secret/add name=alice password=Example-pass-1 \
    profile=subscribers service=pppoe
/interface/pppoe-server/server/add service-name=internet \
    interface=ether3 default-profile=subscribers disabled=no

For each connected user the server adds a dynamic interface, and /ppp/active lists the user with the MAC address of the client:

[admin@Server] > /interface/pppoe-server/print detail
Flags: D - DYNAMIC; R - RUNNING
0 DR name="<pppoe-alice>" user="alice" service="internet" mtu=1492 mru=1492
     remote-address="52:54:0B:81:03:01" encoding="" uptime=13s interface=ether3
  • An interface can have several servers with different service names. The clients select the server by the service name and by the name of the access concentrator.
  • The name of the access concentrator is the identity of the router.
  • Do not use static addresses or DHCP for the clients on an interface that has a PPPoE server, and do not give that interface an IP address: a device could then use the network without a PPPoE login.
  • The server checks that a client is still there with echo requests. With keepalive-timeout=10 (the default) it closes a session that does not answer. With 0, a session stays until the client logs out or the router restarts; one-session-per-host=yes helps in that case.
  • Some instructions for Windows give the "phone number" as MikroTik_AC\mt1: the name of the access concentrator and then the service name.

Send full-size packets

An Ethernet frame carries 1500 bytes. PPPoE uses 6 of them and PPP 2, so a PPPoE link has an MTU of 1492 bytes: a 1492-byte packet passes, and a 1500-byte packet that must not be fragmented does not.

TCP connections normally find the lower MTU with path MTU discovery, but this fails where routers or firewalls drop the ICMP messages that it needs. There are two ways to help:

  • Lower the MSS of the TCP connections that pass the PPPoE link: see Change MSS. The built-in PPP profiles do this with change-tcp-mss=yes.
  • Use Multilink PPP on the link. With mrru on the server and on the client, large packets are split and joined again, and 1500-byte packets pass: see MLPPP over single and multiple links.

Serve VLANs with one server

pppoe-over-vlan-range makes one server accept clients in a range of VLANs on its interface. accept-untagged=no then refuses clients without a VLAN tag.

Do not use this setting together with a VLAN interface whose VLAN ID is in the range:

/interface/vlan
add interface=ether2 name=vlan15 vlan-id=15
/interface/pppoe-server/server
add disabled=no interface=ether2 pppoe-over-vlan-range=10-20

If you need both, take the VLAN ID out of the range and add a second server on the VLAN interface:

/interface/vlan
add interface=ether2 name=vlan15 vlan-id=15
/interface/pppoe-server/server
add disabled=no interface=ether2 pppoe-over-vlan-range=10-14,16-20
add disabled=no interface=vlan15

How PPPoE works

PPPoE has two phases: discovery and session.

Discovery

In the discovery phase the client finds a server. After four packets, both sides know the session ID and the MAC address of the other side, which together identify the session:

  1. PADI (Active Discovery Initiation). The client sends a PADI packet to the broadcast address. The packet has the service name, if one is set on the client.
  2. PADO (Active Discovery Offer). A server that has the requested service answers with a PADO packet to the address of the client. If the PADI has no service name, the PADO lists the services of the server.
  3. PADR (Active Discovery Request). The client answers the first valid PADO with a PADR packet to the address of the server. If the PADI had no service name, the PADR has the first service name of the PADO.
  4. PADS (Active Discovery Session-confirmation). The server makes a session ID and sends it to the client in a PADS packet.

Either side can end the session at any time with a PADT (Active Discovery Terminate) packet.

Session

In the session phase, PPP frames travel in Ethernet frames of the type 0x8864. PPP starts with these steps:

  1. LCP negotiates the link.
  2. The client authenticates (PAP, CHAP or MS-CHAP).
  3. IPCP gives the client an IP address.

If a step fails, the LCP negotiation starts again.

IPv6 PD over PPP

IPv6 prefix delegation over PPP in RouterOS: give each PPPoE user an IPv6 prefix from a pool with a dynamic DHCPv6 server, request the prefix on the client, and use it on the LAN.

IPv6 PD over PPP

A PPP server can give each user an IPv6 prefix for the network behind the user's router. This is DHCPv6 prefix delegation (PD) over the PPP link: when a user connects, the server adds a dynamic DHCPv6 server on the interface of the user, and the router of the user asks it for a prefix with a DHCPv6 client.

The example uses PPPoE.

Server

Add an IPv6 pool. This pool gives a /60 prefix to each user from a /56 block:

/ipv6/pool/add name=pd-pool prefix=2001:db8:7501:ff00::/56 \
    prefix-length=60

Set the pool in dhcpv6-pd-pool of the PPP profile that the users have:

/ppp/profile/set subscribers dhcpv6-pd-pool=pd-pool

The setting applies to users that connect after the change. PPPoE shows how to add the server, the profile and the users.

Client

On the router of the user, add a DHCPv6 client on the PPPoE client interface. It asks for a prefix and puts it into an IPv6 pool:

/ipv6/dhcp-client/add interface=pppoe-out1 request=prefix \
    pool-name=lan-pool pool-prefix-length=64 add-default-route=yes

Give the LAN an address from the pool. advertise=yes announces the prefix to the devices of the LAN:

/ipv6/address/add interface=bridge from-pool=lan-pool advertise=yes

Check

On the server, a dynamic DHCPv6 server exists for the user, and the binding shows the prefix:

[admin@Server] > /ipv6/dhcp-server/print
Flags: D - DYNAMIC
Columns: NAME, INTERFACE, ADDRESS-POOL, PREFIX-POOL, PREFERENCE, LEASE-TIME
#   NAME           INTERFACE      ADDRESS-POOL  PREFIX-POOL  PREFERENCE  LE
0 D <pppoe-alice>  <pppoe-alice>  static-only   pd-pool             255  1d

[admin@Server] > /ipv6/dhcp-server/binding/print
Flags: D - DYNAMIC
Columns: ADDRESS, DUID, SERVER, STATUS
#   ADDRESS                  DUID                    SERVER         STATUS
0 D 2001:db8:7501:ff00::/60  0x0003000152540b7e0101  <pppoe-alice>  bound

The server also adds a route for the prefix through the interface of the user.

On the client, the DHCPv6 client is bound and the pool has the prefix:

[admin@Client] > /ipv6/dhcp-client/print
Columns: INTERFACE, STATUS, REQUEST, PREFIX
# INTERFACE   STATUS  REQUEST  PREFIX                            
0 pppoe-out1  bound   prefix   2001:db8:7501:ff00::/60, 23h59m45s

[admin@Client] > /ipv6/pool/print
Flags: D - DYNAMIC
Columns: NAME, PREFIX, PREFIX-LENGTH, ACTUAL-PREFIX, VALID-LIFETIME
#   NAME      PREFIX                   PR  ACTUAL-PREFIX            VALID-LIF
0 D lan-pool  2001:db8:7501:ff00::/60  64  2001:db8:7501:ff00::/60  23h59m44s

The LAN interface then has a /64 prefix from the pool, here 2001:db8:7501:ff00::/64: see /ipv6/address/print.

MLPPP over single and multiple links

Multilink PPP in RouterOS: use MRRU on a single PPP link to carry full-size packets without lowering the TCP MSS, and join several PPPoE links to one provider into a single connection.

MLPPP over single and multiple links

Multilink PPP (MP, MLPPP, RFC 1990) splits packets into fragments, sends them over one or more PPP links, and joins them again on the other side. Both sides must support it: they agree on it with an LCP option when the link starts. RouterOS uses it in two ways:

  • On a single link, to carry packets that are larger than the MTU of the link.
  • On several links to the same server, to use them as one connection.

MLPPP over a single link

A PPP link has a lower MTU than Ethernet: 1492 bytes for PPPoE, for example. With the Maximum Received Reconstructed Unit (mrru) set on both sides, the link splits larger packets and the other side joins them, so full 1500-byte packets pass.

Set mrru on the server and on the client:

/interface/pppoe-server/server/set [find service-name=internet] \
    mrru=1600

/interface/pppoe-client/set pppoe-out1 mrru=1600

After the client connects again, monitor shows a larger MTU for the link (1596 with mrru=1600), and a 1500-byte packet that must not be fragmented passes.

  • With MRRU on both sides, the TCP MSS does not have to be lowered with a firewall mangle rule, and MRRU needs less CPU than two mangle rules for each client.
  • mrru can be up to 65535 bytes.
  • Windows calls this "Negotiate multi-link for single link connections", in the settings of the Networking tab of the connection. Its MRRU is always 1614, so use mrru=1614 on a server for Windows clients.
  • With MPPE encryption, the MTU of the link is 4 bytes lower.

MLPPP over multiple links

A PPPoE client can use several physical links to one provider as a single connection, for example two DSL lines. All links must end on the same server, the server must support MLPPP over multiple links, and all links use the same user name and password.

RouterOS supports this as a client only. A RouterOS PPPoE server does not join several links.

[gambar: A router is connected to the internet provider with two links]

Name all the interfaces in interface of the client:

/interface/pppoe-client/add name=pppoe-out1 service-name=ISP \
    interface=ether1,ether2 user=alice password=Example-pass-1 \
    add-default-route=yes use-peer-dns=yes disabled=no

active-links in the output of /interface/pppoe-client/monitor shows how many links the connection uses. If it is 1 with two interfaces, the server does not support MLPPP over multiple links.

The rest of the configuration is the same as for a client on one link: the PPPoE client interface is the WAN interface of the router. See PPPoE and, for the firewall, Filter.

PPTP

PPTP (Point-to-Point Tunneling Protocol) is a legacy VPN protocol that carries a PPP session between a client and a server. RouterOS can be either end: /interface/pptp-client connects to a remote server, and /interface/pptp-server accepts clients. PPTP is built into Windows and many older devices, so it is still used where compatibility is the main requirement.

WARNING

PPTP is not secure. Its authentication and encryption mechanisms are weak by current standards, and implementations have a history of vulnerabilities. An exposed PPTP server is a security risk; keep RouterOS up to date and use PPTP only for legacy clients. For new deployments, use L2TP/IPsec, SSTP, OpenVPN or WireGuard.

PPTP runs over IPv4. The control connection uses TCP port 1723, and the tunneled PPP frames travel in GRE (IP protocol 47). Both must be allowed between the endpoints. The PPP session can carry IPv4 and IPv6 traffic, according to the PPP profile.

Authentication, encryption and accounting come from PPP. Users are configured in /ppp/secret or on a RADIUS server, and the session options come from a PPP profile. The default default-encryption profile enables MPPE encryption, which requires MSCHAP authentication; the default profile does not encrypt. See PPP AAA for RADIUS.

How PPTP works

The client opens a TCP connection to the server on port 1723 and establishes the tunnel. The tunneled PPP frames are then exchanged in GRE packets. On the server, each connected user is served by a PPP interface: a dynamic interface, or the static entry for that user. The client entry also creates an interface; it is running (flag R) only while the tunnel is connected.

Both ends have a maximum transmit and receive unit (max-mtu and max-mru), 1450 by default. When the values differ, the tunnel comes up with the lower value. The client's /interface/pptp-client/monitor shows the negotiated MTU, the encryption, and the local and remote tunnel addresses.

Example: two routers

This example connects RouterOS as a PPTP client to RouterOS as a PPTP server over an IPv4 link. ether5 on the client has 192.0.2.2/24 and ether5 on the server has 192.0.2.1/24; the tunnel uses 10.0.0.100 for the client and 10.0.0.1 for the server.

graph LR
    client["PPTP clientether5 192.0.2.2tunnel 10.0.0.100"] ---|"TCP 1723, GRE 47"| server["PPTP serverether5 192.0.2.1tunnel 10.0.0.1"]

Server

Enable the PPTP server and create a PPP secret for the client:

/interface/pptp-server/server/set enabled=yes
/ppp/secret/add name=pptp-test password=<password> service=pptp \
    profile=default-encryption local-address=10.0.0.1 \
    remote-address=10.0.0.100

The server listens on TCP port 1723. The secret supplies the user name, password and tunnel addresses; in the secret, local-address is the server's end of the tunnel and remote-address is the client's end. The PPP profile supplies authentication and encryption settings. The server accepts MSCHAP1 and MSCHAP2 by default; the authentication setting in /interface/pptp-server/server changes that. A client that does not support MPPE can use the default profile with an authentication method it supports, such as PAP; the tunnel then comes up without encryption. A user can also be authenticated through RADIUS.

Client

Create the client entry with the server address and the same credentials:

/interface/pptp-client/add connect-to=192.0.2.1 name=pptp-out1 user=pptp-test \
    password=<password> profile=default-encryption disabled=no

A new PPTP client is disabled by default, so disabled=no is needed to start it. Check the interface:

/interface/pptp-client/print
Flags: R - RUNNING
0 R name="pptp-out1" max-mtu=1450 max-mru=1450 mrru=disabled
    connect-to=192.0.2.1 user="pptp-test" profile=default-encryption
    keepalive-timeout=60 use-peer-dns=no add-default-route=no dial-on-demand=no
    allow=pap,chap,mschap1,mschap2

The server shows a dynamic interface for the connected user:

/interface/pptp-server/print
Flags: D - DYNAMIC; R - RUNNING
Columns: NAME, USER, MTU, CLIENT-ADDRESS, UPTIME, ENCODING
#    NAME              USER        MTU  CLIENT-ADDRESS  UPTIME  ENCODING
0 DR <pptp-pptp-test>  pptp-test  1450  192.0.2.2      4s      MPPE128 stateless

The CLIENT-ADDRESS column is the client's outer IPv4 address (192.0.2.2), not its tunnel address.

The client can reach the server's tunnel address:

/ping 10.0.0.1 count=3
  SEQ HOST                                     SIZE TTL TIME       STATUS
    0 10.0.0.1                                   56  64 469us
    1 10.0.0.1                                   56  64 374us
    2 10.0.0.1                                   56  64 350us
    sent=3 received=3 packet-loss=0% min-rtt=350us avg-rtt=397us
   max-rtt=469us

A route to the peer's tunnel address (10.0.0.1/32) is added automatically. To reach the server's LAN, add a route to that network through the tunnel. To route all traffic through the tunnel, use add-default-route=yes on the client. This adds an IPv4 default route and does not change DNS; set use-peer-dns=yes if the client should also use the DNS servers from the peer.

Static and dynamic server interfaces

A dynamic interface exists only while the user is connected. It is named after the user, for example <pptp-pptp-test>, so it disappears on disconnect and cannot be referenced in configuration.

When a firewall rule or another configuration needs a stable interface name, add a static entry on the server for that user:

/interface/pptp-server/add name=pptp-in1 user=pptp-test

The static interface exists whether the user is connected or not, and the server uses it instead of a dynamic interface when that user connects. If the user already has an active session through the static interface, a second connection gets a dynamic interface, because two interfaces cannot share the name. A static entry only names the interface; the user must still exist in /ppp/secret or RADIUS, otherwise authentication fails.

Firewall

The server must accept TCP port 1723 and GRE from the client. The client must accept GRE from the server. On a default configuration, the input chain ends with a drop rule for traffic that does not come from the LAN, so the rules must be placed ahead of it:

/ip/firewall/filter/add chain=input protocol=tcp dst-port=1723 action=accept \
    place-before=[find comment="defconf: drop all not coming from LAN"]
/ip/firewall/filter/add chain=input protocol=gre action=accept \
    place-before=[find comment="defconf: drop all not coming from LAN"]

On a router without that rule, place the two rules before whatever rule drops the traffic. These are the server's rules; on the client, only the GRE rule is needed. On a router with a default configuration, the input chain accepts established and related traffic, but GRE is a separate protocol; from the WAN it is dropped unless it is accepted explicitly. Restrict the rules to the WAN interface or the peer address when possible.

If the PPTP server is behind NAT, both TCP 1723 and GRE must reach it. Not every NAT device forwards GRE correctly; a public address for the server avoids the problem. Traffic from clients that the server forwards to its LAN passes through the forward chain and needs forwarding rules and routes like any other traffic.

MTU

The tunnel MTU defaults to 1450 on both ends. PPTP does not discover the path MTU, so choose a value that fits the path between the endpoints. Set max-mtu on either end to change it; when the two values differ, the tunnel comes up with the lower one. A client with max-mtu=1400 brings the tunnel up with MTU 1400 even when the server allows 1450.

Lower the MTU when large packets stall or connections open but data transfers fail, for example when the path between the endpoints has a smaller MTU than 1500. A PPP profile can also change the TCP MSS to fit the tunnel MTU (change-tcp-mss).

Troubleshooting

The client does not connect

  • The client is disabled. A newly added PPTP client has disabled=yes; enable it in the client entry. The client shows the R flag only when it is connected.
  • TCP port 1723 is blocked. The client does not connect and the interface has no R flag. Check the input chain on the server and the counters on any rule that drops TCP 1723.
  • The credentials are wrong. The server log reports user <name> authentication failed. Check the /ppp/secret entry or the RADIUS server.
  • The server is not enabled. Check /interface/pptp-server/server/print; enabled must be yes.

The tunnel is up but no traffic passes

  • GRE is blocked at either end. The TCP control connection stays up and the interface keeps the R flag, but pings and other data time out. Check the input chain on both routers for a rule that drops protocol=gre; /ip/firewall/filter/print stats shows whether the rule matches.
  • No route to the remote network. The router adds a /32 route for the peer's tunnel address. A remote LAN needs its own route through the tunnel, or add-default-route=yes on the client.
  • The forward chain blocks the traffic. Traffic that the server forwards between the tunnel and its LAN passes through the forward chain.
  • The MTU is too high for the path. Small packets pass, but large ones stall. Lower max-mtu on the client or server.

Large packets stall

Lower max-mtu on either end and check the PPP profile's TCP MSS setting (change-tcp-mss). The tunnel comes up with the lower of the client and server MTU values.

Technical details

PPTP carries a PPP session: the control connection manages the call over TCP 1723, and the PPP frames travel in GRE. Authentication and encryption are PPP features, not PPTP features, so the same secrets, profiles and RADIUS settings work for PPTP, L2TP, PPPoE and other PPP services.

MPPE encryption is derived from the MSCHAP authentication exchange. With the default profile and a server that allows only PAP, the tunnel comes up without encryption; the client's monitor shows an empty encoding field in that case.

Because PPTP runs over IPv4 GRE, the outer packets cannot use IPv6. The PPP session can still carry IPv6 traffic when the PPP profile enables it.

The menu and its arguments are described in the /interface/pptp-client, /interface/pptp-server and /interface/pptp-server/server CLI references.

SSTP

The Secure Socket Tunneling Protocol (SSTP) carries a PPP link inside a TLS session. It uses TCP port 443, the port of HTTPS, so it passes most firewalls, NAT devices and web proxies. Use SSTP where networks block other VPN protocols.

  • The users and their settings are in the PPP user database or on a RADIUS server: see PPP AAA.
  • SSTP runs over TCP. It is reliable on a bad link, but it has more overhead than a VPN protocol that uses UDP.
  • Microsoft Windows has an SSTP client.

A connection is made in four steps:

[gambar: The four steps of an SSTP connection between a client and a server]

  1. The client opens a TCP connection to the server, to port 443 by default.
  2. TLS starts, and the client checks the certificate of the server if it is set to do so.
  3. The client sends SSTP control packets inside the HTTPS session, and both sides set up the SSTP connection.
  4. PPP starts over SSTP: the client authenticates and the link gets its addresses.

Set up a server and a client

[gambar: An SSTP client connects to an SSTP server over the internet]

On the server, add a pool, a profile and a user, and enable the SSTP server:

/ip/pool/add name=vpn-pool ranges=10.0.0.10-10.0.0.100
/ppp/profile/add name=vpn local-address=10.0.0.1 \
    remote-address=vpn-pool
/ppp/secret/add name=alice password=Example-pass-1 profile=vpn \
    service=sstp
/interface/sstp-server/server/set enabled=yes default-profile=vpn

On a RouterOS client, add an SSTP client with the address of the server:

/interface/sstp-client/add name=sstp-office connect-to=203.0.113.1 \
    user=alice password=Example-pass-1 disabled=no

[admin@Client] > /interface/sstp-client/monitor sstp-office once
               status: connected            
               uptime: 11s                  
             encoding: AES256-CBC           
                  mtu: 1500                 
        local-address: 10.0.0.99            
       remote-address: 10.0.0.1             
   local-ipv6-address: fe80::885c:c65:0:8   
  remote-ipv6-address: fe80::c17c:122c:f0:18

The server adds a dynamic interface for the user:

[admin@Server] > /interface/sstp-server/print detail
Flags: D - DYNAMIC; R - RUNNING
0 DR name="<sstp-alice>" user="alice" mtu=1500 client-address="203.0.113.2"
     uptime=12s encoding="AES256-CBC"

WARNING

This tunnel has no certificates. It works only between two RouterOS devices, and it is encrypted but not protected against an attacker in the path, who can pretend to be the server. Use a server certificate for a tunnel over the internet.

Secure the tunnel with a server certificate

With a certificate, the client can check that it talks to the right server. The server needs a certificate with its address or DNS name, and the client needs the certificate authority (CA) that signed it. Certificates explains how to create, sign, export and import certificates. In this example the server certificate has the name sstp-server and contains the address 203.0.113.1.

On the server, set the certificate:

/interface/sstp-server/server/set certificate=sstp-server

On the client, import the CA certificate as a trusted certificate and turn the check on:

/interface/sstp-client/set sstp-office verify-server-certificate=yes
  • The client connects only when a trusted CA signed the certificate of the server.
  • With verify-server-address-from-certificate=yes (the default), the address or name in connect-to must also be in the certificate.
  • The client uses the certificate to bind the TLS session to the PPP authentication, and this lets the server check that both are secure. For this, use MS-CHAPv2 authentication.
  • A Windows client always checks the server certificate. A certificate from a CA that Windows already trusts works at once. For your own CA, import the CA certificate into the trusted root store of the Windows computer.
  • The RSA key of a certificate for SSTP must have at least 472 bits.
  • add-sni=yes on the client adds the server name (TLS SNI) to the first TLS packet.

Require a client certificate

The server can also ask each client for a certificate. Give the client a certificate that the CA of the server trusts, with its private key:

/interface/sstp-client/set sstp-office certificate=sstp-client

On the server, the CA must be a trusted certificate. Turn the check on:

/interface/sstp-server/server/set verify-client-certificate=yes

A client without a certificate is then refused, and the log of the server has ssl: empty certificate chain received. A Windows client cannot send a client certificate, so this setup is for RouterOS clients.

Choose the TLS settings

  • tls-version on the server and on the client: any, only-1.2, only-1.3, min-1.2 or min-1.3.
  • pfs selects the key exchange. yes uses ECDHE-RSA and DHE-RSA, which give perfect forward secrecy, and required uses only ECDHE.
  • ciphers selects the encryption algorithms.
  • port of the server and of the client changes the TCP port.
  • http-proxy and proxy-port of the client connect through a web proxy.

Use settings that both sides allow, for example tls-version=only-1.2 pfs=yes on the server and on the client.

Allow SSTP in the firewall

The default firewall drops connections that come from the internet. Accept the port of the SSTP server before the default drop rule:

/ip/firewall/filter/add chain=input action=accept protocol=tcp \
    dst-port=443 in-interface-list=WAN comment="accept SSTP" \
    place-before=[find comment="defconf: drop all not coming from LAN"]

Bridge Ethernet over the tunnel

As other PPP tunnels, SSTP can carry Ethernet frames with the Bridge Control Protocol (BCP), so that the networks on both sides are one layer 2 network. Set bridge in the PPP profile on both sides: see L2TP for the steps.

Troubleshoot

A RouterOS client writes the reason of a failed connection to its log. In this output the client connected to another address of the server than the one in the certificate:

[admin@Client] > /log/print where topics~"sstp"
 2026-11-20 09:11:23 sstp,ppp,info sstp-office: terminating... - ssl: name verification failed for: "CN=203.0.113.1" (6)
 2026-11-20 09:11:23 sstp,ppp,info sstp-office: disconnected
Message Meaning
name verification failed The address or name in connect-to is not in the certificate of the server. Connect by the name in the certificate, or set verify-server-address-from-certificate=no.
empty certificate chain received (on the server) The server asks for a client certificate and the client has none.
Certificate is not yet valid The start date of the certificate is in the future. Check the clock of the router.
Certificate has expired The end date of the certificate is in the past. Check the clock of the router.
Invalid certificate purpose The certificate cannot be used for this purpose.
Self signed certificate in a chain The certificate chain has no trusted root on this router.
Unable to get issuer certificate locally The CA certificate is not imported on this router.

When the client stays disconnected without a message, check that the CA certificate on the client is trusted, that the firewall of the server accepts the port, and that the user name and the password are right.

WireGuard is a modern VPN solution offering fast, secure encryption across platforms with detailed configuration options including private/public keys, VRF routing, and peer management for establishing encrypted...

WireGuard is a simple, fast, and modern VPN that uses state-of-the-art cryptography. It aims to be faster, simpler, and leaner than IPsec, and considerably more performant than OpenVPN. WireGuard is a general-purpose VPN designed for embedded interfaces and supercomputers alike, fit for many different circumstances. Initially released for the Linux kernel, it is now cross-platform (Windows, macOS, BSD, iOS, Android) and widely deployable.

Importing and Exporting WireGuard

Configuration can be done in various ways. An example file is available for download: wireguard1.conf. Replace its example keys and endpoint before use.

Importing a WireGuard configuration

/interface/wireguard/wg-import accepts configurations in the standard WireGuard format ([Interface] / [Peer] sections). A minimal working file:

[Interface]  
Address =192.168.88.3/24  
ListenPort = 13533  
PrivateKey = UBLqJEFZZf9wszZSUF2BPWa9dsMX99RbEcxlNfxWffk=

Save the file to the device (for example, via the WebFig/WinBox Files menu) and import it with:

/interface/wireguard/wg-import config-file=wireguard1.conf

The same configuration can be imported directly, without a file, using the config-string parameter:

/interface/wireguard/wg-import config-string="
[Interface]
Address = 192.168.88.3/24
ListenPort = 13533
PrivateKey = UBLqJEFZZf9wszZSUF2BPWa9dsMX99RbEcxlNfxWffk=

[Peer]
PublicKey = EoF7HlFu3fbOnuYbyGqLMJkPZgQk9n3WwONZuJZ6qWc=
Endpoint = 192.0.2.10:51820
AllowedIPs = 0.0.0.0/0
PersistentKeepalive = 25"

Exporting client configurations

Client-side configurations (for phones, laptops and other peer devices) are generated per peer with /interface/wireguard/peers/show-client-config — either as text (conf output, or saved to a file with the file argument), or as a QR code (qr output) that a WireGuard client application can scan.

The generated configuration is built from the peer's client-* properties (see /interface/wireguard/peers). If the peer's client-address is left empty, the default address 192.168.177.2/24 is used in the generated configuration.

NOTE

The "AllowedIPs" value in the generated client configuration is 0.0.0.0/0, ::/0. Since RouterOS 7.21 it can be adjusted with the peer's client-allowed-address property; on older versions the value is fixed and can only be changed in the remote peer software.

Exporting a WireGuard interface

/interface/wireguard/wg-export writes the selected interface and its peers in standard WireGuard configuration format:

/interface/wireguard/wg-export [find name=wireguard1] \
    file=wireguard1.conf

Import this file with wg-import. The export contains [Interface] and [Peer] sections, but does not include the interface's IP addresses or RouterOS routes and firewall rules. Configure those separately on the destination router.

For a RouterOS configuration script, use the regular /interface/wireguard/export command instead. Treat exports and generated client configurations containing private keys as secrets.

NOTE

When you encounter issues with reply traffic having the wrong source address, translating packet source addresses to your loopback interface with NAT is a common workaround. This approach helps ensure the source address is consistent and correct when packets are routed back through the network.

The vrf parameter in the WireGuard context

The vrf parameter does not apply to the WireGuard interface itself (e.g., wg0, wg1), but rather to the UDP socket used for transporting encrypted packets.

There are two distinct layers in WireGuard operation:

  1. WireGuard interface — a virtual network device that handles plain (unencrypted) IP packets. Outgoing packets entering the interface are encrypted by WireGuard and sent through a UDP socket; incoming encrypted UDP packets are decrypted by WireGuard and delivered as plain IP packets through the interface.
  2. UDP socket — handles encrypted WireGuard traffic, receiving encrypted packets from the network and sending encrypted packets to the network.

The vrf parameter is relevant to the UDP socket layer (case 2). It specifies which routing table (VRF) the socket should use to determine how encrypted packets are sent or received.
This ensures that encrypted traffic follows the correct routing path and uses the proper source IP, preventing issues where packets might otherwise go out through the wrong interface or route.

Example

Suppose interface eth1 belongs to VRF foo.
If you want WireGuard to send and receive encrypted packets through eth1, configure WireGuard with vrf=foo.
It is normal for the WireGuard interface (wg0) itself to be in a different VRF than the one specified by the vrf parameter used by the internal UDP socket.

Multi-WAN setup

For WireGuard there is no inherent server-client relationship. Both ends can serve as an endpoint and both ends stream UDP handshake messages to each other if they have endpoints defined in their configurations. You can enable the "responder" option in the peer settings to emulate server-client behavior, where the "server" peer only replies to handshake messages from "client" peers and does not stream handshake messages by itself.
Because of this tunnel establishment behavior, handshake messages from different endpoints of the WireGuard tunnel are treated as two separate connections.
You need to account for this in setups with multiple paths to the "client" peer, as this can cause the "server" to reply to the "client" through a different route instead of the incoming route.
Below is a configuration example that addresses this behavior and ensures the "server" uses the incoming route to reply to the "client".

Configuration example

This example does not include WireGuard interface configuration as it is applicable to both RoadWarrior and Site to Site setups with two WAN connections such as PCC setup. The wan2 and wan3 routing tables must already exist, each with a route to the peer through its corresponding WAN. Replace the interface and table names to match your configuration. The output rules match the local WireGuard source port, because a remote peer can use a different port.

For these rules to work as intended, you need to enable the "responder" option in WireGuard peer settings, as the "server" could send handshakes via the incorrect interface because routing was not marked.

/ip/firewall/mangle
add chain=prerouting action=add-src-to-address-list \
    address-list=WAN2_WireGuard_clients address-list-timeout=1m \
    dst-port=13231 in-interface=ether2 protocol=udp \
    comment="Track WireGuard peers on WAN2"
add chain=output action=mark-connection \
    dst-address-list=WAN2_WireGuard_clients src-port=13231 \
    new-connection-mark=wan2 protocol=udp \
    comment="Mark WireGuard replies"
add chain=output action=mark-routing \
    connection-mark=wan2 src-port=13231 new-routing-mark=wan2 \
    protocol=udp \
    comment="Route WireGuard replies through WAN2"
add chain=prerouting action=add-src-to-address-list \
    address-list=WAN3_WireGuard_clients address-list-timeout=1m \
    dst-port=13231 in-interface=ether3 protocol=udp \
    comment="Track WireGuard peers on WAN3"
add chain=output action=mark-connection \
    dst-address-list=WAN3_WireGuard_clients src-port=13231 \
    new-connection-mark=wan3 protocol=udp \
    comment="Mark WireGuard replies"
add chain=output action=mark-routing \
    connection-mark=wan3 src-port=13231 new-routing-mark=wan3 \
    protocol=udp \
    comment="Route WireGuard replies through WAN3"

/ip/firewall/nat
add chain=srcnat action=masquerade \
    protocol=udp src-port=13231 out-interface=ether2 \
    comment="Use the WAN2 source address"
add chain=srcnat action=masquerade \
    protocol=udp src-port=13231 out-interface=ether3 \
    comment="Use the WAN3 source address"

The first mangle rule catches the source IP address by matching the destination port of the incoming WireGuard handshake and adds it to the list, which is later used to mark the outgoing WireGuard handshake. The timeout ensures that the same source IP address can later establish a WireGuard tunnel through a different WAN interface.
The second mangle rule marks connections that are used for routing marks and ensures the mark stays on the connection after the IP address is gone from the address list and the tunnel is established.
The third mangle rule forces the packet to use the correct routing table for the second WAN interface.
The last NAT rule ensures the packet is sent out with the correct source IP, as it is not adjusted by the mangle rules. Without this rule, the packet could have a different source IP depending on the setup. The rules are duplicated for WAN3 to ensure the WAN3 interface is also usable with WireGuard.

This rule set ensures the WireGuard tunnel is established on the interface that received the incoming handshake.

2FA setup

HotSpot services can be bound to WireGuard interfaces in RouterOS v7. This allows administrators to combine WireGuard's high-performance encryption with the HotSpot's captive portal features, supporting additional user-level authentication through a local database, User Manager, or RADIUS. The OTP feature strengthens security further.

Configuration example

For better security, configure otp-secret in /ip/hotspot/user or /user-manager/user. /ip/hotspot/user/add name=peer1 \

After setup is complete, launch WireGuard on your device. You should use an HTTPS login page for HotSpot and make sure the WireGuard peer can verify the login page certificate.

ZeroTier

The ZeroTier network hypervisor is a self-contained network virtualization engine that implements an Ethernet virtualization layer similar to VXLAN built atop a cryptographically secure global peer-to-peer network. Use cases

  • Hosting a game server at home (suited for LAN-only games) or creating a LAN party with friends.
  • Accessing LAN devices behind NAT directly.
  • Accessing LAN devices with SSH without opening a port to the Internet.
  • Using your local Pi-Hole setup from anywhere over the Internet.

Required Network Configuration

What ports does ZeroTier use?

It listens on 3 UDP ports:

  • 9993 - The default
  • A random, high-numbered port derived from your ZeroTier address
  • A random, high-numbered port for use with UPnP/NAT-PMP mappings

That means your peers could be listening on any port. To talk with them directly, you need to be able to send to them on any port.

Recommended Local Network and Internet Gateway Configuration

These ZeroTier recommended guidelines are consistent with the vast majority of typical deployments with commodity gateways and access points:

  • Don't restrict outbound UDP traffic.
  • Supporting either UPnP or NAT-PMP on your network can greatly improve performance by allowing ZeroTier endpoints to map external ports and avoid NAT traversal entirely.
  • IPv6 is recommended and can greatly improve direct connection reliability if supported on both ends of a direct link. If present, implement it without NAT (NAT is unnecessary with IPv6 and adds complexity) and with a stateful firewall that permits bidirectional UDP conversations.
  • Do not use "symmetric" NAT. Use "full cone" or "port restricted cone" NAT. Symmetric NAT is extremely hostile to peer-to-peer traffic and degrades VoIP, video chat, games, WebRTC, and many other protocols as well as ZeroTier.
  • No more than one layer of NAT should be present between ZeroTier endpoints and the Internet. Multiple layers introduce connection instability from chaotic interactions between states and behaviors at different levels. Do not use double NAT.
  • NAT devices should have a port mapping or connection timeout no shorter than 60 seconds.
  • Place no more than 16,000 devices behind each NAT-managed external IP address to ensure each device can map a sufficient number of ports.
  • Switches and wireless access points should allow direct local traffic between local devices. Turn off any "local isolation" features. If switches allow finer-grained control, allow local UDP traffic to/from port 9993.

Controller

RouterOS implements ZeroTier functionality in the role of a node where most of the network configuration must be done on the ZeroTier webpage dashboard. However, in situations where you would prefer to do all the configuration on your own device, RouterOS offers to host your own controller.

A common misunderstanding is to conflate network controllers with root servers (planet and moons). Root servers are connection facilitators that operate at the VL1 level. Network controllers are configuration managers and certificate authorities that belong to the VL2 level. Generally, root servers don’t join or control virtual networks and network controllers are not root servers, though it is possible to have a node do both.

Every ZeroTier instance has a self-hosting network controller that can be used to host virtual networks. A controller is responsible for admitting members to the network and issuing default configuration information including certificates. Controllers can in theory host up to 2^24 networks and serve many millions of devices, but you should spread large numbers of networks across many controllers for load balancing and fault tolerance.

Controller is configured in /zerotier/controller menu.

Now, create a new network through the controller section which operates at the VL2 level. Each network has its own controller and each network ID is generated from the controller address and controller ID combination.

Use the private=yes option for a more secure network:

[admin@Home] /zerotier> controller/add name=ZT-private instance=zt1 ip-range=172.27.27.10-172.27.27.20 private=yes routes=172.27.27.0/24
[admin@Home] /zerotier> controller/print
Columns: INSTANCE, NAME, NETWORK, PRIVATE
# INSTANCE  NAME        NETWORK           PRIVATE
0 zt1       ZT-private  879c0b5265a99e4b  yes

Add the new network under the interface section:

[admin@Home] /zerotier> interface/add network=879c0b5265a99e4b name=myZeroTier instance=zt1 
[admin@Home] /zerotier> interface/print interval=1
Columns: NAME, MAC-ADDRESS, NETWORK, STATUS
# NAME        MAC-ADDRESS        NETWORK           STATUS
0 myZeroTier  4A:19:35:6E:00:6E  879c0b5265a99e4b  ACCESS_DENIED

Each new peer asks the controller to join the network. In this case, the status is ACCESS_DENIED and the peer must be authorized, because the private=yes option was used.

After authorization, each member in the network receives information from the controller about new peers and approval to exchange packets with them:

[admin@Home] /zerotier> controller/member/print
Columns: NETWORK, ZT-ADDRESS
# NETWORK     ZT-ADDRESS
0  ZT-private  879a0b5265
[admin@Home] /zerotier> controller/member/set 0 authorized=yes

Verify newly configured IP address and route

[admin@Home] /zerotier> `/ip/address/print` where interface~"Zero"
Flags: D - DYNAMIC
Columns: ADDRESS, NETWORK, INTERFACE
# ADDRESS          NETWORK      INTERFACE
4 D 172.27.27.15/24  172.27.27.0  myZeroTier

[admin@Home] /zerotier> `/ip/route/pr` where gateway~"Zero"
Flags: D - DYNAMIC; A - ACTIVE; c, y - COPY
Columns: DST-ADDRESS, GATEWAY, DISTANCE
    DST-ADDRESS     GATEWAY     DISTANCE
DAc 172.27.27.0/24  myZeroTier         0
