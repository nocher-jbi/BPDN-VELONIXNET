IPsec

Internet Protocol Security (IPsec) is a set of protocols of the Internet Engineering Task Force (IETF) that protect IP packets on networks that are not trusted, such as the internet. It encrypts and authenticates the traffic between two routers, or between a router and a remote device, and it works with the devices of most vendors.

The protocols are in three groups:

  • Internet Key Exchange (IKE) makes and renews the keys.
  • Encapsulating Security Payload (ESP), RFC 4303, encrypts and authenticates the packets.
  • Authentication Header (AH), RFC 4302, only authenticates the packets.

The configuration menus

An IPsec connection in RouterOS is built from several entries under /ip/ipsec:

Menu What it has
profile The algorithms and timers of the IKE connection (phase 1).
proposal The algorithms and the lifetime of the encrypted traffic (phase 2).
peer The other side: its address, the IKE version (exchange-mode) and the profile. A peer with passive=yes waits for connections.
identity How the two sides authenticate each other: a pre-shared key, certificates or EAP. It also selects the mode config and the policy group for the peer.
policy Which traffic is encrypted: source and destination addresses, and the peer. A policy with template=yes is a pattern for the policies that are made dynamically.
policy/group A name that connects policy templates to identities.
mode-config Addresses, DNS servers and networks that a server gives to remote clients, or that a client asks for.
active-peers The IKE connections that exist now.
installed-sa The security associations (SAs) that encrypt traffic now.

The entries default of the profile, the proposal and the policy template exist after installation. The examples add their own entries, so that a change for one connection does not affect another.

WARNING

IPsec is sensitive to time changes. If the clocks of the two sides change in different ways, tunnels break and must be made again. Use an NTP client on both sides.

How IKE works

IKE authenticates the two sides and manages the security associations automatically. The IKE service does nothing most of the time. It starts to work in two cases:

  • Traffic matches a policy that has no SA yet. The router then connects to the peer of the policy.
  • A remote peer connects.

In both cases the peers make a connection in two phases:

  • Phase 1. The peers agree on the algorithms for the IKE messages and authenticate each other. They also make the keying material for all SAs. These settings must match on both sides:
  • authentication method
  • DH group
  • encryption algorithm
  • exchange mode
  • hash algorithm
  • NAT-T
  • DPD and lifetime (optional)
  • Phase 2. The peers make one or more SAs that IPsec uses to encrypt data. These settings must match:
  • IPsec protocol
  • mode (tunnel or transport)
  • authentication method
  • PFS (DH) group
  • lifetime

Each SA has a lifetime: a time, an amount of data, or both. There are two limits. At the soft lifetime, the IKE service makes a new SA to replace the old one. At the hard lifetime, the SA is removed.

WARNING

  • Phase 1 is not re-keyed when the lifetime ends if DPD is disabled; only phase 2 is re-keyed. To re-key phase 1, enable DPD.
  • Authentication with a pre-shared key (PSK) is open to offline attacks. This was known for the aggressive exchange mode, and it is also possible in the main and ike2 modes. Avoid pre-shared keys where you can and use certificates. If you use a key, make it long and random.

IKE can provide Perfect Forward Secrecy (PFS): new keying material is made for each phase 2, so that someone who gets the long-term phase 1 key cannot read all the data of the SAs made with it. Making keying material is expensive for the CPU. A modp8192 exchange can take several seconds even on a very fast computer. Without PFS this happens once for each phase 1; with PFS it happens for each phase 2 as well.

To avoid problems with IKE packets that would match a policy before its SA exists, packets that the router sends from UDP port 500, and packets to UDP port 500 of the router, are not checked against the policies.

Diffie-Hellman groups

The Diffie-Hellman (DH) key exchange lets two sides without a shared secret make one securely. RouterOS supports these Modular Exponential (MODP) and ECP groups, also known as Oakley groups:

The profile also accepts x25519. The IANA registry has more about the standards.

Larger groups are more secure but need more CPU:

  • Group 19 (256-bit ECP, ecp256) is fast and secure. Use it when both sides support it.
  • Group 14 (2048-bit MODP) is a practical balance of security and CPU use and is widely supported.
  • Group 5 (1536-bit) is a little less secure than group 14 and needs less CPU.
  • Group 2 (1024-bit) is the least secure of the common groups. Do not use it for new setups; use it only where an old device needs it.

To choose algorithms for a required security level, see https://www.keylength.com/en/4/.

Authentication Header (AH)

AH adds a header with a value that is calculated from the contents of the packet. The receiver can check that the packet was not changed, but the packet is not encrypted: AH gives authentication without privacy. ESP is usually the better choice, because it encrypts and can also authenticate.

RouterOS supports these authentication algorithms for AH: SHA2 (256, 512), SHA1 and MD5.

  • In transport mode, the AH header is put after the IP header. The IP data and the header are used for the calculation. IP fields that can change on the way, such as the TTL, are set to zero for the calculation.
  • In tunnel mode, the original IP packet is put into a new IP packet, and the whole original packet is authenticated.

Encapsulating Security Payload (ESP)

ESP encrypts the data with a shared key, and it can authenticate the packet in the same way as AH. ESP adds three parts to a packet:

  • ESP header - before the encrypted data. Its place depends on the mode.
  • ESP trailer - after the encrypted data. It has the padding that aligns the data.
  • ESP authentication data - the Integrity Check Value (ICV), when authentication is used.

In transport mode, the ESP header is put after the original IP header, and the trailer and the authentication value are added at the end. Only the IP payload is encrypted and authenticated; the IP header is not protected.

[gambar: An ESP packet in transport mode: the original IP header, the ESP header, the encrypted payload, the ESP trailer and the authentication data]

In tunnel mode, the original IP packet is put into a new IP packet, so the payload and the original IP header are both protected.

Algorithms

Authentication:

  • MD5
  • SHA1
  • SHA2 (256-bit, 512-bit; also 384-bit for the IKE connection)

Encryption:

  • AES - AES-CBC, AES-CTR and AES-GCM with 128-bit, 192-bit and 256-bit keys. AES-GCM authenticates the packets itself: a proposal with an AES-GCM algorithm needs auth-algorithms="".
  • ChaCha20-Poly1305
  • Blowfish
  • Twofish
  • Camellia - 128-bit, 192-bit and 256-bit keys.
  • DES - 56-bit DES-CBC.
  • 3DES - 168-bit (3 x 56-bit) DES.

DES, 3DES, Blowfish and MD5 are old algorithms. Use them only for devices that support nothing else.

Site-to-site tunnel

A site-to-site tunnel connects the local networks of two offices over the internet. Each router encrypts the traffic for the other network and sends it to the other router. This page shows a tunnel between two routers with static public addresses, and a GRE tunnel over IPsec for an office without a static address.

[gambar: Two office routers connected through the internet, each with its own local network]

In the examples, Office 1 has the public address 203.0.113.1 and the network 10.1.202.0/24. Office 2 has 203.0.113.2 and 10.1.101.0/24. The two offices must have different networks: if both use 192.168.88.0/24, change one of them first.

Connect two offices

Office 1

Add a phase 1 profile and a phase 2 proposal. The algorithms must be the same on both routers. Use separate entries for each tunnel, so that you can change one tunnel later without an effect on the others:

/ip/ipsec/profile/add name=office2 hash-algorithm=sha256 \
    enc-algorithm=aes-256 dh-group=ecp256
/ip/ipsec/proposal/add name=office2 auth-algorithms=sha256 \
    enc-algorithms=aes-256-cbc pfs-group=ecp256

Add the peer with the address of the other router, and an identity with the pre-shared key:

/ip/ipsec/peer/add name=office2 address=203.0.113.2/32 \
    exchange-mode=ike2 profile=office2
/ip/ipsec/identity/add peer=office2 secret=Example-psk-1

Add a policy for the traffic between the two networks:

/ip/ipsec/policy/add peer=office2 tunnel=yes \
    src-address=10.1.202.0/24 dst-address=10.1.101.0/24 \
    proposal=office2

Office 2

The configuration is the same with the addresses changed:

/ip/ipsec/profile/add name=office1 hash-algorithm=sha256 \
    enc-algorithm=aes-256 dh-group=ecp256
/ip/ipsec/proposal/add name=office1 auth-algorithms=sha256 \
    enc-algorithms=aes-256-cbc pfs-group=ecp256
/ip/ipsec/peer/add name=office1 address=203.0.113.1/32 \
    exchange-mode=ike2 profile=office1
/ip/ipsec/identity/add peer=office1 secret=Example-psk-1
/ip/ipsec/policy/add peer=office1 tunnel=yes \
    src-address=10.1.101.0/24 dst-address=10.1.202.0/24 \
    proposal=office1

WARNING

A pre-shared key is only as strong as the key itself. Use a long random key. For better security, use certificates (auth-method=digital-signature).

A ping without src-address leaves from the public address and does not match the policy.

Keep NAT away from the tunnel traffic

A source NAT rule changes the source address of the packets before IPsec sees them. They then no longer match the policy and are not encrypted: the tunnel is up, but no traffic passes.

The masquerade rule of the default configuration has ipsec-policy=out,none, so it leaves the traffic of IPsec policies alone and nothing more is needed. A masquerade rule without this matcher, for example chain=srcnat action=masquerade out-interface=ether1, needs a rule before it that accepts the traffic between the two networks. On the Office 1 router:

/ip/firewall/nat/add chain=srcnat action=accept place-before=0 \
    src-address=10.1.202.0/24 dst-address=10.1.101.0/24

On the Office 2 router:

/ip/firewall/nat/add chain=srcnat action=accept place-before=0 \
    src-address=10.1.101.0/24 dst-address=10.1.202.0/24
  • The rule must be before all other source NAT rules.
  • Connections that were tried before the rule was added keep their NAT. Remove them with /ip/firewall/connection/remove [find dst-address~"10.1.101."] (on Office 1), or restart both routers.

Keep FastTrack away from the tunnel traffic

FastTracked packets do not pass the IPsec policies, so connections over the tunnel are slow or lose packets when FastTrack takes them.

The default configuration is safe: it has two rules that accept forwarded traffic of IPsec policies (ipsec-policy=in,ipsec and ipsec-policy=out,ipsec) before its FastTrack rule, so the connections of the tunnel are not FastTracked. A firewall that has a FastTrack rule without these two rules before it needs one of the following.

Accept the established connections of the tunnel before the FastTrack rule, on both routers:

/ip/firewall/filter
add chain=forward action=accept connection-state=established,related \
    src-address=10.1.101.0/24 dst-address=10.1.202.0/24 \
    place-before=[find action=fasttrack-connection]
add chain=forward action=accept connection-state=established,related \
    src-address=10.1.202.0/24 dst-address=10.1.101.0/24 \
    place-before=[find action=fasttrack-connection]

With many tunnels and much traffic, these rules add load to the CPU. The other way is to leave the tunnel traffic out of connection tracking. Then the filter rules are not needed, and the CPU load is about 30% lower:

/ip/firewall/raw
add chain=prerouting action=notrack \
    src-address=10.1.101.0/24 dst-address=10.1.202.0/24
add chain=prerouting action=notrack \
    src-address=10.1.202.0/24 dst-address=10.1.101.0/24

Allow IPsec in the firewall

The default firewall drops connections that come from the internet. A router that starts the IKE connection gets the answers, but a router that waits for it does not get the first packet. Accept IKE (UDP port 500, and 4500 when there is NAT between the routers) and ESP from the other router, before the default drop rule, on both routers:

/ip/firewall/filter
add chain=input action=accept protocol=udp dst-port=500,4500 \
    src-address=203.0.113.2 comment="accept IKE" \
    place-before=[find comment="defconf: drop all not coming from LAN"]
add chain=input action=accept protocol=ipsec-esp \
    src-address=203.0.113.2 comment="accept IPsec ESP" \
    place-before=[find comment="defconf: drop all not coming from LAN"]

The default configuration already accepts forwarded traffic that comes out of or goes into an IPsec tunnel (the rules with ipsec-policy).

GRE tunnel over IPsec for an office without a static address

A GRE tunnel over IPsec gives each router an interface for the other office. You can then use routes, and the traffic of the tunnel needs no IPsec policy for each pair of networks. In this example only the server office needs an address that the other one can find: a static address, or a DNS name such as the one of IP Cloud.

[gambar: Two routers with a GRE tunnel between loopback addresses, protected by IPsec]

The server gives the client the address 192.168.99.2 with mode config. The GRE tunnel runs between this address and the address 192.168.99.1 of the server, and IPsec protects exactly this pair of addresses.

TIP

When both offices have static addresses, ipsec-secret of the GRE interface is a shorter way to protect a GRE tunnel with IPsec: see GRE and its reference.

Server

Add a bridge without ports as a loopback interface, with the address for the GRE tunnel:

/interface/bridge/add name=loopback
/ip/address/add address=192.168.99.1 interface=loopback

Add the profile and the proposal. The peer of this example listens for all IKEv2 connections, so other IKEv2 setups on the router, for example road warriors, use the same profile:

/ip/ipsec/profile/add name=ike2 dh-group=ecp256,modp2048 \
    enc-algorithm=aes-256,aes-192,aes-128
/ip/ipsec/proposal/add name=ike2-gre auth-algorithms="" \
    enc-algorithms=aes-128-gcm pfs-group=none

An AES-GCM proposal needs auth-algorithms="": the algorithm authenticates the packets itself.

Add a mode config that gives the client its address and the address of the server loopback, a policy group, and a policy template for this pair of addresses:

/ip/ipsec/mode-config/add name=ike2-gre address=192.168.99.2 \
    address-prefix-length=32 split-include=192.168.99.1/32 \
    system-dns=no
/ip/ipsec/policy/group/add name=ike2-gre
/ip/ipsec/policy/add template=yes group=ike2-gre \
    proposal=ike2-gre src-address=192.168.99.1/32 \
    dst-address=192.168.99.2/32

Add the peer that listens for IKEv2 connections (skip this if the router already has one) and the identity. The client has no fixed address, so the firewall rules for IKE and ESP on the server must not have src-address:

/ip/ipsec/peer/add name=ike2 exchange-mode=ike2 passive=yes \
    profile=ike2
/ip/ipsec/identity/add peer=ike2 secret=Example-psk-1 \
    generate-policy=port-strict mode-config=ike2-gre \
    policy-template-group=ike2-gre

Add the GRE interface, an address on it, and a route to the network of the other office:

/interface/gre/add name=gre-tunnel1 local-address=192.168.99.1 \
    remote-address=192.168.99.2
/ip/address/add address=172.16.1.1/30 interface=gre-tunnel1
/ip/route/add dst-address=10.1.101.0/24 gateway=172.16.1.2

Client

The client connects to the server, so its profile can name the exact algorithms. They must be in the list of the server:

/ip/ipsec/profile/add name=ike2-gre dh-group=ecp256 \
    enc-algorithm=aes-256
/ip/ipsec/proposal/add name=ike2-gre auth-algorithms="" \
    enc-algorithms=aes-128-gcm pfs-group=none

Add a mode config that asks the server for the settings, a policy group and a template:

/ip/ipsec/mode-config/add name=ike2-gre responder=no
/ip/ipsec/policy/group/add name=ike2-gre
/ip/ipsec/policy/add template=yes group=ike2-gre \
    proposal=ike2-gre src-address=192.168.99.2/32 \
    dst-address=192.168.99.1/32

Add the peer with the DNS name or the address of the server, and the identity. With a DNS name, address is for example address=example.sn.mynetname.net:

/ip/ipsec/peer/add name=office1 address=203.0.113.1 \
    exchange-mode=ike2 profile=ike2-gre
/ip/ipsec/identity/add peer=office1 secret=Example-psk-1 \
    generate-policy=port-strict mode-config=ike2-gre \
    policy-template-group=ike2-gre

When the connection is made, the client has the address 192.168.99.2, and /ip/ipsec/policy/print detail shows a dynamic policy from 192.168.99.2/32 to 192.168.99.1/32 with ph2-state=established.

Add the GRE interface, an address and a route:

/interface/gre/add name=gre-tunnel1 local-address=192.168.99.2 \
    remote-address=192.168.99.1
/ip/address/add address=172.16.1.2/30 interface=gre-tunnel1
/ip/route/add dst-address=10.1.202.0/24 gateway=172.16.1.1

The two offices now reach each other through the GRE tunnel, and IPsec encrypts the GRE packets.

Road warrior with certificates

IKEv2 road warrior server with certificates in RouterOS: create the certificates, configure the server, give clients addresses and routes with mode config, and connect RouterOS, Windows, macOS, iOS, Android and Linux...

Road warrior with certificates

A road warrior is a remote device, such as a laptop, a phone or a small router, that connects to the office from any place on the internet. This page sets up a RouterOS IKEv2 server that authenticates the clients with certificates, and the clients for RouterOS and other systems.

[gambar: A remote client connects through the internet to the office router and reaches the networks behind it]

In the examples, the office router has the public address 203.0.113.1 and the network 10.1.202.0/24 behind it. The clients get addresses from 192.168.77.0/24.

To let users log in with a user name and a password in place of a certificate for each device, see Road warrior with EAP and User Manager.

Server

Certificates

The server needs a certificate, and each client needs one. This example makes them on the router with its own certificate authority (CA); you can also use a separate CA. Certificates explains the commands.

The server certificate must meet these conditions, or some clients do not connect:

  • The common name is the IP address or the DNS name of the server.
  • The subject alternative name (SAN) has the IP address or the DNS name of the server.
  • The key usage has tls-server. A client certificate has tls-client.
/certificate
add name=ca common-name=ca key-usage=key-cert-sign,crl-sign
sign ca ca-crl-host=203.0.113.1
add name=server1 common-name=203.0.113.1 \
    subject-alt-name=IP:203.0.113.1 key-usage=tls-server
sign server1 ca=ca
add name=rw-client1 common-name=rw-client1 key-usage=tls-client
sign rw-client1 ca=ca

IPsec configuration

Add a profile and a proposal. pfs-group=none avoids problems with clients of other vendors:

/ip/ipsec/profile/add name=ike2
/ip/ipsec/proposal/add name=ike2 pfs-group=none

Add a pool for the client addresses and a mode config that gives each client an address from it:

/ip/pool/add name=ike2-pool ranges=192.168.77.2-192.168.77.254
/ip/ipsec/mode-config/add name=ike2-conf address-pool=ike2-pool \
    address-prefix-length=32

Add a policy group and a policy template. The template limits the dynamic policies to the client addresses:

/ip/ipsec/policy/group/add name=ike2-policies
/ip/ipsec/policy/add template=yes group=ike2-policies \
    proposal=ike2 src-address=0.0.0.0/0 dst-address=192.168.77.0/24

Add a peer that listens for all IKEv2 connections, and an identity that accepts every client with a certificate that the CA signed:

/ip/ipsec/peer/add name=ike2 exchange-mode=ike2 passive=yes \
    profile=ike2
/ip/ipsec/identity/add peer=ike2 auth-method=digital-signature \
    certificate=server1 generate-policy=port-strict \
    mode-config=ike2-conf policy-template-group=ike2-policies

In the firewall, accept IKE and ESP from the internet: see Firewall and routing for IPsec for the rules.

When a client is connected, the server shows it with the name of its certificate and the address that it got:

[admin@Office1] > /ip/ipsec/active-peers/print
Flags: R - RESPONDER

#   ID             STATE        UPTIME  P  REMOTE-ADDRESS  DYNAMIC-ADDRESS
0 R CN=rw-client1  established  2m16s   1  203.0.113.2     192.168.77.254

Different settings for one client

An identity can match one client and give it other settings. This example gives the client with the certificate rw-client1 a fixed address and access to one network. Add a mode config and a policy template for the address:

/ip/ipsec/mode-config/add name=usr-a address=192.168.66.2 \
    address-prefix-length=32 split-include=10.1.202.0/24 \
    system-dns=no
/ip/ipsec/policy/add template=yes group=ike2-policies \
    proposal=ike2 src-address=0.0.0.0/0 dst-address=192.168.66.0/24

Add an identity that matches the certificate:

/ip/ipsec/identity/add peer=ike2 auth-method=digital-signature \
    certificate=server1 generate-policy=port-strict \
    match-by=certificate remote-certificate=rw-client1 \
    mode-config=usr-a policy-template-group=ike2-policies

WARNING

If the ID that a client sends (ID_i) does not match its certificate, the server finds no identity for it. See remote-id in the identity reference.

Split tunnel and DNS

By default a client sends all its traffic through the tunnel. With a split tunnel, the client sends only the traffic for the office networks through the tunnel and the rest directly to the internet. Set the office networks in split-include of the mode config:

/ip/ipsec/mode-config/set [find name=ike2-conf] \
    split-include=10.1.202.0/24

The server also sends DNS servers to the client. With system-dns=yes (the default) these are the DNS servers of the router. To send another one:

/ip/ipsec/mode-config/set [find name=ike2-conf] system-dns=no \
    static-dns=10.1.202.1

A split tunnel is not a security measure: a client can still ask for other networks in phase 2. Do not narrow the policy template to the split networks, because this breaks clients of some vendors. Limit the access with the firewall:

/ip/firewall/filter/add chain=forward action=drop \
    src-address=192.168.77.0/24 dst-address=!10.1.202.0/24 \
    place-before=[find comment="defconf: accept in ipsec policy"]

The rule must be before the rule of the default configuration that accepts all traffic from IPsec policies, or it never matches. For a client with its own address, such as 192.168.66.2 in the example of one client, add a rule of the same kind with that address. To allow one server only, use its address in dst-address, for example dst-address=!10.1.202.10.

Export the client certificates

Most clients take a PKCS12 file, which has the certificate and its private key:

/certificate/export-certificate rw-client1 type=pkcs12 \
    export-passphrase=Example-p12-pass-1 file-name=rw-client1

The file rw-client1.p12 is now in the files of the router. A PKCS12 file also has the CA certificate, but some systems do not install it from there. Export the CA certificate separately for them:

/certificate/export-certificate ca file-name=ca

For software that does not take PKCS12, export the client certificate in PEM format. This writes a .crt file and a .key file:

/certificate/export-certificate rw-client1 \
    export-passphrase=Example-p12-pass-1 file-name=rw-client1

Send the files to the client in a safe way: they have the private key of the client.

Known limits of clients

  • Windows ignores the networks of split-include and asks for a policy to 0.0.0.0/0. After the SA is made, Windows asks for DHCP option 249, and RouterOS answers with the split-include networks.
  • macOS and iOS accept only the first split-include network.
  • macOS and iOS use the DNS servers of system-dns and static-dns only when split-include is 0.0.0.0/0.
  • Some clients can use another PFS group in phase 2. Use pfs-group=none in the proposal to avoid problems.

IKEv2 road warrior server with EAP-MSCHAPv2 in RouterOS: users log in with a user name and a password that User Manager or another RADIUS server checks, with a Let's Encrypt certificate on the server, static...

Road warrior with EAP and User Manager

With EAP, the users of an IKEv2 server log in with a user name and a password. The router passes the authentication to a RADIUS server. This page uses User Manager, the RADIUS server of RouterOS, on the same router. The computers and phones of the users need no client certificate, and their built-in IKEv2 clients work.

[gambar: A remote client connects through the internet to the office router and reaches the networks behind it]

What you need

  1. A DNS name for the public address of the router. IP Cloud gives one.
  2. TCP port 80 of the router reachable from the internet, for the certificate. If the router is behind NAT, forward the port.
  3. The user-manager package on the router.

Get a certificate

EAP-MSCHAPv2 needs a TLS handshake, so the server needs a certificate that the clients can check. A Let's Encrypt certificate is checked by most systems without any setup on the client. Get one with /certificate/add-acme for the DNS name of the router: Certificates describes the command. The certificate authority checks the name through TCP port 80 of the router, so this port must be open from the internet while the certificate is made and renewed, and it is the port of the www service: do not leave management access open to the internet on it.

The certificate then exists in the certificate store:

/certificate/print detail where name~"letsencrypt"

Set up User Manager

Let the router itself send RADIUS requests to User Manager, enable User Manager with the certificate, and add a user. Use the name of the certificate on your router:

/user-manager/router/add name=local address=127.0.0.1 \
    shared-secret=Radius-Secret-2
/user-manager/set enabled=yes \
    certificate="letsencrypt_2021-04-09T07:10:55Z"
/user-manager/user/add name=user1 password=Example-pass-1

Add the RADIUS client for IPsec with the same secret:

/radius/add address=127.0.0.1 secret=Radius-Secret-2 service=ipsec

Set up the IKEv2 server

The profile, the proposal, the pool, the mode config, the policy template and the peer are the same as for certificates:

/ip/ipsec/profile/add name=ike2
/ip/ipsec/proposal/add name=ike2 pfs-group=none
/ip/pool/add name=ike2-pool ranges=192.168.77.2-192.168.77.254
/ip/ipsec/mode-config/add name=ike2-conf address-pool=ike2-pool \
    address-prefix-length=32
/ip/ipsec/policy/group/add name=ike2-policies
/ip/ipsec/policy/add template=yes group=ike2-policies \
    proposal=ike2 src-address=0.0.0.0/0 dst-address=192.168.77.0/24
/ip/ipsec/peer/add name=ike2 exchange-mode=ike2 passive=yes \
    profile=ike2

The identity uses auth-method=eap-radius and the certificate of the server:

/ip/ipsec/identity/add peer=ike2 auth-method=eap-radius \
    certificate="letsencrypt_2021-04-09T07:10:55Z" \
    generate-policy=port-strict mode-config=ike2-conf \
    policy-template-group=ike2-policies

In the firewall, accept IKE and ESP from the internet: see Firewall and routing for IPsec for the rules.

When a user is connected, the server shows the user name and the address of the client. In this output the user is tst:

[admin@Office1] > /ip/ipsec/active-peers/print
Flags: R - RESPONDER
Columns: ID, STATE, UPTIME, PH2-TOTAL, REMOTE-ADDRESS, DYNAMIC-ADDRESS
#   ID   STATE        UPTIME  PH2-TOTAL  REMOTE-ADDRESS  DYNAMIC-ADDRESS
0 R tst  established  5s              1  203.0.113.2     192.168.77.253

For a split tunnel and DNS servers, see Road warrior with certificates: the mode config settings are the same.

Connect a RouterOS client

A RouterOS router can also be the client. It needs the CA that signed the server certificate as a trusted certificate; in this example the CA certificate has the name ca on the client. The profile, the proposal, the policy group, the template, the mode config and the peer are the same as for a client with a certificate; the identity has the user name and the password:

/ip/ipsec/identity/add peer=office auth-method=eap \
    eap-methods=eap-mschapv2 username=user1 \
    password=Example-pass-1 certificate=ca \
    generate-policy=port-strict mode-config=ike2-rw \
    policy-template-group=ike2-rw

The log of the client has EAP authorized and peer authorized when the login succeeds.

Give a user a fixed address

The RADIUS attribute Framed-IP-Address gives a user a fixed address:

/user-manager/user/set [find name=user1] shared-users=1 \
    attributes=Framed-IP-Address:192.168.77.100

WARNING

Take the fixed address out of the pool of the other users, and keep shared-users=1 for this user: two sessions cannot have the same address.

Send accounting

The router sends RADIUS accounting for IPsec users by default. To also record the traffic while a session is open, set an interval for the updates. With many sessions, use a longer interval to save CPU:

/ip/ipsec/settings/set interim-update=1m

Route-based IPsec with XFRM

Route-based IPsec in RouterOS with XFRM interfaces: bind a policy group to an interface, route traffic into the tunnel, and run OSPF over it.

Route-based IPsec with XFRM

Policy-based IPsec selects traffic by the source and destination addresses of the policies. An XFRM interface adds a route-based mode: a policy group is bound to a virtual interface, and the traffic that is routed into this interface uses the policies of the group. The routing table then decides which traffic enters the tunnel, and dynamic routing protocols can run over it.

An XFRM interface behaves like other interfaces: it has an IP address, an MTU and a running state. It is configured in /interface/xfrm.

Use it for:

  • Dynamic routing over IPsec. A branch office has several networks and gets new ones over time. With policy-based IPsec, each pair of local and remote networks needs a policy. With an XFRM interface, the branch runs OSPF over the tunnel, and new networks are reachable without new policies.
  • Several WAN links and policy routing. The tunnel is a route, so routing marks or a VRF can send selected traffic into it, and the tunnel can move between WAN links without a change of the policies.

In the example, R1 has the public address 203.0.113.1, the LAN 192.168.51.0/28 and the XFRM address 192.168.50.1/24. R2 has 203.0.113.2, the LAN 192.168.52.0/28 and 192.168.50.2/24. R1 starts the connection and R2 answers.

R1

Add the LAN bridge, the XFRM interface and their addresses:

/interface/bridge/add name=lan
/interface/xfrm/add name=xfrm1
/ip/address/add address=192.168.51.1/28 interface=lan
/ip/address/add address=192.168.50.1/24 interface=xfrm1

Add the profile and the proposal. They must be the same on both routers:

/ip/ipsec/profile/add name=xfrm-example hash-algorithm=sha256 \
    enc-algorithm=aes-256 dh-group=modp2048
/ip/ipsec/proposal/add name=xfrm-example auth-algorithms=sha256 \
    enc-algorithms=aes-256-cbc pfs-group=none

Add a policy group and bind it to the interface. A group of its own keeps these policies apart from the other IPsec policies of the router:

/ip/ipsec/policy/group/add name=xfrm1-group interface=xfrm1

Add the peer and the identity. The identity must have the same group in policy-template-group:

/ip/ipsec/peer/add name=xfrm-example address=203.0.113.2/32 \
    local-address=203.0.113.1 exchange-mode=ike2 \
    profile=xfrm-example
/ip/ipsec/identity/add peer=xfrm-example \
    auth-method=pre-shared-key secret=Example-psk-1 \
    generate-policy=port-strict policy-template-group=xfrm1-group

Add the policy for the traffic between the LANs, and route the remote LAN through the interface:

/ip/ipsec/policy/add peer=xfrm-example group=xfrm1-group \
    tunnel=yes src-address=192.168.51.0/28 \
    dst-address=192.168.52.0/28 proposal=xfrm-example
/ip/route/add dst-address=192.168.52.0/28 gateway=xfrm1

R2

R2 has the same configuration with the addresses changed, and its peer has passive=yes:

/interface/bridge/add name=lan
/interface/xfrm/add name=xfrm1
/ip/address/add address=192.168.52.1/28 interface=lan
/ip/address/add address=192.168.50.2/24 interface=xfrm1
/ip/ipsec/profile/add name=xfrm-example hash-algorithm=sha256 \
    enc-algorithm=aes-256 dh-group=modp2048
/ip/ipsec/proposal/add name=xfrm-example auth-algorithms=sha256 \
    enc-algorithms=aes-256-cbc pfs-group=none
/ip/ipsec/policy/group/add name=xfrm1-group interface=xfrm1
/ip/ipsec/peer/add name=xfrm-example address=203.0.113.1/32 \
    local-address=203.0.113.2 exchange-mode=ike2 passive=yes \
    profile=xfrm-example
/ip/ipsec/identity/add peer=xfrm-example \
    auth-method=pre-shared-key secret=Example-psk-1 \
    generate-policy=port-strict policy-template-group=xfrm1-group
/ip/ipsec/policy/add peer=xfrm-example group=xfrm1-group \
    tunnel=yes src-address=192.168.52.0/28 \
    dst-address=192.168.51.0/28 proposal=xfrm-example
/ip/route/add dst-address=192.168.51.0/28 gateway=xfrm1

Check

The interface has the flag R after an SA that uses it is made. Until then, an IP address on the interface is shown as invalid.

[admin@R1] > /interface/xfrm/print detail
Flags: R - RUNNING
0  R name="xfrm1" mtu=1400

The policy is active and shows the interface:

[admin@R1] > /ip/ipsec/policy/print detail where peer=xfrm-example
Flags: A - ACTIVE
0 A peer=xfrm-example tunnel=yes group=xfrm1-group src-address=192.168.51.0/28
    src-port=any dst-address=192.168.52.0/28 dst-port=any protocol=all
    action=encrypt level=require ipsec-protocols=esp sa-src-address=203.0.113.1
    sa-dst-address=203.0.113.2 proposal=xfrm-example active-interface=xfrm1
    ph2-count=1 ph2-state=established

Test the tunnel from the address of one LAN to the other: /ping 192.168.52.1 src-address=192.168.51.1.

WARNING

If the SA is made but the interface does not get the flag R and no traffic passes, re-create the interface or restart the router.

  • A policy group can be bound to one XFRM interface only.
  • mtu is the layer 3 MTU of the interface. The default of 1400 bytes leaves room for the ESP overhead. A change of mtu applies at once, and actual-mtu in /interface/print detail shows the value in use. If actual-mtu is not the configured value, set mtu again.
  • The example uses a pre-shared key. Use certificates in production.
  • With the default firewall, the XFRM interface is not in the LAN interface list, so the router drops what arrives through it for the router itself, for example OSPF packets. Add the interface to the list or add accept rules for it.

OSPF over XFRM

OSPF can run over the XFRM interface, and its routes replace the static routes of the first example. The policy must then match the OSPF packets too, also the multicast hello packets, so replace the LAN-to-LAN policy with a policy for all addresses in the XFRM group. The policy applies only to the traffic that is routed into the interface.

On R1:

/ip/route/remove [find gateway=xfrm1]
/ip/ipsec/policy/remove [find peer=xfrm-example]
/ip/ipsec/policy/add peer=xfrm-example group=xfrm1-group \
    tunnel=yes src-address=0.0.0.0/0 dst-address=0.0.0.0/0 \
    proposal=xfrm-example
/routing/ospf/instance/add name=xfrm-ospf version=2 \
    router-id=192.168.50.1
/routing/ospf/area/add name=backbone instance=xfrm-ospf \
    area-id=0.0.0.0
/routing/ospf/interface-template
add interfaces=xfrm1 area=backbone type=ptp
add networks=192.168.51.0/28 area=backbone

On R2, the same with its router ID and LAN:

/ip/route/remove [find gateway=xfrm1]
/ip/ipsec/policy/remove [find peer=xfrm-example]
/ip/ipsec/policy/add peer=xfrm-example group=xfrm1-group \
    tunnel=yes src-address=0.0.0.0/0 dst-address=0.0.0.0/0 \
    proposal=xfrm-example
/routing/ospf/instance/add name=xfrm-ospf version=2 \
    router-id=192.168.50.2
/routing/ospf/area/add name=backbone instance=xfrm-ospf \
    area-id=0.0.0.0
/routing/ospf/interface-template
add interfaces=xfrm1 area=backbone type=ptp
add networks=192.168.52.0/28 area=backbone

The neighbor reaches the state Full, and each router learns the LAN of the other one as an OSPF route (/ip/route/print where ospf):

[admin@R1] > /routing/ospf/neighbor/print
Flags: D - DYNAMIC
0 D instance=xfrm-ospf area=backbone interface=xfrm1 address=192.168.50.2
    router-id=192.168.50.2 state="Full" state-changes=5 adjacency=45s
    timeout=35s

Both routers must have the same MTU on the XFRM interface. With different values the OSPF neighbor stays in ExStart. Check actual-mtu with /interface/print detail on both routers.

Firewall and routing for IPsec in RouterOS: allow IKE and ESP, accept only traffic that came through IPsec, drop unencrypted traffic with a policy, and make a tunnel use a certain WAN link or public address.

Firewall and routing for IPsec

This page has the firewall rules that IPsec needs, the ways to accept only encrypted traffic, and what to do when a router has several WAN links or several public addresses.

Allow IKE and ESP

IPsec uses these packets between the two routers:

  • UDP port 500 for IKE.
  • UDP port 4500 for IKE and the encrypted traffic when there is NAT between the two sides (NAT traversal).
  • IP protocol 50 (ESP) for the encrypted traffic without NAT, or protocol 51 (AH).

The default firewall drops them when they come from the internet. Accept them before the default drop rule:

/ip/firewall/filter
add chain=input action=accept protocol=udp dst-port=500,4500 \
    in-interface-list=WAN comment="accept IKE" \
    place-before=[find comment="defconf: drop all not coming from LAN"]
add chain=input action=accept protocol=ipsec-esp \
    in-interface-list=WAN comment="accept IPsec ESP" \
    place-before=[find comment="defconf: drop all not coming from LAN"]

For a tunnel to one known router, add src-address with its address to both rules.

Accept only traffic that came through IPsec

Sometimes a service must be reachable only through IPsec. For example, an L2TP server with IPsec must not accept L2TP connections without encryption. There are three ways:

  • The IPsec policy matcher of the firewall.
  • An IPsec policy with the action discard below the dynamic policies. This suits road warrior setups, where the policies are made dynamically.
  • A DSCP value or a priority that is set in mangle before encryption and matched in the firewall after decryption.

IPsec policy matcher

The matcher ipsec-policy has a direction and a policy: in,ipsec matches packets that arrived through IPsec and were decrypted, and in,none matches packets that did not. The firewall sees the packet after decryption, so the other matchers apply to the inner packet.

These rules accept everything that arrived through IPsec and drop the rest:

/ip/firewall/filter
add chain=input action=accept in-interface-list=WAN \
    ipsec-policy=in,ipsec comment="accept IPsec traffic"
add chain=input action=drop in-interface-list=WAN log=yes \
    comment="drop all"

Put the rules for IKE and ESP before these rules, or the tunnel cannot be made. With the default firewall, add the accept rule with place-before=[find comment="defconf: drop all not coming from LAN"]; the drop rule of the default configuration then does the dropping.

To accept only GRE packets from one address through IPsec, and drop the rest:

/ip/firewall/filter
add chain=input action=accept in-interface-list=WAN \
    ipsec-policy=in,ipsec protocol=gre src-address=192.168.33.1
add chain=input action=drop in-interface-list=WAN log=yes \
    comment="drop all"

For an L2TP server, use-ipsec=required of the server does this without firewall rules: see L2TP. With firewall rules, to accept L2TP only through IPsec:

/ip/firewall/filter
add chain=input action=accept in-interface-list=WAN \
    ipsec-policy=in,ipsec protocol=udp dst-port=1701 \
    comment="accept L2TP over IPsec"
add chain=input action=drop in-interface-list=WAN protocol=udp \
    dst-port=1701 log=yes comment="drop L2TP without IPsec"

The default configuration has the same matcher in the forward chain: its rules accept forwarded traffic that comes out of or goes into an IPsec tunnel.

Discard policy

A policy with action=discard drops the packets that match it. Dynamic policies are above it and have priority, so traffic of a connected client is encrypted, and the same kind of traffic without a tunnel is dropped. This example is for an L2TP server with IPsec on the public address 203.0.113.1. The router then drops L2TP traffic that is not encrypted:

/ip/ipsec/policy/add src-address=203.0.113.1 dst-address=0.0.0.0/0 \
    sa-src-address=203.0.113.1 protocol=udp src-port=1701 \
    tunnel=yes action=discard

WARNING

The order of the policies is important. The discard policy must be below the dynamic policies: move it below the policy template if necessary.

When a client is connected, its dynamic policy is above the discard policy. This output is from a server with the address 1.1.1.1:

Troubleshooting

Troubleshooting IPsec in RouterOS: where to look, what the log messages mean, and how to solve tunnels that do not come up, tunnels without traffic, slow connections and XFRM problems.

Troubleshooting

Where to look

Check a tunnel in this order:

  1. /ip/ipsec/active-peers/print - is the IKE connection (phase 1) established? PH2-TOTAL shows the number of phase 2 SAs.
  2. /ip/ipsec/installed-sa/print - are there SAs for both directions? The flag S shows that an SA has carried traffic.
  3. /ip/ipsec/policy/print detail - does a policy exist for the traffic? A dynamic policy shows ph2-state=established.
  4. /ip/ipsec/statistics/print - counters of the errors of the encryption itself.
  5. /log/print where topics~"ipsec" - what happened and why.

The log has more detail when all messages of the ipsec topic except the debug messages are logged. Remove the rule when you are done:

/system/logging/add topics=ipsec,!debug
/system/logging/remove [find topics~"ipsec"]

Messages in the log

Message Meaning
got fatal error: AUTHENTICATION_FAILED on one side, peer failed to authorize on the other The pre-shared keys are different.
no proposal chosen The algorithms of the two sides do not match. The peer is established and PH2-TOTAL is empty: compare the proposals (phase 2): encryption, authentication and PFS group.
No clear message, and the peer is never established Compare the profiles (phase 1): encryption, hash and DH group must have a common value on both sides.
can't get private key The certificate of the identity has no private key on this router. Check that the identity names the right certificate: after the import of a PKCS12 file, the client certificate and the CA certificate can have the same name.
phase1 negotiation failed due to time up The two sides cannot talk to each other. See the section about it on this page.
fatal NO-PROPOSAL-CHOSEN notify message The other side cannot accept the proposed algorithms. Look at the log or the configuration of the other side, and check that both have the same set of algorithms.

The tunnel does not come up

"phase1 negotiation failed due to time up"

The two sides cannot exchange IKE packets. Possible causes:

  • The address of the peer is wrong.
  • A firewall drops UDP port 500 or 4500: see Firewall and routing for IPsec.
  • NAT between the two sides does not pass the IKE packets correctly.
  • local-address of the peer does not fit the link that the packets leave on: see Firewall and routing for IPsec.

How to use IKEv2

Set exchange-mode=ike2 in the peer on both sides.

strongSwan: "initiator did not reauthenticate as requested"

RouterOS does not support IKEv2 reauthentication (RFC 4478). Disable reauthentication in strongSwan.

The tunnel is up, but traffic does not pass

No traffic at all

Check that NAT does not change the packets before IPsec sees them. With a masquerade rule and no bypass rule, the peer is established but the packets do not match the policy: see Site-to-site tunnel.

When you test from the router itself, ping from an address of the local network (src-address). A ping from the public address of the router does not match a policy between two local networks.

Ping works in one direction only

A firewall accepts new connections in one direction only. Check the filter rules, or accept all traffic that comes out of and goes into the tunnel (ipsec-policy=in,ipsec and ipsec-policy=out,ipsec).

Packets are lost or connections are very slow, and the packet sniffer or Torch makes the problem go away

FastTrack or FastPath takes the packets before they are encrypted, so they do not pass the IPsec policies. Leave the traffic of the tunnel out of FastTrack: see Site-to-site tunnel.

Only encrypted traffic must be accepted

See Firewall and routing for IPsec.

XFRM interfaces

The XFRM interface does not come up

The flag R appears only after an SA that uses the interface is made. If the SA is made but the interface stays down, re-create the interface or restart the router. An IP address on the interface is shown as invalid until the interface runs.

The XFRM policy stays in no-phase2

Check that the policy group is bound to the XFRM interface, that the identity has the same group in policy-template-group, and that the traffic is routed through the XFRM interface. If you use the default policy group, check that no other policy of the group takes the traffic.

OSPF over XFRM stays in ExStart

The XFRM interfaces of both routers must have the same MTU. Check actual-mtu with /interface/print detail on both routers and set mtu again if the values differ. With different values, the OSPF database description exchange cannot finish.

IKEv2 EAP between NordVPN and RouterOS

Starting from RouterOS v6.45, it is possible to establish an IKEv2 secured tunnel to NordVPN servers using EAP authentication. This manual page explains how to configure it.

Installing the root CA

Start off by downloading and importing the NordVPN root CA certificate.

/tool/fetch url="https://downloads.nordvpn.com/certificates/root.der"
/certificate/import file-name=root.der

There should now be the trusted NordVPN Root CA certificate in the System/Certificates menu.

[admin@MikroTik] > /certificate/print where name~"root.der"

 #         NAME            COMMON-NAME            SUBJECT-ALT-NAME                                         FINGERPRINT           
 0       T root.der_0      NordVPN Root CA                                                                 8b5a495db498a6c2c8c...

Finding out the server's hostname

Navigate to https://nordvpn.com/servers/tools/ and find out the recommended server's hostname. In this case, it is lv20.nordvpn.com.

Setting up the IPsec tunnel

It is advised to create a separate Phase 1 profile and Phase 2 proposal configurations to not interfere with any existing or future IPsec configuration.

/ip/ipsec/profile
add name=NordVPN
/ip/ipsec/proposal
add name=NordVPN pfs-group=none

While it is possible to use the default policy template for policy generation, it is better to create a new policy group and template to separate this configuration from any other IPsec configuration.

/ip/ipsec/policy/group
add name=NordVPN
/ip/ipsec/policy
add dst-address=0.0.0.0/0 group=NordVPN proposal=NordVPN src-address=0.0.0.0/0 template=yes

Create a new mode config entry with responder=no that will request configuration parameters from the server.

/ip/ipsec/mode-config
add name=NordVPN responder=no

Lastly, create peer and identity configurations. Specify your NordVPN credentials in the username and password parameters.

/ip/ipsec/peer
add address=lv20.nordvpn.com exchange-mode=ike2 name=NordVPN profile=NordVPN
/ip/ipsec/identity
add auth-method=eap certificate="" eap-methods=eap-mschapv2 generate-policy=port-strict mode-config=NordVPN peer=NordVPN policy-template-group=NordVPN username=support@mikrotik.com password=secret

Verify that the connection is successfully established.

/ip/ipsec
active-peers print
installed-sa print

Choosing what to send over the tunnel

If we look at the generated dynamic policies, we see that only traffic with a specific (received by mode config) source address will be sent through the tunnel. But a router in most cases will need to route a specific device or network through the tunnel. In such a case, we can use source NAT to change the source address of packets to match the mode config address. Since the mode config address is dynamic, it is impossible to create a static source NAT rule. In RouterOS it is possible to generate dynamic source NAT rules for mode config clients.

Option 1: Sending all traffic over the tunnel

In this example, we have a local network 10.5.8.0/24 behind the router and we want all traffic from this network to be sent over the tunnel. First of all, we have to make a new IP/Firewall/Address list which consists of our local network.

/ip/firewall/address-list
add address=10.5.8.0/24 list=local

It is also possible to specify only single hosts from which all traffic will be sent over the tunnel. Example:

/ip/firewall/address-list
add address=10.5.8.120 list=local
add address=10.5.8.23 list=local

When it is done, we can assign the newly created IP/Firewall/Address list to mode config configuration.

/ip/ipsec/mode-config
set [ find name=NordVPN ] src-address-list=local

Verify correct source NAT rule is dynamically generated when the tunnel is established.

[admin@MikroTik] > /ip/firewall/nat/print 
Flags: X - disabled, I - invalid, D - dynamic 
 0  D ;;; ipsec mode-config
      chain=srcnat action=src-nat to-addresses=192.168.77.254 src-address-list=local dst-address-list=!local

INFO

Warning

Make sure the dynamic mode config address is not a part of the local network.

Important: It is also possible to combine both options (1 and 2) to allow access to specific addresses only for specific local addresses/networks.

Option 2: Accessing certain addresses over the tunnel

It is also possible to send only specific traffic over the tunnel by using the connection-mark parameter in the Mangle firewall. It works similarly to Option 1 - a dynamic NAT rule is generated based on the configured connection-mark parameter under mode config.

First of all, set the connection-mark under your mode config configuration.

/ip/ipsec/mode-config
set [ find name=NordVPN ] connection-mark=NordVPN

When it is done, a NAT rule is generated with the dynamic address provided by the server:

[admin@MikroTik] > /ip/firewall/nat/print 
Flags: X - disabled, I - invalid, D - dynamic 
 0  D ;;; ipsec mode-config
      chain=srcnat action=src-nat to-addresses=192.168.77.254 connection-mark=NordVPN

After that, it is possible to apply this connection-mark to any traffic using the Mangle firewall. In this example, access to mikrotik.com and 8.8.8.8 is granted over the tunnel.

Create a new address list:

/ip/firewall/address-list
add address=mikrotik.com list=VPN
add address=8.8.8.8 list=VPN

Apply connection-mark to traffic matching the created address list:

/ip/firewall/mangle
add action=mark-connection chain=prerouting dst-address-list=VPN new-connection-mark=NordVPN passthrough=yes

QKD Integration in RouterOS IPsec (PPK)

1. Introduction

This manual describes the Post-Quantum Pre-shared Key (RFC9867) feature in RouterOS IPsec and its integration with Quantum Key Distribution (QKD).

PPK provides forward security against quantum attacks by using keys that are either dynamically distributed or statically configured. All PPK types (static, PSK, QKD) benefit from RFC 8784 recommendations: keys should have at least 256 bits of entropy to provide ~128 bits of post-quantum security.

RouterOS supports three PPK sources:

  • Static PPK — manually configured per-peer secret.
  • PSK (Pre-shared Key) — one-time generated keys, optionally usable only for initial IKE SA.
  • QKD — dynamically distributed keys from a QKD server.

Dynamic keys (PSK/QKD) are consumed and invalidated after use. Static keys remain valid across sessions but offer weaker security if reused.

2. Concepts

  • PPK (Post-Quantum Pre-shared Key): An additional secret shared during IKE negotiation to resist quantum attacks.
  • QKD: Quantum-based key distribution providing fresh symmetric keys via a Key Management Entity (KME).

IKE SA vs ESP SA

  • IKE SA: Controls tunnel negotiation.
  • ESP SA: Carries encrypted user data.

Static vs Dynamic keys

  • Dynamic: ephemeral PSK or QKD-distributed secrets, used once and discarded.
  • Static: manually set per peer, persistent across sessions.

2.1 RouterOS PPK Sources

PPK Source Description
Static Persistent, manually configured secret.
PSK One-time dynamically generated pre-shared keys. Can optionally be used only for initial IKE SA (psk-ike-initial).
QKD Keys pulled dynamically from a QKD server, consumed after use.

3. Security Recommendations

  • All PPK keys should meet RFC 8784 recommendations: ≥256 bits of entropy.
  • Static PPK keys improve post-quantum protection if sufficiently long, but re-use reduces security.
  • Dynamic keys (PSK/QKD) offer stronger security since they are one-time use. Synchronization failure may cause key desynchronization.

4. Two-Device Setup Overview

This manual focuses on a minimal setup with two devices:

Role Device Function
Server RouterOS Hosts an IPsec tunnel; provides a QKD/PPK key
Client ROS/LibreSwan Connects to the server using QKD/PPK

The RouterOS server may act as a QKD client to a KME, so no third device is required.

# Example of pushing a configuration to a remote peer (IPsec)
/ip ipsec peer
add address=192.168.88.1/32 name=Server exchange-mode=ike2
/ip ipsec proposal
set [ find default=yes ] auth-algorithms=sha256 enc-algorithms=aes-256-gcm

5. Configuration Objects

5.1 Certificates

QKD requires:

  • CA certificate (to validate the server).
  • SAE client certificate (for authentication to the QKD server).
/certificate/import file-name=ca.crt.pem
/certificate/import file-name=sae-server.crt.pem
/certificate/import file-name=sae-server.key.pem

5.2 PSK Example

Generate one-time PSKs for PPK use:

/ip/ipsec/key/psk/generate count=10 key-size=32
  • count → number of PSKs to generate.
  • key-size → size of each key in bytes (32 bytes = 256 bits).

5.3 QKD Key Manager

RouterOS server can act as a QKD client:

/ip/ipsec/key/qkd/set address=10.2.3.4:8020 \
    cache-size=1 \
    certificate=sae-server \
    key-size=32 \
    kme-id=server-kme-id \
    peer-sae-id=client-sae-id

Parameter descriptions:

Parameter Description
cache-size Number of keys IPsec will prefetch from the QKD server.
cache-state Current number of keys cached and available.
key-size Requested size of each key in bytes (e.g., 32 bytes = 256 bits).
kme-id Used for certificate validation. If not specified, the KME identity will not be validated.
peer-sae-id Identifier for the peer SAE.

5.4 Profiles and Peers

/ip/ipsec/profile/add name=qkd-profile ppk=qkd
/ip/ipsec/peer/add address=10.2.1.2 exchange-mode=ike2 \
    name=peer-client profile=qkd-profile proposal-check=obey
/ip/ipsec/identity/add peer=peer-client profile=qkd-profile

PPK options for profiles:

Option Description
no PPK disabled.
psk One-time PSK used for IKE and ESP rekey.
psk-ike-initial PSK used only for the initial IKE SA (renamed from psk-ike-only).
qkd Keys retrieved from a QKD server.

5.5 Proposal / Policy

/ip/ipsec/proposal/add name=qkd-proposal auth-algorithms=sha256 \
    enc-algorithms=aes-256-gcm pfs-group=modp2048
/ip/ipsec/policy/add src-address=10.1.0.0/24 dst-address=10.2.0.0/24 \
    peer=peer-client proposal=qkd-proposal tunnel=yes

6. Behaviour

  • Dynamic keys: Pulled from /ip/ipsec/key/psk/ or QKD server, consumed once, then deleted.
  • Static key: Configured per peer, used repeatedly.
  • One-time dynamic keys ensure the strongest protection but require synchronization.
  • Static fallback guarantees tunnel establishment but should be long enough (≥256 bits entropy).
  • PPK usage can optionally be restricted to IKE SA only (psk-ike-initial) to reduce key consumption.

Notes

QKD as a Distribution Mechanism

  • QKD in RouterOS is not a new encryption method itself - it’s a key distribution mechanism.
  • It provides dynamically generated keys via the Key Management Entity (KME), which both peers retrieve securely.

Dynamic vs Static Sources

  • Dynamic sources: QKD-distributed keys, one-time PSKs from /ip/ipsec/key/psk/.
  • Static sources: Per-peer configured static PPK secret.
  • Recommendation: prefer dynamic keys for long-term security; keep a static fallback to prevent tunnel drops if dynamic keys run out.

Security Guidelines (RFC 8784)

  • Post-quantum preshared keys should contain at least 256 bits of entropy to provide 128-bit post-quantum security.
  • Using only one static key for IKE SA protection is possible, but carries risk if reused.

Operational Considerations

  • Key exhaustion: one-time PSKs are consumed quickly during aggressive rekeying (IKE + ESP). QKD avoids this by continuously providing fresh keys.
  • Hub-and-spoke topologies: dynamic PSKs need peer association to avoid desynchronization between spokes.
  • Fallback behavior: ensure the system can gracefully switch to static PPK if dynamic keys are unavailable.

Compatibility Notes

  • RouterOS - RouterOS: supports both PSK and QKD PPK.
  • RouterOS - LibreSwan: works with static PPK; dynamic PSK may require custom builds.
  • RouterOS - StrongSwan: requires adaptation, as identifiers differ between draft versions.
