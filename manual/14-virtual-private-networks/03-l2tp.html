L2TP

The Layer Two Tunneling Protocol (L2TP, RFC 2661) carries a PPP link over an IP network. RouterOS uses it in two ways:

  • An L2TP server gives remote users and remote routers a PPP connection into the network. The users and their settings are in the PPP user database or on a RADIUS server: see PPP AAA.
  • L2TP Ether connects two sites at layer 2: it carries Ethernet frames with L2TPv3 (RFC 3931).

L2TP runs over IPv4 and IPv6. It uses UDP port 1701 for both the control and the data packets, so it passes most firewalls and NAT.

WARNING

L2TP does not encrypt the traffic. Use it with IPsec when the tunnel crosses a network that you do not trust.

[gambar: An L2TP client connects to an L2TP server over the internet]

Set up a server and a client

On the server, add a pool, a profile and a user, and enable the L2TP server. The router gets the address 10.0.0.1 inside the tunnels:

/ip/pool/add name=vpn-pool ranges=10.0.0.10-10.0.0.100
/ppp/profile/add name=vpn local-address=10.0.0.1 \
    remote-address=vpn-pool
/ppp/secret/add name=alice password=Example-pass-1 profile=vpn \
    service=l2tp
/interface/l2tp-server/server/set enabled=yes default-profile=vpn

On the client, a RouterOS router in this example, add an L2TP client with the address of the server:

/interface/l2tp-client/add name=l2tp-office connect-to=203.0.113.1 \
    user=alice password=Example-pass-1 disabled=no

The client shows the state and the addresses of the link:

[admin@Client] > /interface/l2tp-client/monitor l2tp-office once
               status: connected           
               uptime: 10s                 
             encoding:                     
                  mtu: 1450                
                  mru: 1450                
        local-address: 10.0.0.100          
       remote-address: 10.0.0.1            
   local-ipv6-address: fe80::978e:f47e:0:5 
  remote-ipv6-address: fe80::2562:b1b9:f0:0

The server adds a dynamic interface for the user and lists the user in /ppp/active:

[admin@Server] > /interface/l2tp-server/print detail
Flags: D - DYNAMIC; R - RUNNING
0 DR name="<l2tp-alice>" user="alice" mtu=1450 mru=1450
     client-address="203.0.113.2" uptime=10s encoding=""
  • An empty encoding means that the link is not encrypted.
  • To send the traffic for the office network through the tunnel, add a route on the client with the client interface as the gateway, or set add-default-route=yes to send all traffic through it.
  • The client and the server both use UDP port 1701. With random-source-port=yes the client uses a random source port.

Protect the tunnel with IPsec

With use-ipsec, the server and the client add the IPsec configuration for the tunnel themselves. Both sides need the same ipsec-secret:

/interface/l2tp-server/server/set use-ipsec=required \
    ipsec-secret=Example-ipsec-secret-1

/interface/l2tp-client/set l2tp-office use-ipsec=yes \
    ipsec-secret=Example-ipsec-secret-1
  • use-ipsec=yes on the server accepts clients with and without IPsec. use-ipsec=required refuses a client without IPsec, and the log of the server has L2TP connection rejected no IPsec encryption while it was required.
  • The server adds a dynamic IPsec peer l2tp-in-server and, for each client, a dynamic policy for UDP port 1701 in transport mode. The client adds a dynamic peer and policy with the name of its interface.
  • Several clients behind the same NAT address cannot use L2TP with IPsec at the same time in this mode.
  • Microsoft Windows uses L2TP with IPsec by default.
  • Take care if the router also has static IPsec peers: the dynamic peer of the L2TP server listens for all addresses.

When IPsec protects the link, encoding shows the algorithms:

[admin@Server] > /interface/l2tp-server/print detail
Flags: D - DYNAMIC; R - RUNNING
0 DR name="<l2tp-alice>" user="alice" mtu=1450 mru=1450
     client-address="203.0.113.2" uptime=25s encoding="cbc(aes) + hmac(sha1)"

Allow L2TP in the firewall

The default firewall drops connections that come from the internet. For L2TP with IPsec, accept IKE, IPsec ESP, and UDP port 1701 only when IPsec protects it. Put the rules before the default drop rule:

/ip/firewall/filter
add chain=input action=accept protocol=udp dst-port=500,4500 \
    in-interface-list=WAN comment="accept IKE" \
    place-before=[find comment="defconf: drop all not coming from LAN"]
add chain=input action=accept protocol=ipsec-esp \
    in-interface-list=WAN comment="accept IPsec ESP" \
    place-before=[find comment="defconf: drop all not coming from LAN"]
add chain=input action=accept protocol=udp dst-port=1701 \
    ipsec-policy=in,ipsec in-interface-list=WAN \
    comment="accept L2TP over IPsec" \
    place-before=[find comment="defconf: drop all not coming from LAN"]

All three rules are needed: the client connects only when the last one is in place. UDP port 4500 is used when there is NAT between the client and the server.

For L2TP without IPsec, one rule accepts UDP port 1701, without ipsec-policy.

A connected user can reach the devices of the LAN, but not the services of the router. PPP AAA shows how to limit what the users reach.

Connect a branch office

An L2TP client on a branch router connects the branch network to the office. The tunnel is a routed link, so each side needs a route to the network of the other side. In this example the office LAN is 192.168.88.0/24 and the branch LAN is 192.168.2.0/24.

On the office router, give the branch a fixed address and a route to its LAN in the user entry. The router adds the route when the branch connects:

/ppp/secret/add name=branch1 password=Example-pass-2 profile=vpn \
    service=l2tp remote-address=10.0.0.5 \
    routes="192.168.2.0/24 10.0.0.5 1"

On the branch router, add the client and a route to the office LAN through it:

/interface/l2tp-client/add name=l2tp-office connect-to=203.0.113.1 \
    user=branch1 password=Example-pass-2 use-ipsec=yes \
    ipsec-secret=Example-ipsec-secret-1 disabled=no
/ip/route/add dst-address=192.168.88.0/24 gateway=l2tp-office
  • The two LANs must use different networks.
  • For a tunnel between two routers with static addresses, IPsec or WireGuard needs no PPP users.

Send large packets and bridge Ethernet

The MTU of an L2TP link is 1450 bytes by default, so a 1500-byte packet that must not be fragmented does not pass. Multilink PPP splits such packets and joins them on the other side. Set mrru on the server and on the client:

/interface/l2tp-server/server/set mrru=1600

/interface/l2tp-client/set l2tp-office mrru=1600

A PPP link can also carry Ethernet frames, with the Bridge Control Protocol (BCP). Name a bridge in the PPP profile on both sides, and the router adds the link to the bridge as a dynamic port when the user connects:

/ppp/profile/set vpn bridge=bridge
  • Set mrru as well, so that full-size Ethernet frames pass.
  • A PPP link has no MAC address. The bridge needs an Ethernet-like port or a MAC address that you set (admin-mac).
  • To connect two sites at layer 2 only, L2TP Ether is simpler.

Use L2TPv3

The client uses L2TP version 2 by default. l2tp-proto-version selects version 3 over UDP (l2tpv3-udp) or directly over IP (l2tpv3-ip, IP protocol 115). Version 3 needs a circuit ID on the client:

/interface/l2tp-client/set l2tp-office \
    l2tp-proto-version=l2tpv3-udp l2tpv3-circuit-id=office

The server accepts both versions by default. accept-proto-version of the server limits it to one, and accept-pseudowire-type limits it to PPP sessions (ppp) or to Ethernet sessions (ether).

Connect two sites at layer 2 with L2TP Ether

An L2TP Ether tunnel carries Ethernet frames between two routers. One router connects to the other:

  • The active side has an /interface/l2tp-ether entry with the address of the other router in connect-to.
  • The passive side has the L2TP server enabled.

On the passive side, enable the server and add an interface for the tunnel. connect-to=0.0.0.0 makes it wait for the connection, and circuit-id names the tunnel:

/interface/l2tp-server/server/set enabled=yes
/interface/l2tp-ether/add name=l2tp-site1 connect-to=0.0.0.0 \
    circuit-id=site1

On the active side, use the same circuit ID:

/interface/l2tp-ether/add name=l2tp-ether1 connect-to=203.0.113.1 \
    circuit-id=site1

Add the interface to the LAN bridge on each side (l2tp-ether1 on the active side), and the two networks are one layer 2 network. Both sides then share one network: use one DHCP server and different addresses for the two routers.

/interface/bridge/port/add bridge=bridge interface=l2tp-site1

monitor shows the state of the tunnel:

[admin@Client] > /interface/l2tp-ether/monitor l2tp-ether1 once
           status: link up    
       circuit-id: site1      
    cookie-length: 0          
    header-format: L2TPv3 UDP 
      l2-sublayer: no         
   remote-sess-id: 33         
    local-sess-id: 125        
  control-conn-id: 104        
     peer-address: 203.0.113.1
           uptime: 17s
  • The MTU of the interface is 1450 bytes. Check that the bridge and the devices behind it can work with this MTU.
  • l2tp-proto-version=l2tpv3-ip on the active side carries the tunnel directly over IP and not over UDP.
  • use-ipsec and ipsec-secret protect the tunnel in the same way as for an L2TP client, and the firewall rules for L2TP with IPsec apply. On the passive side, these settings and the cookie and digest settings are in /interface/l2tp-server/server, not in the interface.
  • A static tunnel without a control connection is also possible: unmanaged-mode with the tunnel IDs, session IDs and cookies set by hand. See the CLI reference.

Dynamic interfaces on the passive side

When the active side has no circuit ID, the passive side does not need an interface: the server adds a dynamic one for each tunnel.

[admin@Server] > /interface/l2tp-ether/print detail
Flags: D - DYNAMIC; R - RUNNING
0 DR name="<l2eth-23>" mtu=auto actual-mtu=1450 connect-to=0.0.0.0
     mac-address=FE:36:0B:1B:B5:5E use-ipsec=no allow-fast-path=no
     l2tp-proto-version=l2tpv3-udp circuit-id="<l2eth-23>" cookie-length=0
     digest-hash=md5 use-l2-specific-sublayer=no

A dynamic interface gets a new name with each connection. To use it in a bridge, set l2tpv3-ether-interface-list of the server: the server adds each dynamic interface to this interface list, and a bridge port can be an interface list.

/interface/list/add name=l2tp-ether-ports
/interface/l2tp-server/server/set \
    l2tpv3-ether-interface-list=l2tp-ether-ports
/interface/bridge/port/add bridge=bridge interface=l2tp-ether-ports

Troubleshoot L2TP Ether

Log the l2tp topic on the passive side to see why a tunnel does not come up:

/system/logging/add topics=l2tp,debug action=memory
What you see What to check
The active side shows status: link down. The log of the passive side has has reached maximum session count, disconnecting, and the server answers with CDN and Result-Code=4. The server found no interface for the session. If the active side has a circuit-id, the passive side needs an l2tp-ether interface with connect-to=0.0.0.0 and the same circuit-id. Also check max-sessions of the server.
The tunnel does not come up at all. accept-proto-version of the server must allow l2tpv3, and accept-pseudowire-type must allow ether. In a firewall, accept UDP port 1701, or IP protocol 115 for l2tpv3-ip.
The tunnel does not come up after a change of digest-hash. With digest-hash=none on one side and a hash on the other, the tunnel stays down. Use the same value on the active side and in l2tpv3-digest-hash of the server.

LAC and LNS setup with Cisco as LAC

LAC/LNS setup, otherwise known as Virtual Private DialUp Network (VPDN), allows long-distance point-to-point connection between remote dial-up users and private networks.

A Dial-up client uses PPPOE to connect to a L2TP access concentrator (LAC), LAC determines that the session should be forwarded through an IP network to the L2TP Network Server (LNS), creates L2TP tunnel and forwards PPP frames to the server where the client is authenticated and the session is established (see diagram below).

At the time of writing this article RouterOS cannot be used in the LAC role. For this reason, the article will demonstrate how to set up a very basic network with RouterOS as an LNS and a Cisco router as a LAC.

Configuration

We will be using a simple configuration to demonstrate the very basics of VPDN setup. Let's assume that LAC will forward to the LNS clients with FQDN name containing the mt.lv domain.

Client

For the sake of simplicity let's assume that the client is a RouterOS router:

/interface/pppoe-client/add interface=ether1 user=good_worker@mt.lv password=strongpass

LAC

Let's assume that the client is connected to the GigabitEthernet1 port and the IP address of the LNS server is 10.155.101.231

aaa new-model
!
aaa authentication ppp default local
!
vpdn enable
vpdn aaa attribute nas-ip-address vpdn-nas
vpdn search-order domain dnis 
!
vpdn-group LAC
 request-dialin
  protocol l2tp
  domain mt.lv
 initiate-to ip 10.155.101.231
 source-ip 10.155.101.216
 local name LAC
 l2tp tunnel password 0 tunnelpass
!
bba-group pppoe MAIN-BBA
 virtual-template 1
!
interface GigabitEthernet1
 pppoe enable group MAIN-BBA
!
interface Virtual-Template1
 description pppoe MAIN-BBA
 no ip address
 no peer default ip address
 ppp mtu adaptive
 ppp authentication chap
!

Note that this setup does not authenticate the client either locally or via RADIUS, does not actually check the domain name, does not control L2 access for the sake of simplicity. If you want to use those features, refer to Cisco configuration manuals.

LNS

On the LNS we need to enable L2TP server and set up a method to authenticate the L2TP connection from the LAC.

/interface/l2tp-server/server
set enabled=yes
/ppp/l2tp-secret
add address=10.155.101.216/32 secret=tunnelpass

Now the actual user authentication. In this case we will be using a local authentication method for the sake of simplicity.

/ip/pool
add name=pool0 ranges=192.168.99.2-192.168.99.99
/ppp/profile
set default local-address=192.168.99.1 remote-address=pool0
/ppp/secret
add name=good_worker@mt.lv password=strongpass

Session Establishment

Let's look closely at how client sessions get authenticated and established over the LAC.

  • Client initiates PPPoE call.
  • LAC and Client begin LCP negotiation.
  • After CHAP has been negotiated, LAC sends CHAP challenge.
  • Client sends CHAP response.
  • LAC checks whether client session should be forwarded to the LNS based on received domain name. The check can be done locally or using a RADIUS server. Client also can be authenticated here before forwarding session.
  • LAC brings up an L2TP tunnel.
  • LNS checks if the LAC is allowed to open a tunnel and run the authentication process. The Tunnel is up and ready to forward VPDN sessions.
  • LAC forwards LCP options negotiated with the client, username and password to the LNS.
  • LNS authenticates the client locally or using RADIUS and sends a CHAP Success or CHAP Failure message.
  • IP Control Protocol (IPCP) phase is performed, IP addresses and routes are installed. At this point the session is considered established.

OpenVPN

OpenVPN is a VPN protocol that uses TLS. Clients exist for Linux, Windows, macOS and other systems, which makes it a common choice for remote access from computers and phones. RouterOS has its own implementation of an OpenVPN server and client.

  • A tunnel carries routed IP traffic (mode=ip, known as tun) or Ethernet frames (mode=ethernet, known as tap).
  • It runs over TCP or UDP, on port 1194 by default, with IPv4 and IPv6.
  • The users and their settings are in the PPP user database or on a RADIUS server: see PPP AAA.

[gambar: Two remote clients connect to the office router and reach a host and a network behind it]

Limitations

RouterOS does not support all features of OpenVPN, and not all unsupported features are listed here. The most important ones:

  • LZO compression. Compression is deprecated in OpenVPN and not recommended: tunnels with compression are open to the VORACLE attack.
  • Cipher negotiation (NCP). The cipher must be set in the .ovpn file of a client that connects to a RouterOS server. The file that RouterOS exports has it.
  • tls-auth, tls-crypt and tls-crypt v2 work only in the RouterOS client, and only when the configuration is imported from a .ovpn file.

A password can have up to 1000 characters.

Set up a server

The server needs a certificate. Certificates explains how to create and sign one. In this example the certificate has the name ovpn-server and contains the address of the router, 203.0.113.1.

Add a pool, a profile and a user, and then the server:

/ip/pool/add name=vpn-pool ranges=10.0.0.10-10.0.0.100
/ppp/profile/add name=vpn local-address=10.0.0.1 \
    remote-address=vpn-pool
/ppp/secret/add name=alice password=Example-pass-1 profile=vpn \
    service=ovpn
/interface/ovpn-server/server/add name=ovpn-server1 \
    certificate=ovpn-server default-profile=vpn protocol=udp \
    auth=sha256 cipher=aes256-gcm disabled=no
  • A new server allows only the ciphers blowfish128 and aes128-cbc, and a RouterOS client uses blowfish128 with sha1 by default. These are old algorithms: set cipher and auth as in the example.
  • A new server uses TCP. UDP has less overhead and is the usual choice.
  • The certificates have dates. Set the clock of the server and of the clients correctly, for example with NTP, or the certificate check fails.

Connect a RouterOS client

Add a client with the same protocol, cipher and authentication as the server:

/interface/ovpn-client/add name=ovpn-office connect-to=203.0.113.1 \
    protocol=udp auth=sha256 cipher=aes256-gcm \
    user=alice password=Example-pass-1 disabled=no

/interface/ovpn-client/monitor ovpn-office once shows status: connected and the algorithms in encoding, here AES-256-GCM/SHA256. The server adds a dynamic interface <ovpn-alice> for the user, and /ppp/active lists the user with the service ovpn.

  • When the cipher or the authentication of the client is not allowed on the server, the client shows terminating... - peer disconnected.
  • With a GCM cipher, auth=null also works, because the cipher authenticates the packets itself.
  • To reach the networks behind the server, add routes on the client with the client interface as the gateway, or let the server push them.

Check the server certificate and require client certificates

Without more settings, the client does not check the certificate of the server. To check it, import the certificate authority (CA) that signed it on the client as a trusted certificate and set:

/interface/ovpn-client/set ovpn-office verify-server-certificate=yes

The client then also checks that the address or name in connect-to is in the certificate.

The server can ask each client for a certificate. The client certificate must be signed by a CA that the server trusts:

/interface/ovpn-server/server/set [find name=ovpn-server1] \
    require-client-certificate=yes

/interface/ovpn-client/set ovpn-office certificate=ovpn-client

A client without a certificate is then refused with TLS error: ssl: unknown certificate.

Push routes to the clients

The server can send routes to the clients, so that they do not need static routes. Each route is network netmask gateway, and several routes are separated with commas:

/interface/ovpn-server/server/set [find name=ovpn-server1] \
    push-routes="192.168.88.0 255.255.255.0 10.0.0.1"

The client adds the route when it connects:

[admin@Client] > /ip/route/print where gateway~"ovpn|10.0.0.1"
Flags: D - DYNAMIC; A - ACTIVE; c - CONNECT, v - VPN
Columns: DST-ADDRESS, GATEWAY, ROUTING-TABLE, DISTANCE
    DST-ADDRESS      GATEWAY      ROUTING-TABLE  DISTANCE
DAc 10.0.0.0/24      ovpn-office  main                  0
DAv 192.168.88.0/24  10.0.0.1     main                  1
  • push-routes can have up to 1400 characters or 37 routes. push-routes-ipv6 has the IPv6 routes, for example push-routes-ipv6="fdaa::/64,2001:db8::/32".
  • redirect-gateway=def1 sends all traffic of the clients through the tunnel. The client adds the routes 0.0.0.0/1 and 128.0.0.0/1, which take precedence over its default route.
  • route-nopull=yes on a RouterOS client ignores the routes of the server.

Export a configuration file for other clients

export-client-configuration writes a .ovpn file that OpenVPN clients on computers and phones can import. It needs the CA certificate, a client certificate and its key as files, and the server must have require-client-certificate=yes. In this example vpn-ca is the CA that signed the server certificate and ovpn-client is a client certificate that this CA signed; make one client certificate for each user. Export the client certificate with its key first:

/certificate/export-certificate ovpn-client file-name=client1 \
    export-passphrase=Example-key-pass-1
/certificate/export-certificate vpn-ca file-name=vpn-ca
/interface/ovpn-server/server/export-client-configuration \
    server=ovpn-server1 server-address=203.0.113.1 \
    ca-certificate=vpn-ca.crt client-certificate=client1.crt \
    client-cert-key=client1.key

The command writes a file with a name such as client1795166484.ovpn. It has the address, the port, the protocol and the cipher of the server, and the three certificates. The users also need their user name and password: the file asks for them (auth-user-pass). Copy the file from the files of the router.

The file has the private key of the client. Send it to the user in a safe way, and give the passphrase of the key in another way.

Two more example files, for a client and for an OpenVPN server on another system: client-1.ovpn, server-1.conf.

Import a configuration file on a RouterOS client

A RouterOS client can be made from a .ovpn file. Copy the file to the router and import it with the user name, the password and the passphrase of the key:

/interface/ovpn-client/import-ovpn-configuration \
    file-name=office.ovpn ovpn-user=alice \
    ovpn-password=Example-pass-1 key-passphrase=Example-key-pass-1
  • The command adds a disabled client interface with a name such as ovpn-import1795166676, and imports the certificates of the file. Check the settings and enable the interface.
  • Import the file on a router that does not have its certificates yet. skip-cert-import=yes imports the settings without the certificates.
  • A RouterOS client always sends a user name and a password. A server that authenticates with certificates only ignores them.

TLS authentication keys

tls-auth and tls-crypt add a shared key that protects the TLS handshake. The RouterOS client supports them only through the import of a .ovpn file that has the key:

key-direction 1
<tls-auth>
#
# 2048 bit OpenVPN static key
#
-----BEGIN OpenVPN Static key V1-----
-----END OpenVPN Static key V1-----
</tls-auth>

For tls-crypt and tls-crypt v2, the other system needs auth SHA256 and no key-direction in the server configuration, and auth SHA256 with key-direction 1 in the client configuration.

Carry Ethernet frames

With mode=ethernet on the server and on the client, the tunnel carries Ethernet frames. The client gets an address with the netmask set in netmask of the server (24 by default).

Allow OpenVPN in the firewall

The default firewall drops connections that come from the internet. Accept the port of the server before the default drop rule, with the protocol that the server uses:

/ip/firewall/filter/add chain=input action=accept protocol=udp \
    dst-port=1194 in-interface-list=WAN comment="accept OpenVPN" \
    place-before=[find comment="defconf: drop all not coming from LAN"]

Use a VRF

vrf of a server sets the VRF in which it listens for connections. The default is main.

/interface/ovpn-server/server/set [find name=ovpn-server1] vrf=vrf1

Troubleshoot

monitor on the client shows the reason of a failed connection in status, and the log has the same text under the topic ovpn.

Status of the client What to check
disconnected, or it stays at link established The server is not reached. Check the address, the port, that the client and the server use the same protocol, and the firewall of the server. With verify-server-certificate=yes, also check that the address in connect-to is in the certificate of the server.
terminating... - peer disconnected The cipher or the authentication of the client is not allowed on the server.
TLS error: ssl: no trusted CA certificate found verify-server-certificate=yes is set and the CA of the server is not a trusted certificate on the client.
TLS error: ssl: unknown certificate The server requires a client certificate and the client has none.
