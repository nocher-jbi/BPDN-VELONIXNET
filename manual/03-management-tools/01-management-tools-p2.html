RoMON

RoMON

RoMON (Router Management Overlay Network) builds an independent MAC-layer peer discovery and data forwarding network between routers. RoMON packets use EtherType 0x88bf and destination multicast MAC 01:80:c2:00:88:bf and are handled independently of L2 or L3 configuration: a router stays reachable through RoMON even when its IP configuration, routing or firewall is broken. That makes RoMON a recovery path into misconfigured routers, one overlay hop at a time.

Each router on the RoMON network has a RoMON ID, either selected automatically from a port MAC address or configured with id.

The RoMON protocol does not encrypt messages. Encryption comes from the application running on top of it, for example SSH or a secure WinBox connection.

INFO

RoMON packets can be forwarded through network switches or bridges, unless there are specific restrictions on multicast traffic. When using a MikroTik bridge with hardware offloading, these packets are treated like regular multicast packets and are flooded across the network.

If the RoMON service is enabled and the switch chip supports ACL rules, dynamic rules are automatically created to redirect these packets to the CPU, where the RoMON service operates. However, if the switch does not support ACL rules and the configuration does not align, such as when the CPU and RoMON untagged packets are not in the same VLAN, the RoMON service might not function as expected.

RB5009 (switch-chip 88E6393X) does not support this path. The chip's frame-types=admit-only-vlan-tagged filter drops RoMON frames before any ACL rule can be applied, so the packets never reach the CPU.

Enable RoMON

Enable the service in the /tool/romon menu:

/tool/romon/set enabled=yes

When the ID is not configured, it is selected automatically:

[admin@MikroTik] > /tool/romon/print
     enabled: yes
          id: 00:00:00:00:00:00
  current-id: DC:2C:6E:E7:10:6B

Choose ports

Ports that participate in the RoMON network are configured in the /tool/romon/port menu. Each entry matches one physical interface name (or the built-in wildcard all) and either forbids RoMON on it or allows it with a port cost. Bridge or other master interfaces are not accepted as RoMON ports — name the physical ports that talk to the network. More specific entries override the wildcard entry.

A default entry with the interface list all is preconfigured, so every interface participates with cost 100 until you change it:

[admin@MikroTik] > /tool/romon/port/print
Flags: * - DEFAULT
Columns: INTERFACE, FORBID, COST
#   INTERFACE  FORBID  COST
0 * all        no       100

RoMON should not listen on the untrusted side of a router (it accepts management connections by MAC address). Forbid the WAN port and keep the LAN:

/tool/romon/port/add interface=ether1 forbid=yes

Or the other way around: forbid everything with the wildcard entry, then allow the trusted interfaces one by one:

/tool/romon/port/set [find default=yes] forbid=yes
/tool/romon/port/add interface=ether2 forbid=no
/tool/romon/port/add interface=ether3 forbid=no

Protect the overlay with secrets

RoMON secrets authenticate messages, check their integrity and prevent replays by hashing the message contents with MD5. Every router in the same RoMON network should use the same secrets. On a fresh setup, set the secret on all routers:

/tool/romon/set secrets="mysecret"

The global list lives in /tool/romon; an interface-specific list can be set per port in /tool/romon/port (if the port list is empty, the global list is used).

When sending, messages are hashed with the first secret in the list, unless the list is empty or starts with the empty secret (in that case messages are sent unhashed). When receiving, unhashed messages are accepted only by an empty list or a list that contains the empty secret; hashed messages are accepted when they carry any secret in the list.

That behaviour makes a rolling change possible without splitting the network — and the rotation works even when you do it while connected through RoMON itself:

# 1. every router still sends unhashed, but also accepts "mysecret"
/tool/romon/set secrets=("","mysecret")
# 2. every router sends hashed with "mysecret", but still accepts unhashed
/tool/romon/set secrets=("mysecret","")
# 3. every router sends and only accepts "mysecret"
/tool/romon/set secrets="mysecret"

To change a secret later, run the same rotation with both the old and the new secret in the list for a while.

NOTE

In the CLI, list entries that contain an empty secret need parentheses: secrets=("","mysecret"). In WinBox, press the small + in the Secrets field and leave the first row empty.

A client whose secret does not match gets no answer:

[admin@MikroTik] > /tool/romon/ping id=DC:2C:6E:E7:10:6B count=3
  SEQ HOST                                    TIME  SIZE STATUS
    0 DC:2C:6E:E7:10:6B                           32 timeout
    1 DC:2C:6E:E7:10:6B                           32 timeout
    2 DC:2C:6E:E7:10:6B                           32 timeout
    sent=3 received=0 packet-loss=100%

Run /tool/romon/discover to list the reachable routers:

[admin@MikroTik] > /tool/romon/discover
Flags: A - ACTIVE

A F4:1E:57:46:89:89   200     1  F4:1E:57:46:89:89   1500  Router-B  7.26beta1

The discovery table keeps refreshing; with duration it stops after the given time. The address column holds the RoMON ID of the found router, which is what the other RoMON tools take.

    sent=5 received=5 packet-loss=0% min-rtt=0ms avg-rtt=0ms max-rtt=1ms

Open an SSH session over RoMON

/tool/romon/ssh opens an SSH session through the overlay, even when the remote router has no IP address:

[admin@MikroTik] > /tool/romon/ssh F4:1E:57:46:89:89 user=admin

Connect with WinBox

In WinBox, select Connect To > RoMON Agent on the login screen and choose a saved router with RoMON enabled as the agent, then connect to the target by its RoMON ID (see WinBox). Watch the video tutorial.

You can also run WinBox from the command line with a RoMON agent and the target router's ID. The agent router must be saved in the WinBox managed router list for the connection to succeed:

winbox.exe --romon 192.168.88.24 F4:1E:57:46:89:89 admin ""

Technical details

  • Discovery, ping and RoMON SSH all run over raw Ethernet frames, so they keep working without any IP configuration.
  • The packet sniffer and Torch show only the RoMON frames that the router sends; received RoMON frames are not shown.
  • hops, path and cost in the discovery table describe the RoMON path: routers that run RoMON forward the overlay traffic, so a target several segments away shows the intermediate IDs in path.
  • A [find default=yes] wildcard port entry always exists: it cannot be removed, disabled or enabled — only its cost, forbid and secrets can be changed ("failure: only cost, forbid and secrets can be changed for preset"). Setting it to forbid=yes turns the default into "deny all".

The sniffer and Torch see RoMON frames (EtherType 0x88BF) only in the tx direction. Received RoMON frames do not appear in a capture or in Torch, not even with mac-protocol=romon or direction=rx, so a capture on a router that answers another router's discovery holds only the frames it sends:

[admin@MikroTik] > /tool/sniffer/start interface=ether2 mac-protocol=romon
[admin@MikroTik] > /tool/sniffer/stop
[admin@MikroTik] > /tool/sniffer/packet/print proplist=time,direction,src-mac,dst-mac,protocol,size
Columns: TIME, DIRECTION, SRC-MAC, DST-MAC, PROTOCOL, SIZE
#  TIME      DIRECTION  SRC-MAC            DST-MAC            PROTOCOL  SIZE
0  0.449619  tx         DC:2C:6E:E7:10:6B  F4:1E:57:46:89:89  romon      171
1  0.44973   tx         DC:2C:6E:E7:10:6B  F4:1E:57:46:89:89  romon      145
2  0.950712  tx         DC:2C:6E:E7:10:6B  F4:1E:57:46:89:89  romon      171
3  0.951016  tx         DC:2C:6E:E7:10:6B  F4:1E:57:46:89:89  romon      145

To see both directions of a RoMON exchange, capture on a device between the two routers, for example through a mirror port of a switch.

For all parameters, see the /tool/romon, /tool/romon/port, /tool/romon/discover, /tool/romon/ping and /tool/romon/ssh CLI reference pages.

MAC server

The RouterOS MAC server lets you reach a router by its MAC address on the same layer-2 segment, without IP configuration: connect with MAC Telnet, find routers with MAC scan, limit MAC Telnet and MAC WinBox to...

MAC server

The MAC server lets you reach a router by its MAC address from a device on the same layer-2 segment, without any IP configuration on either side. It serves three things:

  • MAC Telnet - A console session, like Telnet over IP. The RouterOS client is /tool/mac-telnet.
  • MAC WinBox - WinBox connects to the router by its MAC address.
  • MAC ping - Answers pings sent to the router's MAC address.

Use MAC access to recover a router whose IP settings are wrong or missing, and for the first setup of a new router. The default configuration allows MAC Telnet and MAC WinBox only on the interfaces in the LAN interface list, which holds the LAN bridge: on most routers every port except the WAN port ether1, and the Wi-Fi interfaces. Without the default configuration, they are allowed on all interfaces. The MAC ping server is on by default. In production networks, you should turn MAC access off or limit it to trusted interfaces; see Securing your router. To reach routers beyond one layer-2 segment by MAC address, use RoMON.

Connect with MAC Telnet

From a computer, use WinBox: the Neighbors tab lists the routers on the network, and selecting the MAC address connects by MAC WinBox. WinBox also has a terminal. From another RouterOS device, find the MAC address of the router with MAC scan or in the neighbor list, then connect with MAC Telnet:

MAC Telnet logs in with a user name and password; SSH keys do not apply. The user's group needs the telnet policy. After you log in, correct the IP settings, for example in /ip/address. When the target does not answer or refuses the connection, for example because MAC Telnet is not allowed on the interface the request arrives on, the client prints Trying ... and returns to the local prompt without an error message.

Without interface, the client sends its connection attempts out of every interface of the router. To send them out of one interface only:

/tool/mac-telnet FE:F1:E6:82:D5:B6 interface=ether1

The router you connect to lists the open MAC Telnet sessions, with the interface the session arrived on and the MAC address of the client:

/tool/mac-server/sessions/print

Columns: INTERFACE, SRC-ADDRESS, UPTIME
#  INTERFACE  SRC-ADDRESS        UPTIME
0  ether2     DC:2C:6E:E7:10:6A  2s

The list shows MAC Telnet sessions only, not MAC WinBox connections. The sessions also appear in /user/active with mac-telnet in the VIA column.

Find routers with MAC scan

MAC scan lists the devices that send MikroTik Neighbor Discovery (MNDP) announcements on an interface, with their MAC address and IPv4 address:

/tool/mac-scan interface=ether2 duration=8s

Columns: MAC-ADDRESS, ADDRESS, AGE
MAC-ADDRESS        ADDRESS      AGE
FE:F1:E6:82:D5:B6  203.0.113.1   17

AGE is the time in seconds since the device's last announcement. The list comes from neighbor discovery, not from the MAC server: a device appears whatever its MAC server settings are, and a device whose neighbor discovery is off on that interface does not appear. The list includes devices heard before the scan started, so AGE can be longer than duration; devices announce themselves every 30 seconds by default. /ip/neighbor/print shows the same devices with more details, such as the identity and RouterOS version.

On a bridge, scan one of its ports or interface=all: the bridge interface itself shows no devices. Without duration, the scan runs until you stop it with Control+C. MAC scan is not available on devices with the SMIPS architecture.

Allow MAC access only on trusted interfaces

MAC Telnet and MAC WinBox each have their own allowed-interface-list setting: /tool/mac-server for MAC Telnet and /tool/mac-server/mac-winbox for MAC WinBox. Each takes an interface list.

To allow MAC Telnet and MAC WinBox only on the LAN:

/tool/mac-server/set allowed-interface-list=LAN
/tool/mac-server/mac-winbox/set allowed-interface-list=LAN

The default configuration already has the LAN list, with the LAN bridge in it. On a router without it, create the list first:

/interface/list/add name=LAN
/interface/list/member/add list=LAN interface=bridge

Check the current settings with /tool/mac-server/print and /tool/mac-server/mac-winbox/print.

Put the bridge in the list, not its ports: a bridge in the list allows connections that arrive through any of its ports, and a bridge port alone in the list does not allow them. A change applies to the next connection immediately; sessions that are already open stay open.

To keep one port of the bridge out, for example the port of a guest Wi-Fi network, drop MAC access on it with a bridge filter rule, or put the guests on their own bridge:

/interface/bridge/filter/add chain=input in-interface=wifi2 \
    mac-protocol=ip ip-protocol=udp dst-port=20561 action=drop

To turn MAC Telnet and MAC WinBox off, set the lists to none:

/tool/mac-server/set allowed-interface-list=none
/tool/mac-server/mac-winbox/set allowed-interface-list=none

An interface list you create without members blocks MAC access in the same way.

NOTE

The IP firewall does not protect MAC access: an IP filter rule that drops UDP port 20561 does not block MAC Telnet or MAC ping. Limit MAC access with allowed-interface-list, or with a bridge filter rule on a bridge port. For the other ports RouterOS uses, see Services.

Enabling IP Source Guard on a bridge blocks MAC Telnet, MAC WinBox and MAC ping on its untrusted ports.

MAC ping

The MAC ping server (/tool/mac-server/ping) answers pings sent to the router's MAC address. It is enabled by default. To ping a MAC address, see Ping a MAC address.

To turn the MAC ping server off:

/tool/mac-server/ping/set enabled=no

With the server off, the router no longer answers MAC pings, and it cannot send MAC pings either: its own MAC pings fail with the status unknown interface. ARP ping works in both directions regardless of this setting.

Technical details

Transport

MAC Telnet, MAC WinBox and MAC ping use UDP port 20561 inside Ethernet frames addressed to the MAC address of the target. The IP header carries the addresses 0.0.0.0 and 255.255.255.255, so the packets do not depend on IP configuration. The MAC server takes them directly from the interface, so IP firewall rules do not stop them.

Security

MAC Telnet is not encrypted. The commands you type and the router's output cross the link in clear text. The password is not sent in clear: the login uses a challenge and response. Use MAC Telnet on trusted links, for example to recover a router, and use SSH for regular access.

A MAC login has no IP address, so the address setting of a user in /user does not apply to it: a user restricted to certain IP addresses can still log in with MAC Telnet. The group policies do apply.

For all parameters, see /tool/mac-server, /tool/mac-telnet and /tool/mac-scan in the CLI reference.

TR-069

Manage RouterOS devices from a TR-069 (CWMP) Auto Configuration Server: connect the router over HTTPS, allow connection requests, troubleshoot sessions, change the configuration, upgrade RouterOS, upload files and...

TR-069

The TR-069 client implements the CPE WAN Management Protocol (CWMP), standardized by the Broadband Forum (BBF). The router (the CPE) connects over HTTP or HTTPS to an Auto Configuration Server (ACS), which can read and change parameters, run RouterOS scripts, upgrade RouterOS, upload the configuration and the log, and reset the router. ISPs use it to manage customer routers; it also works for managing network infrastructure devices.

The client is in the tr069-client package, which is not part of the main RouterOS package. Install it as described in Packages. The client is disabled by default.

Connect the router to an ACS

This example connects a router with the default configuration to the ACS at https://acs.example.com:7547/, whose address is 198.51.100.10. Before you start, upload the CA certificate that signed the ACS certificate to the router as acs-ca.crt (see Files for the ways to upload a file), and create the device credentials on the ACS.

/certificate/import file-name=acs-ca.crt passphrase=""
/tr069-client/set acs-url=https://acs.example.com:7547/ \
    username=cpe-0001 password=Cpe-0001-secret \
    connection-request-username=acs \
    connection-request-password=Acs-request-secret enabled=yes
/ip/firewall/filter/add chain=input action=accept protocol=tcp \
    dst-port=7547 src-address=198.51.100.10 in-interface-list=WAN \
    place-before=[find comment~"not coming from LAN"] \
    comment="TR-069 connection requests from the ACS"
  • The import deletes the file and adds the CA as a trusted certificate. With the default check-certificate=yes, the router connects only if the ACS certificate is signed by a CA in the store and its name matches the host in acs-url.
  • username and password are the credentials the router uses to log in to the ACS.
  • connection-request-username and connection-request-password are the credentials the ACS uses to ask the router to start a session (a connection request). Always set them.
  • The firewall rule lets connection requests from the ACS reach the router. The client adds no firewall rule itself, and the default configuration drops them with all other input from the interfaces in the WAN list. The rule is placed before the default rule defconf: drop all not coming from LAN. Without the rule, the router still contacts the ACS on its own events and periodically, but the ACS cannot reach it in between.

Check the client:

/tr069-client/print

                      enabled: yes
                      acs-url: https://acs.example.com:7547/
                     username: cpe-0001
      periodic-inform-enabled: yes
     periodic-inform-interval: 1d
  connection-request-username: acs
      connection-request-port: 7547
            provisioning-code:
           client-certificate: none
            check-certificate: yes
                       status: running
           last-session-error:
                  retry-count: 0

An empty last-session-error with retry-count: 0 means the last session with the ACS succeeded. The ACS now lists the router as a new device: its first Inform carries the 0 BOOTSTRAP event.

NOTE

Use plain HTTP only to test a setup in a private network. Anyone on the path can read and change the parameters of an HTTP session. In production, use HTTPS and keep check-certificate=yes.

Check and troubleshoot

status shows whether the client is configured: disabled, waiting-url (enabled, but no ACS URL) or running. A failing ACS does not change it. Failures show in last-session-error and retry-count. For example, with a password the ACS does not accept:

/tr069-client/print

                      enabled: yes
                      acs-url: https://acs.example.com:7547/
                     username: cpe-0001
      periodic-inform-enabled: yes
     periodic-inform-interval: 1d
  connection-request-username: acs
      connection-request-port: 7547
            provisioning-code:
           client-certificate: none
            check-certificate: yes
                       status: running
           last-session-error: HTTP authentication error. Wrong username/password.
                  retry-count: 3

The client retries a failed session with a growing delay, from a few seconds up to minutes, and resets retry-count after the next successful session. A corrected setting is used at the next retry.

To follow each session, log the tr069 topic:

/system/logging/add topics=tr069
/log/print where topics~"tr069"

 2026-11-23 08:16:43 tr069,debug session finished with error: "HTTP authentication error. Wrong username/password."

 2026-11-23 08:17:02 tr069,debug starting session, events: [4 VALUE CHANGE, 1 BOOT, ] retry-count: 2

Here the first session after a reboot started before the DHCP client had an address, and the following ones were refused by the ACS. A successful session ends with session finished ok and scheduled next Periodic Inform.

Common errors in last-session-error:

Error Cause
HTTP authentication error. Wrong username/password. The ACS refused username and password.
SSL: ssl: no trusted CA certificate found (6) The CA that signed the ACS certificate is not in the certificate store.
SSL: ssl: name verification failed for: "CN=..." (6) The ACS certificate is for another name than the host in acs-url.
resolving error The router cannot resolve the host name in acs-url. Check /ip/dns.
Connection refused Nothing listens on the host and port in acs-url.
Network unreachable The router has no route to the ACS yet, for example right after boot.
HTTP error code: 500 The ACS answered with an HTTP error. Check the ACS logs.

If the ACS cannot reach the router with a connection request, check the firewall rule from the example and its counters, and the connection request credentials on the ACS.

How a session works

The router starts every session. It sends an Inform RPC that lists the events that caused the session, the device identity and a few parameters. When the router has nothing more to send, the ACS calls its RPCs: reading and setting parameters, downloads, uploads, reboot or factory reset.

Event in the Inform When
0 BOOTSTRAP First session with an ACS: after the client is enabled for the first time, after acs-url changes, and after a configuration reset.
1 BOOT After a reboot, and when the client is enabled.
2 PERIODIC Every periodic-inform-interval (default one day), if periodic-inform-enabled=yes.
4 VALUE CHANGE A client setting changed since the last session.
6 CONNECTION REQUEST After a connection request from the ACS.
7 TRANSFER COMPLETE with M Download or M Upload After a download or upload the ACS asked for, with the result.
M Reboot After a reboot the ACS asked for.

The Inform identifies the router with Manufacturer MikroTik, an OUI, a ProductClass and a SerialNumber. It also carries the RouterOS version (Device.DeviceInfo.SoftwareVersion), provisioning-code (Device.DeviceInfo.ProvisioningCode) and the connection request URL (Device.ManagementServer.ConnectionRequestURL).

A connection request is an HTTP request from the ACS to that URL, http://<router address>:<connection-request-port>/<random path>, where the address is the router's own address. The ACS must be able to open a TCP connection to it, so a router behind NAT receives connection requests only if the NAT device forwards the port. The router accepts the request only with HTTP Digest authentication and the connection-request-username and connection-request-password. It then starts a new session with the configured ACS. A connection request cannot make the router contact any other server.

Parameters and data models

Parameters are name and value pairs, such as Device.DeviceInfo.SoftwareVersion. The set of parameters a device supports is its data model. The BBF defines the root data models TR-098 and TR-181 (Issue 1 and Issue 2), on which vendors base their parameters. The RouterOS data model is based on TR-181 Issue 2: the router reports Device.RootDataModelVersion 2.15. MikroTik-specific parameters start with X_MIKROTIK_, for example Device.DeviceInfo.X_MIKROTIK_SystemIdentity.

Some parameters map to RouterOS settings. For example, setting Device.DeviceInfo.X_MIKROTIK_SystemIdentity changes /system/identity, and setting Device.ManagementServer.PeriodicInformInterval to 300 sets periodic-inform-interval=5m.

See the RouterOS TR-069 parameter reference for all supported parameters.

Change the configuration

Not every RouterOS setting has a CWMP parameter. To change any setting, the ACS sends a RouterOS script with the Download RPC and FileType 3 Vendor Configuration File. The URL's file name decides what the router does with it. Put the file on an HTTP or HTTPS server that the router can reach, for example the file server of the ACS:

  • A file name ending in .alter changes the configuration: the router runs the script as it is, without a reboot, and reports the result with TransferComplete.
  • Any other file name replaces the configuration: the router removes the whole configuration, reboots and applies the file. The next session starts with 0 BOOTSTRAP and 1 BOOT.

For example, a file named identity-dns.alter with this content renames the router and sets its DNS server:

/system/identity/set name=CPE-altered
/ip/dns/set servers=192.0.2.53

WARNING

A file that replaces the configuration must bring the router back to the ACS on its own. The rest of the file is not applied after a line that fails, so a single error can leave the router without the TR-069 client and out of reach of the ACS. Test each file on a local router first. Things to include:

  • A startup delay, so that the interfaces exist before the script configures them.
  • Passwords: an exported configuration, including the file the router sends with the Upload RPC, does not contain them, including the TR-069 client password. Such a file cannot replace the configuration unchanged.
  • Certificates that the configuration needs, such as the CA certificate of the ACS.

Upgrade RouterOS

The CWMP standard upgrades firmware with the Download RPC, FileType 1 Firmware Upgrade Image and a single URL (HTTP or HTTPS). RouterOS is installed as packages, so the URL points to an XML file that lists the package files to install, for an upgrade or a downgrade. The router downloads the XML, checks it, downloads every listed file and installs them as in an upgrade by package file upload, then reboots. It reports the result with TransferComplete in the first session after the reboot (events 7 TRANSFER COMPLETE, M Download and 1 BOOT).

Put the XML file and the packages on an HTTP or HTTPS server that the router can reach, and send the Download RPC with the URL of the XML file, for example https://example.com/path/upgrade.xml. List the tr069-client package together with the RouterOS package, so that the client is upgraded with it. The packages must match the router's architecture, which the router reports in Device.DeviceInfo.X_MIKROTIK_ArchName:

<upgrade version="1" type="links">
   <config/>
   <links>
       <link>
          <url>https://example.com/routeros-X.Y.Z-mipsbe.npk</url>
       </link>
       <link>
          <url>https://example.com/tr069-client-X.Y.Z-mipsbe.npk</url>
       </link>
   </links>
</upgrade>

If the download fails, the router reports a fault in TransferComplete, for example 9015 with Connection refused.

NOTE

Upgrade step by step: first upgrade a router you have tested locally, and check that it reconnects to the ACS and that the functions you need work. Then upgrade groups of routers. Do not upgrade all remote routers at once. Serve the files over HTTPS in production.

Upload files to the ACS

With the Upload RPC, the router sends a file to the URL the ACS gives, with HTTP PUT, and reports the result with TransferComplete. The FileType selects the file:

  • 1 Vendor Configuration File: the current configuration, as /export shows it. Passwords and other sensitive values are not included.
  • 2 Vendor Log File: the log, similar to /log/print: one line per entry with the time (in ISO 8601 format), topics and message.
  • X MIKROTIK Factory Configuration File: the default configuration script that runs at the next configuration reset. If a custom script is installed, this is the custom script, which differs from the one /system/default-configuration/print shows.

Reset the router to its default configuration

The FactoryReset RPC resets the configuration in the same way as this command:

/system/reset-configuration skip-backup=yes

The reset removes the whole configuration, including certificates, and runs the default configuration script. The default configuration differs between devices (see Default configurations). To bring routers back to the ACS after a reset, install a custom default configuration that configures the TR-069 client, as the next section describes.

Prepare routers for TR-069 management

A provider who manages routers over TR-069 can replace MikroTik's default configuration with a custom script that brings the router back to the ACS after a reset: a FactoryReset RPC, /system/reset-configuration or the reset button. This makes a router reachable again after a configuration that cannot be fixed remotely.

The custom default configuration script can be installed in two ways:

  • With Netinstall, which installs the script in place of MikroTik's default configuration.
  • With the Download RPC and FileType X MIKROTIK Factory Configuration File. The router stores the script without a reboot and without changing the current configuration.

After a Download of the script, /system/default-configuration/print keeps showing MikroTik's script. The custom script shows in /system/default-configuration/custom-script/print, and /export starts with the comment # custom default configuration script installed.

WARNING

The script runs on a router with an empty configuration and no certificates. If it fails, the router can end up unreachable for the ACS. Test it with a reset on a local router first.

At minimum, the script imports the CA certificate of the ACS, configures IP connectivity, a firewall and the TR-069 client. The ACS configures the rest.

Run the Dude server

The Dude server runs on the router and comes in the dude extra package (see Packages). After installing the package, enable the server and choose the folder for its database:

/dude/set enabled=yes data-directory=dude
/dude/print

         enabled: yes
  data-directory: dude
          status: running

The router creates the folder with the database (dude.db) and the default files of the Dude. While the server runs, RouterOS adds a dynamic dudes service on UDP port 514 (see /ip/service/print). On a router with a flash folder or an attached disk, choose a folder there, for example flash/dude, so that the database is kept on persistent storage.
