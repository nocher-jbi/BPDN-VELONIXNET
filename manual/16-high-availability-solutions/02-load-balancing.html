Load Balancing

Load balancing in RouterOS: use two or more links at the same time, the difference between per-connection and per-packet balancing, which method does which, and a simple failover example.

Load Balancing

Load balancing spreads traffic over two or more links. A router with two internet links can use both at the same time, and keep working when one of them fails.

There are two kinds of balancing:

  • Per-connection. All packets of one connection use the same link. This is the only kind that works when you control one end only, for example a home or office router with two internet providers: the other end sees each connection from one public address.
  • Per-packet. The packets of one connection can use different links. This works reliably, especially for TCP and encrypted connections, only when you control both ends of the links.

Simple failover

The simplest setup with two gateways uses one gateway and changes to the other when the first one fails. Give the second route a larger distance, and add check-gateway to the routes:

/ip/route/add gateway=192.168.1.1 distance=1 check-gateway=ping
/ip/route/add gateway=192.168.2.1 distance=2 check-gateway=ping

The router pings the gateway of each route. When the first gateway does not answer, its route becomes inactive and the second route takes over. When the first gateway answers again, its route is active again and the second is the backup. Failover (WAN Backup) has the complete setup and a way to check the path behind the gateway.

Failover (WAN Backup)

WAN failover in RouterOS: use a second internet link when the first one fails, check the link with check-gateway, detect a failure behind the provider's gateway with recursive routes, and see which link is in use.

Failover (WAN Backup)

A router with two internet links can use the second link when the first one fails. This page shows two ways to do it with routes only:

  • Check the gateway of each provider. This is simple, but it does not see a failure inside the network of the provider.
  • Check hosts on the internet through each link, with recursive routes. This also sees a failure behind the gateway.

[gambar: A router with a LAN and two links to two internet providers]

In the examples, the first provider (ISP1) is on ether1 with the gateway 10.111.0.1, and the second (ISP2) is on ether2 with the gateway 10.112.0.1. ISP1 is the main link.

Prepare NAT

The devices of the LAN must reach the internet through both links, so each WAN interface needs a masquerade rule:

/ip/firewall/nat
add chain=srcnat action=masquerade out-interface=ether1
add chain=srcnat action=masquerade out-interface=ether2

With the default configuration, the masquerade rule uses the interface list WAN, and the two rules are not needed. Take the second WAN port out of the LAN bridge and add it to the list. The default firewall then also protects it. Without this, the traffic through the second link is not translated and gets no answers:

/interface/bridge/port/remove [find interface=ether2]
/interface/list/member/add list=WAN interface=ether2

The routes of this page are static and need the address of each gateway. If a link gets its settings from a DHCP or PPPoE client, set add-default-route=no in the client, so that its own default route does not compete with the routes of this page.

Check the gateways

Add a default route for each link. The route with the lower distance is used while it is active:

/ip/route
add distance=1 gateway=10.111.0.1 check-gateway=ping
add distance=2 gateway=10.112.0.1 check-gateway=ping

With check-gateway=ping, the router pings the gateway of the route. When the gateway does not answer, the route becomes inactive, and the route with the next distance takes over. When the gateway answers again, the first route becomes active again. Routing decision describes the timing of the check.

In /ip/route/print, the route of ISP1 has the flag A (active). After the gateway of ISP1 stops answering, this route gets the flag I (inactive) and the route of ISP2 becomes active. This takes about 20 seconds with the default timing of the check.

An answer from the gateway shows only that the link between the router and the gateway works. The gateway can answer while the provider has no connection to the internet, and then the router keeps using a link that does not work.

Check hosts on the internet

To check the path to the internet, ping a host on the internet through each link. Choose two reliable hosts that answer pings, one for each link. This example uses the public DNS servers 8.8.8.8 and 8.8.4.4.

First add a route to each host through its link. Then add the default routes with the hosts as gateways:

/ip/route
add dst-address=8.8.8.8 scope=10 gateway=10.111.0.1
add dst-address=8.8.4.4 scope=10 gateway=10.112.0.1
add distance=1 gateway=8.8.8.8 target-scope=11 check-gateway=ping
add distance=2 gateway=8.8.4.4 target-scope=11 check-gateway=ping

These are recursive routes: the gateway of a default route is not directly connected, and the router finds the way to it through another route. scope and target-scope control which routes can be used for this: a route can resolve its gateway through routes whose scope is not greater than its target-scope. The host routes have scope=10, and the default routes have target-scope=11.

The scope=10 counts. A static route has the default scope of 30, and a host route that kept the default could not resolve the gateway of the route with target-scope=11: the default route would then have no valid next hop and stays inactive. Routing decision lists the default scope and target-scope of connected, IGP, static and BGP routes.

The detail output shows the real next hop of each default route in immediate-gw:

[admin@Router] > /ip/route/print detail where dst-address=0.0.0.0/0
Flags: A - ACTIVE; s - STATIC
2 As dst-address=0.0.0.0/0 routing-table=main gateway=198.51.100.1
     immediate-gw=10.111.0.1%ether2 check-gateway=ping distance=1 scope=30
     target-scope=11

3  s dst-address=0.0.0.0/0 routing-table=main gateway=198.51.100.2
     immediate-gw=10.112.0.1%ether3 check-gateway=ping distance=2 scope=30
     target-scope=11

This output is from a test network, where the hosts are 198.51.100.1 and 198.51.100.2 and the WAN interfaces are ether2 and ether3.

  • When the host of ISP1 stops answering, the first default route becomes inactive within about half a minute and the traffic uses ISP2, also when the gateway of ISP1 still answers. When the host answers again, the route becomes active again.
  • The host routes are necessary. Without them, both default routes are inactive.
  • Each host is reachable only through its own link. Do not use an address that your network needs through the other link, for example the DNS server that the LAN uses.

Check two hosts for each link

With one host for each link, a failure of that host alone switches the traffic to the backup link. To avoid this, add a second host for each link, here 208.67.222.222 and 208.67.220.220:

/ip/route
add dst-address=208.67.222.222 scope=10 gateway=10.111.0.1
add dst-address=208.67.220.220 scope=10 gateway=10.112.0.1
add distance=1 gateway=208.67.222.222 target-scope=11 \
    check-gateway=ping
add distance=2 gateway=208.67.220.220 target-scope=11 \
    check-gateway=ping

ISP1 now has two default routes with the distance 1. While both hosts answer, the two routes are one ECMP route (flag +). When one host stops answering, the other route of ISP1 stays active. The traffic moves to ISP2 only when both hosts of ISP1 do not answer.

What happens to open connections

A connection that is open when the route changes can break. The devices open it again. New connections use the link of the active route.

To use both links at the same time, see Per connection classifier.

Per connection classifier

Per connection classifier (PCC) in RouterOS: balance connections over two internet links with mangle rules, routing tables and failover, a complete example, and how the classifier divides connections.

Per connection classifier

The per connection classifier (PCC) is a firewall matcher that divides connections into groups and keeps all packets of a connection in the same group. Its most common use is to share the connections of a network between two or more internet links.

PCC takes selected fields of the packet header (addresses, ports), makes a 32-bit hash of them, divides the hash by a number (the denominator) and compares the remainder with a given value. The syntax is:

per-connection-classifier=
PerConnectionClassifier ::= [!]ValuesToHash:Denominator/Remainder
  Remainder ::= 0..4294967295    (integer number)
  Denominator ::= 1..4294967295    (integer number)
  ValuesToHash ::= both-addresses|both-ports|dst-address-and-port|
  src-address|src-port|both-addresses-and-ports|dst-address|dst-port|src-address-and-port

For example, both-addresses:2/0 and both-addresses:2/1 are the two halves of all pairs of source and destination address.

PCC only matches packets. It does not send traffic anywhere: the connection marks have an effect only when other rules change them into routing marks, and routing tables with those names have routes. The example on this page has all the parts.

WARNING

PCC does not work together with HotSpot: HotSpot uses a web proxy, which uses only the main routing table.

Balance two internet links

[gambar: A router with a LAN and two links to two internet providers]

In this example the router has two provider interfaces, ether_ISP1 with the address 10.10.4.100/24 and the gateway 10.10.4.1, and ether_ISP2 with 10.10.5.100/24 and the gateway 10.10.5.1. The LAN interface ether_LAN has 192.168.100.1/24. On a router with the default configuration, use your interface names: the LAN interface is bridge, and the second provider port must first be removed from the bridge (/interface/bridge/port/remove [find interface=ether2]).

/ip/address
add address=10.10.4.100/24 interface=ether_ISP1
add address=10.10.5.100/24 interface=ether_ISP2
add address=192.168.100.1/24 interface=ether_LAN

Routing tables

Add a routing table for each provider:

/routing/table
add name=ISP1_table fib
add name=ISP2_table fib

Keep connected networks in the main table

The classification rules that follow look at all connections from the LAN. Traffic to the networks that are connected to the router must not get a routing mark, or the router sends it to a provider gateway and the hosts of those networks cannot be reached. Put the connected networks into an address list and accept them before the other mangle rules. accept ends the mangle processing of a packet:

/ip/firewall/address-list
add address=10.10.4.0/24 list=ConnectedNetworks
add address=10.10.5.0/24 list=ConnectedNetworks
add address=192.168.100.0/24 list=ConnectedNetworks
/ip/firewall/mangle
add chain=prerouting action=accept \
    dst-address-list=ConnectedNetworks
add chain=output action=accept dst-address-list=ConnectedNetworks

The rule in the output chain does the same for the connections of the router itself. Without it, the router cannot reach the devices of its own LAN after the rules for its own connections are added.

Classify the connections of the LAN

/ip/firewall/mangle
add chain=prerouting action=mark-connection \
    connection-mark=no-mark connection-state=new \
    dst-address-type=!local in-interface=ether_LAN \
    per-connection-classifier=both-addresses:2/0 \
    new-connection-mark=ISP1
add chain=prerouting action=mark-connection \
    connection-mark=no-mark connection-state=new \
    dst-address-type=!local in-interface=ether_LAN \
    per-connection-classifier=both-addresses:2/1 \
    new-connection-mark=ISP2
  • The rules match the first packet of each new connection without a mark, and put the connection into one of two groups by its source and destination address. The connection mark then stays with all packets of the connection.
  • dst-address-type=!local leaves out packets for the router itself.
  • The rules are in the prerouting chain, because the routing mark must be set before the routing decision. A connection that is marked first in the forward chain leaves with its first packet through the main table: connections of one packet, such as DNS requests, would always use the main table, and the other packets of a TCP connection would leave through another provider than the first one.

Classify the connections of the router

/ip/firewall/mangle
add chain=input action=mark-connection connection-state=new \
    in-interface=ether_ISP1 new-connection-mark=ISP1
add chain=input action=mark-connection connection-state=new \
    in-interface=ether_ISP2 new-connection-mark=ISP2
add chain=output action=mark-connection \
    connection-mark=no-mark connection-state=new \
    per-connection-classifier=both-addresses:2/0 \
    new-connection-mark=ISP1
add chain=output action=mark-connection \
    connection-mark=no-mark connection-state=new \
    per-connection-classifier=both-addresses:2/1 \
    new-connection-mark=ISP2
  • The input rules are for connections that come to the router from the internet, for example to a VPN server on the router. The mark remembers the interface that the connection came in on, so the answers leave through the same interface from the same public address. A router that accepts connections from the LAN only does not need them.
  • The output rules put the connections that the router itself starts into the same two groups. Packets of the router do not pass the prerouting chain, so these rules are in output.

Change the connection marks into routing marks

/ip/firewall/mangle
add chain=output action=mark-routing connection-mark=ISP1 \
    new-routing-mark=ISP1_table
add chain=prerouting action=mark-routing connection-mark=ISP1 \
    in-interface=ether_LAN new-routing-mark=ISP1_table
add chain=output action=mark-routing connection-mark=ISP2 \
    new-routing-mark=ISP2_table
add chain=prerouting action=mark-routing connection-mark=ISP2 \
    in-interface=ether_LAN new-routing-mark=ISP2_table

mark-routing works only in the prerouting and output chains. The prerouting rules have in-interface=ether_LAN, so that packets that arrive from the providers follow the normal routing decision: only the traffic to the internet needs the routing marks.

Routes

Add a default route to each provider table, and two default routes with different distances to the main table:

/ip/route
add gateway=10.10.4.1 routing-table=ISP1_table check-gateway=ping
add gateway=10.10.5.1 routing-table=ISP2_table check-gateway=ping
add gateway=10.10.4.1 distance=1 check-gateway=ping
add gateway=10.10.5.1 distance=2 check-gateway=ping

The routes of the main table give failover. When a provider gateway does not answer, check-gateway makes the route of its table inactive. The traffic with that routing mark then uses the main routing table, where the route through the other provider is active.

The routes of the main table need check-gateway=ping too. Without it, the route through a failed gateway stays active there, and connections of that group are lost. Connections that are open when a gateway fails or comes back can break and must be opened again.

NAT

With the default configuration, add both provider interfaces to the WAN interface list: its masquerade rule and its firewall then cover both, and the two rules below are not needed. The FastTrack rule of the default configuration can stay: connections keep the provider of their group with it.

Without the default configuration, add a masquerade rule for each interface. The routing decision is made by now. The NAT rules only set the source address of the packets: 10.10.4.100 for those that leave through ether_ISP1 and 10.10.5.100 for ether_ISP2.

/ip/firewall/nat
add chain=srcnat action=masquerade out-interface=ether_ISP1
add chain=srcnat action=masquerade out-interface=ether_ISP2

Check

  • /ip/firewall/mangle/print stats shows the packet counters of the rules. With traffic from several devices to several destinations, both mark-connection rules of the LAN count packets.
  • /ip/route/print shows the routes of the three tables. A route of a failed gateway has the flag I.
  • /ip/firewall/connection/print shows the mark of each connection in connection-mark.

With both-addresses, all connections between one device and one server use the same provider. Different servers can use different providers, so a test to a single server always shows the same link.

Failover with more than two links

Extend the example above with a third provider on ether_ISP3 (gateway 10.10.6.1), the routing table ISP3_table, and a third masquerade rule (or move all provider interfaces into the WAN list).

With one default route in each provider table, the share of a failed link falls back to the main table and leaves through one provider by distance. To divide the failed share over all remaining links instead, each table keeps the remaining gateways as one equal-distance set:

/ip/route
add gateway=10.10.4.1 routing-table=ISP1_table check-gateway=ping
add gateway=10.10.5.1 routing-table=ISP1_table distance=2 check-gateway=ping
add gateway=10.10.6.1 routing-table=ISP1_table distance=2 check-gateway=ping

add gateway=10.10.5.1 routing-table=ISP2_table check-gateway=ping
add gateway=10.10.4.1 routing-table=ISP2_table distance=2 check-gateway=ping
add gateway=10.10.6.1 routing-table=ISP2_table distance=2 check-gateway=ping

add gateway=10.10.6.1 routing-table=ISP3_table check-gateway=ping
add gateway=10.10.4.1 routing-table=ISP3_table distance=2 check-gateway=ping
add gateway=10.10.5.1 routing-table=ISP3_table distance=2 check-gateway=ping

Each table carries its traffic through its own provider first. When the gateway of a table stops answering, the two distance=2 routes join into one ECMP route (flag + in /ip/route/print), and the share of the failed link leaves equally through the two remaining links. In the three-link setup, every link carries a third of the connections, and each remaining link ends up with half of the full flow.

The split between the remaining links follows the ECMP hash policy. By default, the Layer3 policy hashes each connection by its addresses and keeps it on one link. With L3 hardware offloading, the switch uses its own hash mask, and the configured hash policy is ignored; Multipath (ECMP) routes describes the details. Connections that are open when a link fails or comes back follow the two-link rule: they break and must be opened again.

If the failed share should move in a known order instead of spreading equally, give each fallback route in a table a different distance. Every table then sends its traffic to the lowest active distance, and each table keeps its own preference order.

How PCC works

This article aims to explain in simple terms how PCC works. The definition from the official manual wiki page reads: "PCC takes selected fields from the IP header, and with the help of a hashing algorithm converts selected fields into a 32-bit value. This value then is divided by a specified Denominator and the remainder then is compared to a specified Remainder, if equal then the packet will be captured. You can choose from src-address, dst-address, src-port, dst-port from the header to use in this operation.", with the full number of fields available being: "both-addresses|both-ports|dst-address-and-port|src-address|src-port|both-addresses-and-ports|dst-address|dst-port|src-address-and-port". If you understand that definition, there'll be nothing interesting in this article for you.

First, here are the terms necessary to understand the definition.

IP packets have a header that contains several fields. Two of those fields are the IP address of the source of the packet and the IP address of the destination of the packet. TCP and UDP packets also have headers that contain the source port and the destination port.

Denominators and remainders are parts of modulus operations. A modulus operation produces the integer left over when you divide two numbers and only accepts the whole number portion of the result. It is represented by a % sign. Here are some examples: 3 % 3 = 0, because 3 divides cleanly by 3. 4 % 3 = 1, because the next smallest number before 4 that cleanly divides by 3 is 3, and 4 - 3 = 1. 5 % 3 is 2, because the next smallest number before 5 that divides cleanly by 3 is 3, and 5 - 3 = 2. 6 % 3 = 0, because 6 divides cleanly by 3.

A hash is a function that is fed input, and produces output. Hashes have many interesting properties, but the only important one for the purpose of this article is that hash functions are deterministic. That means that when you feed a hash function an input that reads 'hello' and it produces the output '1', you can rely on the fact that if you feed it 'hello' a second time it will produce the output '1' again. When you feed a hash function the same input, it will always produce the same output. What exact hashing algorithm is used by PCC is not important, so for this discussion let's assume that when you feed it IP addresses and ports, it just adds up the octets of the IP addresses as decimal numbers as well as the ports, and then takes the last digit and produces it as the output. Here is an example:

The hash function is fed 1.1.1.1 as the source IP address, 10000 as the source TCP port, 2.2.2.2 as the destination IP address and 80 as the destination TCP port. The output will be 1+1+1+1+10000+2+2+2+2+80 = 10092. The last digit of that is 2, so the hash output is 2. It will produce 2 every time it is fed that combination of IP addresses and ports.

At this point it's important to note that even though PCC is most often used for spreading load across circuits, PCC itself has absolutely nothing to do with routing, routing marks or spreading load. PCC is simply a way to match packets, and not directly related to the action of then marking those matched packets even if that is its main purpose.

Mangle rules that classify connections by PCC look like this:

/ip/firewall/mangle/add chain=prerouting action=mark-connection \
 new-connection-mark=1st_conn per-connection-classifier=src-address-and-port:3/0
/ip/firewall/mangle/add chain=prerouting action=mark-connection \
  new-connection-mark=2nd_conn per-connection-classifier=src-address-and-port:3/1
/ip/firewall/mangle/add chain=prerouting action=mark-connection \
  new-connection-mark=3rd_conn per-connection-classifier=src-address-and-port:3/2

The three rules classify connections only. In a working load-balancing setup the surrounding pieces matter just as much: which packets are accepted before classification, where connection marks become routing marks, and which routes the special routing tables hold. The Configuration Example puts all of those pieces together.

Here is what the different field options mean for the purpose of packet matching, these are the fields that will be fed into the hashing algorithm (and, for the purpose of spreading load across links, decide what link a packet will be put on). Remember that a hash function will always produce the same output when it's fed the same input:

  • src-address: The source address of a client will always be the same, so all traffic from a particular client will always match the same PCC matcher, and will always be put on the same link.
  • dst-address: The destination address of a specific server will always be the same, so all traffic to that server (say, the Mikrotik Wiki) will always match the same PCC matcher, and will always be put on the same link.
  • both-addresses: The source and destination IP pair between the same client and server will always be the same, so all traffic between one specific client and a specific server (say, your laptop and the Mikrotik Wiki) will always match the same PCC matcher, and will always be put on the same link.
  • src-port: Source ports of clients are usually randomly chosen when the connection is created, so across many connections different source ports will be fed into the hash function, and different PCC matchers will match and traffic will go across different links. However, some client protocols always choose the same source port, and servers behind your router will most likely always use the same service port to send traffic back to their clients. A web server behind your router would send most traffic from its HTTP (80) and HTTPS (443) ports, and that traffic would always match the same PCC matcher and would be put on the same link.
  • dst-port: Destination ports of clients are usually well defined service ports, all HTTP (80) traffic between your clients and servers on the Internet would always match the same PCC matcher, and would be put on the same link. However, the same clients doing HTTPS (443) traffic could match a different PCC matcher, and would go across a different link.
  • both-ports: Since the client port is (usually) randomly chosen, the combination of the two ports is (usually) random and will spread load across links.
  • src-address-and-port: Same caveat as src-port.
  • dst-address-and-port: Same caveat as dst-port.
  • both-addresses-and-ports: This is the most random way to spread traffic across links, since it has the most number of variables.

It's important to note that even though the hash function discussed in this article is greatly simplified and not what is used in real life, it nicely demonstrates another property of hash functions: two completely different inputs can produce the same output. In our example, 3 % 3 = 0, and 6 % 3 = 0; we get back 0 when we feed it a 3 as well as when we feed it a 6. The same is true for the actual function used for PCC, even though I don't know what it is, we do know from the definition that it produces a 32-bit value as output. IP addresses are 32 bits, and ports are 16 bits, so assuming that we're using both-addresses-and-ports, we'd be feeding it 32+32+16+16 = 96 bits of input and would only receive 32 bits back, so it must be producing the same output for different inputs. This means that two completely unrelated connections could match the same PCC matcher, and would be put on the same line. PCC works better the more connections you put across it so that the hash function has more chances to produce different outputs.

Multi-chassis Link Aggregation Group

Introduction

MLAG (Multi-chassis Link Aggregation Group) implementation in RouterOS allows configuring LACP bonds on two separate devices, while the client device believes it is connected to the same machine. This provides a physical redundancy in case of switch failure.

Both peers establish the MLAG interfaces and update the bridge host table over mlag-peer-port using ICCP (Inter Chassis Control Protocol). RouterOS ICCP does not require an IP configuration; it sends untagged Layer2 packets marked with EtherType 0x88B5 and a destination MAC address of 01:80:C2:00:00:0E. ICCP packets are link-local, meaning they are always received and handled by the MLAG devices themselves and never forwarded to other parts of the network. The peer-ports on each MLAG device must be directly connected to each other. It is also recommended to keep the untagged VLAN used by the peer ports separate from the rest of your network, either by assigning a dedicated untagged VLAN (using pvid), or by setting the peer port to only allow VLAN tagged frames (using frame-types=admit-only-vlan-tagged). Peer ports can be configured as single Ethernet interfaces or bonding interfaces. However, using a bonding interface is recommended, as it helps prevent a single interface failure from affecting connectivity, especially when both MLAG nodes are still up and running.

When mlag-peer-port is running and ICCP is established, the primary device election happens and the system-id will be selected. The peer with the lowest priority will act as the primary device. If the priorities are the same, the peer with the lowest bridge MAC address will become the primary. This system-id is used for STP BPDU bridge identifier and LACP system ID. MLAG supports STP, RSTP or MSTP protocols. Use the same STP priority and the same STP configuration on dual-connected bridge ports on both nodes. When MLAG bridges are elected as the STP root, then both devices will show as root bridges under the bridge monitor.

INFO

MLAG is configured per bridge interface. Any RouterOS device (including virtual CHR instances) can be used as an MLAG node.

Bridge hardware offloaded MLAG is only available on MikroTik devices with Marvell Prestera switch. All other devices support MLAG only in software.

INFO

The MLAG is not compatible with L3 hardware offloading. When using MLAG, L3 hardware offloading must be disabled on the whole switch (/interface/ethernet/switch/set 0 l3-hw-offloading=no). Setting l3-hw-offloading=no on individual switch ports is not sufficient.

DANGER

MLAG host synchronization can be CPU and memory intensive in networks with many hosts and VLANs. For switches with a single-core MIPSBE CPU (for example, CRS326-24S+2Q+RM, CRS354-48P-4S+2Q+RM, CRS518-16XS-2XQ-RM), it is recommended to use MLAG only in networks with up to 1,000 hosts.

In networks with a larger number of hosts, MLAG on these switches may lead to unexpected behavior.

[gambar: Two MLAG peer switches connected with a peer port, and a client connected to both with one LACP bond]

Packet forwarding and load balancing

The BUM (broadcast, unknown unicast, multicast) packet forwarding happens in two stages.

Stage 1 - local forwarding

When a node receives BUM traffic, it floods the packet locally to all ports that are members of the same VLAN - just like in a traditional (non-MLAG) setup. Additionally, it forwards the traffic over the peer-port to the other MLAG node.

INFO

Forwarding over peer-port only happens if the peer-port is also a member of the VLAN. This is why the documentation emphasizes that the peer-port should be included in all VLANs that span both MLAG nodes.

Stage 2 - remote forwarding by peer

When the peer node receives the BUM traffic over the peer-port, it floods the traffic to all regular bridge ports that are members of the same VLAN. These are ports that do not have an mlag-id specified (i.e., standalone Ethernet or bond interfaces). For mlag-id bond interfaces, the peer node makes a decision based on link status:

  • If both links (local and remote) are active, it does not flood the traffic to its own MLAG bond port - this avoids sending duplicate packets since the first node has already handled that.
  • If the remote peer’s link is inactive, and the local is active, the peer node will flood the traffic to the MLAG bond to ensure delivery.

The unicast traffic behaves similarly, but there is one key difference when comparing regular LAG with MLAG. In a regular LAG setup, outgoing packets are load-balanced across all active links based on the transmit hash policy. In MLAG setups with both links active, traffic is not load-balanced across the peer-port between the two switches. Instead, traffic is forwarded only through the local member links of the MLAG - it always takes the shortest path. The peer-port is used only if the local MLAG link fails. In that case, traffic is forwarded to the other node via the peer-port to reach the destination. When this happens, the host table also updates the MAC address entries learned on MLAG bonds to indicate that the destination is now reachable via the peer-port. In setups where MLAG bonds consist of 2 + 2 active links (2 links per node), the transmit hashing is performed only among the two local links - not across all four links. Load balancing can be achieved when an MLAG pair is used for multiple dual-connected bonds and the incoming traffic is already distributed across both pairs.

Quick setup

In this example, CRS317 and CRS309 devices are used as MLAG peers, and any device with two SFP+ interfaces can be used as an LACP client. The SFP+1 interface is used on both peer nodes to create mlag-peer-port, and it is used for ICCP, see a network scheme below.

[gambar: Peer1 and Peer2 connected through sfp-sfpplus1, and a client connected to sfp-sfpplus2 of each peer]

Configure bonding interfaces for MLAG on Peer1 and Peer2 devices, use a matching mlag-id setting on both peer devices, and set the 1-second LACPDU transmission rate:

# Peer1
/interface/bonding
add mlag-id=10 mode=802.3ad name=client-bond slaves=sfp-sfpplus2 lacp-rate=1sec

# Peer2
/interface/bonding
add mlag-id=10 mode=802.3ad name=client-bond slaves=sfp-sfpplus2 lacp-rate=1sec

Set up the bridge interface with vlan-filtering enabled. Specify mlag-peer-port to enable MLAG. To control which device becomes the primary MLAG node, set a lower mlag-priority value on the preferred device. In this example, we want Peer1 to be the primary, so we set its priority=50. Peer2 keeps the default priority of 128, making it the secondary.

In this example, we want both MLAG nodes to act as the root bridge, so we assign a better (lower) bridge priority using priority=0x1000. Make sure both MLAG nodes use the same priority value.

Optionally, you can set frame-types=admit-only-vlan-tagged on the bridge interface to disable the default untagged VLAN 1 (pvid=1).

# Peer1
/interface/bridge
add name=bridge1 vlan-filtering=yes mlag-peer-port=sfp-sfpplus1 mlag-priority=50 priority=0x1000 frame-types=admit-only-vlan-tagged

# Peer2
/interface/bridge
add name=bridge1 vlan-filtering=yes mlag-peer-port=sfp-sfpplus1 priority=0x1000 frame-types=admit-only-vlan-tagged

Next, add the necessary interfaces to the bridge. In this example, only the peer port (sfp-sfpplus1) and the client-bond interface need to be added.

For the peer port, we disable the default untagged VLAN 1 (pvid=1) by configuring it to accept only VLAN-tagged traffic (frame-types=admit-only-vlan-tagged).

For the client-bond interface, we want untagged traffic to belong to VLAN 10, so we set pvid=10 on that interface.

# Peer1
/interface/bridge/port
add bridge=bridge1 interface=sfp-sfpplus1 frame-types=admit-only-vlan-tagged
add bridge=bridge1 interface=client-bond pvid=10

# Peer2
/interface/bridge/port
add bridge=bridge1 interface=sfp-sfpplus1 frame-types=admit-only-vlan-tagged
add bridge=bridge1 interface=client-bond pvid=10

DANGER

The MLAG supports STP, RSTP or MSTP protocols. Use the same STP priority and the same STP configuration (e.g. path-cost, priority, edge) on dual-connected bridge ports on both nodes.

INFO

If the dual-connected bond interface is not connected to any other RSTP/MSTP bridges or switches, you can set edge=yes on that interface on both MLAG nodes.

This setting allows the bond port to quickly enter the forwarding state, which helps reduce packet loss when one side of the MLAG becomes available again.

In this example, client-bond interfaces use VLAN 10 for untagged traffic (set with pvid=10), and we also want to allow tagged VLAN 20. To make sure traffic for both VLANs can pass between the MLAG devices, we need to add the peer ports as tagged members of VLANs 10 and 20 on both MLAG nodes. It is important to include the peer ports in all VLANs that are used on other bridge ports. This includes the untagged and tagged VLANs. Below are configuration commands for both peer devices:

# Peer1
/interface/bridge/vlan
add bridge=bridge1 tagged=sfp-sfpplus1 vlan-ids=10
add bridge=bridge1 tagged=sfp-sfpplus1,client-bond vlan-ids=20

# Peer2
/interface/bridge/vlan
add bridge=bridge1 tagged=sfp-sfpplus1 vlan-ids=10
add bridge=bridge1 tagged=sfp-sfpplus1,client-bond vlan-ids=20

DANGER

All VLANs used for bridge slave ports must also be configured as tagged VLANs for peer-port, so that peer-port is a member of those VLANs and can forward data.

MLAG settings and monitoring

There are several MLAG related settings and monitoring options: mlag-heartbeat, mlag-init-delay, mlag-lacp-fallback, mlag-peer-port, mlag-priority from interface/bridge menu and mlag-id from interface/bonding menu.

By default, MLAG uses the elected primary node's system ID as the shared system ID for both the RSTP bridge ID and the LACP system ID of dual-connected bonds. If the primary node reboots, the remaining secondary node reverts its bonds to its own LACP system IDs (see mlag-lacp-fallback). The LACP partner must then renegotiate the bond, causing brief packet loss.

Consider setting mlag-lacp-fallback=no to keep the shared MLAG system ID after the peer link is lost, avoiding LACP renegotiation. The primary node must rejoin the cluster to restore the shared system ID.

When a node joins or rejoins the cluster, its dual-connected bond slaves stay out of the 802.3ad bond until the MLAG system ID syncs with the peer. mlag-init-delay controls how long the slaves stay excluded after reboot, preventing the bond from briefly activating with a local system ID.

Use the /interface/bridge/monitor commands to see the current MLAG state and active role. The mlag-state field shows connected after ICCP is established, connecting while the peers establish or re-establish the connection, or an error such as peer port not running when the configured peer port is unavailable.
